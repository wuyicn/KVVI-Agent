# 00 · 需求（听懂阶段）

> 原型：事项登记
> 生成引擎：KVVI 搭建引擎
> 状态：**未与需求方确认**。本文的「假设」和「待确认」两节是交付说明的一部分，不是装饰。

## 1. 业务原话

> 做一个「事项登记」的业务系统原型：员工提交事项，提交后需要主管审批，主管可驳回。

## 2. 复述（用原话里的名词和动词）

| 原话里的词 | 词性 | 在原型里落成什么 |
|---|---|---|
| 员工 | 名词 | 实体 `员工` —— 事项的提交人，也是审批人（主管）的身份来源 |
| 事项 | 名词 | 实体 `事项` —— 有独立身份、有生命周期（可多次创建、可查单条） |
| 提交 | 动词 | 状态迁移 `草稿 → 待审批`，由申请人触发，产生一条审批记录 |
| 主管 | 名词 | `员工.直属主管id` 的引用目标；审批人按「发起人直属主管」策略解析，不写死人名 |
| 审批 | 动词 | 实体 `事项` 的 `状态` 字段 + 流程 `事项审批` 的审批节点 |
| 驳回 | 动词 | 状态迁移 `待审批 → 已驳回`，**必填意见**，驳回目标态显式声明 |

**不引入的行业家具**：原话里没有「报货单」「工单」「报销」「金额」这类词，因此本模型不含任何金额字段、不含费用类实体。原话没说的业务规则一律进第 4 节，不猜。

## 3. 我做的假设（需要你确认，未确认前按此实现）

这些不是原话，是我为了让原型能跑通而补的最小决定。**每条都可推翻。**

| 编号 | 假设 | 理由 | 若推翻的影响面 |
|---|---|---|---|
| A1 | 事项的业务字段为 `标题`（必填，1–100 字）+ `内容说明`（必填，1–2000 字）+ `附件`（选填） | 除「事项」这个名词外没有任何字段信息；取最小可用集，附件是最常见的补充材料载体 | `01-数据模型.yml`、`02-表单/事项登记.yml`、`05-接口.yml` |
| A2 | `单号` 由系统生成，格式 `SX-YYYYMMDD-NNNN`，全局唯一 | 业务系统需要给人报的单号；格式可改 | `01`、`05` |
| A3 | 保留 `草稿` 状态，可先存草稿再提交 | 长表单需要中途保存；**原话未提草稿** | `01` 状态机、`03-流程` |
| A4 | 驳回后进入 `已驳回`（不是直接回 `草稿`），申请人可修改后**重新提交**，重新提交后回到 `待审批` | 驳回原因要留痕，且「驳回后能否重提」是审批系统的常见必需能力 | `03-流程` 驳回边、`05` 动作端点 |
| A5 | 审批为**一级**：仅发起人的直属主管 | 原话只说「主管审批」，没说多级 | `03-流程` 节点图 |
| A6 | 驳回**必须填意见**；通过时意见选填 | 驳回不给理由会让申请人无法修改 | `02-表单/事项审批.yml`、`05` |
| A7 | 不能自己审批自己提交的事项（自审拦截） | 原话未说，但缺了这条审批形同虚设 | `01` 不变量、`03` 边界用例 |
| A8 | 审批记录 **append-only**，不可改不可删 | 「谁在什么时候通过/驳回、理由是什么」必须可追溯 | `01`、`05` |
| A9 | 数据可见范围：申请人看自己提交的，主管看自己作为当前审批人的，管理员看全部 | 原话未说；不设范围则越权 | `04-看板` 权限、`05` 各接口权限 |
| A10 | 审批人解析失败（无直属主管 / 主管离职）时，转交管理员并告警，流程不静默卡住 | workflow-builder 规范强制要求兜底 | `03-流程` 兜底 |

## 4. 待确认问题清单（**原型不替你决定**）

| 编号 | 问题 | 为什么必须问 | 当前原型的临时行为 |
|---|---|---|---|
| Q1 | 主管关系从哪来？HR/AD 同步，还是本系统维护？一个员工能有多个主管吗？ | 决定 `员工.直属主管id` 是引用本系统数据还是外部系统 | 按「本系统内自引用」建模，数据来源桩掉 |
| Q2 | 事项还需要哪些字段？分类 / 优先级 / 期望完成时间 / 关联项目 / 金额？ | A1 只实现了最小集，业务上大概率不够 | 仅实现标题 + 内容说明 + 附件 |
| Q3 | 驳回后是「可修改重提」还是「直接终止」？ | 决定驳回目标态；两种做法都有真实业务 | 按 A4 取「可重提」 |
| Q4 | 要不要草稿？还是提交即进入待审批？ | A3 是我加的，可能多余 | 按 A3 保留草稿 |
| Q5 | 通过后是否终态？需要撤销 / 关闭 / 归档吗？ | 当前把 `已通过` 当终态，无出路 | `已通过` 视为终态，无后续迁移 |
| Q6 | 要不要多级审批（例如某类事项需上级再批）？ | 决定流程是否需要条件分支节点 | 仅一级主管，无条件分支 |
| Q7 | 审批时限？超时是提醒、升级上级，还是自动通过？ | 不设超时待办会永久堆积；自动通过有误批风险 | 见 `03-流程` 的超时段（默认值，待确认） |
| Q8 | 提交后在主管处理前能否撤回？ | 原话未说 | 暂不支持撤回 |
| Q9 | 主管能否把审批转交他人？转交后原待办怎么算？ | 主管请假时流程会卡住 | 暂不支持转交，靠 A10 兜底 |
| Q10 | 通知走什么渠道（站内 / 邮件 / IM）？ | 原话未说，原型不实现通知 | 通知为桩，仅在流程里标注「应通知」 |
| Q11 | 员工与「主管」的组织关系变更后，历史事项的审批人是否跟着变？ | 影响审批人写入时机（提交时快照 vs 审批时实时解析） | 提交时解析并**快照**写入 `当前审批人id` |
| Q12 | 看板要不要按**部门**统计？ | 原话没有「部门」这个词，故本模型无部门实体 | 看板按「审批人」维度统计，不按部门 |

## 5. 本原型不做什么

- 不做登录、不做账号体系（`申请人id` 假定来自登录态，桩掉）
- 不做通知发送（Q10）
- 不做员工/组织数据维护界面（Q1）
- 不做权限管理后台（A9 的范围是硬编码在契约里的规则）
- 不声称生产可用、不声称任何合规结论
