## 二、业务理解（我听到的）

- **谁做**：前台做登记；被访人做接待决定。
- **登记什么**：访客姓名、手机号、来访事由、被访人。
- **登记之后**：被访人要么确认接待，要么拒绝并说明原因。
- **拒绝必须有原因**——这是你明确说过的，所以它是硬约束 `INV-01`，服务端强制。

## 三、状态机（原型的骨架）

```
待接待确认 ──同意接待──▶ 已确认接待 ──前台登记离场──▶ 已离场（终态）
     │
     ├────拒绝接待───▶ 已拒绝接待（终态，拒绝原因已留痕）
     │
     └────前台取消────▶ 已取消（终态）
```

**你只说了登记和确认两件事**，所以：
- 「已离场」「已取消」两个状态是我为了让记录有收尾而补的，**不是你说的**，见 Q4、Q5；
- 「已确认接待」之后**为什么没有继续流转**（比如访客进楼、离开）我没有编造。

## 五、我替你做的假设（你不认可就得改）

你要求我不要提问，所以以下都是我按常识补的，**每一处都可能与你的业务不符**：

| # | 假设 | 如果错了会怎样 |
|---|---|---|
| A1 | 被访人从员工花名册里选（存员工 id），不是手填姓名 | 若只能是手填文本，「只有被访人本人能确认」这条权限规则就**无法校验**，谁来点确认都算数 |
| A2 | **前台不能代被访人确认**（`INV-04`） | 若业务上被访人常口头同意、由前台代点，流程会卡住 |
| A3 | 被访人拒绝后**不能反悔**，要重新来访得另起一条登记 | 若允许反悔，状态机要多一条返向边 |
| A4 | 手机号只做格式校验，**不查重**（同一人可多次来访） | 若要求「同一手机号当天只能登记一次」，要加跨记录不变量 |
| A5 | 拒绝原因**同意时不许填**、拒绝时必填 2–200 字 | 若同意时也可以写备注，应是独立字段而不是复用拒绝原因 |
| A6 | 访客姓名/手机号在确认后**不可再改**（`INV-06`） | 若前台需要事后纠正错字，要放开并留痕 |
| A7 | 没有超时机制——被访人不处理，单子**永久挂着** | 这是原型**已知的卡点**，见 Q3 |

## 六、待确认清单（需要你拍板的业务规则）

### 高优先（影响流程能不能成立）

- **Q1 被访人怎么指定？** 花名册选人，还是前台手填姓名+电话？→ 直接决定「谁有权确认」能否被系统判定。
- **Q2 被访人拒绝后能否反悔？** 保持拒绝不动，还是允许改确认 / 前台改指被访人后重来？（本原型：保持拒绝，重新来访另起一条）
- **Q3 被访人不确认怎么办？** 是否需要超时提醒、升级上级、或自动放行？本原型**未实现超时**。
  - 特别提请注意：**「自动放行」等于无人接待也让人进门**，属安全决策，我没有替你默认。
- **Q4 前台能否取消登记？** 在哪个状态下能取消？（本原型只在「待接待确认」允许）
- **Q7 前台能否代被访人确认？** 本原型按「不能」实现。

### 中优先（影响字段与界面）

- **Q5 登记离场要不要保留？** 你只说了登记与确认；我补的「登记离场」动作若不需要可整块删除。
- **Q6 访客信息的敏感度**：手机号是否需要脱敏展示、短信验证、证件号登记？是否要求数据保留期限（Q10）？→ 涉及个人信息处理，**必须由业务方给口径**，实现方不能默认。
- **Q8 拒绝原因谁能看到？** 只有前台与被访人，还是行政/主管也能看？
- **Q9 登记单号规则**（前缀、日期、流水位数、是否按站点分段）。
- **Q10 来访记录保留多久？**

### 流程外但仍需决定

- **通知渠道**：被访人收到的「待确认」通过什么送达（系统待办 / 短信 / 企业 IM）？本原型只写「产生待办」，未指定渠道。

## 七、接口契约（只是定义，没有实现）

契约写在 `02`、`03` 两个文件的 `接口绑定` 章节里，两条硬规则：

1. **状态变更走动作端点**，不走 `PATCH` 直接改状态：
   - `POST /来访登记/{id}/同意接待`
   - `POST /来访登记/{id}/拒绝接待`
   - 用 `PATCH` 改状态会**绕过权限校验（INV-04）与审计**。
2. **有副作用的创建接口必须幂等**（`Idempotency-Key`），否则前台连点两下会产生两条登记。

统一错误体：`{ 错误码, 消息, 字段错误[], 追踪id }`；时间一律 ISO 8601 带时区；金额类字段本系统不涉及。
