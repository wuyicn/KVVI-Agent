**1. 「加载即生效」是否制造了新问题？**

v2.13 在 §4.1.1 四 的「状态语义」部分写了三条：
1. 加载前必须检查激活状态——无激活批准记录则不加载；
2. 加载时与「激活批准记录」比对指纹，不是安装记录；
3. 「加载」与「生效」的关系（v2.13 修正为如实表述）：
   - 激活是加载的前置条件——无激活批准记录则不加载（机制，可核验）；
   - 加载即生效——不再声称存在「加载但不生效」的中间态；
   - 不设「运行开关」语义——动作全集不含「去激活」，关闭一个已激活插件的路径只有卸载。

(a) 自洽性检查：
- 「激活是加载的前置条件」+「加载即生效」——这两条合起来意味着：激活 ⟹ (下次加载时生效)。但没有「去激活」，那么「激活」这个动作的语义是什么？如果加载即生效，那么激活的**唯一直接效果**是允许后续加载。这在语义上是自洽的：激活 = 授权加载；加载 = 生效。
- 但有一个时序问题：插件在**已加载运行中**时，所有者想关闭它——只有卸载。卸载「由所有者发起」（v2.12 明确）。那么「激活」后插件何时加载？是激活后立即加载，还是等下次进程启动？
  - §4.1.1 四的表：「加载 | ❌ 不须批准 | ⚠️ 尽力而为 | 仅当存在激活批准记录时才允许加载；与激活批准记录比对指纹（防热替换）」
  - 如果激活后插件立即加载（热加载），那么「加载」既发生在进程启动时，也发生在激活后。§9.6.3 第 8 项说「加载发生在进程启动时」。如果激活后需要热加载才能生效，那么激活后到加载前有一个窗口——插件已激活但未生效。这个窗口是否存在、如何处理，PRD 没有写。
  - 反过来说，如果激活后不立即加载，那么「激活」这个批准动作的效果被推迟到下次重启——这意味着「激活」不是立即可见的，所有者批准激活后插件不工作，需要重启才生效。这个语义也没有写。
  - 这是一个真实的小空洞：激活与加载的时序关系未定义。「加载即生效」本身自洽，但「激活后何时加载」未定义。

(b) 与 §9.10.1、§5.7.1 的一致性：
- §5.7.1：profile 插件「进程级」生效，跨重启保留；运行时动态插件「仅进程内存」，重启消失。
- §9.10.1：插件可注册 Service / HTTP 路由 / 客户端 UI。
- 「加载即生效」与「进程级生效」一致——加载进进程即注册即生效。OK。
- 但等等：运行时动态插件「仅进程内存，重启消失」——它的生命周期是什么？动态插件也需要经过安装/注册/激活吗？§9.10.2 说「动态插件生产环境默认禁用」。§4.1.1 四的动作全集是对所有插件还是只对 profile 插件？如果动态插件重启即消失，那么「激活批准记录」对动态插件的意义是什么？PRD 没有区分两类插件的生命周期动作适用性。这可能是一个小问题，但动态插件生产默认禁用，所以也许不算大问题。

(c) 没有「去激活」动作是否可接受？
- v2.13 明确写了：「不设『运行开关』语义——动作全集不含『去激活』，关闭一个已激活插件的路径只有卸载（若将来需要，须新增动作并纳入全集与审计）。」
- 这是明确的产品决策，且卸载不须批准（紧急动作）、由所有者发起。所以关闭路径存在（卸载），语义清晰。可接受。
- 但有一个小问题：卸载是「尽力而为」留痕，且卸载后插件代码是否被移除？如果卸载只是卸载但不删除批准记录，那么重新加载需要什么？如果卸载后想重新启用，需要重新安装/注册/激活？这个生命周期状态机没有完整定义。不过这可能是实现细节。
- 更重要的：激活是加载的前置条件，卸载是唯一的关闭路径。那么「激活」后如果所有者后悔了呢？只能卸载。卸载后批准记录状态如何？这些都没有写，但属于生命周期细节。考虑到 PRD 的精度边界，这可能算建议级。

**2. §9.4.2 续发机制是否成立？**

v2.13 §9.4.2 新增：
「令牌续发机制（v2.13 新增）| 令牌到期前，由运行时进程以当前会话名义向签名接口重新申请（与 §9.4.1 ② 衔接）。续发须满足：① 会话仍在有效期内；② 撤销查询通过；③ 授权版本一致。续发不改变主体与声明。」

与 §9.4.1 ② 的衔接：
- §9.4.1 ②：「签名进程只为平台服务进程中已认证的会话签发；不接受请求方声称的身份」「调用方只能请求『为当前会话签发令牌』，不能请求『为某主体签发某声明』」
- 续发：「由运行时进程以当前会话名义向签名接口重新申请」——这与 ② 的请求主体规则一致（运行时进程请求为当前会话签发）。

但有一个矛盾需要注意：
- §9.4.4 的表：「新令牌签发 | ✅ 需要平台在线 | 拒绝」——平台不可用时新令牌签发被拒。
- 续发 = 新令牌签发的一种。所以平台不可用时续发也会被拒。这意味着：平台不可用时，令牌到期后（≤5分钟）无法续发，Agent 会话将无法继续调用业务系统。这与 §4.6.2 规则 3「平台不可用在声明的残留窗口内不应使业务系统停摆」的关系——业务系统本身可以继续接受已签发的令牌（在残留窗口内），但新令牌（续发）需要平台在线。OK，这个逻辑是自洽的：离线时业务系统用缓存继续验签，但令牌到期后无法续发。但等等——残留窗口 ≤ 5 分钟，令牌有效期 ≤ 5 分钟，二者是同一配置项。平台不可用时，已签发令牌在残留窗口内仍被接受（基于缓存），令牌到期（≤5分钟）后没有新令牌可用。所以实际可用窗口就是 5 分钟左右。自洽。

- 续发条件「② 撤销查询通过」——但 §9.4.4 说撤销查询需要平台在线，且有残留窗口。续发时撤销查询通过是指实时查询还是缓存？如果是实时查询，那续发要求平台在线，与「新令牌签发需要平台在线」一致。OK。

「不防冒用」的范围是否比 v2.12 更大？
- v2.12 的说法（§9.4.1 保证表 v2.12 版）：「插件可为活跃会话持续取得新令牌……按 §9.4.1 ②，插件在运行时进程内为当前会话请求签发本身即合规（不需要『窃取』）」——这个表述在 v2.12 已经存在（看 v2.12 修改记录 #4：「收缩为两项成立 + 两项明确不防；窗口改为会话级」）。
- v2.13 §9.4.2 新增的话：「由此产生的如实结论：按 §9.4.1 ②，插件在运行时进程内为当前会话请求签发是合规的——它甚至不必『窃取续发令牌』，可主动申请新令牌。因此 §9.4.1 保证表的『不防』结论方向正确，但最弱假设不是『窃取』而是『主动申请』」
- 这个「如实结论」确实确认了不防冒用的范围——但这是**如实披露**，不是新的过度承诺。问题是：这是否暴露了设计上的一个真实缺陷？

让我想想：插件在运行时进程内，可以「以当前会话名义」请求续发新令牌。续发条件：① 会话仍在有效期内；② 撤销查询通过；③ 授权版本一致。插件发起的续发请求与合法 Agent 发起的续发请求**不可区分**——因为请求主体都是「运行时进程为当前会话」。签名接口无法区分请求来自 Agent Loop 还是来自插件。这是两进程划分 + 「声明不可由调用方指定」的必然结果：签名接口只认「当前会话」，不认调用方身份（插件 vs Agent）。

那么这意味着：插件冒用的窗口 = min(会话存活期, 插件驻留期)，且插件可以主动续杯。这在 v2.12 已经声明为「不防」。v2.13 只是把这个机制写实了（续发机制存在 + 插件可主动申请）。

这是否是一个**问题**？从 PRD 的角度看：
- 这是如实披露，符合「做不到的就不声称能做到」的原则。
- 但评审任务问：「这是否意味着『不防冒用』的范围比 v2.12 写的还大？」——答案：范围没有变大，v2.12 已经写了「冒用窗口 = min(会话存活期, 插件驻留期)，远超 5 分钟」。v2.13 只是补了机制细节。所以不是新问题，是把 v2.12 引用的不存在机制补实了。

但有一个潜在的新问题：续发机制给了插件一个**更干净**的攻击路径——插件不需要读内存窃取令牌，只需要调用签名接口（合法的进程间接口）就能拿到新令牌。这使得「插件无法取得非当前会话主体的令牌」这个负向测试仍然可判定（插件只能拿当前会话的令牌），OK。但也意味着插件的冒用能力**机制化**了——它是签名接口的合法调用方。PRD 对此如实披露了。我认为这不算新缺陷，算如实披露。但可以在「建议」里提一句：续发接口是否需要某种调用方鉴别（如 Agent Loop 与插件的区分）？不过 §4.6.5 说「两进程间接口有调用方鉴别」——这个鉴别是进程级的（运行时进程 vs 平台服务进程），不是进程内调用方级的（Agent Loop vs 插件）。进程内无法区分。这是固有的。PRD 已经如实披露。

任务要求全文搜索「留痕」「审计」「全程」「逐项」等词，确认没有第七处仍写「必须留痕」而无降级标注。

让我再读一遍这段：
「⚠️ 审计留痕的循环依赖须知情（v2.9 新增）| 本表把『全程审计留痕』列为四项硬性要求之一，但该留痕以被审计的插件不拦截审计写入为前提——而 §5.7.3 已承认它可以拦截。因此：留痕保证的是『生命周期动作经接口发生』，不是『插件运行期行为受审计约束』。红线 3 的两段划分见 §10.1」

问题：这句话写于 v2.9，当时还没区分「加载/卸载不经接口」。v2.13 已在同表上一行加了「强度不同」的降级标注，但这段知情说明仍说「留痕保证的是『生命周期动作经接口发生』」——字面读法会认为「生命周期动作都经接口发生」，而加载/卸载不经接口。这是否算第七处未同步？

严格来说：这句话的**意图**是解释循环依赖——留痕只对「经接口发生」的动作有保证。加载/卸载不经接口，所以不在保证内。但字面表述「留痕保证的是生命周期动作经接口发生」有歧义：可以读作「留痕保证的是：生命周期动作（都是）经接口发生的」——这对加载/卸载为假。也可以读作「留痕保证的范围是：那些经接口发生的生命周期动作」——这是正确意图。

这是一个措辞残留问题。考虑到这是第十二轮阻断的同类（留痕降级传播），这算一个**同类残留的第七处**，但严重程度：重要还是建议？它在一个⚠️知情说明里，且上下文紧接着有降级标注，误读风险中等。我倾向于列为「重要」（因为按加严标准零重要才能冻结，需要指出）或「建议」。让我再想想。

实际上，§9.11.2 的「加载/卸载留痕的可信度边界」段落（v2.12 新增）已经写了：「§9.10.2 的循环依赖知情说明写的是『留痕保证的是生命周期动作经接口发生』，恰好不覆盖这两项不经接口的动作。」——等等，PRD 自己在 §9.11.2 里已经指出了这一点！让我找到原文：

「⚠️ 加载/卸载留痕的可信度边界（v2.12 新增，第十一轮复评 kimi-k3 重要 5）：加载/卸载的留痕只能由运行时进程自行上报，而 §5.7.3 已承认已加载的恶意插件『可以拦截审计写入』——插件在加载完成那一刻即可拦截或伪造自己『已加载』这条记录，卸载时同理。§9.10.2 的循环依赖知情说明写的是『留痕保证的是生命周期动作经接口发生』，恰好不覆盖这两项不经接口的动作。」

所以 PRD 在 §9.11.2 已经明确指出 §9.10.2 那段话的局限。那么 §9.10.2 那段话本身虽然措辞有歧义，但全文已经在 §9.11.2 消解了。这降低了问题的严重性。但 §9.10.2 那段话没有指向 §9.11.2 的边界声明（它在同一表内有降级标注了）。我认为这最多算建议级。

6. **§9.11.2 审计日志的完整性与访问控制**表：「⚠️ 对已批准插件的边界（v2.9 新增，v2.12 补加载/卸载）| 本节的『完整性可验证』以写入者不拦截审计为前提。§5.7.3 已承认已批准的插件可拦截审计写入——因此本节对插件运行期操作的保证不成立（红线 3 亦然，见 §10.1）。安装 / 注册 / 激活经产品接口发生，受本节约束；加载 / 卸载不暴露独立产品端点（§9.6.3 第 8 项），只能由运行时进程在进程行为中记录上报——其可信度边界见下方」✅ 已降级

- ## 阻断（必须修，否则不能开工）：### 1. ... 位置/原文/问题/建议
- ## 重要（应修）
- ## 建议（可选）
- ## 覆盖范围自述
- 额外回答三问（我加一节「冻结结论与处置建议」，并在其中或单独一节回答五问的关键点——五问的回答散见各条目，我在冻结结论前加「审查五问结论」一节汇总）。

写吧。
