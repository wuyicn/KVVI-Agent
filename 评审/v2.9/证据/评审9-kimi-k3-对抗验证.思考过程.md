但等等——v2.9 修订 #8 修的是 §9.6.3 清单接入 §7.1。而 §9.4.1 的签名进程分离没有接入任何阶段的验收锚点（除了阶段五的负向测试提及 §9.4.1）。而 §9.4.1 自己又声明「§7.1 阶段一验收锚点须反映」——这个声明是假的。按照同样的定级逻辑（同类问题第八轮定重要），这条应该定「重要」。不过因为它直接涉及 v2.9 的核心安全决策的可验收性，且文档明确声称了一个不存在的修订，我可以考虑定为「重要」上限或「阻断」。

让我想想：冻结的意义是「按这份文档开工」。开工后阶段一按 §7.1 锚点验收。§9.4.1 说阶段一锚点须反映签名进程分离，但实际没反映。后果：阶段一 Docker 骨架可能不会预留签名进程边界，到阶段四建身份层时再发现骨架不支持分离，需要返工。这是「开工会撞上」的问题。参照第五轮 Kimi 的判定标准（「阶段一可动手，整体不可承诺」判不冻结），这个够得上「阻断」吗？

我认为更准确的定级是「重要」：因为 (a) 阶段五锚点确实覆盖了 §9.4.1 的负向测试（含「已批准插件无法取得签名能力」）；(b) 阶段一的 Docker 骨架不包含身份层，签名进程分离在阶段一本来就无法完整验收；(c) 真正的问题是 §9.4.1 写了一句不实的「§7.1 阶段一验收锚点须反映」以及 §4.6 拓扑未同步签名进程。但按加严标准「零重要也必须全部处理」，重要级就足以阻止冻结。我不需要把它升格为阻断。

不过还有一个更深的点：**§9.4.1 说「§4.6 拓扑……签名进程与插件宿主进程分离」，但 §4.6 没有改。** 这意味着存储/部署拓扑基线没有纳入签名进程。这属于「改一半」。

(b) 独立进程与业务系统的关系：委派令牌的签发由谁发起、经什么路径？

现在的链路：员工 → Agent（KVVI 运行时，加载插件）→ 身份层 → 业务系统。
§9.4 说「令牌由身份层签发，不由 Agent 运行时代发」。
v2.9 §9.4.1：签名模块独立进程，「加载插件的运行时只能经受控接口请求签名」。

问题 1：**「受控接口」是什么？** 插件宿主进程（Agent 运行时）向签名进程请求签名时，签名进程凭什么决定签不签？如果 Agent 运行时可以为任意用户/任意公司/任意业务系统请求签名，那么**控制了 Agent 运行时的插件，就可以通过受控接口请求任意签名**——不需要偷私钥，直接用签名进程当签名机（signing oracle）。

这正是任务书 (d) 问的：「有没有残留的路径让插件仍能取得签名能力（例如插件的进程能否向签名进程请求任意签名）？」

让我看 PRD 是否定义了「受控接口」的授权语义。§9.4.1 只写了「加载插件的运行时只能经受控接口请求签名」。**「受控」一词没有任何定义**：谁控？控什么？按什么策略决定可以签哪些令牌？

正常的设计应该是：签名进程只接受来自身份层的请求，且请求内容（用户、公司、业务系统、会话、授权版本）由身份层根据已认证会话确定——而不是由调用方任意指定。但 PRD 没有写这一点。

关键：插件是进程内任意代码，运行在 KVVI 运行时（Agent 运行时）内。Agent 运行时正常工作需要请求签名（为员工会话申请委派令牌）。因此插件与合法的签名请求路径**同进程**——插件可以调用同样的内部接口，或者篡改请求参数（把 user_id 改成别人）。如果「受控接口」不对请求内容做授权决策（即「这个进程可以为哪些主体请求签名」），那么插件就获得了「请求任意签名」的能力——效果等价于拿到私钥（只能在线用，但对攻击者来说足够了：插件在运行时长期驻留，随时可以请求）。

这个残留路径是否真实存在？让我构造攻击：
1. 所有者批准安装插件 P（合法流程，指纹绑定也过了）。
2. P 在 Agent 运行时进程内执行任意代码。
3. P 调用运行时内部的「请求签名」函数（与 Agent Loop 为员工申请令牌用的是同一个），参数指定：user=CEO, tenant=公司A, system=任意业务系统。
4. 签名进程签名，返回令牌。
5. P 用该令牌直接调业务系统，验签通过、审计记录「CEO 经 Agent 通道操作」——不可检测。

要使这个攻击不成立，需要：签名请求的授权决策必须在插件够不到的地方做出——即「谁可以请求签名、签什么内容」由身份层/签名进程根据服务端会话状态决定，而不是由 Agent 运行时进程内的调用方决定。但这里有个根本困难：**委派令牌的请求天然是由 Agent 运行时发起的**（员工在会话中操作，Agent 需要令牌）。会话状态在 Agent 运行时内。如果会话状态在插件同进程，插件可以伪造「这是 CEO 的会话」。

嗯，但等等——会话绑定、账号身份这些应该在身份层（§3.2 自建账号体系）。令牌绑定「会话」，会话创建时绑定公司与账号。如果身份层持有会话状态，签名进程只接受「身份层已认证会话的签名请求」，那么插件要伪造需要伪造身份层的会话记录——这在插件够不到的地方（身份层与插件宿主分离？）。

但问题：**身份层在哪？** §4.1 架构图把身份层画在「KVVI 运行时改造层」内（★ 新增：身份层、模式开关、系统分区）。这个「运行时改造层」是不是加载插件的进程？§9.10.1 说插件在「KVVI 运行时进程内」注册 Service/路由。第八轮 kimi-k3 的推理正是：架构图把身份层画在运行时改造层内 + 插件是该运行时的进程内任意代码 ⟹ 插件可读私钥。

v2.9 的修复只把「签名模块」移出插件进程。**但身份层（会话管理、授权版本、账号）是否也在插件进程内？** 如果身份层仍在插件宿主进程内，那么：
- 插件可以篡改身份层内存中的会话状态（§4.6.4 已承认插件可「直接改内存」），把当前会话的账号改成 CEO；
- 然后正常走「身份层 → 签名进程」的请求路径，签名进程看到的是一个「合法的 CEO 会话签名请求」；
- 签名隔离失效。

v2.9 只移了签名私钥，没有讨论身份层其余部分（会话、授权版本判定）与插件的进程关系。而 §4.6.4 的身份层服务接口契约（撤销/授权版本查询）也承认了「不防御进程内篡改」。

所以：签名模块独立进程这个决策，**只解决了「私钥被读走」这一条路径**，但没有解决「签名请求被伪造/篡改」的路径——而后者不需要读私钥。具体残留路径至少两条：
1. **签名预言机**：插件以运行时身份向签名进程发起任意签名请求（如果「受控接口」不做请求内容的授权校验）。PRD 未定义「受控接口」的授权语义。
2. **会话/身份状态篡改**：若身份层（会话状态、授权版本）仍在插件同进程，插件改内存伪造会话，签名进程按被篡改的状态签名。§9.4.1 未声明身份层其余部分与插件的进程关系。

这是任务书 (d) 明确问的「残留路径」。我认为这是**真实的、基于 PRD 原文的**发现。定级：这直接削弱 v2.9 最重要的决策之一。但公平地说：任何「签名进程」设计都需要有一个调用方；只要调用方在插件进程内，这个风险就存在，除非签名进程自己做授权决策。PRD 写了「受控接口」但没写受控什么。这是一个「声明 vs 机制」的问题——v2.3 复评的老问题在 v2.9 的新决策上重现：「要求隔离」写成了意愿，但「隔离后插件通过受控接口请求任意签名」的路径没有关闭。

定级：我倾向于「阻断」或「重要」。让我再想想。

v2.9 决策声称的安全收益是：「取得私钥的插件可签发任意员工、任意公司的委派令牌——验签通过、审计留下合法痕迹、不可检测」。修复后，插件不能取得私钥。但如果插件可以：
- (a) 请求签名进程签任意令牌（oracle），或
- (b) 篡改身份层会话状态使签名进程基于被篡改状态签出令牌，

那么「签发任意员工、任意公司的令牌，验签通过、审计完美、不可检测」**仍然成立**——只是攻击方式从「偷私钥离线签」变成「在线用签名进程签」。不可检测性完全一样（审计记录的是签名请求对应的内容）。甚至 (a) 情况下审计可能记录「Agent 运行时为 CEO 申请了令牌」——看起来「合法」。

所以 v2.9 的决策**没有完全解决它自己定义的问题**。它把「私钥外泄」关了，但把「签名能力滥用」留着。而 PRD 自己的威胁陈述是「签发任意员工、任意公司的令牌」——不是「私钥外泄」。

但是！我要小心不要过度发挥。让我检查：委派令牌的正常签发路径是什么？§9.4：「令牌由身份层签发，不由 Agent 运行时代发」。所以正常路径是：身份层 → 签名。Agent 运行时不直接请求签名？那「加载插件的运行时只能经受控接口请求签名」这句话里的「运行时」指谁？如果身份层独立部署/独立进程，Agent 运行时请求身份层，身份层请求签名进程……

嗯，§9.4 说「令牌由身份层签发，不由 Agent 运行时代发」。那么签名请求的发起者是身份层。插件在 Agent 运行时进程内。插件要么：
- 冒充 Agent 运行时向身份层请求令牌（伪造会话）；
- 或者如果身份层与插件同进程，直接篡改身份层。

v2.9 §9.4.1 新写的「加载插件的运行时只能经受控接口请求签名」暗示：**加载插件的运行时**确实需要请求签名（否则不需要写这句话）。这说明至少某些签名请求是从插件宿主进程发起的。那么「受控接口」的授权语义就是关键。PRD 没定义。

我认为这是一个真实的重要问题，可以定为「阻断」级别，理由是：v2.9 的头条决策（签名隔离）没有关闭它自己要关的攻击（任意主体令牌签发，不可检测），残留路径在 PRD 内可构造，且「受控接口」无任何约束定义。按照「能强制的才可承诺」的项目标准，这里的承诺（「插件无法取得签名能力」——已写入负向测试）缺乏机制支撑：**负向测试「已批准插件无法取得签名能力」怎么测？** 如果「签名能力」定义为「读取私钥」，可测；如果定义为「取得任意主体令牌」，按现有文本无法判定通过与否。

不过，「零阻断+零重要」标准下，定重要也足以阻止冻结。我需要谨慎判断这究竟是阻断还是重要。我倾向定「阻断」：因为它是 v2.9 两项核心修订之一的核心声明（负向测试清单新增「已批准插件无法取得签名能力」），而该声明在现有文本下不成立（存在可构造的残留路径），属于「声明的安全属性与机制不符」——这与第八轮判「批准只绑定名字」为阻断是同类同量级的问题。

(a) 所有者如何看到并信任指纹？可见性要求？

§9.6.2：「批准记录须含插件包的内容指纹（哈希）与来源；加载/激活时与批准记录比对，不一致则拒绝并告警」。

问题：**批准界面展示什么？** 所有者批准时，界面展示的是插件标识+来源+指纹？PRD 没有要求「批准界面必须向所有者展示指纹」。§9.6.6 要求发布前生成权限差异报告（「审批人不能在不了解影响的情况下批准」），但明确说差异报告不适用于插件（§9.6.2「是否适用差异报告：不适用」）。

那么所有者批准插件时看到什么？一个名字、一个来源、一串哈希。普通所有者（客户企业主，非技术人员）无法验证这串哈希对应什么。这是一个可用性/可知情性问题，但 PRD 的立场可能是「指纹用于机器比对，不用于人验证」。这可以接受——机器比对才是防线。但有一个真实问题：**所有者如何确认他批准的那个指纹就是他想装的那个插件的指纹？** 如果安装源被污染，所有者看到的指纹就是被污染包的指纹，他会批准它——指纹绑定防的是「批准后包被换」，不防「批准时包就是错的」。这不是 PRD 必须解决的（来源可信是另一个维度），PRD 写了「来源」作为批准记录的一部分。可以接受，不构成阻断。但「批准界面须展示指纹与来源」这个可见性要求缺失值得提——不过，PRD 对审批界面有一般性要求吗？§9.6.6 差异报告是针对契约的。对插件，PRD 没写批准界面要求。v2.9 修订 #17 加了「当前生效插件清单」查询和链式注册告知（「须在批准界面如实告知所有者」）。所以批准界面至少要告知链式注册风险。展示指纹的要求没有。这是「建议」级。

(b) 指纹变更即重新批准——插件升级流程？

「指纹变更即重新批准：内容任何变化都要求重新批准，不得沿用旧批准」。所以升级 = 重新批准。流程清楚。没问题。

(c) 热替换：运行中的插件能否被替换？

任务书问：若插件已在运行中，能否被热替换？§9.10.2 的「动作全集」是否覆盖？

动作全集：安装/注册/激活/加载/卸载（§4.1.1 四、§9.10.2）。

检查：「升级」或「替换」不在全集内。升级路径 = 卸载旧版 + 安装新版（重新批准）。这条路径存在且被全集覆盖（卸载+安装）。所以功能上可覆盖。

但「加载/激活时比对指纹」——如果插件已激活运行中，包文件被带外替换（不是经安装端点），运行中的代码不会自动重载；下次加载（重启？）时比对拒绝。那么存在一个窗口：磁盘上的包被换，但运行中的旧代码继续跑——这不算安全问题（旧代码是批准的）。反向：如果运行时支持热加载（DSH 的动态插件是「仅进程内存」的），热替换是否经过「加载时比对」？「加载」在动作全集内，且 §9.6.2 说「加载/激活时与批准记录比对」。所以热替换=加载，会触发比对。看起来覆盖了。

但是注意一个细节：**比对的是「包的指纹」还是「加载到内存的代码」？** 进程内任意代码可以在加载后自我修改，或者插件宿主可以在运行时动态拉取代码（如果插件有网络访问）。指纹比对发生在加载时，之后插件做什么（比如下载并执行新代码）不在任何控制内。这是 TCB 语义的固有部分——PRD 已承认插件是 TCB。所以不构成新问题。

还有一个细节：**「卸载」是否需要批准？** §9.6.2 第五类是「插件安装/注册/激活」需审批。卸载不在审批类里（合理——卸载降低风险）。动作全集含卸载，审计覆盖卸载。OK。

再检查 §9.6.2 的一句话：「**链式注册须声明（v2.9 新增）**：插件在进程内注册另一个插件（不经安装端点）不受本节接口约束——本节效力范围是产品接口面。该路径属 TCB 既有语义，须在批准界面如实告知所有者」。

这是诚实的声明。但它有一个含义值得注意：**链式注册的插件没有批准记录、没有指纹**——它是 TCB 内部行为。这与「当前生效插件清单」对账：生效清单会显示链式注册的插件吗？如果显示，它没有对应的批准记录，对账会发现「有生效插件无批准记录」——这其实是可检测的！PRD 没有写这个对账语义。建议级：生效清单与批准记录对账时，无批准记录的插件应触发告警。这是 v2.9 新增「当前生效插件清单」的自然延伸，但未写。建议。

分析：
- 生命周期动作段：这些动作本来就少（安装/注册/激活/加载/卸载），且本来就有审批+留痕要求。红线 3 覆盖它们的增量价值不大——但也不是零：它承诺「可追溯至批准人账号」，这有意义（谁批准的）。
- 运行期业务操作段：这才是红线 3 的本体（「操作可追溯」防的是「出问题无法追溯」）。插件的运行期操作（读写业务数据、代表用户操作）不在追溯保证内。

那么这是否「掏空」？我的判断：**这是诚实的界定，但有一个如实性问题：两段划分意味着「所有者批准插件」=「放弃该插件一切业务操作的可追溯性」**。这个后果与第八轮签名决策的理由完全一致：「承认等于批准插件=同时交出整个令牌信任体系，而批准界面不会写这句话——所有者无从知情」。

v2.9 对签名问题选择「要求隔离，而不是承认」，理由正是「所有者无从知情」。但对红线 3，v2.9 选择「承认」（运行期操作不可追溯），那么同样的问题：**批准界面是否告知所有者「您批准的此插件的一切业务操作将不受审计追溯保证」？**

§9.6.2 v2.9 新增要求「链式注册须在批准界面如实告知所有者」。§9.10.2 也有「审计留痕的循环依赖须知情」——「须知情」。但「知情」的对象是谁？§9.10.2 写「本表把『全程审计留痕』列为四项硬性要求之一，但该留痕以被审计的插件不拦截审计写入为前提……因此：留痕保证的是『生命周期动作经接口发生』，不是『插件运行期行为受审计约束』」。这是写给 PRD 读者的，不是写给批准界面所有者的。**PRD 没有要求批准界面向所有者展示「此插件的运行期操作不受审计追溯」这一后果。**

对比：链式注册有「须在批准界面如实告知所有者」；签名隔离决策的理由是「批准界面不会写这句话——所有者无从知情」。同样逻辑，红线 3 的放弃也应当在批准界面告知——否则所有者以为「全程审计留痕」（§9.10.2 四项硬性要求④的字面）保护着他。

这是一个真实的不一致：v2.9 在签名问题上用「所有者无从知情」作为拒绝「承认」的理由，但在红线 3 问题上选择「承认」却不要求界面告知。两处标准不一。定级：重要（产品一致性问题+可知情性）。嗯，或者建议？让我想想。

§9.10.2 的循环依赖说明标题就是「审计留痕的循环依赖须知情（v2.9 新增）」——「须知情」三个字暗示了知情要求，但正文没有写「由谁在什么界面知情」。而链式注册明确写了「须在批准界面如实告知所有者」。所以红线 3 放弃段的告知要求缺失或含糊。我认为这值得「重要」级别：因为 v2.9 自己在签名决策中确立的原则（「所有者无从知情的后果不应作为默认」）在红线 3 上没有被贯彻——而这两个后果是同量级甚至同级（一个是令牌体系失守，一个是审计追溯失守）。

PRD 原文：「签名须经独立进程（不加载任何插件）完成，**加载插件的运行时只能经受控接口请求签名**」。

这句话的主语是「加载插件的运行时」——即 Agent 运行时（插件宿主）。它说运行时「只能经受控接口请求签名」。在善意解释下，「受控接口」= 身份层/签名进程对请求做校验。但校验什么？请求来自运行时，运行时声称「员工 E 在公司 X 的会话 S 需要令牌」。签名进程/身份层如何验证这个声称？会话 S 的记录在哪？如果会话记录在平台库（§4.6.1：会话属平台数据），身份层可以查会话状态验证。那么「受控接口」的有效定义是可行的——但 PRD 没写。而插件与运行时同进程，插件可以：
1. 直接调用运行时内部的签名请求函数（为任意主体）；
2. 篡改运行时内存中的会话状态（§4.6.4 承认插件可改内存）——如果会话状态在运行时内存。

身份层在架构图上与插件同层（运行时改造层）。v2.9 没有声明身份层的进程边界。所以：在 PRD 文本下，「受控接口」没有定义任何能阻止「插件以运行时身份请求任意主体令牌」的校验。这是真实缝隙，不是吹毛求疵——因为 v2.9 决策的整个价值主张就是关闭「任意主体令牌、不可检测」，而它在文本上没有关闭（只关闭了私钥外泄）。
