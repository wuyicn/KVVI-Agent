让我仔细审读这份 v2.8 PRD，按照第八轮复评的六个任务逐项对抗验证。

## 任务 1：插件审批「不走发布通道」是否站得住？

先看 v2.8 §9.6.2 新增的插件审批形式：

> **是否走发布通道** | **不走**发布通道。发布通道管的是**声明式契约与策略**（§9.6.3）；插件是**代码**，二者通道不同
> **是否适用差异报告** | **不适用**（§9.6.6 的差异报告针对契约与策略差异，对代码无意义）
> **审批形式** | 所有者**显式批准**每一次安装/注册/激活；**不得批量预授权**
> **落地检查** | 插件安装端点**须纳入 §9.6.3 的产品接口面清单**，并有负向测试：非所有者请求被拒

(a) 「差异报告无从生成」的理由成立吗？

差异报告（§9.6.6）展示「新增了谁能看到什么、谁能做什么动作、数据范围档位变化、工具启用范围变化」。对插件而言，确实无法从任意代码中静态推导出这些——插件是进程内任意代码，没有声明式语义可供比较。这个理由基本成立：对任意代码做「它会改变什么权限」的静态分析是不可判定的问题。

但注意：审批人批准插件时，展示的「影响」是什么？§9.6.6 要求「没有差异报告的变更不得提交审批——审批人不能在不了解影响的情况下批准」。插件不适用差异报告，那么所有者批准插件时**依据什么了解影响**？v2.8 没有回答。审批插件时审批人看到的是「插件 X 请求安装」，没有任何关于它将获得什么能力的信息。这比契约审批的信息量还低。这是一个真实的缺口：审批的形式存在，但审批的**信息基础**不存在。所有者批准插件时是在盲批——批准的是一段无法预览影响的任意代码。

不过，这是否构成冻结阻断？可以这样看：PRD 已经明确把插件定位为「扩展 TCB」，即「所有者信任这段代码」。TCB 的语义就是「无条件信任」，所以「批准时无法预览影响」与 TCB 定位是一致的——你信任它就不需要差异报告。所以这一点可以降级为「重要」：建议在 §9.6.2 插件审批形式中补一句「批准即表示所有者将该代码纳入信任基，审批界面应展示插件来源、标识、哈希等可核验信息」，至少让「批准的是什么」可核验（插件标识、版本、哈希）。目前 §9.10.2 的审计要求有「插件标识」，但批准动作本身没有要求核验「批准的这段代码」与「实际安装的代码」是同一个东西。

(b) 插件脱离发布通道后，还有什么机制能阻止「所有者忘记自己批准过什么」或「批准被冒用」？

- 「忘记批准过什么」：§9.10.2 要求「注册行为审计：插件的加载、注册、卸载全部留痕（§9.11.2 的防篡改存储）」。审计在防篡改存储里。但「留痕」不等于「可查询的当前有效清单」。有没有「当前已安装插件清单」的查询要求？§9.10.2 没有明确要求系统提供「当前生效插件清单」视图。审计日志是追加的，所有者要知道「现在有哪些插件在跑」需要回放审计。这是一个小缺口，但不算阻断——审计留痕可以支撑事后重建。
- 「批准被冒用」：批准动作本身如何防伪？这依赖于身份层的认证（§3.2、§9.4）——所有者的批准动作是在他登录会话内发生的，审计记录账号。但是！关键问题：插件安装后是在**进程内**运行的。恶意插件安装后能否伪造「所有者批准」记录去安装第二个插件？插件是进程内任意代码，它可以调用插件安装端点的内部实现（如果同进程）或者直接注册自己。§9.6.3 清单第 8 项的断言是「非所有者请求被拒」——这是**产品接口面**的断言。但插件不走产品接口面，它在进程内。一个已批准的恶意/被劫持插件能否在进程内直接调用插件注册逻辑，安装另一个未批准的插件？DSH 的「一切皆插件」架构里，插件注册是进程内 API 调用。如果插件注册的唯一防线是「安装端点要求所有者身份」，那么进程内代码绕过这个端点直接操作注册表，就构成了「插件安装插件」的链式扩张。PRD 没有处理这个。而且按 v2.8 自己的逻辑（插件可绕过执行点），这个问题无法用产品机制回答——它属于「TCB 内部的自律」。但值得指出：这意味着「仅所有者批准」这条保证在第二个插件起就没有机制保障了。第一个恶意插件可以安装第二个，审计也可能被拦截（§5.7.3 v2.8 新增声明已承认插件「可以拦截审计写入」）。

等等，§5.7.3 的 v2.8 新增明确写了：「**没有隔离机制能阻止其触碰地基**——它可以拦截审计写入、替换权限校验钩子」。所以 PRD 自己已经承认了「审计可被已批准插件拦截」。那么 (b) 的答案是：**没有机制**。「所有者忘记自己批准过什么」靠审计，但审计可被插件拦截；「批准被冒用」靠身份层，但插件可替换权限校验钩子。PRD 的立场是：TCB 内的恶不在防御范围。这是一致的（一致的悲观），但评审应该如实指出：四项约束中「全程审计」这一项与 §5.7.3 自己承认的「插件可拦截审计写入」存在张力——审计保证对插件自身行为的记录，依赖于被审计对象不作恶。这是一个诚实的表述问题：§9.10.2 的「全程审计留痕」应当加上与 §9.4.4 类似的边界声明（审计记录以防插件可信为前提——但插件正是被信任的对象，所以这是循环的）。实际上 §4.1.1 四的表里有「审计留痕」要求，但没说边界。

嗯，但这是否算 v2.8 引入的新问题？不是，v2.7 就有「全程审计」。但 v2.8 在 §5.7.3 新增了「插件可以拦截审计写入」的承认，却没有同步修改 §9.10.2 的「全程审计留痕」的表述边界——这属于「改一半」：§5.7.3 承认了审计可被插件拦截，§9.10.2 却仍把「全程审计」作为四项硬性要求之一而无边界声明。这可以算一个重要项：两处表述需要协调（在 §9.10.2 的审计行补「该留痕以插件自身不拦截审计写入为前提；TCB 的审计保证是弱的」之类）。

(c) 把插件放在发布通道之外，是否让 §9.6.3 的「唯一发布通道」变成两条通道？

§9.6.3 原文：「**所有权限策略、数据范围、工具启用范围、聚合口径的生效，必须经过唯一发布通道。**」注意这个清单：权限策略、数据范围、工具启用范围、聚合口径。插件不在其中。所以字面上 §9.6.3 的唯一性主张是针对这四类对象的，插件本来就不在其管辖范围。「唯一发布通道」的意思是「这四类变更只有一条路」，不是说「系统里只有一条变更通道」。v2.8 在 §9.6.2 明确了「发布通道管的是声明式契约与策略；插件是代码，二者通道不同」——这是对管辖范围的澄清，逻辑上自洽。

但这里有个实质问题：插件可以**改变**这四类对象的运行时行为（替换权限校验钩子、拦截审计）——§5.7.3 自己承认了。所以「权限策略只经发布通道生效」这个保证，在插件存在时的真实含义是「权限策略的**声明**只经发布通道变化，但其**执行**可被插件改写」。这正是红线例外已承认的。§9.6.3 的范围声明也写了「实例所有者在信任边界之内，可批准插件绕过本条」。所以 (c) 的答案是：字面上没有变成两条通道（管辖对象不同），但实质上「唯一通道」保证的对象（声明式策略）与系统实际行为之间的缝隙已被如实承认。这条主张没有矛盾，但被掏空了相当一部分——这是任务 5 要回答的产品级判断。

## 任务 2：§9.10.2 删除「插件不得绕过」后，四项约束是否足以支撑「受控的扩展通道」？

四项：仅所有者批准、搭建者不得安装、生产默认禁用、全程审计。

分析：
1. **仅所有者批准**——入口控制。但如 (b) 分析，第一插件可装第二插件（进程内绕过安装端点），所以「仅所有者批准」保证的是「第一个插件的安装动作」，不保证「系统中运行的所有插件都经过所有者批准」。除非有机制保证「插件注册面在进程内不可达」——但 PRD 明确不设隔离机制。
2. **搭建者不得安装**——§9.6.3 清单第 8 项有负向测试支撑（对产品接口面而言）。但同样，搭建者能否通过已安装插件间接安装？如果所有者是可信的且插件是可信的，这个保证成立。
3. **生产默认禁用动态插件**——注意：这一项只针对「运行时动态插件」（第四通道），profile 插件不在此列。读一下：「动态插件生产环境默认禁用 | 仅在受控调试场景开启，开启须留痕并告警」。而 profile 插件（进程级、跨重启保留）是正常安装通道。OK。
4. **全程审计**——如上，可被插件自身拦截。

那么「受控的扩展通道」这个说法是否成立？关键在于「受控」的定义。如果「受控」=「每个运行的插件都可追溯到所有者的一次显式批准」，那么缺两个东西：
- **安装动作的闭环验证**：批准的插件（标识/哈希/版本）与加载的插件同一性核验。现在只有「留痕含插件标识」，没有「加载时校验与批准记录一致」。恶意场景：所有者批准插件 A（看了标识），安装时实际加载 A'（被替换的代码）。没有哈希绑定，批准就形同虚设。§9.6.2 插件审批形式没有要求记录或校验插件的**内容指纹**。
- **当前生效清单的可查询性**（次要）。

缺的第一项是真实的、重要的缺口：**批准与加载之间没有同一性绑定**。所有者批准的是「名字」，安装的是「字节」。这与其他条款的精度水平不匹配——PRD 对交付包有指纹（G5），对 MetaSchema 有哈希（§5.3），对令牌有签名，但对唯一引入任意代码的通道，批准动作只绑定「插件标识」（名称）。改成「批准记录须含插件包的内容指纹，加载时校验一致」是 PRD 级的要求（是什么，不是怎么做）。这够得上「重要」甚至「阻断」？

让我权衡：这是「插件批准」机制的核心空洞。v2.8 的核心修订就是插件审批通道。如果批准不绑定内容，「仅所有者批准」的实际保证是「所有者批准过一个叫 X 的东西」。这在对抗性视角下是机制的实质空洞。但反方观点：TCB 语义下，所有者批准安装本身即信任委托；供应链层面的「装的是什么」属于部署治理。然而 PRD 自己在 §7.5.2 G5 和 §5.3 都对「内容指纹」有明确要求，说明本项目接受「标识≠内容」的威胁模型。而且对插件而言，连「安装来源」都没说（从哪里获得插件？npm？本地文件？URL？§5.6 说搭建引擎「安装依赖（npm/CDN/任意URL）」不允许，但插件安装来源对所有者通道没有约束）。

我认为这够得上**阻断**的候选：因为本次修订的核心主张是「插件审批通道已闭合」，而审批语义（批准什么、如何确保批准的就是安装的）未定义，第八轮又是「冻结前最终验证」。这是开工时会立刻撞上的问题：实现者会问「所有者批准界面显示什么？批准记录存什么？加载时校验什么？」PRD 精度标准（按 v2.5 的先例：「部署单元构成、存储拓扑」这类「系统是什么」的问题要收回 PRD）——「批准动作绑定插件内容指纹」属于安全属性的定义，不是实现细节。对标 §3.5.1 的先例：v2.6 判定「链接签名的最小安全属性」是产品安全属性而非实现细节，并列出签发主体、签名方式、防重放等。插件批准完全同构：批准记录的内容（插件标识 + 版本 + 内容指纹 + 批准人 + 时间）、加载时校验（指纹一致才激活）。缺了它，「仅所有者批准」是不完整的机制。

再想想是否真阻断。判定标准是「能不能开工且不埋雷」。没有内容指纹绑定，开工后实现者可能实现为「批准=在数据库插一行 plugin_name」，然后安装任意来源的同名包。这埋的雷与 v2.7 的「审批引用落空」同级别（一个是引用落空，一个是语义落空）。我倾向于把它列为**阻断**，但措辞要克制：最小要求是「批准记录绑定插件内容指纹（哈希），加载/激活时校验与批准记录一致；不一致拒绝」。这不需要技术设计文档级别的细节。

另外还有一个问题：任务 2 问「缺的是什么」。我的答案：缺（i）批准与加载的同一性绑定（内容指纹）；（ii）「仅所有者批准」只覆盖产品接口面，对进程内链式安装无机制（这一点 PRD 已承认 TCB 语义，可不再要求，但应如实写明「本保证仅及首个插件的安装动作」——即批准的效力范围声明）。嗯，（ii）其实是 (b) 的核心。PRD 现在的立场是「TCB 内部不防御」，按 §4.1.1 二的处理原则，这可以是一致的：第一个插件由所有者批准，之后的恶属于「所有者批准了不该批准的代码」。这是自洽的。但评审应如实记录：四项约束合起来支撑的是「插件通道的**入口**受控」，而不是「运行中的插件集合始终等于所有者批准的集合」。措辞上，「受控的扩展通道」这个说法在 PRD 里其实没有直接出现——任务 2 的引号是评审任务自己的表述。PRD 的说法是「扩展可信基」。TCB 语义本身是自洽的：你信它，它做什么都不算违反。所以严格说，四项约束 + TCB 定位在逻辑上是自洽的——PRD 没有声称「受控通道」，它声称的是「入口仅所有者 + 留痕」。那么缺的就是审计的边界声明（可被插件拦截，§5.7.3 已承认但 §9.10.2 未同步）和内容指纹绑定。

好，调整：阻断候选聚焦在**批准语义空洞（无内容绑定）+ 审计表述未同步**这两个。审计同步问题更像「重要」。

## 任务 3：v2.8 是否又引入新的过度承诺？

逐处检查 v2.8 新增断言：

**§9.6.2 插件审批形式**：
- 「搭建者与员工**无任何**安装/注册/激活路径」——对产品接口面而言可测（清单第 8 项负向测试）。OK。
- 「审批主体：仅所有者」——可测。OK。
- 无过度承诺。

**§9.6.3 分项断言**：逐条看：
- 第 1 项「搭建舱 API：不提供变更业务权限策略的旁路；产出物只能经发布通道生效」——可测（构造请求尝试直写）。
- 第 3 项「经差异报告 → 审批 → 发布全流程的操作被接受；跳过任一环节的直写被拒」——可测。
- 第 6 项「未授权主体被拒（非所有者不得授予搭建权限）；经授权的合法操作须留痕」——可测。
- 第 9 项「业务系统侧的契约激活端点：只激活经发布通道送达的契约包；本地其他契约包不构成激活依据」——可测。
- 无过度承诺。这些断言都是产品接口面断言，与范围声明一致。

**§9.4.4 批次签名**：
- 「每批带**本地签名与单调批次号**；批次号不得跳号」——可测。
- 「批次签名的签发主体与密钥保管位置属产品级安全属性，须在阶段四定明；不得由业务系统本地生成并持有唯一私钥」——这是**要求**而非承诺，且明确留了「阶段四定明」。注意：这里说「不得由业务系统本地生成并持有唯一私钥（否则主机被控即可伪造）」。但离线时业务系统要对批次签名，签名私钥必须在业务系统侧可用（平台离线）。如果私钥不在业务系统本地持有，那在哪？平台？平台离线时拿不到。这是一个潜在的内在矛盾：批次签名发生在离线期，签名密钥必须在业务系统本地可得；而条款说「不得由业务系统本地生成并持有唯一私钥」。

细读：「**不得**由业务系统本地生成并持有唯一私钥（否则主机被控即可伪造）」。括号给出理由：本地持有唯一私钥 → 主机被控即可伪造。但上一行刚承认「主机/部署方被控不在防御范围内」「签名密钥若在本地持有则可伪造批次」。所以 v2.8 的两条新增合起来是：边界声明说「密钥若在本地则可伪造（主机被控时）」，密钥属性说「不得本地持有唯一私钥」。那么密钥该在哪？选项：(i) 业务系统本地持有非唯一私钥（比如密钥分片/门限？）；(ii) 硬件模块（HSM/TPM）持有，进程不可导出——这是常见答案：密钥在 TPM 里，主机被控（拿到 shell）也不能导出私钥，只能调用签名。但「主机被控」通常意味着攻击者也能调用 TPM 签名……不过 TPM 至少能防止「事后伪造历史批次」（如果密钥不可导出，攻击者拿到控制权后签的新批次会……等等，批次号是单调的，攻击者可以继续签）。这个细节进入实现层了。PRD 的要求层级：「签发主体与密钥保管位置属产品级安全属性，须在阶段四定明」——它把答案推迟到阶段四，只给了一个否定约束（不得本地持有唯一私钥）。这个否定约束与「离线时必须能签」之间存在张力吗？「本地生成并持有唯一私钥」——禁止的是「本地生成 + 本地持有 + 唯一」三者合取。可行的满足方案：密钥由身份层（平台）生成，离线前分发给业务系统（非本地生成）；或密钥在 TPM（持有但不是软件层持有）。所以「本地生成」被禁，「平台预置的密钥存于本地」是否被禁？字面是「本地生成并持有唯一私钥」——平台生成、下发到本地持有、且唯一，字面上违反「本地生成并持有」的合取吗？合取的三个成分：本地生成 ∧ 持有 ∧ 唯一。平台生成则不满足「本地生成」，所以不违反字面。OK，字面自洽。但「持有唯一私钥」的业务系统在主机被控时仍可伪造——括号理由「否则主机被控即可伪造」对任何本地持有的密钥都成立，不只是本地生成的。所以理由与约束之间存在错位：约束禁的是「本地生成」，理由担心的是「本地持有」。不过边界声明已承认主机被控不在防御范围，所以这条的实际增量是「密钥签发主体要在阶段四定明」。这是个悬而未决但已声明推迟的项——不是过度承诺，是开放点。可以接受，但值得在「建议」里指出字面错位（约束写「本地生成并持有」，理由说的是持有问题；若要理由成立，约束应是「密钥不得可被进程内任意读取」之类——不过这已经进入实现层，PRD 只说「阶段四定明」是诚实的）。降级为建议或重要？倾向建议。

**§9.10.2 四项要求**：「全程审计留痕」——如上，与 §5.7.3 承认的「插件可拦截审计写入」存在未同步的张力。这既是任务 2 的点也是任务 3 的点：「全程审计」是一个保证性表述，其前提（被审计的插件不拦截审计）与 v2.8 自己在 §5.7.3 的新增承认冲突。这是 v2.8 新引入的过度承诺/未同步。重要。

还有 §9.6.2 插件形式表里的「审计：安装、注册、卸载全程留痕（§9.11.2）」——同样的问题。注意是「安装、注册、卸载」没有「激活」？§9.6.2 第五类标题是「插件安装/注册/激活」，审批形式要求「所有者显式批准每一次安装/注册/激活」，但审计行写「安装、注册、卸载全程留痕」。§9.10.2 写「插件的加载、注册、卸载全部留痕」。§4.1.1 四写「安装、注册、激活插件必须留痕」。三处列举不一致：
- §4.1.1 四：安装、注册、激活
- §9.10.2：加载、注册、卸载
- §9.6.2：安装、注册、卸载
激活 vs 加载 vs 卸载，三个不同集合。这是 v2.8 引入的新计数漂移（§9.6.2 是 v2.8 新增的）！§9.6.2 要求批准「激活」但审计行漏了「激活」；§9.10.2 有「加载」无「安装/激活」。这属于 check_prd.py 抓不到、但评审该抓的不一致。算什么级别？审计留痕是插件通道的核心约束之一，「激活」是审批对象却不在审计清单里（§9.6.2 审计行）。这是真实的「改一半」。重要级，可能阻断边缘。嗯，§4.1.1 四有激活，§9.6.2 审计行无激活——同一份文档内部对「插件生命周期哪些动作留痕」给了三个不同清单。这必须统一。我把它列为重要（不是阻断，因为审计要求整体存在，只是列举漂移；但这正是本项目连续三轮的错误模式，值得点名）。

**§9.4.4 边界声明**：「以防业务系统主机可信为前提；主机/部署方被控不在防御范围」——这是收窄，不是过度承诺。OK，反而合格。

**§10.1 红线注记**：如实记录例外。OK。

**§9.6.4 离线预授权不生效**：「离线窗口内预授权不生效——R3 一律阻塞。不存在『R3 的离线预授权路径』」——收窄。OK。

**三处 TTL 同一配置项**（§9.4.2、§3.5.1、§9.4.4）：检查落实。§9.4.2：「有效期 ≤ 5 分钟（与 §9.4.4 的产品级上限同一配置项）……该值与 §9.4.4 残留窗口、§3.5.1 访客链接缓存 TTL 必须相等，三处引用同一配置项（v2.8 定值）」。§3.5.1：「残留窗口……上限 ≤ 5 分钟，与 §9.4.4 同一配置项、同一处置」。§9.4.4：「产品级上限：≤ 5 分钟（v2.7 定值）」+「三处须一致：本值与 §9.4.2 的短时令牌有效期、§3.5.1 的访客链接缓存 TTL 是同一个全局配置项」。三处都写了。OK，落实了。

但等一下——有个语义问题：令牌有效期 ≤ 5 分钟、撤销缓存 TTL ≤ 5 分钟、访客链接缓存 TTL ≤ 5 分钟，三者**相等**。令牌有效期是「签发后活多久」，撤销缓存 TTL 是「业务系统缓存撤销状态多久」。三者相等有意义吗？§9.4.2 说「短时有效期（首选）：有效期 ≤ 5 分钟……使权限变更后的最大残留窗口被限制在该时长内」。如果令牌有效期 5 分钟、撤销缓存 TTL 也是 5 分钟，那么权限回收后的最大残留窗口实际上是：令牌剩余有效期 + 缓存陈旧度，最坏接近 5+5=10 分钟（权限在 t=0 回收，撤销状态在 t=-ε 刚被缓存，缓存到 t≈5 才过期；令牌在 t=0 签发……不对，令牌签发于 t=-δ，回收发生于 t=0，令牌有效期到 t=-δ+5）。最坏窗口 ≈ 缓存 TTL + 令牌有效期 = 10 分钟，而不是 5 分钟。PRD 声称「最大残留窗口被限制在该时长（5分钟）内」——这是过度承诺！除非「残留窗口」定义为「从令牌角度」与「从缓存角度」各自独立。细读 §9.4.4：「允许本地缓存：业务系统可以本地缓存撤销状态与授权版本」「窗口内可放行：窗口内，验签通过且未命中缓存的已撤销记录的令牌可继续接受」。场景：t=0 所有者停用账号 X。业务系统缓存的撤销状态是 t=-4 分钟拉取的（缓存新鲜，TTL 5 分钟，t=1 才过期）。X 的令牌签发于 t=-4（有效期到 t=1）。那么 t∈[0,1] 内，业务系统验签通过、缓存说「未撤销」（陈旧）→ 放行到 t=1。最坏窗口约 5 分钟（受缓存 TTL 限制）。但如果缓存是 t=-4:59 拉取的，过期于 t=0:01——OK。最坏情况：缓存刚拉取（t=0 拉取，里面还没有「X 已撤销」，因为撤销发生在拉取之后瞬间），缓存有效到 t=5；令牌签发于 t=0-ε，有效到 t=5-ε。则放行窗口 ≈ [0, 5) ≈ 5 分钟。哦，因为两者都是 ≤5 且同时起算（最坏对齐），窗口上限是 max(缓存TTL, 令牌有效期) ≈ 5 分钟，不是相加。再想：令牌 t=-4 签发（有效到 t=1），撤销 t=0 发生，缓存 t=0+ε 拉取（含撤销）→ t=0+ε 后拒绝。若缓存 t=-4:59 拉取（无撤销），有效到 t=0:01 → 拒绝在 t=0:01 后。若缓存 t=-ε 拉取（撤销前），有效到 t=5-ε；令牌 t=-4 有效到 t=1 → 放行到 t=1。最坏对齐：缓存 t=-ε（有效到 5-ε），令牌 t=-ε（有效到 5-ε）→ 放行到 5-ε。所以最坏窗口 ≈ 5 分钟。OK，「≤5分钟」的声称在两者相等时成立（当两者起算点对齐时，窗口由大者决定；不对齐时由「晚结束者」决定，而晚结束者 ≤ 起算点+5，起算点必在撤销前，撤销后窗口 ≤ 5）。严格证明：缓存过期时间 ≤ 缓存拉取时间+5 ≤ 撤销时间+5？不对——缓存可以在撤销后拉取吗？撤销后拉取的缓存包含撤销状态（假设平台一致），则立即拒绝。所以「不含撤销的缓存」必然是撤销前拉取的，其过期时间 ≤ 撤销时间 + TTL ≤ 撤销时间+5。同理有效令牌必然签发于撤销前（撤销后身份层不应再签发该账号令牌……呃，撤销后用户不能登录签发新令牌，成立），其过期时间 ≤ 撤销时间+5。所以放行时间 ≤ min(缓存过期, 令牌过期) ≤ 撤销时间+5。窗口 ≤ 5 分钟成立。好，这个声称自洽。但前提是「撤销后身份层不再为该账号签发新令牌」——账号停用即不能登录，会话结束令牌失效，OK。

不过还有个细节：§3.5.1 说访客链接的吊销残留窗口「上限 ≤ 5 分钟，与 §9.4.4 同一配置项、同一处置」——「由有效期兜底：链接自身有效期上限即残留窗口的最终兜底」。访客链接有效期是「天」级，缓存 TTL 5 分钟。OK。

任务 3 小结：v2.8 新增断言大部分是收窄或要求式（非承诺式）。发现的过度承诺/未同步：
1. §9.6.2/§9.10.2/§4.1.1 的插件审计动作清单三处不一致（激活/加载/卸载），且「全程审计」未加「以插件不拦截审计为前提」的边界（§5.7.3 已承认插件可拦截审计写入）——v2.8 自己埋的半同步。
2. 批次签名密钥条款的约束与理由字面错位（小，建议级）。

## 任务 4：§9.6.3 分项断言是否可测？哪些是同义反复？

第 3 项：「发布通道端点：经差异报告 → 审批 → 发布全流程的操作被接受；跳过任一环节的直写被拒」。可写成负向测试：构造跳过差异报告的提交 → 拒；跳过审批 → 拒；跳过发布直接激活 → 拒（与第 9 项呼应）。可测。✓

第 6 项：「身份层端点：未授权主体被拒（非所有者不得授予搭建权限）；经授权的合法操作须留痕」。前半可测（非所有者调用授予接口 → 拒）；后半「合法操作须留痕」可测（执行授权操作 → 审计存在记录）。可测。✓ 注意：这修正了 v2.7 的矛盾（身份层端点本就是合法通道）。✓

第 8 项：「插件安装端点：非所有者请求被拒」。评审任务问：这在「仅所有者可操作」前提下是定义而非测试？我认为不是同义反复：断言「非所有者请求被拒」是对**端点行为**的可执行断言——以搭建者身份、员工身份、无身份分别构造安装请求，期望拒绝。它测试的是端点是否真的实施了身份检查（而不是假定）。「仅所有者可操作」是规范，「非所有者请求被拒」是对该规范的可执行检验——规范与检验的关系本来就是「定义→测试」，这不构成同义反复。同义反复是指「测试的通过条件由定义本身保证，无法失败」。这里可以失败（实现漏了身份检查），所以是可测的。✓ 不过第 8 项有一个真实的弱项：它只覆盖「端点」层。如任务 1(b) 分析，插件作为进程内代码的**链式安装**（已安装插件在进程内调用注册逻辑）不在「端点」层面——该断言对产品接口面成立，对进程内不成立。这与 §9.6.3 范围声明一致（清单本来就是「产品接口面」清单），所以不算缺陷，但值得在回答任务 4 时说明：第 8 项可测，但其保证范围与 §9.6.3 整体一致地限定在产品接口面。

那么有没有哪项实际上是弱的？第 1、2、4、5、7 项（「不提供旁路」类）：断言形式是「不存在旁路」——这是全称否定断言，测试只能采样（构造若干已知旁路尝试被拒），不能穷举。但 PRD 已声明这是「产品接口面清单」逐项负向测试，对每项的具体测试是「构造直写请求被拒」。这是可执行的（虽不能证明不存在）。第 3 项的「全流程操作被接受」是正向断言，可测。整体可测性成立。

评审任务特别问「有没有哪一项是同义反复」。我的结论：第 8 项不是同义反复（可失败的检验）。但让我再细想……「仅所有者可批准安装」+「非所有者请求被拒」——如果测试就是「以非所有者身份请求安装端点」，断言拒绝。这是一个真实的测试（类似 §3.5、§9.4 的各负向测试）。OK，不是同义反复。

不过，等等——还有一个更微妙的点。第 6 项后半「经授权的合法操作须留痕」：测试「留痕」需要定义留痕内容（谁、何时、授予了谁——§3.1 有要求）。可测。✓

第 9 项「只激活经发布通道送达的契约包」：如何判定「经发布通道送达」？需要一个可验证的标志（发布记录/签名）。测试：把契约包直接放到业务系统本地（不经发布通道）→ 尝试激活 → 拒。可测。✓ 但这隐含一个机制前提：业务系统能区分「经发布通道送达」与「本地存在」——这要求发布通道送达的契约包带有可验标记（§4.1.1 五「激活来源受限」已声明）。机制存在（发布记录 + 可能签名），可测。✓

结论：三项被点名的断言均可写成负向测试，无同义反复。第 8 项表面像定义复述，实质是可失败的端点行为检验。但应在回答中说明第 8 项保证范围的边界（产品接口面，不含进程内链式安装）。

## 任务 5：三条核心红线对插件路径不成立，产品还剩多少安全主张？

如实盘点：
- 红线 1（同一套校验）：对插件不成立。剩：对搭建者与员工成立。
- 红线 2（读走预定义视图）：对插件不成立。剩：同上。
- 红线 3（可追溯）：对插件**部分**成立？审计留痕要求存在（安装/注册留痕），但插件执行的业务操作是否留痕？插件绕过执行点后的操作不经过审计埋点（除非插件自己埋）。且 §5.7.3 承认插件可拦截审计写入。所以红线 3 对插件路径的操作基本不成立（只能追溯「安装了插件」，不能追溯「插件做了什么」）。§10.1 注记只写了红线 1/2/4 的例外，**没有写红线 3 对插件路径的例外**——但按同一逻辑，插件绕过执行点后，其操作不经统一执行点、不留标准审计痕迹，红线 3「操作可追溯至账号与执行通道」对插件路径的操作同样不成立（或仅存于「插件自愿留痕」）。这是一个真实的遗漏：§10.1 的注记列举了红线 1/2/4，漏了红线 3 的同类例外。

验证一下：红线 3 是「操作可追溯至账号与执行通道」。插件作为进程内代码执行操作时，有没有「账号」概念？插件不是账号主体。插件写业务数据（绕过执行点），审计里不会有「插件 X 代表谁」。所以红线 3 对插件操作不成立。§10.1 注记说「红线 1/2/4 保证范围均为搭建者与员工，不覆盖已批准的插件」——为什么红线 3 不在列？可能作者认为「安装动作留痕」就够了，但红线 3 管的是「操作」，不是「安装」。插件的**运行时操作**无法追溯至账号（它没有账号）。这是 §10.1 注记的遗漏，属于「改一半」（v2.8 第 7 项修订本身不完整）。

且 §9.2 范围声明的连带段（v2.8 改为开放式列举）说「任何依赖『本执行点唯一』的条款，对所有者所批准的插件均不成立——包括但不限于 §9.3、§9.6、§9.7、§9.8.1、§9.9、§9.11.3、以及红线 1/2/4」——这里也漏了红线 3！开放式列举「包括但不限于」覆盖了没列出的，字面上红线 3 可被「包括但不限于」吞进去。但 §10.1 的注记是**封闭**写法：「红线 1、2、4 的保证范围均为『搭建者与员工』」——读者会得出结论「红线 3 对插件成立」。这是真实的内部不一致。级别：重要（边缘阻断？）。红线总表是安全主张的汇总面，遗漏一条例外会误导。我认为重要即可，因为 §9.2 的开放式表述已在字面覆盖了它，但 §10.1 应同步。

再核实红线 3 是否真对插件不成立——插件操作时是否可以「留痕」？§9.10.2 要求「注册行为审计」（加载、注册、卸载留痕），不要求插件的**业务操作**留痕。所以是的，插件的业务操作不在红线 3 覆盖内。结论成立。

现在回答任务 5 的产品级判断：当红线 1/2/4（+实际上的 3）对插件路径不成立时，产品还剩什么？

剩余的安全主张：
1. 对搭建者与员工的全部主张（这是产品的**主要用户面**）——完整保留：红线 1-4、8，§9 全部机制。
2. 对访客的受限主张（§3.5.4 已如实声明）。
3. 对所有者：插件入口控制（仅所有者批准）+ 安装留痕。
4. 对基础设施管理员：无（信任边界内，已声明）。

这个结构是自洽的：它是一个「双主体信任模型」——产品防御的是「搭建者与员工」（构造性），信任的是「所有者与基础设施管理员」（声明边界）。这种模型在自托管软件中是标准形态（类比：任何自托管软件都不防御 root）。PRD 的诚实度在于把例外写进了红线表。

但产品级的代价要说清楚：
- 对**客户**（购买私有化部署的企业）而言，安全故事变成了：「你的员工和搭建者被严格约束；但你的所有者（主账号）可以通过一个插件让全部约束失效，且系统无法告诉你之后发生了什么（审计可被拦截）」。这实际上把产品的全部安全财产**单点化**在所有者的一个决策上。这在商业上是否可接受？对小微企业客户（所有者=老板），老板自己不会装恶意插件，风险主要在「所有者被骗装插件」（供应链/社工）。此时产品剩下什么？剩「安装留痕」（如果恶意插件不拦截审计——但它可以）。所以严格说，一旦恶意插件进入，产品的可追溯性也归零。
- PRD 已把这一切如实声明（信任边界、TCB），逻辑自洽。但有一个**表述层面**的剩余问题：§10.1 红线总表的注记写的是例外，首行却仍写「红线 1–4 与 8 在首版全部生效，无一可豁免」。对插件而言红线 1/2/4 实际上**有豁免**（被批准的插件）。「无一可豁免」与「对插件路径不成立」之间的措辞需要调和：准确表述是「无主体可豁免其适用范围；但适用范围本身不含已批准插件」。现在首行的「全部生效，无一可豁免」在不了解注记的读者（客户、销售、实现者）那里会过度承诺。这是重要级措辞问题。

嗯，这个点值得放进去：§10.1 首行「红线 1–4 与 8 在首版全部生效，无一可豁免」与注记的插件例外并存，首行应加限定（「在其声明的适用范围内」）。这是 v2.8 第 7 项修订留下的「改一半」。

产品级判断的结论：产品的安全主张对**其主要用户面（搭建者与员工）保持完整**，对所有者插件通道退化为「入口批准 + 弱审计」，对基础设施层无主张——这是自托管产品的标准信任形状，且已如实声明；**但 §10.1 的总表表述（「全部生效无一可豁免」+ 例外清单漏红线 3）没有把这个形状准确传达**。所以「还剩多少」的答案：主体面完整，但总表需要一次措辞校准。不构成冻结阻断（因为各处范围声明已在细节层面准确），但属于应修的重要项。

## 任务 6：还有没同步的「改一半」？（检查未加范围声明的条款）

作者已加：§9.2、§2.5.3、§9.6.3、§9.6.4、§9.8.1、§10.1、§5.7.3。逐处检查其它隐含「插件不构成绕过」或「唯一执行点对所有人成立」假设的条款：

1. **§2.5.2 红线 1-3**：红线 1「Agent 代员工执行操作，必须走与该系统 UI 完全相同的授权与状态机校验」——红线 1 在 §10.1 注记里已被声明对插件不成立，但 §2.5.2 本节没有范围声明。§2.5.3（红线 4）有，§2.5.2（红线 1-3）没有。不过 §10.1 注记覆盖了红线 1/2，且红线是总表层面声明的——是否每处都要重复声明？v2.7 的先例是给 §9.2 和 §2.5.3 加。§2.5.2 没有加。这算半个遗漏。但考虑可维护性，在 §10.1 统一声明 + §2.5.3 示例，可能够用。弱重要/建议。

2. **§9.3 写操作数据范围原子谓词**：「写命令必须以『目标 ID＋当前租户＋当前数据范围』作为同一原子谓词定位记录」——这是执行点行为，插件绕过执行点后不成立。§9.2 的连带段已把 §9.3 列入「不成立」清单（v2.8 开放式列举）。OK，已覆盖（在 §9.2）。

3. **§9.4 委派令牌**：「业务系统只接受身份层签发的短时委派令牌」——插件在进程内可否伪造令牌或绕过令牌校验？插件可替换权限校验钩子（§5.7.3 承认）。但插件运行在哪？§9.10.2 说「插件运行在控制面」（KVVI 运行时侧），业务系统是独立部署的。插件在 KVVI 运行时进程内——它能否伪造委派令牌？令牌由身份层私钥签发，私钥「仅存于身份层」（§9.4.1）。如果身份层与 KVVI 运行时是同一进程/部署单元，插件作为进程内代码可能读到私钥（内存）→ 伪造令牌 → 以任意身份调用业务系统。§4.6.4 提到「若身份层与平台库同进程宿主，『直连』与『经服务』的边界会被弱化」——承认了同进程问题，但没提私钥。插件能否读取身份层私钥取决于部署形态（身份层是否独立进程）。PRD 没有声明「身份层签名私钥所在进程不得加载插件」或「身份层独立部署」。这是一个真实的未声明假设：§9.4.1「私钥仅存于身份层」+ 插件是 KVVI 运行时进程内任意代码 → 若身份层与运行时同进程，私钥对插件可读，§9.4 的整个委派令牌体系对所有者插件路径失效（插件可冒充任意员工调业务系统，且业务系统验签通过、留痕正常——完美的不可检测绕过）。

等等，插件能直接以进程内调用绕过执行点（§9.2 已承认），那它还需要伪造令牌吗？如果目标是 KVVI 运行时内的资源，不需要；但目标是**独立部署的业务系统**时，插件在 KVVI 运行时进程内，要操作业务系统需经网络调用，业务系统要求委派令牌。插件可以：(a) 等待真实用户令牌流经运行时（它能看到），重放或篡改；(b) 若私钥同进程可读，直接签发。所以「插件可拦截/伪造令牌」是 §9.4 体系对插件路径的实际例外。§9.2 连带段的开放式列举没有包括 §9.4！列举是：「§9.3、§9.6、§9.7、§9.8.1、§9.9、§9.11.3、以及红线 1/2/4」——§9.4（令牌）不在列。虽然是「包括但不限于」，但 §9.4 的例外不那么直接：插件绕过执行点 ≠ 自动能伪造令牌（需要私钥或令牌窃取）。这里有一个未被声明的部署级假设：**身份层私钥对插件的可达性**。按 §9.4.1「私钥仅存于身份层，不得随部署包明文分发」——但没写「身份层须与不加载插件的进程边界隔离」。如果身份层就是 KVVI 运行时的一部分（同一进程），则「私钥仅存于身份层」在插件面前等于「私钥对插件可读」。这值得列为重要（或建议）：要么声明「身份层签名密钥所在进程不得加载所有者插件之外的代码/身份层独立部署边界」，要么在范围声明中承认「插件可能取得令牌签发能力」。这是任务 6 要的「隐含假设插件不构成绕过」的条款。

嗯，但 PRD 的 TCB 立场可以回应：插件是 TCB，TCB 读到私钥不算「绕过」，算「信任的前提」。是的——TCB 语义下这不算矛盾。但与 §9.4.1「私钥仅存于身份层」的**精神**有张力：该条的防护意图是限制私钥暴露面，而插件架构使「身份层进程」的暴露面包含全部已安装插件。我认为这值得一个「重要」：§9.4.1 或 §9.10.2 应声明插件与身份层密钥的共址关系（例如「身份层签名操作所在运行时与插件宿主的关系须在部署拓扑中定明」或承认「已批准插件与身份层同进程时，可取得令牌签发能力——这属于 TCB 的既有语义」）。后者更符合 PRD 的收窄风格。

4. **§9.7 注入防护**：执行前确认——插件可绕过（§9.2 连带段已列 §9.7）。OK。

5. **§9.9 租户隔离**：已列入 §9.2 连带段。OK。

6. **§9.11.2 审计**：「防篡改存储」「读权限独立（搭建者不得读取或删除审计）」——插件可拦截审计写入（§5.7.3 承认）。§9.11.2 没有范围声明。虽然 §5.7.3 承认了「插件可以拦截审计写入」，但 §9.11.2 的「完整性可验证」「防篡改」未同步声明插件例外。§10.1 红线 3 的插件例外也没写（如上）。这是一组：审计相关条款（§9.11.2、红线 3、§9.10.2 的审计行）在 v2.8 承认了「插件可拦截审计」（§5.7.3）后没有同步。这是 v2.8 引入的新「改一半」——因为「插件可拦截审计写入」这个承认是 v2.8 才写进 §5.7.3 的！v2.7 没有这句。所以 v2.8 在 §5.7.3 新承认了一件事，却没有把它传播到 §9.11.2 / §10.1 红线 3 / §9.10.2。这是本轮修订**自己制造**的未同步。重要级，且很契合任务 6 的命题。

7. **§9.11.3 配额**：已列入 §9.2 连带段。OK。

8. **§4.1.1 五 发布最小语义**：「无通道外变更：不存在产品接口内不经发布通道的契约变更路径」——「产品接口内」限定，OK。

9. **§3.1 授权模型**：「员工永远无法通过任何路径获得搭建权限」——「任何路径」！插件呢？插件是进程内代码，可以替换权限校验钩子，让员工获得搭建能力。不过 §3.1 的语境是授权模型（产品机制），插件路径已由全局范围声明覆盖？没有——§3.1 没有范围声明。「员工**永远无法**通过任何路径获得搭建权限」是「任何人都无法…」式的绝对表述吗？不完全是，它是对员工的断言。但「任何路径」字样与 v2.6 禁令（「不得使用『任何人都无法…』形式」）的精神相近。插件可让「员工获得搭建权限」成为事实（改内存中的权限判定）。严格说，这属于「插件可替换权限校验钩子」（§5.7.3 已承认）的推论。但 §3.1 未同步。弱。建议级。

10. **§3.3.4 账号停用**：「不能登录；Agent 通道立即关闭」——插件可绕过。弱，不列。

11. **§7.1 阶段五验收锚点**：「§9.2 差分测试通过」等——验收条件，不涉及。

12. **§9.6.5 工具归属**：「不存在把 Builder 工具登记到 User Gateway 的操作」——产品接口内不存在；插件可以改。§9.6.5 未加范围声明。但 §9.2 连带段的「§9.6」涵盖了 §9.6.x。OK。

13. **§5.2 工作模式能力红线**：「工作模式不得挂载任何可修改系统结构的工具」「不得直接访问业务系统的数据层」——这是工具装配约束，插件不影响工作模式的工具集……但插件可以注册新路由/服务，间接提供能力。§5.2 的「不得」是产品装配约束（不挂载），插件介入后工作模式会话里 Agent 可调用的端点可能增加（插件注册的 HTTP 路由如果可被 Agent 工具访问）。有点远。不列。

14. **§2.3 模式隔离**：「工作模式的 Agent 不挂载任何搭建类 Skill 与工具」——装配约束。插件理论上是宿主级，不按模式区分——profile 插件注册的 Service/路由对两个模式都可达？DSH 的 profile 插件是进程级（§5.7.1「进程级」）。进程级意味着搭建舱与工作台共享宿主时，插件注册的 HTTP 路由对两侧都暴露。那么「能力隔离」（工作模式不挂载搭建类工具）在插件注册了搭建类服务后是否被架空？工作模式 Agent 的工具集由 Preset 决定，不含插件自动注册的工具……插件注册的是 Service/路由/UI，不是 Agent 工具。Agent 能否调用插件注册的路由取决于工具配置。默认不能。OK，不深挖。

15. **§9.4.3 契约版本**：「业务系统只接受契约版本等于其当前激活版本的调用」——业务系统侧的行为，插件在 KVVI 运行时侧。插件伪造令牌后自然携带任意版本声明……版本由业务系统比对请求头与实际激活版本，伪造者声明正确版本即可通过（版本不是秘密）。所以插件伪造令牌 + 正确版本号 → 通过契约版本校验。这进一步支持「§9.4 体系对插件路径的例外未声明」这一点。

16. **§3.5 访客链接**：签名「必须由身份层或其同等信任锚点签发」（§3.5.1）——与 §9.4 同构：私钥对插件的可达性。并入上一点。

## 阻断候选：

**B1. 插件批准缺乏内容绑定（批准语义空洞）**
- 位置：§9.6.2 插件审批形式 / §9.10.2 / §4.1.1 四
- 现状：批准记录含「批准人、时间、插件标识」（§4.1.1 四）；审批形式规定「显式批准每一次」（§9.6.2）
- 问题：批准只绑定「标识」（名字），不绑定代码内容。所有者批准「报表插件 v1.2」后，实际加载的同名插件内容是否就是被批准的那一份，全文无任何要求。这使「仅所有者批准」这一核心保证退化为「所有者批准过一个名字」——供应链替换（同名包内容被换）、安装源污染都不在视野内。对比：交付包有指纹（G5）、MetaSchema 有哈希（§5.3）、访客链接有签名属性（§3.5.1）、批次有签名（§9.4.4）——本项目对「标识 ≠ 内容」的威胁模型是接受的，唯独任意代码入口没有。且这正是本轮核心修订区域。
- 建议：§9.6.2 审批形式表增加一行：批准记录须含插件包的**内容指纹（哈希）与来源**；加载/激活时与批准记录比对，不一致则拒绝并告警。这是「做什么」级要求，不是实现细节。

这够阻断吗？让我用「能不能开工且不埋雷」检验：没有这条，实现者会按「批准 = 数据库插一行记录（name）」实现，雷埋下；有这条，实现明确。且它处在本轮修订的核心主张上（「插件审批通道已闭合」），空洞恰好打在核心上（与第七轮的「引用落空」同构：一个是审批的**依据**落空，一个是审批的**对象**落空）。判定：阻断。是的。

- 问题：批准对象只有「标识」，不绑定代码内容。交付包有指纹（G5）、MetaSchema 有 SHA-256（§5.3）、访客链接有签名（§3.5.1）、离线批次有签名（§9.4.4）——本项目处处接受「标识≠内容」，唯独任意代码入口没有。批准与加载之间无同一性校验：同名包内容被替换、安装源污染均不可检出。「仅所有者批准」因此退化为「所有者批准过一个名字」。第七轮修的是审批的「依据落空」（引用断裂），但审批的「对象」仍落空——这个空洞恰好打在本轮修订的核心上。按 §3.5.1 先例（链接签名属性被判为产品安全属性而非实现细节），这属 PRD 级。
- 建议：§9.6.2 审批形式表补一行：批准记录须含插件包内容指纹（哈希）与来源；加载/激活时与批准记录比对，不一致拒绝并告警；纳入 §9.6.3 第 8 项的负向测试。

- 位置：§4.1 架构图、§9.4.1、§9.10.1；旁证 §4.6.4
- 原文：架构图「KVVI 运行时改造层 ★ 新增：身份层」；§9.4.1「私钥仅存于身份层」；§9.10.1「进程内任意代码」；§4.6.4 自认插件「可跳过验签逻辑或直接改内存」
- 问题：身份层画在 KVVI 运行时改造层内，插件是该运行时的进程内任意代码——同进程即可读私钥（与「改内存」同类能力，§4.6.4 已承认后者）。取得私钥的插件可签发任意员工/任意公司的委派令牌，业务系统验签通过、审计留「合法」痕迹——这是比「绕过执行点」更深的绕过：跨部署单元、留痕完美、不可检测。§9.2 连带段的开放式列举（§9.3/9.6/9.7/9.8.1/9.9/9.11.3 + 红线 1/2/4）恰好不含 §9.4。所有者批准插件时不知道自己同时交出了整个令牌信任体系。
- 建议：二选一并写入 PRD（这是产品决策不是文字）：(a) 承认——在 §9.10.2/§9.4.1 声明「已批准插件与身份层同进程时可取得令牌签发能力，属 TCB 既有语义」；或 (b) 要求——身份层签名模块运行于不加载插件的进程（影响 §4.6 拓扑与阶段一 Docker 骨架）。不决策即开工，实现者默认走 (a) 而不自知。
