Web 端（搭建舱/工作台）在上面「KVVI 自有 Web 端」层。用户与工作台对话，请求到哪个进程？工作台是业务系统的界面，内嵌工作模式 Agent。Agent 对话必然到达 Agent 运行时进程（Agent Loop 在那）。那么**会话凭据（session cookie/token）必须随用户请求经过/到达运行时进程**——否则运行时进程怎么知道这是哪个会话？

关键问题：插件在运行时进程内，能否窃取**会话凭据本身**（不是委派令牌，而是用户会话的认证凭据）？

如果用户会话凭据（如 session token）需要被运行时进程验证或持有，插件就可以窃取它，然后**冒充该用户从别处发起请求**——包括向平台服务进程发起请求（若平台服务进程端点对外可达）。这样插件就不必窃取委派令牌，而是直接劫持整个会话。

PRD 现在的保证表只谈「委派令牌」（Agent→业务系统），没有谈「用户→平台」的会话凭据。§4.6.5 说会话状态在平台服务进程，但运行时进程处理 Agent 对话时，总要以某种方式关联会话。可能的设计：用户请求先到平台服务进程鉴权，再转发到运行时？但 §9.2 说 UI 与 Agent 调用同一业务命令端点……业务命令端点在哪？业务系统独立部署。

实际上 PRD 没有定义「用户请求的路由拓扑」：浏览器 → 哪个进程？这个问题在 v2.12 中仍未定义。这可能是一个残留空洞：**会话凭据（session token）是否会被插件窃取**没有讨论。若 session token 经过运行时进程（很可能，因为 Agent 对话在运行时进程），插件窃取 session token 后可：
- 向平台服务进程请求签发新委派令牌（以该会话名义）——因为签名接口「只为当前已认证会话签发」，插件拿着 session 就能让平台签出更多令牌。不过这和窃委派令牌效果相当，已列入「不防」。
- 或直接以用户身份调用业务系统（业务系统验的是委派令牌还是 session token？§9.4 说业务系统只接受委派令牌）。

所以窃取 session token ≈ 窃取委派令牌的能力，已在「不防」区。但严格说，「插件可窃取会话凭据并冒充用户发起新会话级请求」这一条没有列出。不过它实质上没有超出「冒用活跃会话」的范畴——都在「插件可冒用活跃会话」的不防区里。可以算已覆盖（泛化覆盖），不必单列。作为建议级可以提。

- (d) **插件为「无会话主体」取得令牌的其他路径**：签名接口「只为当前已认证会话签发」。插件在运行时进程，能否伪造一个「会话」？§4.6.5：平台服务进程不接受运行时进程对会话状态的写请求。会话创建（登录）在平台服务进程的认证端点。插件无法接触。所以插件不能凭空造会话。✅
- (e) **重放/绑定问题**：签名请求与「当前会话」的绑定——插件借运行时身份调用签名接口时，运行时进程持有的是真实会话的上下文，签出的令牌绑定该会话。这已是「冒用活跃会话」不防区。

- (h) **钓鱼 UI 之外的凭据获取**：键盘记录？profile 插件可注册客户端 UI（浏览器侧？）——「客户端 UI」是 Web 前端的 UI 组件。登录表单本身也是客户端 UI。如果插件可以注册客户端 UI，它能否**替换/包裹登录表单本身**？登录页面是不是也在同一个 Web 前端壳内？§4.3 说 Web 前端壳复用 apps/web。profile 插件可注册客户端 UI——如果插件 UI 与登录页面同源（同一个 Web 应用），那么插件的 JS 就能读取登录表单（DOM 同源），根本不需要「钓鱼」——直接键盘记录真实登录页。这比「钓鱼界面」更强：不需要诱导用户去假页面，**在真实登录页上就能窃取凭据**。

1. **会话凭据（session token/cookie）窃取**：如上，实质归入「冒用活跃会话」不防区。建议级提及。

4. **R3 与插件**：插件冒用令牌执行 R3 动作——R3 须所有者审批，审批在平台服务进程。插件持令牌直接调业务系统…… R3 审批链：§9.6.4.1 员工动作 R3 须所有者审批。这个审批在 Agent 路径的执行前确认/审批层。插件持令牌**直接调业务系统接口**，绕过了 Agent 路径的确认/审批层！§9.6.1 说额外防护（确认与审批）只加在 Agent 路径上。业务命令端点（§9.2 唯一执行点）做基础校验（身份、租户、行范围、字段、动作、状态机），但**不做 R3 审批**——R3 审批是 Agent 路径的额外防护。所以插件窃取员工的令牌直接调业务系统，可以执行 R3 级动作（批量、跨范围、金额超限）而**不经过任何审批**，只要该员工账号本身有该业务权限！

等等，R3 的定义是「员工不可逆动作的风险分级」——针对的是 Agent 代办的动作。如果员工自己在 UI 上执行批量操作呢？§9.6.4：「员工（工作模式）按 §9.6.4.1 的封闭清单分级：一般不可逆动作走 §9.7 的执行前确认；清单中的最高风险类别须所有者审批」。执行前确认是 Agent 路径的（§9.6.1 额外防护仅对 Agent 发起的操作，UI 用户正常操作不受此层影响）。那 R3「须所有者审批」对 UI 路径适用吗？§9.6.1 说「额外防护仅对 Agent 发起的操作，否（UI 用户正常操作不受此层影响）」。那么 R3 审批到底约束谁？如果 UI 用户做 R3 不需要审批，而 Agent 代做需要审批，那么插件持员工令牌直接调端点（模拟 UI 路径？）——业务系统端点无法区分调用来自 UI 还是插件（都是 HTTP 调用，持合法令牌）。所以 R3 审批在端点层不可强制——它只能在 Agent 路径的应用层强制。

这是结构性问题：§9.2 唯一执行点做基础校验，R3 审批不在基础校验里。插件冒用令牌即可绕过 R3 审批。但这属于「冒用活跃会话」不防区的后果之一，PRD 已声明冒用不防。R3 绕过是冒用的一个具体后果，没超出已声明范围。可以不单提，或建议级。

5. **离线窗口 + 插件**：插件窃取令牌在离线窗口内使用，业务系统缓存验签……已在不防区。

6. **平台→运行时的终止通知**：§4.6.5 说「会话终止时，平台服务进程可向运行时进程下发终止通知（单向、只读语义，不构成写请求）。实质机制是令牌撤销」。**插件可拦截该通知**——运行时进程收到终止通知后应销毁令牌，但插件在同进程，可以拦截通知让运行时继续持有令牌。不过「实质机制是令牌撤销」——撤销后业务系统拒绝（在窗口内可能仍接受，残留窗口 ≤5 分钟）。所以通知被拦截的后果被令牌撤销兜底。OK，已闭环。等等，令牌撤销查询需要平台在线；若平台在线（能下发通知就能被查询），业务系统查撤销状态即拒绝。残留窗口内仍可用——≤5 分钟。已覆盖。

### 任务 2：「激活=运行开关，加载不构成生效」能否落地？

§4.1.1 四 v2.12 新增三条：
1. 加载前必须检查激活状态——无激活批准记录则不加载；
2. 加载时与「激活批准记录」比对指纹；
3. 「激活」定义为「允许该插件在加载后生效」的运行开关，加载本身不构成生效。

任务问：§9.10.1 说 profile 插件进程级生效、可注册 Service/HTTP 路由/UI。若插件在加载时就注册了路由，在「激活」之前它是否已经能被调用？

分析：第 1 条说「无激活批准记录则不加载」——所以正常流程下，未激活的插件根本不会被加载。那「激活=运行开关」针对的场景是：**激活被撤销后**？等等——激活是一次性批准动作还是可切换的状态？

动作全集：安装/注册/激活/加载/卸载。没有「停用/去激活（deactivate）」动作！如果所有者想暂停一个插件而不卸载，有没有路径？「激活=运行开关」暗示可以开/关。但动作全集里**没有去激活动作**。如果激活不可撤销，「运行开关」就不是开关而是闸刀（只能合一次）。「激活=运行开关」的语义与动作全集不匹配：
- 若激活是一次性事件（激活后永远激活，直到卸载），那「开关」用词误导；
- 若激活可来回切换，则全集缺「去激活」动作，且审计、批准规则都要覆盖它。

这是一个真实的语义缺口：**「运行开关」意味着可开可关，但动作全集无 deactivate；卸载是唯一的关闭路径，且卸载须免审批（紧急动作）**。用「开关」这个词引入了未定义的语义。等级：重要（定义不一致，实现者会问「如何关闭一个已激活插件」）。

再一个更尖锐的：**激活与加载的时序**。场景：插件已安装、已注册、已激活（有激活批准记录）→ 进程启动 → 加载（查激活状态 ✓，比对指纹 ✓）→ 插件代码运行。**插件代码一旦运行（profile 插件在加载时注册路由/Service/UI），它就生效了**。那「加载不构成生效」是什么意思？

如果「加载不构成生效」要成立，需要：加载后插件代码不立即运行，等待「激活」信号才运行。但激活发生在加载之前（无激活记录不加载）！时序是：激活（批准记录）→ 加载（进程启动时）→ 生效。**激活在前，加载在后**——那「加载后生效」的「运行开关」在哪？插件加载即运行（§5.7.1 profile 插件进程级生效），激活记录只是加载的前置条件。此时「激活=运行开关，加载不构成生效」这句话描述的语义是空的：**加载就是生效，激活只是加载的门票**。除非存在这样的设计：插件可以被加载（代码读入）但不执行，直到收到激活指令——但激活批准记录是静态的，加载时检查一次就够了，不需要运行时再翻。

唯一让「开关」有意义的场景：**激活状态在运行期被撤销**（所有者撤销激活）→ 运行中的插件应停止生效。但全集无去激活/撤销激活动作！撤销激活怎么表达？重新批准？卸载？

所以任务的第二问「在激活之前它是否已经能被调用」——按第 1 条，未激活不加载，所以不能被调用。✅ 这一半堵住了。但反向——**已激活插件的「关」路径不存在**，「开关」名不副实。而且 §9.10.1/§5.7.1 自述 profile 插件「进程级」生效、加载时注册路由——**加载即生效是 profile 插件的既定事实**，「加载本身不构成生效」与 §5.7.1「profile 插件 进程级生效 跨重启保留」的实测语义冲突。v2.12 第 3 条自己也意识到了：「若加载即生效，激活批准就失去意义。因此……」。但它的修法是**定义**「激活=运行开关」，**没有给机制**（加载后如何不生效？谁把插件置于未生效状态？生效/失效如何切换？）。按 v2.3 以来的标准「声明 vs 机制」，这是一个「声明」层修复。

不过等等，我要公平：第 1 条「无激活批准记录则不加载」已经解决了 Kimi 指出的具体场景（已安装未激活的插件在重启时被加载）。在这个修法下，激活检查在加载前，加载即生效也无所谓——因为只有已激活的才会被加载。「激活=运行开关」这个表述反而是多余的、且引入了未定义语义（开关暗示可关）。真正的问题剩下两个：
- (i) 全集无去激活动作，「开关」不可关（除卸载）；
- (ii) 「加载不构成生效」与 §5.7.1「profile 插件进程级生效（加载即注册路由/Service/UI）」的实测事实之间的张力没有被机制填平——如果加载即生效，那么第 3 条「加载本身不构成生效」是假陈述；如果加载不即生效，则与 §5.7.1 冲突，需要机制（延迟执行/门控注册）。PRD 二选一没有选。

等级：我认为这构成**重要**（语义不一致 + 缺机制），是否阻断？判定标准「零阻断+零重要」。这条至少重要。是否阻断？它不影响安全保证的正确性（第 1 条已堵住安全洞），影响的是术语一致性与可实现性。我定为重要。

还有：**运行时动态插件**。§5.7.1 运行时动态插件「仅进程内存，跨重启消失」。动态插件也走「安装/注册/激活/加载/卸载」全集吗？§9.10.2 说动态插件生产默认禁用。动态插件的生命周期与 profile 插件不同（无跨重启加载）。全集是否适用于动态插件？PRD 未区分。边角，建议级或不提。

同样 §4.1.1 四的分工表：「卸载 | ❌ 须批准 | ✅ 须留痕 | 不得需要审批（紧急动作）；由所有者发起」。「须留痕 ✅」无尽力而为标注。而「由所有者发起」（v2.12 #15）——卸载由所有者发起，但恶意插件自己会不会「卸载」来销毁证据？或者插件拦截卸载？§9.11.2 已说卸载留痕可被拦截。那么「卸载由所有者发起」这个要求的可执行性——插件无法被强制不自行移除自身代码（进程内任意代码）。「卸载由所有者发起」是产品约束非机制保证，没标注。不过卸载动作本身（从插件目录移除）是运行时/部署层行为，插件代码被移除后自然无法运行——但「留痕」可被抢先拦截。这些在 §9.11.2 已承认。核心还是四处未同步。

### 任务 4：v2.12 是否引入新的过度承诺？

候选：
1. §4.1.1 四 v2.12 三条状态语义里「加载本身不构成生效」——如上，与 §5.7.1 冲突，是一句过度承诺/假陈述（声称了一个没有机制的语义）。
