总体判断：新增三处架构级内容存在未闭合矛盾：平台可用性与安全拒绝冲突、访客链接安全机制未定义、契约版本无回滚语义，不可冻结。

## 阻断（必须修，否则不能开工）

### 1. “平台不可用不应使业务系统停摆”与“撤销查询不可用应拒绝”直接冲突
- **位置**：§4.6.2 规则 3 与 §9.4.2
- **原文**：§4.6.2 规则 3 写“平台库与业务系统库可分离部署……平台不可用不应使业务系统停摆”。§9.4.2 写“撤销查询（账号停用与会话结束时必选）”，负向测试要求“撤销查询不可用时的降级行为（应拒绝而非放行）”，并称短时有效期“不能替代立即撤销”。
- **问题**：这两个要求是同一个架构下的两个相反姿态。若平台与业务系统分离，平台/身份层不可用时，业务系统无法完成撤销查询；按 §9.4.2 必须拒绝，于是所有依赖该查询的调用大面积失败，业务系统实际上停摆。反之，若允许平台不可用时继续放行，就违反 §9.4.2 的“应拒绝而非放行”。PRD 没有定义任何离线撤销清单、本地缓存、最大残留窗口或恢复补偿机制。
- **建议**：必须在 PRD 明确平台不可用时的撤销查询降级策略：要么允许业务系统本地缓存撤销/授权版本并明确最大残留窗口、日志补传与恢复后补偿；要么删除或修改 §4.6.2 规则 3 的“平台不可用不应使业务系统停摆”。不能同时保留两者。

### 2. 契约版本“不可回退”与发布失败回滚场景自相矛盾
- **位置**：§9.4.3；§4.1.1
- **原文**：§9.4.3 写“失败即拒绝……不降级、不做兼容猜测、不回退到旧版本”“不存在‘客户端要求降级到某版本’的路径”。§4.1.1 写“每次发布产生新的契约版本，单调递增，不可回填”。
- **问题**：发布失败需要回滚是现实运维场景。一旦新契约版本发布出错并激活，业务系统和 Agent 侧都会拒绝调用；此时若按“不回退到旧版本”，故障不能通过回滚恢复。若回滚激活上一契约版本，又会违反“单调递增、不可回填”。PRD 没有定义发布失败/回滚时的版本语义，规则在回滚场景下自相矛盾。
- **建议**：明确区分“客户端/运行时自行协商降级”（禁止）与“发布通道作为受控操作回滚/重新激活上一版本”（允许）。回滚必须是一次审计留痕的发布操作，或有明确故障恢复策略；不可只写“不回退”。

### 3. 访客签名链接的安全机制完全未定义，无认证写入入口仍然悬空
- **位置**：§3.5.1
- **原文**：§3.5.1 写“访问方式：带签名的限时链接，由已认证用户（员工或所有者）生成后定向发送”“链接必须有明确到期时间；到期即失效”。全文未定义签名算法、签名密钥来源、有效期上限、防重放、单链接是否一次使用、链接被转发后的责任归属。
- **问题**：访客是无 KVVI 账号的写入入口。§3.5.1 声称不是“公开匿名链接”，但“签名”由什么保证完全没有落在 PRD 内。未定义签名机制时，该链接只是“一种尚未定义的链接”。§0.5 将签名算法等转入技术设计的边界不能覆盖这一点，因为这里缺的不是实现细节，而是产品安全属性：至少需要声明签名密钥与身份层的关系、有效期量级、防重放/一次性策略。否则无法评估伪造链接、重放、链接被转发后的风险。
- **建议**：在 PRD 增加产品级约束：链接签名必须由身份层或同等信任锚点签发，使用非对称签名；规定有效期上限量级（如小时/天）；明确单链接是否允许多次提交；若允许多次，必须声明该风险以及与 §3.5.4 追溯单位的关系；链接生成与吊销必须纳入审计。

## 重要（应修）

### 1. 审计“不同库”不足以建立防篡改拓扑
- **位置**：§4.6.2 规则 1
- **原文**：规则 1 为“审计不与业务数据同库”，理由是“把审计与被审计数据放在同一库、同一管理域，等于让被审计方有机会修改审计——审计的防篡改（§9.11.2）在拓扑上就不成立”。
- **问题**：该理由自己提到了“同一管理域”，但规则只写了“不同库”。如果审计存储与业务库仍在同一主机、同一管理域、同一 DBA 账号、同一备份通道，被审计方仍可通过主机权限或备份通道篡改/替换审计。§9.11.2 的防篡改只覆盖追加写/哈希链/WORM，未覆盖管理域与备份通道。另一个歧义是 §4.6.1 平台数据包含“审计日志”，而审计数据又标为“平台侧独立存储”，审计与平台库的关系不清晰。
- **建议**：将规则 1 扩展为“审计不与业务数据同库、同主机管理域、同 DBA、同备份通道”；明确审计存储与平台库是否同库，若同库则说明平台库内部的访问隔离及平台库失陷对审计的影响。

### 2. 平台库集中高价值数据，成为未被单独评估的单点攻击面
- **位置**：§4.6.1
- **原文**：“平台数据包含：账号、会话（含会话绑定的公司与业务系统）、授权版本、撤销状态、发布记录与契约包版本、审计日志。”
- **问题**：平台库集中了身份、授权、撤销、发布和审计。平台库一旦失陷，攻击者可修改授权版本、撤销状态、发布记录甚至审计，使所有业务系统的权限校验和可追溯性同时失效。PRD 未为平台库定义任何独立安全边界：谁可访问、业务系统运行时是否有直接连接、数据库管理员与业务库管理员是否分离、平台库的备份/恢复与应急处置。集中度放大后果与防护不成比例。
- **建议**：为平台库增加产品级安全边界：业务系统运行时和搭建者不得直接访问平台库；平台库写路径仅限身份层与发布通道；平台库管理凭据与业务库分离；定义平台库失陷/不可用的影响与恢复目标。

### 3. 三维度限流可被多个签发账号横向绕过，来源维度不可靠
- **位置**：§3.5.2
- **原文**：“三维度限流：链接维度、来源维度、签发人维度”“单个签发人可同时有效的链接数上限（防绕过账号配额批量签发）”。
- **问题**：限流只到单个签发人，没有租户/公司维度聚合总量。多个低权限员工账号可各自签发链接，合计可绕过整体配额；来源维度依赖 IP/设备指纹，在 NAT/代理后可能共享或易被伪造，不能作为强控制。PRD 没有定义三维度的权重、组合或聚合层级。
- **建议**：增加租户/公司维度的聚合上限；将来源维度明确为辅助信号，不作为可靠安全边界；超限行为除拒绝外应审计并告警。

### 4. “访客提交文本不得被当作指令”与 §9.7.1 的已知前提冲突
- **位置**：§3.5.3 与 §9.7.1
- **原文**：§3.5.3 写“访客提交的内容一律视为不可信数据，不得被当作指令”。§9.7.1 已明确“本 PRD 明确声明：KVVI 不承诺阻止不可信文本进入模型上下文……任何声称‘已阻止注入文本被当作指令’的设计，都只是声明而非机制”。
- **问题**：§3.5.3 的“不得被当作指令”正是 §9.7.1 否定的“声明而非机制”。访客路径把写入门槛降到无账号，文本进入后续 Agent 上下文时，与 §9.7.3 负向测试第一条完全重合。若后续确认界面不提示内容来源为访客，高权限用户可能将被注入内容当作正常业务输入确认，风险被放大。
- **建议**：删除“不得被当作指令”这一措辞，改为“按 §9.7 视为不可信数据，不构成执行授权；相关文本触发工具调用时必须进入执行前确认/审批”；并在确认界面显示该内容来源为访客/外部填写者。

### 5. §3.5.4 的追溯单位不是红线 3 的“等价形式”，而是实质放宽
- **位置**：§3.5.4
- **原文**：“访客路径的追溯单位为‘链接签发人 + 链接 ID + 提交通道’……红线 3 的实质（不存在无主的操作）在访客路径上依然成立——访客本人可以匿名，但为其提供入口的账号不可匿名。”
- **问题**：红线 3 原文是“操作可追溯至账号与执行通道”。§3.5.4 将实际操作主体替换为“链接签发人”，即访客的操作追溯到另一个人的账号。若同一链接被转发给多个访客，多个不同实际提交者的操作全部只追溯到同一签发人和同一链接 ID，无法区分实际提交者。这不是等价形式，而是责任主体转移；PRD 却称“实质依然成立”，措辞不准确，可能让红线 3 被静默放宽。
- **建议**：改为“红线 3 在访客路径的责任主体为链接签发人，不承诺区分访客个体”；明确访客提交不触发 Agent 代执行操作；若允许同链接多次提交，审计需记录每次提交来源与时间，并明确接受无法区分访客个体的风险。

### 6. 契约版本与授权版本同时失败时，错误处理与诊断未定义
- **位置**：§9.4.3；§4.1.1
- **原文**：§4.1.1 写“任一不符都足以拒绝”；§9.4.3 写“不降级、不做兼容猜测、不回退到旧版本”。
- **问题**：契约版本失配与授权版本失配是两套独立拒绝路径。一次发布可同时递增两者，或只一侧失配。PRD 没有规定拒绝响应如何区分“授权版本失配”“契约版本失配”“撤销查询不可用”等不同原因，也没有监控与告警要求。当批量拒绝发生时，运维可能无法快速定位是哪个版本问题，形成拒绝风暴且难诊断。
- **建议**：规定业务系统在拒绝响应中返回可区分的错误类别（如授权版本失配、契约版本失配、撤销不可用），并记录当前版本与请求版本；两端日志须含诊断信息；同时失配时仍按最严格拒绝，但错误响应必须给出两个版本码。

## 建议（可选）

### 1. 双引擎“开发期一致”需要 CI 门禁与回归保证
- **位置**：§4.6.3
- **原文**：“两套引擎对同一输入必须给出相同结论；分歧即视为缺陷，须在开发期消解”
- **问题**：这只覆盖开发期样本。若某个分歧输入未进入开发期测试，生产权威 Node 可能按错误实现运行，而 Python 已不参与生产比对。PRD 没有规定双引擎一致性测试的持续运行位置。
- **建议**：将双引擎一致性测试纳入 CI/阶段验收门禁，随新增 MetaSchema 用例持续回归；分歧不得合并。

### 2. Agent 侧如何取得“业务系统激活版本”未定义，可能引入隐形平台依赖
- **位置**：§9.4.3
- **原文**：“Agent 侧校验：接口契约客户端（§4.3）在调用前比对自身契约版本与业务系统激活版本”
- **问题**：PRD 未说明 Agent 侧从何处取得“业务系统激活版本”。如果需要实时查询平台或业务系统，则又引入一个平台在线依赖，可能与 §4.6.2 规则 3 的可用性目标冲突。
- **建议**：明确激活版本随发布通道下发/缓存，或由业务系统在拒绝响应中返回当前版本，避免额外的运行时平台查询。

### 3. §4.6.1 表格与文字对“审计日志是否在平台库”存在歧义
- **位置**：§4.6.1
- **原文**：平台数据行包含“审计日志”；审计数据行又写“平台侧独立存储，不与业务数据同库”
- **问题**：审计日志究竟属于平台库还是独立于平台库不清晰，直接影响规则 1 的拓扑判定。
- **建议**：明确审计日志是否与账号等其他平台数据同库；若同库，须说明平台库内部访问隔离与平台库失陷对审计的影响。
