## 重要（应修，影响成功率或成本）

### 1. §5.7.3 地基计数与 §9.1 实际条目不一致（"七项"应为"八项"）
- **位置**：§5.7.3
- **原文**：「§9.1 列出的**七项**地基（身份鉴权、租户策略、权限校验、金额精度、状态机核心语义、审计、双网关工具归属）任何扩展都不得改动。」
- **问题**：§9.1 表格实际有 **8 项**——S4 新增了「令牌签名密钥管理（S4 新增）」作为第 8 行。§5.7.3 的"七项"及括号内列举均停留在 S4 新增之前，遗漏了「令牌签名密钥管理」。若扩展者仅依据 §5.7.3 判断地基边界，可能认为密钥管理不在"不可改"范围内，从而尝试通过插件通道修改密钥分发逻辑——这直接违反 §9.4.1「密钥管理属地基」与 §9.1 的约束。
- **建议**：将 §5.7.3 改为「§9.1 列出的**八项**地基（身份鉴权、租户策略、权限校验、金额精度、状态机核心语义、审计、双网关工具归属、**令牌签名密钥管理**）」，或直接改为「§9.1 所列全部地基项」以避免未来再增时遗漏。

### 2. "M4" 编号被两个不同决策复用
- **位置**：§4.6.3 标题、§0.6 表格第 4 行 vs §10.3 决策表
- **原文**：
  - §4.6.3 标题：「验证器引擎的运行时权威（**M4** 新增，v2.5）」
  - §0.6 表格第 4 行：「**M4**：Node 为生产权威，Python 降级为开发期交叉验证」
  - §10.3 决策表：「**M4** 采用 KVVI-Builder 的「公司即租户」组织模型，并据此修正 Q6」
- **问题**：同一个 "M4" 编号指向两个完全不同的决策（验证器引擎 vs 公司即租户）。§10.3 的 M4 是 v2.1 合并时的决策，§4.6.3/§0.6 的 M4 是 v2.5 新增的决策。读者在 §7.5.2 G3 或 §9.12 中看到 "M4" 时无法判断指哪一个。
- **建议**：将 §4.6.3 与 §0.6 中的 "M4" 改为不冲突的编号（如 "V2.5-D4" 或直接去掉 M 前缀，改为「v2.5 决策 4」），避免与 §10.3 的 M1–M4 系列冲突。

### 3. §4.6.2 规则 3 与 §9.4.2 撤销查询必选之间存在未闭合的矛盾
- **位置**：§4.6.2 规则 3 vs §9.4.2
- **原文**：
  - §4.6.2 规则 3：「平台库与业务系统库可分离部署……**平台不可用不应使业务系统停摆**」
  - §9.4.2：「撤销查询（账号停用与会话结束时**必选**）身份层提供撤销状态查询」；负向测试：「撤销查询不可用时的降级行为（**应拒绝而非放行**）」
- **问题**：§4.6.1 将「撤销状态」归入平台数据（平台库）。若平台库不可用，业务系统无法查询撤销状态，按 §9.4.2 应拒绝所有请求——业务系统事实上"停摆"。两条规则在"平台不可用"场景下给出矛盾的行为要求。PRD 未区分"平台库不可用"与"身份层服务不可用"，也未说明短时令牌在平台不可用期间是否仍可被接受（公钥验签不需要平台在线，但授权版本比对和撤销查询需要）。
- **建议**：在 §4.6.2 规则 3 或 §9.4.2 中增加一条澄清：「平台库不可用期间，**仍在有效期内的已签发令牌**（公钥验签通过）可继续被接受；但**新令牌签发、撤销查询、授权版本比对**不可用时，对应操作应拒绝。短时有效期（§9.4.2）即为平台不可用时的最大残留窗口。」

### 4. "地基不变量检查"的执行归属在 §9.1 与 §9.6.3/G5 之间不统一
- **位置**：§9.1（地基不变量检查）、§9.6.3 末段、§7.5.2 G5、§7.1 阶段五锚点④
- **原文**：
  - §9.1：「纳入**产出物验证管道**……检查内容：产出物是否试图覆盖或修改 §9.1 表中的任一项」
  - §9.6.3：「§9.1 的验证管道须含一条地基不变量检查：**'部署单元内不存在非平台提供的可执行运行时'**」
  - G5：「地基不变量检查通过：'部署单元内不存在非平台提供的可执行运行时'」
- **问题**：§9.1 将地基不变量检查定义为"产出物验证管道"的一部分（检查对象是**产出物**）。但"部署单元内不存在非平台提供的可执行运行时"是**部署环境的属性**，不是产出物的属性——一份 MetaSchema 契约无法"包含"一个可执行运行时。把环境检查归入"产出物验证管道"在逻辑上不通，且导致执行主体模糊：产出物验证器（Node 引擎）无法检查部署环境。G5 将其列为阶段门禁（一次性检查），但 §9.1 暗示它是每次产出物验证时的持续性检查。两者频率不同，PRD 未统一。
- **建议**：将"部署单元内不存在非平台提供的可执行运行时"从 §9.1 的"产出物验证管道"中拆出，单独定义为**部署环境不变量**，明确：(a) 执行主体为部署工具/CI 流水线（非产出物验证器）；(b) 执行时机为每次部署/发布时 + 阶段五门禁时；(c) 与 §9.1 的"产出物是否试图修改地基"检查并列但独立。

## 建议（可选优化）

### 1. §0.6 "此前八份评审"的计数口径
- **位置**：§0.6
- **原文**：「本轮换了一个此前**八份**评审都没覆盖的视角」
- **问题**：v2.4 之前的评审为 v2.1（5 份）+ v2.2 复评（2 份）+ v2.3 复评（2 份）= **9 份**。若"八份"是排除 deepseek-v4-pro（标注为"重做"）后的独立评审数（4+2+2=8），则计数口径与 §0.3 的"5 份评审"不一致。
- **建议**：改为「此前**九份**评审」或「此前**四轮**评审」，避免与 §0.3 的"5 份"产生计数歧义。

### 2. §9.12 末尾引用 §0.4 的"尚待复评"已过时
- **位置**：§9.12 末段
- **原文**：「本轮修订（v2.2 → v2.3）本身亦未经复评，见 §0.4。」
- **问题**：§0.4 原文为「v2.3 尚待第三轮复评」。但 v2.3 已经历第三轮（§0.5）和第四轮（§0.6）复评。在 v2.5 的上下文中引用"尚待复评"会让读者误以为 v2.3 的修订仍未被验证。
- **建议**：改为「v2.3 的修订已经历第三轮与第四轮复评（§0.5、§0.6），但**每轮修订本身可能引入新问题**，故 v2.5 仍需独立验证。」

### 3. §5.6 "调用双引擎验证器"在生产语境下不准确
- **位置**：§5.6 允许表
- **原文**：「调用**双引擎**验证器 对产出物做结构与语义校验」
- **问题**：§4.6.3 已明确"Python 引擎降级为开发期交叉验证，**不进生产链路**"。生产环境只有 Node 引擎。§5.6 的"双引擎"表述会让实现者以为生产环境也需部署 Python 运行时。
- **建议**：改为「调用验证器（生产：Node 引擎；开发期：双引擎交叉验证，§4.6.3）」。

### 4. §4.6.1 "审计数据"的"独立存储"含义不明确
- **位置**：§4.6.1 表格
- **原文**：审计数据 → 存放位置「**平台侧独立存储**，不与业务数据同库」；同时"平台数据包含：……审计日志"
- **问题**：审计日志既被归入"平台数据"（平台库），又被单列为"审计数据"（"独立存储"）。"独立存储"是独立数据库实例？还是平台库中的独立 schema/表？若为独立实例，则与"平台数据包含审计日志"矛盾；若为独立表，则"独立存储"用词过重。
- **建议**：明确为「审计日志存放于**平台库内的独立 schema**（或独立表），与业务数据分库；隔离方式为追加写 + 哈希链 / WORM」。

### 5. §3.5.1 链接"吊销"的传播机制未定义
- **位置**：§3.5.1
- **原文**：「链接生成者可**随时吊销**；吊销后未提交的链接**立即失效**」
- **问题**：业务系统独立部署（§4.1.1），链接验证若为本地签名验证（公钥），则"吊销"状态需要平台推送或业务系统主动查询。PRD 未说明吊销信息如何到达业务系统，也未说明平台不可用（§4.6.2 规则 3）时已吊销链接是否仍有效。
- **建议**：补充一句：「吊销状态由平台维护，业务系统在每次链接验证时查询（或缓存 + 短 TTL）；平台不可用时，已吊销链接在缓存有效期内可能仍被接受，此为已知残留窗口，由链接有效期上限兜底。」

### 6. §10.3 Q10 "权限唯一源头"未限定为"搭建权限"
- **位置**：§10.3 Q10
- **原文**：「所有者（主账号）是**权限唯一源头**」
- **问题**：§3.1 明确"业务权限可由搭建者在授权范围内代为配置"。Q10 的"权限唯一源头"若不加限定，与 §3.1 的"搭建者可配置业务权限"在字面上矛盾。§3.1 的 C2 澄清已解决此问题，但 Q10 本身未引用该澄清。
- **建议**：改为「所有者（主账号）是**搭建权限**的唯一源头；业务权限可由搭建者在所有者设定的范围内代为配置（§3.1 C2 澄清）」。
