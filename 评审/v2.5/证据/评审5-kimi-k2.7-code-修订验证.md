八项修订基本成立，但存储拓扑自洽性、M4 编号冲突与访客红线等价性仍需修正。

## 阻断（必须修，否则不能开工）

### 1. 审计数据归属在 §4.6.1 表格与正文中直接矛盾
- **位置**：§4.6.1
- **原文**：
  - 表格中：审计数据“存放位置”为“**平台侧独立存储**，**不与业务数据同库**”；
  - 同节紧接着写：“平台数据包含：账号、会话（含会话绑定的公司与业务系统）、授权版本、撤销状态、发布记录与契约包版本、**审计日志**。”
- **问题**：若审计日志属于“平台数据”并放在“平台库”，则与表格中“平台侧独立存储”相冲突。实现者无法判断审计到底是否与平台数据同库、是否需独立 WORM/哈希链存储。作为本轮三项架构级新增之一，这一自洽性缺陷会直接削弱 §9.11.2 审计防篡改的拓扑保证，也使 §4.6.2 规则 1“审计不与业务数据同库”变得不完整。
- **建议**：二选一并全文统一：
  - 若审计必须独立存储，则将“审计日志”从“平台数据包含”列表中删除，并在 §4.6.2 增加“审计亦不与平台数据同库”；
  - 若审计仅在平台库内以追加写/WORM 分区存在，则修改表格中审计数据的“存放位置”为“平台库内独立审计存储（追加写/WORM）”。

## 重要（应修）

### 1. M4 编号被同时用于两个完全不同的决策
- **位置**：§0.6、§4.6.3、§10.3
- **原文**：
  - §0.6 修订表 #4：“**M4**：Node 为生产权威，Python 降级为开发期交叉验证……”
  - §4.6.3 标题：“验证器引擎的运行时权威（**M4 新增**，v2.5）”
  - §10.3 决策表：“**M4** | 采用 KVVI-Builder 的「公司即租户」组织模型……”
- **问题**：同一个标签 M4 既指代“Node 验证器为生产权威”，又指代“公司即租户”的组织模型。跨章节引用时会产生歧义，验收或任务拆分可能指向错误决策。
- **建议**：将验证器引擎决策重新编号（例如 M5），并在 §0.6、§4.6.3、§10.3 中统一引用。

### 2. §9.6.3“技术上不可达”的表述超过 §4.1.1 的防护范围
- **位置**：§4.1.1、§9.6.3
- **原文**：
  - §4.1.1：“KVVI 运行时……部署后不可替换、不可修改；**搭建者与员工均无写入路径**。”
  - §9.6.3：“**任何**绕过通道的写入或部署在技术上不可达……一旦运行时变得可被**部署方**或搭建者替换，本行的「不可达」立即退化为「不被允许」。”
- **问题**：§4.1.1 只保证搭建者和员工无法修改运行时，未约束实例所有者/部署方；§9.6.3 却用“任何绕过”并承认部署方可破坏该保证。在私有化交付（一个客户企业 = 一个实例）下，客户掌握基础设施，若不排除该主体，“技术上不可达”是过度承诺。
- **建议**：将 §9.6.3 的“任何绕过”收紧为“搭建者与员工可用的任何绕过通道在技术上不可达”，并显式说明实例所有者/基础设施管理员不在此保证范围内，或把该保证归入部署/运维约束。

### 3. 访客路径的“红线 3 等价形式”实质是放宽，不宜称“等价”
- **位置**：§3.5.4、§10.1
- **原文**：
  - §3.5.4：“访客路径的追溯单位为「链接签发人 + 链接 ID + 提交通道」。”
  - §10.1：“红线 3 的**实质**（不存在无主的操作）在访客路径上依然成立。”
- **问题**：红线 3 原文要求“操作可追溯至**账号**与执行通道”。访客提交无法追溯到实际提交者账号，只能追溯到链接签发人，二者可能不是同一人。称其为“等价形式”掩盖了这一放宽，可能在审计层面不满足红线的字面要求。
- **建议**：不宣称“实质等价”，而将访客路径单列说明为“红线 3 的受限落地形式”；或补充记录来源 IP/设备指纹等可辅助定位实际提交者的非敏感标识；或修改红线 3 文本，明确“访客以链接签发人账号为追溯锚点”。

## 建议（可选）

### 1. 动态插件与“运行时不可修改”声明的边界需澄清
- **位置**：§4.1.1、§5.7.1、§9.10.2
- **原文**：
  - §4.1.1：“KVVI 运行时……部署后不可替换、不可修改。”
  - §5.7.1 / §9.10.2：运行时动态插件可在进程内存注册路由/服务，生产环境默认禁用，但所有者批准后可开启。
- **问题**：动态插件本质是对运行时的临时修改，虽受控，但与 §4.1.1 的“不可修改”声明之间存在张力。
- **建议**：在 §9.10.2 明确动态插件属于受控运维调试例外，重启即失效，不破坏 §9.6.3 对搭建者/员工的保证。

### 2. 审计独立存储的公司维度隔离未说明
- **位置**：§4.6.1
- **原文**：审计数据“隔离方式：追加写 + 哈希链 或 WORM”
- **问题**：若审计数据使用独立存储，是否仍按公司维度隔离未说明；多公司实例下可能出现跨公司审计读取风险。
- **建议**：在 §4.6.1 表格中补充“按公司维度分区/RLS（若与平台库分离，则独立存储侧同等实施）”。
