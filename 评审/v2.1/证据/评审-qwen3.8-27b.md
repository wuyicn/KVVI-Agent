## 总体判断

工期数字缺乏人力假设支撑，阶段三与阶段四的工作量密度在单人/小团队下不可实现，关键路径判断不完整。

---

## 阻断（必须修，否则不能开工）

### 1. 全篇无团队规模与技能构成假设，工期数字不可验证
- **位置**：§7.1、§7.2.3
- **原文**：§7.1 仅给出"阶段一 第1-2周""阶段三 第5-10周"等周期与任务列表；§7.2.3 说"先按完整平台工作量如实上浮（24→34周）"，但"完整平台工作量"未除以任何人力系数。
- **问题**：30-31 周的工作量涵盖 5 个 Skill 开发、命令引擎、页面编译器、自建账号体系、9 项安全地基、数据运行时、ContextGraph/Policy Checker、AI 越权防护、工作台前端、审批流、子表、多个样例、交付包。这些工作横跨前端、后端、AI/LLM 工程、安全/权限、DevOps 至少四个技能域。PRD 未声明需要几人、什么角色、每人每周可用多少有效工时。没有这个前提，"6 周""7 周"等数字无法被任何读者验证或挑战，也无法在资源不足时触发裁剪决策。
- **建议**：在 §7.1 表格中增加"所需角色 × 人数"列，或在 §7 开头增加"人力假设"小节，明确：(a) 最小可行团队构成（如 2 后端 + 1 前端 + 1 AI/LLM + 1 安全/权限）；(b) 各阶段哪些任务可并行、哪些必须串行；(c) 若实际人力低于假设，哪些阶段先裁剪。

### 2. 阶段三 6 周承载 7 项独立工作且末项依赖前 6 项全部完成，实际可用窗口被压缩
- **位置**：§7.1 阶段三行
- **原文**："五个搭建 Skill 落地……命令引擎（0C-7）；页面编译器（0C-2）；最小表单 + 编译预览（0A-13）；去行业化自查（0A-14）；AI 蓝图闭环（0D-1）"
- **问题**：`0D-1`（AI 蓝图与整包建系统闭环）从名称和语义看，要求 5 个 Skill + 命令引擎 + 页面编译器全部就绪后才能做端到端闭环验证。这意味着 6 周中至少最后 1-2 周被 `0D-1` 独占，前 5 项实际只有 4-5 周。而 5 个 Skill 各自需要：理解对应 MetaSchema 契约 → 实现自然语言到结构化输出的生成逻辑 → 与双引擎验证器对接 → 编写测试用例。即使契约已冻结（§7.2.1 确认），生成逻辑本身是全新实现。在人力假设缺失（问题 1）的前提下，6 周完成 7 项独立工作且末项串行依赖前 6 项，对 2 人团队不可实现，对 4 人团队也仅够"刚好完成"、无缓冲。
- **建议**：(a) 将 `0D-1` 拆出为独立子阶段或移至阶段三末尾并显式标注"依赖前 6 项全部完成"；(b) 为阶段三增加"若人力不足，优先保 5 Skill + 命令引擎，`0A-13`/`0A-14`/`0D-1` 可顺延至阶段四前"的降级路径；(c) 给出阶段三的最低人力要求。

## 重要（应修，影响成功率或成本）

### 3. 关键路径判断不完整：整条链均为串行，阶段三可能是更长瓶颈
- **位置**：§7.1 末尾"关键路径"段
- **原文**："阶段四与阶段五是串联阻塞的，不能并行跳过。"
- **问题**：§7.1 的七阶段是严格线性排列（1→2→3→4→5→6→7），没有任何阶段被标注为可并行。因此关键路径就是整条 30-31 周的链，而非仅"四与五"。PRD 将注意力集中在四/五（安全地基与运行时），但阶段三（6 周、7 项工作）和阶段四（7 周、14 项工作）的工作量密度可能更高。若阶段三因人力不足延期 2 周，后续全部顺延，而 PRD 没有为这种情形提供预警或缓冲。
- **建议**：(a) 将"关键路径"表述改为"整条链为串行关键路径，其中阶段三与阶段四为工作量最密集段"；(b) 在 §7.1 中为阶段三和阶段四各标注"缓冲周"或"最早可裁剪项"；(c) 若阶段二（品牌替换）与阶段三（Skill 开发）在技术上可部分并行（品牌替换不阻塞 Skill 逻辑开发），应显式说明并调整排期。

### 4. 阶段内任务依赖顺序未显式声明，存在隐式串行被当作并行排期的风险
- **位置**：§7.1 阶段三、阶段六；§7.2.2
- **原文**：阶段三同时列出"页面编译器（0C-2）"与"最小表单 + 编译预览（0A-13）"；阶段六同时列出"子表与明细行（0C-3）"与"家具'报货申请'样例（0C-6）"。
- **问题**：`0A-13`（最小表单 + 编译预览）从语义上依赖 `0C-2`（ViewSchema 编译器）的编译能力——没有编译器就无法"编译预览"。`0C-6`（报货样例）依赖 `0C-3`（子表/明细行）——PRD 自己在 §7.4.4③ 说"报货单＝主表＋明细行"。这两组依赖在阶段内是串行的，但 PRD 的表格呈现方式暗示它们可并行。若团队按"6 周内 7 项并行推进"理解，会在 `0C-2` 未完成时就开始做 `0A-13`，导致返工。
- **建议**：在 §7.2.2 的分配表中增加"阶段内前置依赖"列，显式标注：阶段三内 `0C-2` → `0A-13` → `0D-1`；阶段六内 `0C-3` → `0C-6`。或在阶段描述中用"先…后…"句式替代并列罗列。

### 5. 被裁项的连带影响评估不足：无备份对开发/测试期的持续风险、无环境晋级对验收的阻塞
- **位置**：§7.4.4
- **原文**：①"首版无灾备——必须写进交付说明"；②"首版为单环境交付，升级需人工"。
- **问题**：PRD 将"无备份"的后果定位为"交付时告知客户"，但忽略了**开发期自身**的风险：阶段五（数据运行时）和阶段六（审批流、报货样例）的开发与测试会反复写入/修改业务数据。没有备份恢复能力意味着一次错误的测试脚本或 Agent 越权操作（红线 1 要防的正是这种场景）就可能损坏开发数据库且无法回滚。同理，"无环境晋级"不仅是"升级需人工"，更意味着**阶段七的验收测试无法在独立环境进行**——验收操作会直接作用于开发/生产同一套数据，验收证据包的可信度受损。
- **建议**：(a) 在 §7.4.4① 中补充"开发/测试期间应使用可丢弃的临时数据库实例，每次测试前重置"作为缓解措施；(b) 在 §7.4.4② 中补充"阶段七验收应在独立 Docker 容器中进行，验收后销毁重建"；(c) 评估是否可用"每日自动 `pg_dump`"作为最低成本备份（不属于 `0D-6` 的完整备份恢复方案，但能覆盖开发期风险）。

### 6. DSH 处于 alpha 版本，30 周内的 API 稳定性风险未量化为具体应对
- **位置**：§9.2"上游变更"行；§6.1
- **原文**：§9.2 写"DSH 处于 0.1.6-alpha.2，API 可能变动 | 锁定版本，建立升级评估流程"；§6.1 确认"根包 @deepseek-ai/dsh-root v0.1.6-alpha.2"。
- **问题**："锁定版本"在 30 周周期内意味着：(a) 若 DSH 修复了 KVVI 依赖的 bug，KVVI 无法获取修复；(b) 若 DSH 的 alpha 版本存在未发现的构建/运行时缺陷，KVVI 在阶段一锁定后可能长期携带；(c) "建立升级评估流程"是空话——30 周后若需升级，阶段一锁定的基座（Docker 镜像、构建脚本、依赖树）可能需要重新适配，影响面未评估。PRD 未说明：锁定的是 git commit 还是 npm 版本？是否 fork 到私有仓库？若上游删除仓库（alpha 项目常见），源码是否已持久化？
- **建议**：(a) 在阶段一交付物中明确"将 DSH 源码 fork 至 KVVI 私有仓库，后续开发基于 fork 而非上游"；(b) 在 §9.2 中量化"若上游 API 变动，预计影响哪些阶段、适配工作量量级"；(c) 明确"锁定"的具体操作（commit hash + 私有 fork + lockfile）。

### 7. 阶段四 7 周承载 14 项工作，其中"自建账号体系"本身是完整子系统，与 9 项安全地基存在强串行依赖
- **位置**：§7.1 阶段四行；§7.4.2 B 表
- **原文**："自建账号体系与两级授权（§3.1）；0B 安全地基整块：登录/切换公司、多公司隔离 RLS、表单权限、字段权限、五档数据范围、流程权限、金额精确、单号唯一、审计留痕；账号生命周期与离职交接（§3.3）；身份源适配器路口（§3.4）；双网关隔离（0D-7 隔离部分）"
- **问题**：这 14 项中，"自建账号体系"是前置（没有账号，登录/权限/RLS 无从谈起），"多公司隔离 RLS"依赖账号体系 + 租户模型（0A-7 契约），"表单权限/字段权限/流程权限"依赖 RLS 基础设施，"审计留痕"需贯穿以上所有操作。这意味着 14 项中至少 8-9 项是串行的。7 周做 8-9 项串行工作（每项含设计+实现+测试），即使 2 人全职也仅够"刚好完成"。而 §3.3 的离职交接方案（停用/交接/归档三动作分离、前置检查、继任者解析）本身就是一个中等复杂度的功能模块，被压缩在"账号生命周期与离职交接"一行中。
- **建议**：(a) 将阶段四拆为 4a（账号体系 + 登录 + RLS，4 周）和 4b（四维权限 + 审计 + 离职交接 + 双网关隔离，3 周），使串行依赖显式化；(b) 为"账号生命周期与离职交接"单独估算工作量（§3.3 的方案含 6 个子节，不是"一个功能"）；(c) 明确阶段四的最低人力要求（建议 ≥ 3 人）。
