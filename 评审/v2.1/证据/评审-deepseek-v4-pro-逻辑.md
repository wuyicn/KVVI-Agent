总体判断：PRD 合并 v2.1 后存在多处未同步修正：租户标识、组织关系、路线图任务、验收范围自相矛盾；另有公司/系统概念混淆，须先归口。

## 阻断（必须修，否则不能开工）

### 1. Q6「预留租户标识位」与「无需预留」直接冲突
- **位置**：§9.3 Q6 行 vs §9.3.1 / §4.5
- **原文**：§9.3 Q6 仍写「⚠️ 但数据结构须**预留租户/组织标识位**，使将来转 SaaS 不必重构全链路分区（见 §4.5）」；§9.3.1 又写「数据结构不需要「预留」租户标识位——**租户上下文是一等公民，从一开始就存在**」。
- **问题**：同一决策点在决策表与修正说明中完全相反。M4 已宣布修正 Q6，但 Q6 行未同步修改。数据结构是否预留租户标识位是底层模型问题，必须只有一个答案。
- **建议**：更新 §9.3 Q6 行及所有旧表述，统一为「采用公司即租户，无 SQL 层预留但租户上下文一等公民」；删除或显式作废「预留租户/组织标识位」的旧句。

### 2. 组织关系字段「可选」与「默认补齐/必须含」冲突
- **位置**：§3.3.5 / §9.3 Q14 vs §9.3 Q16
- **原文**：§3.3.5 写「组织关系是 `data-model` Skill 产出物里一个**可选的、但会解锁自动化的字段集**」「自动解析**只在搭建产出物定义了组织关系时才可用**」；§9.3 Q16 写「`data-model` Skill 在搭建时**默认补齐组织关系字段**」「员工/组织实体**须含** `直属主管id` 及部门链」。
- **问题**：同一字段集一边说可缺省、缺省后降级手动；一边说默认补齐且必须存在。这直接改变 `business-schema` 的约束强度与离职交接默认路径。
- **建议**：二选一。若采用 Q16，需改写 §3.3.5/Q14 为「默认补齐；仅在数据源缺失且人工未确认时降级手动」；若保留可选，应删除或弱化 Q16 的「须含/默认补齐」。

### 3. 路线图任务阶段分配前后冲突
- **位置**：§7.2.2 vs §7.1 / §7.4.2
- **原文**：§7.2.2 将 `0C-5` 事件/定时、`0D-5` 付款 Fake 放入**阶段六**，将 `0D-2` 黄金样例放入**阶段七**；但 §7.4.2 C 明确 `0C-5`、`0D-5` 为首版**延后**，§7.1/§7.4.2 B 又将 `0D-2` 放入**阶段六**。
- **问题**：同一个任务被指向两个阶段。§7.2.2 未标注「裁剪前原始分配」，读者无法判断哪份是最终计划，实施排期会歧义。
- **建议**：将 §7.2.2 标明为「裁剪前并入视图」，或直接改为最终分配表；至少增加「最终以 §7.4.2 为准」的显式提示，并消除 `0D-5`/`0C-5`/`0D-2` 等错位。

### 4. `0C-3` 验收含「传图片」，但文件上传已延后
- **位置**：§7.4.4 ③ vs §7.4.2 D / §7.1 阶段六
- **原文**：§7.4.4 ③写「`0C-3` 的验收是「表单里能加明细行、**传图片**」……仅「文件上传」延后」；但 §7.4.2 D 明确「文件上传 ⏸ 延后」，§7.1 阶段六也把「文件上传（`0C-3` 后半）」列为已移出。
- **问题**：传图片就是文件上传的一种。验收标准要求一个已延后的能力，导致首版范围不清。
- **建议**：将验收改为「表单里能加明细行」；或者明确「传图片」作为文件上传的特例纳入首版，并同步修改范围与工期。

### 5. 技术路线「先 B 后 A 推荐起步」与阶段一直接做 A 冲突
- **位置**：§6.2 vs §7.1
- **原文**：§6.2 将「C. 先 B 后 A」标为「**推荐起步**」；§7.1 阶段一为「克隆并构建 DSH 源码；跑通 `pnpm build` / `pnpm build:web`」。
- **问题**：推荐策略说先用 npm 发行版/插件叠加跑通，再迁移到源码 fork；详细路线图一开始就是源码 fork（A），没有 B 阶段。开发团队会收到互相矛盾的技术路线指令。
- **建议**：若保留「先 B 后 A」，阶段一应改为插件原型验证；若路线图按 A 起步，应修改 §6.2 的推荐结论或说明 A 起步但用 B 做局部验证。

## 重要（应修）

### 1. 「公司即租户」被当作「多系统路口」的实现方式，概念混淆
- **位置**：§9.3.1 vs §9.3 Q4/Q12 / §2.4
- **原文**：§9.3.1 写「一个账号可加入多家公司……这正是**「多系统路口」**的实现方式，不需要额外设计」；Q4/Q12 讨论的是「一个员工同时使用多个**系统**」。
- **问题**：公司/租户 ≠ 业务系统。员工完全可能在同一个公司租户内使用多个搭建产出的业务系统；账号能切换公司不自动解决跨系统会话、权限与入口。此处理会误导 Q4/Q12 的预留设计被误判为已完成。
- **建议**：明确「业务系统」与「公司/租户」是两级概念，补充账号—公司—系统关系；或承认 Q4/Q12 仍需独立设计，不能仅靠公司切换覆盖。

### 2. 「生产环境仍由我方部署」与私有化交付方式①冲突
- **位置**：§4.5 vs §7.4.4 ②
- **原文**：§4.5 方式①「部署包交付……对方自己部署运维」；§7.4.4 ②称「缓解：首版应约定「生产环境仍由我方部署」，不在客户侧做多环境」。
- **问题**：若首版提供方式①，客户自己部署运维，生产环境不可能由我方部署。Q11 尚未确定首发交付方式，提前把「我方部署」作为缓解措施与既有交付选项冲突。
- **建议**：要么首版暂不提供方式①，要么将缓解措施改为「若采用②/③，生产由我方部署；若采用①，则明确客户只能单环境并承担漂移风险」。

### 3. 「所有者是权限唯一源头」与「搭建者可创建员工并配置权限」未区分权限类型
- **位置**：§3.1 / §9.3 Q10 vs §3.2 Q3
- **原文**：§3.1 写「所有者是权限的唯一源头」「搭建者……不可：授予他人搭建权限」；§3.2 Q3 写「员工账号由所有者**或搭建者**创建并配置权限」。
- **问题**：如果搭建者能创建员工账号并配置业务权限，他们就是业务权限的第二个配置来源。PRD 没有区分「搭建权限的授权」与「员工业务权限的配置」，导致「唯一源头」「不可授权」的含义漂移。
- **建议**：明确「不可授权」只指搭建权限；同时定义搭建者能否配置员工业务权限、是否需所有者预授权范围、是否留痕，避免与「唯一源头」矛盾。

### 4. 红线 4 混淆「修改系统（结构）」与「修改业务数据」
- **位置**：§2.5.3
- **原文**：标题为「读写权限分离」，引文为「使用系统和修改系统不能共用权限——能查数据不等于能改系统」，但落地写「FormPolicy / FlowPolicy 的 actions 必须能表达读与写的独立授权，不得用「能进这个表单」推导出「能改这个表单」」。
- **问题**：「能查数据不等于能改系统」针对结构修改；「能进表单不等于能改表单」针对业务数据写权限。两者不是同一层问题，却都被塞进同一条红线。按此实现，FormPolicy/FlowPolicy 只能覆盖业务读写，无法防止系统结构被改。
- **建议**：拆分或澄清：系统结构修改由双网关/工作模式无 Builder 工具负责；业务数据读/写独立授权由 FormPolicy/FlowPolicy 负责。另注意 §2.5.2 标题「三条红线」已过时，§2.5.3 新增后实为四条。

### 5. 「不做通用编程 Agent」与搭建引擎模式含「编码工具」冲突
- **位置**：§1.3 vs §2.4
- **原文**：§1.3 明确「不做通用编程 Agent（那是 DSH 标准模式的领域）」；§2.4 搭建引擎模式能力面为「全量搭建 Skill + **编码工具**」。
- **问题**：「编码工具」若指通用代码生成/编辑，就打破了 §1.3 的产品边界；若指仅产出类型化搭建资产，PRD 未定义清楚，实施时极易越界。
- **建议**：明确「编码工具」的封闭范围，例如只允许生成/校验 MetaSchema、YAML 视图、命令 payload，不得提供任意语言代码执行或任意编程能力。

## 建议（可选）

### 1. 离职草稿「随账号转移」与「是否交接：否」语义冲突
- **位置**：§3.3.2 vs §3.3.6
- **原文**：§3.3.2 草稿行为「归档封存，随账号一并转移给继任者」，但「是否交接」为「否」；§3.3.6 又说「Agent 产生的草稿要能被接管」。
- **问题**：草稿到底由谁可见、是否随账号转给继任者，表述含糊。
- **建议**：明确草稿归档后归属继任者可见但不自动激活，并解释与「不交接」的区别。

### 2. 旧 YAML 语法仍在使用
- **位置**：§3.3.1 / §3.3.3 vs §5.5
- **原文**：§5.5 已明确 `enum[...]`→`single_select`、`ref(X)`→`AssetRef`；但 §3.3.1 仍引 `enum[在职,离职]`，§3.3.3 仍写「单据以 `ref(员工)` 引用账号」。
- **问题**：v2.1 已定 MetaSchema 为真理源，但生命周期章节仍用旧 YAML 语法描述模型。
- **建议**：统一为 MetaSchema 表述，或明确标明「这些是旧样例描述，不改设计」。

### 3. 红线 5/6/7 在总表中未标注「条件性」
- **位置**：§9.1 vs §9.3.2
- **原文**：§9.1 写「全部为不可违反项，违反任一条即不可交付」；§9.3.2 写红线 5/6/7 首版不适用，转为条件性红线。
- **问题**：总表未标注条件性，容易让团队在首版误将付款沙箱、迁移备份、同包晋级当成交付门槛。
- **建议**：在 §9.1 表 5/6/7 行增加「首版条件性触发」标记。

### 4. 「一家公司 = 一个实例」与集团多公司租户模型需区分
- **位置**：§4.5
- **原文**：§4.5 写「一家公司 = 一个实例 = 一个所有者账号」，随后又写「私有化交付给集团型客户时本就需要在同一套部署内隔离多个公司」。
- **问题**：第一个「公司」指客户企业，第二个「公司」指租户组织单元；同一节内同一个词含义漂移。
- **建议**：用「客户企业/集团」与「租户公司/子公司」分开命名，避免落入交付模式与租户模型混淆。
