## 二、经核实成立的问题

### 阻断级

#### B1. 全篇无人力假设，工期数字不可验证（来源：qwen3.8）

- **位置**：§7 全章
- **核实**：`grep -E "人天|人力|团队规模|全职|人月|FTE"` **零命中**
- **问题**：30-31 周的工作量横跨前端、后端、AI/LLM 工程、安全/权限、DevOps 至少四个技能域，
  却没有声明需要几人、什么角色、每人每周多少有效工时。这使所有周期数字**无法被验证，
  也无法在资源不足时触发裁剪决策**。
- **建议**：§7 开头增加「人力假设」小节，明确最小团队构成、可并行项、以及人力不足时的裁剪顺序。

#### B2. 规则变更对「在途单据」的影响完全未定义（来源：gemma4）

- **位置**：§2.5 与 §7.1 阶段五
- **核实**：`grep -E "在途.*变更|变更.*在途|版本隔离|存量单据"` **零命中**
- **问题**：PRD 主张产出物是「权限与状态机的唯一真理源」。但**没有定义**：
  当搭建者修改已发布的 `workflow-spec`（例如把某字段从 `EDITABLE` 改为 `READ_ONLY`，
  或改状态机迁移路径）时，**正在流程中的存量单据**如何处理？
  这会直接导致存量单据违反新规则、流程死锁。
- **这是本次评审发现的最高价值缺口。**
- **建议**：定义「规则变更策略」——版本隔离（仅新单据适用）还是强制生效（需数据对平）。

### 重要级

#### I1. 关键路径判断不完整（来源：qwen3.8）

- **位置**：§7.1 末尾
- **核实**：原文只写「阶段四与阶段五是串联阻塞的」
- **问题**：七阶段是**严格线性排列**，没有任何阶段标注可并行。因此关键路径是**整条链**，
  而非仅四、五两段。阶段三（6 周 7 项）与阶段四（7 周 14 项）的工作量密度可能更高。
- **建议**：改为「整条链为串行关键路径，阶段三与阶段四为最密集段」，并标注缓冲或最早可裁剪项。

#### I2. 阶段内依赖未声明，有被误读为并行的风险（来源：qwen3.8）

- **位置**：§7.1 阶段三、阶段六
- **问题**：以下依赖在表格中看不出来，团队可能按并行推进而返工：
  - `0C-2`（页面编译器）→ `0A-13`（最小表单 + **编译预览**）：没有编译器就无法预览
  - `0C-3`（子表/明细行）→ `0C-6`（报货样例）：PRD 自己在 §7.4.4③ 说「报货单＝主表＋明细行」
- **建议**：在 §7.2.2 分配表增加「阶段内前置依赖」列。

#### I3. 无备份的**开发期**风险被低估（来源：qwen3.8）

- **位置**：§7.4.4 ①
- **问题**：PRD 把「无备份」的后果定位为「交付时告知客户」，但忽略了**开发自身**的风险：
  阶段五、阶段六的开发测试会反复写入业务数据，一次错误的测试脚本或 Agent 越权操作
  （**红线 1 要防的正是这种场景**）就可能损坏开发库且无法回滚。
  同理，无环境晋级意味着**阶段七验收无法在独立环境进行**，验收证据包可信度受损。
- **建议**：开发期使用可丢弃的临时数据库、每次测试前重置；验收在独立容器中进行。
  另评估「每日自动 `pg_dump`」作为最低成本兜底（不等于 `0D-6` 的完整方案）。

#### I4. DSH 版本锁定策略过于笼统（来源：qwen3.8）

- **位置**：§9.2「上游变更」行
- **核实**：全文仅此一处提到，且只有一句「锁定版本，建立升级评估流程」
- **问题**：未说明锁的是 git commit 还是 npm 版本、是否 fork 到私有仓库、
  源码是否已持久化。**alpha 项目若上游删库，源码需已持久化**。
- **建议**：阶段一交付物明确「fork 至私有仓库、锁定 commit hash、保留 lockfile」。
  **注：本项目已实际 fork 到 `vendor/dsh` 的 `kvvi` 分支，本节据实更新即可。**

#### I5. Agent 对模糊意图的失败模式未定义（来源：gemma4）

- **位置**：§2.2
- **核实**：`grep -E "歧义|澄清|clarification"` **零命中**
- **问题**：员工说「把这个单改了」而同时存在多个可能目标时，Agent 应如何表现？未定义。
- **建议**：定义澄清机制——低置信度或多目标匹配时（agent 应）通过对话二次确认，而非猜测执行。

#### I6. 权限变更的生效时机未定义（来源：gemma4）

- **位置**：§3.1
- **核实**：零命中
- **问题**：所有者回收某人的搭建权限后，该人**正在进行的会话**是立即中断还是允许完成？
- **建议**：明确生效边界（按会话还是按下一次请求校验）。

#### I7. 单环境内缺少版本回滚（来源：gemma4）

- **位置**：§7.1 阶段七、§7.4.4
- **核实**：「回滚」零命中
- **问题**：`0D-8`（跨环境晋级）已移出首版，但**单环境内的回滚**也未定义。
  搭建者发布一个错误的 MetaSchema（例如错误权限配置导致全员无法操作）后，
  系统将不可用，且因「历史不可改写」原则修复成本极高。
- **建议**：即便不做跨环境晋级，也应提供「回滚至上一个已验证版本」的能力。

## 六、限制说明

1. **本评审不构成验收。** 三个模型均为本地量化版本，能力有限；
   `deepseek-r1:32b` 已证实在本次任务上产生编造。
2. **未做交叉评审。** 三份评审独立完成，本汇总的「成立/不成立」判定由人（Agent）逐条核对原文得出，

3. **外部资料不可核实。** PRD 引用的 KVVI-Builder 与 DeepSeek Harness 未提供给评审模型，
   涉及其内部内容的判断未纳入本汇总。
4. **只审文档，不审代码。** 本评审不检查任何实现。
