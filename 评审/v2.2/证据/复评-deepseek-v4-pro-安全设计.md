## 总体判断

§9 原则方向基本正确，但 A1、A2、A5、A7 的“修复”多停留在声明层面，缺乏强制机制与实现规范，若干攻击路径仍可存活，须补齐后才能开工。

## 阻断（必须修，否则不能开工）

### 1. A1 提示注入防护第一层缺乏可执行技术机制，「全局禁止开关」概念不清
- **位置**：§9.7.1
- **原文**：「指令与数据结构化隔离」「模型上下文明确分区」「工具调用只由当前用户消息触发」「本层提供可配置的全局开关，可整体启用/关闭」
- **问题**：LLM 看到的上下文只是一串 token，天然不存在「指令区」与「数据区」的结构化隔离。PRD 没有给出任何实现机制来保证注入文本不会被当作指令解析——例如数据区编码/转义、工具调用执行前的服务端验证、双通道输入格式等。「工具调用只由当前用户消息触发」在模型生成层面无法可靠强制，模型完全可以因历史消息或数据文本中的内容生成工具调用，除非在工具执行前加一道验证。更严重的是「全局禁止开关」本身：它控制的具体机制未被定义，关闭权限未限定（按 §9.7.1 只需留痕告警，未限定仅所有者可操作），一旦被注入诱导关闭，第一层防护整体消失。§9.7 的两层防护中第一层实际上不可实现，只剩第二层审批兜底，A1 没有被真正堵住。
- **建议**：删去或大幅改写第一层，改为可落地的具体机制：例如要求所有业务数据在进入模型上下文前进行安全编码（如 XML CDATA / 特殊转义）；所有工具调用在执行前由服务端解析并验证其触发来源是否为「当前用户消息」；不设可随意关闭的全局开关，若必须保留则应限定仅所有者可操作、通过 §9.6 审批、关闭期间禁止执行任何高风险动作。

### 2. A7 审计“可证意图”的判定不成立：会话与消息引用不能证明语义等价
- **位置**：§9.8.2
- **原文**：「审计事件必须携带会话与消息引用」「链路可重建：由一条审计记录出发，可还原『用户说了什么 → 模型如何理解 → 执行了什么 → 改了什么数据』」「本产品的审计建立在表单数据的关联性之上，可追溯完整链路，故不另立机制」
- **问题**：A7 的核心是“员工说『把这个单改了』，事后主张自己没要求改金额”。审计携带会话与消息引用只能证明「这个会话里出现过这句话」和「系统执行了这个动作」，不能证明语义映射的等价性。「模型如何理解」在其中是一个不可审计的黑箱：若要记录它，只能记录模型生成的中间映射结果，但该结果本身也是模型输出，可能被注入或推理错误污染。「表单数据的关联性」只能说明数据之间可关联，与意图证明完全是两个问题。§9.8.2 的结论「已由既有链路设计覆盖」不成立。
- **建议**：要么明确「KVVI 不承诺意图证明」并将风险前移到操作确认——高风险动作执行前必须向用户展示完整的结构化参数（目标对象、动作、字段、值）并要求显式确认，审计记录该确认动作；要么在审计链路中增加对模型生成的「自然语言→命令映射」结果的签名记录，并声明该记录的证明力边界。简单的消息引用是必要不充分。

### 3. A2 仍可绕过：审批机制缺「发布路径唯一性」，初始创建的权限策略审批未覆盖
- **位置**：§9.6 / §9.5
- **原文**：「均须所有者批准方可发布/生效」「没有差异报告的变更不得提交审批」；§9.5.1「搭建者可以使用搭建引擎生成/修改业务系统」
- **问题**：§9.6 假设审批发生在「发布前」，但 PRD 从未定义什么是「发布」，也没有规定「发布」必须是权限策略、工具归属、聚合口径生效的**唯一**技术通道。搭建者若直接修改存储中的 MetaSchema、或调用部署 API 将未审批的契约加载到业务系统，唯一服务端执行点（§9.2）会忠实地执行被篡改后的策略，审批形同虚设。此外，§9.6.1 的清单覆盖“新增或变更”但审批规则描述围绕“变更”，初始创建一个全新系统时若包含「公司全部」数据范围或过宽的 `FieldPolicy`，是否触发审批语焉不详。搭建者完全可以通过“新建一个系统”而非“修改现有系统”来绕开审批。
- **建议**：在 §9.6 增加一条硬性要求：所有权限策略、数据范围、工具归属、聚合口径的生效必须经过唯一的发布通道，该通道强制执行审批检查，任何绕过通道的写入或部署操作在技术上不可达。同时明确：初始创建的系统同样进入同类审批流程，首次权限差异报告不可豁免。

### 4. A5 无法落地：令牌签名验证的信任锚点与密钥管理完全未定义
- **位置**：§9.4
- **原文**：「业务系统只接受身份层签发的短时委派令牌」「业务系统自行验证签名，并从令牌导出身份」「令牌由身份层签发，不由 Agent 运行时代发」
- **问题**：§9.4 要求业务系统验证身份层签名，但业务系统是**独立部署**的（§4.1/§4.5），身份层也是自建（§4.3）。二者之间的信任关系如何建立？签名密钥如何分发、存储、轮换？令牌格式、签名算法、公钥信任锚点均未定义。若没有这些，业务系统根本「无法验证签名」——用共享密钥则存在泄漏扩大面，用非对称密钥则需公钥基础设施。§9.1 的地基清单也完全没有包含「令牌签名密钥管理」。§9.4 的整个机制在工程上悬空。
- **建议**：将令牌签名密钥管理纳入 §9.1 地基，并明确：身份层持有私钥仅用于签发；业务系统侧配置对应公钥或信任锚点；密钥轮换流程、令牌格式（JWT 类）与签名算法作为接口契约的一部分；私钥不可随部署包明文分发。

## 重要（应修）

### 5. A6 前置约束缺乏强制执行机制，差分攻击可在合法权限配置中复活
- **位置**：§9.8.1
- **原文**：「不得产生「汇总可见、个体不可见」的权限切分」「前置约束必须写下来」
- **问题**：§9.8.1 声称首版不适用，但前提「不得产生汇总可见而个体不可见的权限切分」只是一条纸面约束，没有任何自动检查、审批规则或不变量验证来保证它不被违反。权限差异报告（§9.6.3）只展示变化，不校验该不变量。如果搭建者配置了一个「部门汇总可见，但个人明细字段被 HIDDEN」的组合，且所有者批准发布，A6 差分攻击立即成立。§9.8.1 的“不适用”前提实际未被保护。
- **建议**：在权限策略验证器或 §9.6.3 差异报告中加入机器可执行的**聚合差分不变量检查**：对每个聚合口径，验证所有可查到该聚合结果的用户，其权限配置是否同样可访问构成聚合的个体数据；不满足则拒绝发布。若认为该检查过于复杂，至少应在「高风险操作审批」清单中把任何会产生此类切分的配置**强制升级为最高风险级别并显式警告审批人**。

### 6. §9.6 高风险操作清单过宽，与红线 1「同一套校验」存在张力
- **位置**：§9.6.1 / §9.6.2 / §2.5.2
- **原文**：§9.6.1 把「审批、确认、终态变更、批量动作、敏感字段修改」列为高风险业务动作；§9.6.2「员工触发『业务动作』类高风险操作时，须所有者审批或本人二次确认」；§2.5.2 红线 1「Agent 代员工执行操作，必须走与该系统 UI 完全相同的授权与状态机校验」
- **问题**：如果把“审批、确认”列为高风险，而 UI 用户执行同样的审批操作不需要额外所有者审批，则 Agent 路径与 UI 路径行为不一致，违背红线 1；如果统一执行点强制审批，则 UI 用户的日常审批、确认操作全部被阻断，产品不可用。PRD 没有定义这层额外审批的实施位置和适用边界，留下实现时两难或绕过空间。
- **建议**：明确区分**基础校验**（授权+状态机，统一执行点，UI 与 Agent 一致）与**额外注入防护**（仅对 Agent 发起的操作增加确认/审批，不影响 UI 正常操作）。同时收窄高风险业务动作清单：仅对不可逆、大额、批量、权限变更类操作附加审批，普通审批/确认动作从清单中移除，或改为「本人二次确认」即可。

### 7. 搭建者可自我配置业务权限，使「搭建权限 ≠ 数据权限」落空
- **位置**：§9.5.2 第 5 条 / §3.1
- **原文**：§9.5.2「凭搭建权限获得生产业务数据访问权——搭建权限 ≠ 数据权限」；§3.1 表格显示搭建者可「配置员工业务权限（在所有者设定的范围内）」
- **问题**：§3.1 授予搭建者配置员工业务权限的能力，但没有禁止搭建者将自己纳入“员工”范围并配置高数据范围（如「公司全部」）。若搭建者可以给自己或同伙配置业务数据访问权，§9.5.2 第 5 条的原则就形同虚设。所有者设定的“范围”是否包含“搭建者本人”未明确。
- **建议**：在 §3.1 或 §9.5 增加约束：搭建者不得直接或间接配置自己的业务数据访问权限；其业务权限只能由所有者显式授予，且该授予本身须经审计并纳入高风险操作审批。

### 8. §9 完全缺失模型服务商数据流出、拒绝服务、部署运维面（密钥/配置/日志）安全要求
- **位置**：§9 整章
- **原文**：§9 仅覆盖权限、注入、身份、数据范围、审计、租户隔离，未提及模型供应商风险、DoS、运维安全；§3.2 提到「统一 Key / 每人自带 Key / 本地模型」但 §9 未跟进。
- **问题**：三个缺失：① 使用云模型 API 时业务数据（可能含客户名、金额、备注）流出到模型服务商，私有化客户对此极度敏感，PRD 无任何脱敏、审计、供应商信任要求；② 工作模式 Agent 可被对话诱导频繁调用读视图或批量创建草稿，§9 无速率限制、配额、并发上限，虽 §5.2 出现「限额/速率」字样但无安全要求；③ §9.4 的签名密钥管理未定义（已列阻断第 4 条），更广泛地日志安全（审计日志是否含敏感数据、防篡改存储）、配置文件保护、上游依赖安全更新等均无要求。
- **建议**：在 §9 增加一节「运行与运维安全」，至少覆盖：发送到模型服务商的数据最小化与脱敏要求；调用速率限制与资源配额；审计日志完整性保护（WORM 或哈希链）；敏感配置的保管与加密。模型服务商风险可注明“私有化部署下由客户选择本地模型时规避”，但须作为明确的部署约束而非默认忽略。

### 9. §9.7 第一层“历史消息”定位不清，注入可能通过会话历史复活
- **位置**：§9.7.1 / §9.7.3
- **原文**：「用户消息是唯一指令来源」「工具调用只由当前用户消息触发」；§9.7.3 负向测试包含「在历史消息中写入指令」
- **问题**：负向测试提到历史消息，但第一层防护只谈“数据区”与“用户消息”。历史消息既不是数据区文本，也不一定是“当前用户消息”。当高权限用户让 Agent 查看此前低权限用户留下的消息时，该历史消息是否按不可信数据处理？模型是否可能将其内容当作指令来源？PRD 没有明确历史消息的隔离策略，导致 §9.7.3 的测试与 §9.7.1 的防护错位。
- **建议**：明确所有非当前用户消息的上下文内容（包括历史消息、业务数据、工具返回结果）在进入当前推理上下文时统一按不可信数据处理；受 §9.7.1 的隔离约束；负向测试应验证历史消息中的注入不会触发工具调用。

## 建议（可选）

### 10. §9.9.2 与 §9.4 的租户标识注入方式存在表述矛盾
- **位置**：§9.9.2 / §9.4
- **原文**：§9.9.2「所有 `target_ref` / `AssetRef` 携带不可由模型修改的租户标识」；§9.4「模型与工具参数不得控制 `actor` / `tenant`」
- **问题**：若 `target_ref` 作为工具参数由模型生成并提供，而其中又携带租户标识，则模型事实上就控制了租户字段；若要求“不可由模型修改”，则租户标识必须由服务端在解析引用时从令牌导出，不能作为工具入参出现。PRD 两处没有协调，实现时容易落入“信任了客户端传入的 ref 中的 tenant”。
- **建议**：明确租户标识不在模型的工具参数中出现；服务端在收到工具调用后以令牌中的活动租户覆盖/校验引用中的租户标识，且任何不一致一律拒绝。

### 11. 审计日志防篡改机制需要更具体
- **位置**：§9.1
- **原文**：「审计｜留痕机制与其不可篡改性」仅列为地基项
- **问题**：“不可篡改性”只提到不做定义，实现时可能退化为普通数据库日志，有权限者即可修改。红线 3 的可归责依赖于此。
- **建议**：要求采用追加写+哈希链或 WORM 存储，并规定审计日志的访问控制独立于搭建权限，仅所有者或审计角色可读。

### 12. 地基违规检测未定义
- **位置**：§9.1 / §5.6
- **原文**：「搭建引擎不产出对地基的修改」「改动地基只能通过产品发版」
- **问题**：没有说如何检测搭建引擎是否尝试修改地基。MetaSchema 验证器只验证格式，不检查是否触碰地基。
- **建议**：在产出物验证管道中加入地基不变量检查，拒绝任何试图覆盖地基项的契约或配置。

## 红队清单（§9 仍未覆盖的攻击路径，按严重程度排序）

1. **通过搭建引擎生成新系统直接植入宽泛权限（绕过 A2 审批）**：搭建者新建一个系统，初始权限配置即为「公司全部」数据范围 + `EDITABLE` 敏感字段，未经差异报告发布。
2. **通过直接修改 MetaSchema 存储绕过发布审批**：搭建者绕过发布通道，直接操作存储或调用内部部署接口，使未审批的权限策略生效。
3. **历史消息中注入指令诱导高权限用户**：低权限用户在历史对话中写入指令，高权限用户后来查看历史时模型执行该指令。
4. **通过诱导 Agent 批量查询/批量创建导致资源耗尽**：员工反复要求 Agent 查大范围视图或创建大量草稿，无速率限制。
5. **云模型 API 数据流出**：业务数据发送到外部模型服务商，无脱敏，导致客户数据泄漏。
6. **审计日志被管理员或搭建者篡改**：因无防篡改要求，操作者删除或修改日志，破坏归责链条（红线 3）。
7. **搭建者配置自己的业务数据访问权限**：通过自我配置高数据范围获得生产数据访问权，违反「搭建权限 ≠ 数据权限」。
8. **聚合差分攻击在含「汇总可见个体不可见」的权限配置下复活**：因 A6 前置约束无强制检查，该权限组合可被发布。
9. **令牌密钥泄漏导致委派身份被伪造**：身份层签名私钥未受保护，攻击者伪造合法员工委派令牌。

## 覆盖范围自述

我检查了以下方面并认为设计基本合理、暂未发现重大问题：

- **§9.2 唯一服务端策略执行点**：原则正确，将 UI 隐藏/禁用排除在安全控制之外、差分测试要求具体，可执行方向明确。
- **§9.3 写操作数据范围原子谓词**：「ID+租户+范围」一次性定位、零行命中返回 404、响应不可区分等设计要求具体，能有效堵住盲写问题。
- **§9.9 公司切换与上下文隔离**：会话绑定公司（结构性免疫）优于事后清理；引用绑租户作为纵深防御；并发会话隔离要求明确，负向测试覆盖到位。
- **§9.5 的「搭建权限 ≠ 数据权限」方向正确**：作为原则成立，尽管执行上有上述缺口，但方向本身没问题。
- **§9.6.3 权限差异报告作为审批前置条件**：设计合理，能提升审批有效性。
