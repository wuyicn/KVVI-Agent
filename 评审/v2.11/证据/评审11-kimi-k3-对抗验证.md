## 重要（应修）

### 1. 「激活」与「加载」的状态语义未定义，激活批准存在被绕过的实现空间
- **位置**：§4.1.1 四（分工表）、§9.6.2（批准记录条款）、§9.10.1
- **原文**：分工表：激活「✅ 须批准 + 与批准记录的内容指纹比对」；加载「❌ 不须批准 + 与批准记录的内容指纹比对（防热替换）」。§9.6.2：「**加载/激活时与批准记录比对**，不一致则拒绝并告警」。
- **问题**：(a) 安装、注册、激活**各产生一条批准记录**还是共用一条？「加载时与批准记录比对」——与**哪一条**比对？若与安装批准记录比对，则「已安装（已批准，指纹在录）但**所有者拒绝激活**」的插件在进程重启加载时指纹比对**通过**。(b) §9.10.1 自述 profile 插件加载后可「注册 Service / HTTP 路由 / 客户端 UI」、§5.7.1 自述 profile 插件「进程级」生效——若**加载即生效**，激活批准形同虚设；若加载≠生效，则「激活是运行开关」这一语义全文未写。任务问题 1(b)「指纹比对能否替代批准」的答案因此是：**能，但前提是比对激活批准记录且加载前检查激活状态——这两点均未写明**。
- **建议**：补一句状态语义，如「插件仅在存在激活批准记录时被加载；加载与激活时均与**激活批准记录**比对指纹」。

### 2. 「暴露窗口 ≤ 5 分钟 ✅ 成立」对持续驻留插件不成立
- **位置**：§9.4.1「两进程划分的真实保证」表第三行
- **原文**：「**暴露窗口 ≤ 5 分钟**（短时令牌 + 撤销） | ✅ 成立」
- **问题**：该保证只对**单次窃取**成立。令牌有效期 ≤5 分钟（§9.4.2），但会话存续期间运行时进程会**持续获得续发令牌**（§9.4.1 自述「运行时进程就是持有者」；§9.4.4 确认「新令牌签发」机制存在）。插件驻留在运行时进程内（§9.10.1），可**窃取每一个续发令牌**——实际冒用窗口 = min(会话存活期, 插件驻留期)，远超 5 分钟。「≤5 分钟」给读者的印象是「5 分钟后风险消失」，这是本版核心承诺「如实写出边界」内部的一行不如实。
- **建议**：该行改为如实两段式：「单令牌有效期 ≤5 分钟（限制单次窃取的窗口）；**但插件可随会话续发持续窃取，持续冒用窗口延续至会话结束或插件移除**」。

### 3. 「无活跃会话的主体完全免疫 ✅」未限定前提，且认证端点归属未定义
- **位置**：§9.4.1 保证表第一行、§4.6.5 两进程表
- **原文**：「**无活跃会话的主体完全免疫**（插件无法凭空为任意员工/公司令牌） | ✅ 成立」
- **问题**：「完全免疫」只在「插件无法促成该主体产生会话」时成立。但 §9.10.1 自述 profile 插件可注册「**客户端 UI**」——插件可呈现钓鱼界面获取用户凭据，再经真实认证创建真实会话，此后落入「冒用活跃会话」的不防区。其次，**登录/认证端点归属哪个进程全文未定义**（§4.6.5 两进程表列了身份层、签名模块、发布通道、平台库访问 | Agent Loop、Skill、插件宿主，无认证端点）；若登录流量经运行时进程转发，插件可直接窃凭据。「完全免疫」一词没有写出这些前提，与本版对 §4.6.5 自立的「可核验事实 vs 机制条件」表述标准不一致。
- **建议**：改述为「插件**仅凭进程内能力**无法为无会话主体取得令牌；若插件经钓鱼/窃取获得主体凭据则可创建真实会话，此后适用『冒用活跃会话』的不防声明」；并在 §4.6.5 明确认证（登录/登出）端点归属平台服务进程。

### 4. 「不接受会话状态写请求」与用户登出的传导路径冲突未消解
- **位置**：§4.6.5（信任输入面）、§9.4.2、§3.3.4
- **原文**：§4.6.5：「平台服务进程**不接受**来自 Agent 运行时进程对**会话状态与授权判定**的任何写请求。会话生命周期事件由平台服务进程**基于认证事件自行维护**，不依赖运行时进程通知。」§9.4.2：「**账号停用或会话结束时，旧令牌必须立即失效**」。
- **问题**：任务问题 3 的焦点确凿存在：账号停用由身份层端点执行（平台服务进程侧，自闭合）✓；超时由平台服务进程自行判定 ✓；但**用户登出**——用户在工作台的 Agent 会话中点登出，该请求架构上先到达哪个进程？若工作台 API 在运行时进程，登出请求须转发至平台服务进程，而这正是一次「对会话状态的写请求」。「基于认证事件自行维护」一句想盖住此点，但「认证事件」**未枚举**——是否包含登出？登出请求的入口进程是什么？全文无答案。实现者只能二选一：违反约束（让运行时进程转发登出），或无法实现登出使「会话结束立即失效」落空。
- **建议**：枚举会话生命周期事件（登录、登出、超时、停用、管理员吊销），并明确这些事件的入口**直接在平台服务进程**，不经过运行时进程。

### 5. 加载/卸载的留痕机制空洞：无端点、依赖被审计者上报、可信度边界未声明
- **位置**：§9.6.3 清单第 8 项、§9.11.2、§4.1.1 四、§5.7.3
- **原文**：§9.6.3 第 8 项：「⚠️ **加载与卸载不暴露独立产品端点**」；§9.11.2：「插件的生命周期动作（动作全集，见 §4.1.1 四）**经产品接口发生**，仍受本节约束」；§4.1.1 四：「动作全集**逐项必须留痕**」。
- **问题**：三处字面冲突：加载/卸载**无端点**，却被称为「经产品接口发生」。更深的空洞在于留痕机制本身：加载/卸载的留痕只能由**运行时进程自行上报**，而 §5.7.3 已承认已加载的恶意插件「**可以拦截审计写入**」——插件在加载完成时即可拦截/伪造自己「加载」这条留痕，被卸载时同理。§9.10.2 的循环依赖知情说明（「留痕保证的是生命周期动作**经接口发生**」）恰好**不覆盖**这两项不经接口的动作。这直接回答任务问题 1(a) 关于卸载的追问：卸载不须批准的定位本身成立（紧急动作 + 审计是地基非插件），但「卸载✅须留痕」在恶意插件场景下是**空文**。
- **建议**：(a) §9.11.2 改述为「安装/注册/激活经产品接口发生；加载/卸载由运行时进程在进程行为中记录上报」；(b) 按 v2.9 的知情原则补边界：「加载/卸载的留痕以运行时进程未被同进程插件拦截为前提，该前提对已作恶插件不成立」。

### 6. §9.10.2 控制要求首行左列仍写「仅所有者可批准安装/注册」，漏「激活」

### 7. 部署基线是安全成立条件，但交付物中无任何告知部署方的要求
- **位置**：§4.6.5（部署基线限定）、§7.1 阶段七锚点②、§4.5
- **原文**：§4.6.5：「上述边界**在以下基线下成立**：两进程分属不同容器或不同系统用户；禁止跨进程调试；无共享可写文件系统……**基线之外的部署不属于本节的保证范围**」。§7.1 阶段七锚点②：「操作手册覆盖**所有者 / 搭建者 / 员工**三种角色的完整流程」。
- **问题**：任务问题 4 的答案：四条基线中，「禁止跨进程调试」「无共享可写文件系统」**产品无法在运行期强制**，只能由部署方维持——写成「基线之外的部署不属于保证范围」这一限定本身是妥当的（非过度承诺）。但 §4.5 明确存在「部署包交付：对方自己部署运维」，部署方是真实角色，而操作手册不覆盖部署方。**善意部署方无意破坏基线**（为调试方便挂共享卷、开跨进程调试）将使两进程隔离失效且无人知情——这与 §7.4.4「首版无灾备必须书面告知客户」、§9.6.2「批准界面须如实告知放弃项」是同一知情原则，此处缺位。
- **建议**：阶段七锚点或操作手册要求中补一条：「交付文档须包含 §4.6.5 部署基线与安全成立条件」。

若 OpenAI 家族恢复参与、标准降回「零阻断」，则硬阻塞仅阻断 1；但按当前加严标准，重要项不得仅记录。
