## 任务 1：「批准集 ≠ 审计集」这个新规则成立吗？

### (a) 安装/注册/激活须批准、加载/卸载不须批准——这个划分对不对？

看 §4.1.1 四的分工表：

| 动作 | 须批准 | 须留痕 | 附加要求 |
|---|---|---|---|
| 安装 | ✅ | ✅ | — |
| 注册 | ✅ | ✅ | — |
| 激活 | ✅ | ✅ | 与批准记录的内容指纹比对 |
| 加载 | ❌ | ✅ | 与批准记录的内容指纹比对（防热替换） |
| 卸载 | ❌ | ✅ | 不得需要审批（紧急动作） |

「加载」真的不须批准吗？评审任务提示说「它也是让代码进入运行的时刻」。但 PRD 的论证是：
- 加载是进程启动行为——每次重启都要求所有者重新批准不可执行
- 加载时比对指纹（防热替换）——这意味着加载的代码必须与已批准的内容一致

这个论证是否成立？关键问题是：**激活与加载的区别是什么？** PRD 没有明确定义「激活」和「加载」的区别。从上下文推测：
- 激活（activate）：让插件生效（可能是在运行时启用）
- 加载（load）：进程启动时把插件载入内存

如果激活须批准、且激活时比对指纹，那么代码进入运行的时刻实际上是「激活」而不是「加载」？还是说加载后即可运行？

§9.6.3 清单第 8 项写：「⚠️ **加载与卸载不暴露独立产品端点**（加载发生在进程启动时、卸载须免审批，见 §4.1.1 四）」

这里有个问题：如果「激活」是批准点，而「加载」只是进程启动时的机械动作，那么：
- 一个已安装+已注册但未激活的插件，在进程重启时会被「加载」吗？
- 如果加载 = 代码进入内存但不一定运行，那么「代码进入运行的时刻」是激活，批准点在激活是合理的。
- 但如果加载后插件代码即可执行（DSH 的 profile 插件是进程级生效的），那么加载才是真正的风险时刻。

PRD 没有定义「激活」与「加载」的语义区别和先后关系。这是一个潜在的模糊点。但是从产品角度看：
- 激活须批准 + 指纹比对
- 加载不须批准但比对指纹（与批准记录比对）

指纹比对能否替代批准？如果指纹比对是「与批准记录的指纹比对」，那么加载的代码必须是某个已批准的内容。这种情况下，加载不批准的风险窗口是：
1. 批准记录本身可以被谁写入？如果批准记录只能由所有者经批准界面写入，那么指纹比对确实把「加载」约束在「已批准内容」的集合内。
2. 热替换：进程运行期间替换插件文件——下次加载时指纹不符会被拒绝。这个防的是「批准后被偷换」。

这个逻辑是自洽的：**批准绑定内容（指纹），加载/激活时验证内容**。批准是授权行为，加载时的指纹比对是技术验证。只要「指纹比对强制且不可跳过」，加载不须批准是可辩护的。

但有一个问题：**卸载不须批准是否会被滥用（卸载掉审计插件）？**

PRD 里有没有「审计插件」的概念？看 §9.11.2 审计是地基项，由平台提供，不是插件。插件是扩展，审计机制在运行时地基里。但假设有一个安全/审计类插件（比如第三方审计扩展），恶意卸载它——但谁能卸载？卸载的操作者是谁？

PRD 没有明确「谁可以执行卸载」。§9.6.2 说「搭建者与员工无任何安装/注册/激活路径（加载与卸载同理无路径）」——等等，这里说搭建者与员工「加载与卸载同理无路径」。那么卸载由谁执行？所有者？运维？

如果只有所有者/运维能卸载，那卸载不批准的风险是：所有者自己卸载，或者进程管理者卸载。这在信任边界内（所有者是可信主体）。卸载掉审计功能——但审计不是插件（审计是地基，§9.1），插件不能提供地基功能。所以「卸载审计插件」这个攻击在 PRD 框架内不成立：审计机制在平台运行时内，不在插件里。

不过，如果某个安全增强功能以插件形式存在，卸载它会降低安全性但不破坏核心保证。这个风险接受度由所有者掌握——所有者批准安装，所有者/运维卸载，这是自洽的。

但注意一个细节：§9.6.2 表格里写「**审批主体** | **仅所有者**（§9.10.2）。搭建者与员工**无任何**安装/注册/激活路径（**加载与卸载同理无路径**，但这两项本身不须批准）」。

「无路径但须留痕」——卸载由谁触发？如果是所有者触发，那其实是「所有者执行，不需额外批准」，这说得通：所有者本来就是批准主体，所有者卸载等于所有者自己撤销。但如果是运维（基础设施管理员）触发，那他们在信任边界内，做什么都防不住，所以不须批准也无妨。

这个划分我认为基本成立，但有一个真问题：**卸载的触发主体未明确**。是建议级问题。

另外一个更深的问题：**「激活」和「加载」的语义与关系未定义**。
- 已批准激活的插件，进程重启后需要重新「激活」吗？如果重启后自动激活，那「加载」时只比对指纹就够了吗？
- 如果「激活」状态持久化（激活一次永久激活），那么加载时除了比对指纹还应检查「该插件处于已激活状态」。PRD 只说加载比对指纹，没说检查激活状态。
- 一个已安装+注册但**从未被批准激活**的插件，其指纹是否在批准记录里？等等——安装和注册都需要批准，批准记录包含指纹。所以一个插件只要安装过就有批准记录（含指纹）。那么「加载时与批准记录比对指纹」能通过的是：已安装（含注册）的插件。但它可能**未激活**。

问题：未激活的插件会被加载吗？如果会，它加载后能运行吗？如果加载即可运行，那「激活须批准」就形同虚设——安装时批准了（含指纹），加载时指纹比对通过，插件就运行了，激活这个批准点毫无作用。

这是一个真实的设计空洞：**三个批准动作（安装/注册/激活）之间的状态机没有定义**。安装批准了什么？注册批准了什么？激活批准了什么？如果安装批准记录含指纹，加载时比对安装批准的指纹就能通过，那激活批准的增量是什么？

不过，从 PRD 层面看，这可能是「实现细节」？不，这是产品级安全语义：批准的对象是什么。三个动作都须批准，但批准记录字段只有一套（标识+指纹+来源+批准人+时间），没有区分动作类型……等等，§4.1.1 四说审计留痕「含批准人、时间、插件标识、内容指纹与来源」，§9.6.2 说批准记录含「插件内容指纹（哈希）+ 来源 + 标识 + 批准人 + 时间」。批准记录是否记录「批准的是哪个动作」（安装/注册/激活）？没写。加载时与「批准记录」比对指纹——哪个批准记录？安装的？激活的？

这些模糊点在实现时会产生真实分歧。但考虑到 PRD 的精度边界（v2.4 确立：PRD 定义做什么，怎么做属技术设计文档），状态机细节可以下放。但「加载时与哪条批准记录比对」是安全语义的关键，不算实现细节。

嗯，让我重新想想这是不是阻断级。

场景：所有者批准安装了插件 P（记录指纹 F1）。插件 P 需要「激活」才能生效——激活也须批准。假设所有者不批准激活。那么 P 处于「已安装未激活」状态。进程重启，发生「加载」——加载时比对指纹 F1，通过（因为与安装批准记录一致）。P 被加载。P 现在能运行吗？

如果「加载」≠「运行」，未激活的插件加载后不运行，那激活是运行开关，批准点在激活有意义。但 PRD 没有这个语义。如果「加载」= 代码进入进程即可执行（DSH profile 插件的实际行为是进程级生效），那激活的批准就被绕过了。

§5.7.1 说 profile 插件「进程级」生效，运行时动态插件「仅进程内存」。§9.10.1 说 profile 插件能「注册 Service / HTTP 路由 / 客户端 UI」——一旦加载进进程就能注册路由，即已生效。

所以「激活」和「加载」的区别在 PRD 体系里是模糊的，而安全语义依赖这个区别。这是一个重要级问题（可能阻断）：**批准点在「激活」，但 DSH 的实际生效点是「加载」（进程级注册路由/Service），若加载≠未生效，则激活批准可被绕过——已安装（已批准，指纹在录）的插件在重启加载时即可获得执行能力，无需激活批准**。

不过，等等。我要小心不要编造。让我重新读原文。

§4.1.1 四：
- 动作全集：安装/注册/激活/加载/卸载
- 分工表：安装✅批准✅留痕；注册✅✅；激活✅✅+指纹比对；加载❌✅+指纹比对（防热替换）；卸载❌✅

§9.6.2：
- 审批主体：仅所有者。搭建者与员工无任何安装/注册/激活路径（加载与卸载同理无路径，但这两项本身不须批准）
- 批准须绑定内容：批准记录须含插件包的内容指纹与来源；加载/激活时与批准记录比对，不一致则拒绝并告警

§9.6.3 第 8 项：
- 插件安装/注册/激活端点：非所有者请求被拒；所有者批准须留痕；同名但内容指纹不符的包被拒。⚠️ 加载与卸载不暴露独立产品端点（加载发生在进程启动时、卸载须免审批，见 §4.1.1 四）

好，所以「加载发生在进程启动时」。那么语义是：进程启动时加载插件。哪些插件？已安装的？已激活的？

如果语义是「进程启动时加载所有已安装且已激活的插件」，那么加载时除了比对指纹还应验证激活状态——PRD 没写验证激活状态。如果语义是「加载所有已安装插件」，那激活批准形同虚设（如上分析）。

这是一个真实的模糊点。严重吗？从对抗角度看：所有者批准安装 P（指纹 F1），但拒绝激活 P（认为太危险）。重启后 P 被加载（指纹比对通过）。P 注册了一条 HTTP 路由。如果加载即生效，安全保证破产。

但是——另一个角度：也许「激活」就是「安装后经批准使其进入可加载集合」，即激活 = 把插件标记为「下次加载时允许加载」。那么加载时实际检查的是「已激活 + 指纹一致」，PRD 只写了指纹比对，漏写激活状态检查。这是「改一半」的同类——定义了状态但检查时只用了一部分。

我认为这至少算**重要**级，可能算阻断。它属于「规则本身对了但落地语义不全」。任务问题 1(b) 问「加载『比对指纹』能否替代批准？」——我的答案：能，前提是「指纹比对 + 激活状态检查」，但 PRD 只写了指纹比对，没写激活状态检查。已安装未激活的插件（指纹在批准记录中）在加载时能通过指纹比对。

嗯，不过再想想：注册是什么？安装、注册、激活三个动作都要批准。也许语义是：安装=把包放进系统，注册=登记到插件注册表，激活=启用。批准记录在每个动作时分别产生。加载时比对「批准记录」——哪一条？如果是最新的（激活批准记录），那未激活的插件没有激活批准记录，指纹比对无记录可比对→拒绝？这取决于「批准记录」的查询语义。PRD 写的是「与批准记录比对指纹」，没说是「安装批准记录」还是「激活批准记录」还是「任一」。

这个模糊性在实现时会导致两种实现：
1. 与任一批准记录比对 → 已安装未激活的插件可通过 → 激活批准被绕过
2. 与激活批准记录比对 → 正确，但未写明

这是**重要**级问题（应修），因为修法很简单（写明「加载与激活时比对的批准记录是激活批准记录」或定义状态机）。是不是阻断？考虑到这是第十一轮冻结评审，标准极高（零阻断+零重要），一个会导致实现分歧且影响安全语义有效性的模糊点……我倾向于**重要**级，因为它更可能是「补充一句就能修」而非「设计错了」。但按加严标准，重要项也必须修才能冻结。

好，先记下：**候选重要 1：加载时指纹比对未指明与「激活批准记录」比对，「安装→注册→激活」三批准动作的状态机语义未定义，已安装未激活的插件能否被加载不明确——若可加载且加载即生效，激活批准形同虚设。**

### (b) 卸载不批准被滥用

如上分析，审计不是插件（§9.1 地基），卸载审计插件的场景在 PRD 框架内不存在。但「卸载的触发主体」未写明。§9.6.2 说搭建者与员工无路径，那剩下所有者（和运维）。所有者卸载不需批准=所有者自己决定，自洽。这不算问题，最多建议级。

## 任务 2：签名隔离的真实保证边界写对了吗？

§9.4.1 的表：

| 保证 | 是否成立 |
|---|---|
| 无活跃会话的主体完全免疫 | ✅ |
| 令牌声明不可伪造 | ✅ |
| 暴露窗口 ≤ 5 分钟 | ✅ |
| 插件可冒用活跃会话的既有令牌 | ⚠️ 不防 |

逐项检查：

### 「无活跃会话的主体完全免疫」——真的免疫吗？插件能否通过某种方式让某个主体产生一个活跃会话？

插件在运行时进程内。会话创建（登录）在哪里？§4.6.5 说平台服务进程含「身份层（会话状态、授权判定）」，且「会话生命周期事件由平台服务进程基于认证事件自行维护，不依赖运行时进程通知」。

认证事件来自哪里？用户登录请求。登录请求的入口在哪？Web 端 → 经过哪个进程？如果是经平台服务进程的认证端点，那插件无法直接创建会话。

但插件能做什么：
1. 插件可以注册 HTTP 路由（§9.10.1）。如果插件注册一个假登录端点？但认证逻辑在平台服务进程，插件的路由在运行时进程。外部请求打到哪个进程？架构上 Web 端调用 API——API 由哪个进程提供？§9.6.3 的接口清单列了「搭建舱 API」「工作台 API」，没说是哪个进程的。嗯，这里有个架构模糊：两进程划分后，HTTP API 面在哪个进程？§4.6.5 说平台服务进程有「发布通道、平台库访问」，运行时进程有「Agent Loop、Skill 执行、插件宿主」。那搭建舱/工作台 API 呢？登录端点呢？没写。

如果登录端点在运行时进程（因为 Web 端 API 历史上由 DSH runtime 提供），那插件可以拦截登录请求、窃取凭据、或以某种方式触发认证事件。插件窃取了用户的用户名密码后，可以代表该用户向平台服务进程发起真实认证——创建一个真实会话。这样「无活跃会话的主体」就变成了「有活跃会话的主体」！

但这算「插件让主体产生活跃会话」吗？严格说：
- 插件窃凭据 → 用凭据创建会话 → 该主体有了活跃会话 → 插件再窃取该会话的令牌（或直接利用）
- 这其实是凭据窃取问题，不是令牌体系问题。「无活跃会话的主体完全免疫」的保证只在「插件无法获得该主体的凭据」时成立。

但等等，插件在运行时进程内，能读到什么？登录请求的密码会不会经过运行时进程？取决于登录端点在哪。PRD 未定义。这是个缺口但也许算实现细节。

另一个更直接的路径：**插件能否直接调用签名接口？** §9.4.1 ②说「签名进程只为平台服务进程中已认证的会话签发；不接受请求方声称的身份」，「调用方只能请求『为当前会话签发令牌』」。那么「当前会话」如何鉴别？调用方（运行时进程）调用签名接口时带上什么？会话标识？如果签名接口接受「会话 ID」参数并查平台服务进程的会话状态验证该会话活跃，那插件可以窃取一个活跃会话的 ID 然后请求签名——得到的令牌就是这个活跃会话的，即「冒用活跃会话」，已声明不防。

那么「为无活跃会话的主体取得令牌」真的不可行吗？插件需要：一个属于该主体的活跃会话 ID。如果不存在，插件能伪造会话 ID 吗？不能（会话状态在平台服务进程）。能创建吗？创建会话需要认证事件（凭据）。插件若无凭据，无法创建。

但注意：**插件在运行时进程内，而运行时进程承载 Agent Loop 和 Skill 执行——所有用户的 Agent 交互都经过运行时进程**。用户的认证呢？如果认证（登录）也经过运行时进程（Web 前端→运行时→平台服务），插件可窃取凭据。如果认证直接到平台服务进程，插件碰不到凭据。

PRD 没写登录端点归属哪个进程。这是一个真实缺口。但它是否推翻「无活跃会话的主体完全免疫」？严格说，「免疫」一词仍过强：
- 路径 1：插件窃取登录凭据（若登录流量经过运行时进程）→ 创建真实会话 → 该主体不再「无活跃会话」
- 路径 2：插件作为恶意代码，能否诱导用户认证？比如插件篡改运行时进程的响应，向用户展示假界面钓凭据？插件能注册客户端 UI（§9.10.1 profile 插件可注册「客户端 UI」）→ 钓鱼界面钓取凭据 → 创建会话。

路径 2 更现实：profile 插件可以注册客户端 UI，它可以呈现一个假的登录框，钓到凭据，然后调真实认证端点创建会话。于是目标主体有了活跃会话，插件再冒用。

所以「无活跃会话的主体完全免疫」的准确边界是：**在插件无法获得该主体凭据的前提下成立**。而插件有两条获得凭据的潜在路径（若登录流量经运行时进程；若插件可注册 UI 钓鱼）。PRD 把这项写成 ✅ 成立无附加条件，是过度声称吗？

嗯，但要公平：任何系统里，能钓取凭据的恶意代码都能创建会话——这是凭据安全而非令牌体系问题。「无活跃会话的主体完全免疫」的语境是「令牌体系的保证」：在令牌体系内，插件无法凭空造令牌。凭据钓鱼是另一个攻击面（客户端安全），任何产品都防不住可信基内的钓鱼 UI。

我认为这里值得指出：**「完全免疫」的表述未排除「插件先促成会话再冒用」的路径**（凭据经运行时进程被窃、插件注册 UI 钓鱼），准确表述应是「插件无法仅凭进程内能力为无会话主体取得令牌；若插件获取主体凭据则可创建会话，此后适用『冒用活跃会话』的不防声明」。这与 v2.11 的诚实风格一致，应该写。算**重要**级。

不过等一下，登录端点归属是个更基础的问题：§4.6.5 的两进程表没有列出「认证/登录端点」在哪个进程。§9.6.3 接口清单的「工作台 API」「搭建舱 API」也没归属。如果认证端点在运行时进程，那「会话生命周期事件由平台服务进程基于认证事件自行维护」的认证事件就来自运行时进程的转发——插件在运行时进程内可以伪造认证事件吗？「基于认证事件自行维护」——认证事件从哪来？如果平台服务进程自己处理认证（用户名密码校验在平台服务进程），那登录流量必须直达平台服务进程。架构上这就要求登录端点在平台服务进程。PRD 没写。这个模糊点影响「信任输入面」的完整性。

### 「暴露窗口 ≤ 5 分钟」——对已签发的活跃令牌成立吗？

任务提示：活跃令牌有效期 5 分钟，但它可能在窗口内被用很多次。

PRD 的说法：「暴露窗口 ≤ 5 分钟（短时令牌 + 撤销）✅ 成立」。

分析：令牌有效期 ≤5 分钟（§9.4.2）。插件窃取令牌后，在 5 分钟内可以使用任意多次。5 分钟后呢？插件还在运行时进程内——它可以窃取**下一个**令牌！只要受害者会话还活跃，运行时进程会不断获取新令牌（令牌过期后需要刷新——等等，令牌过期后怎么获得新令牌？需要重新向签名进程请求。谁发起？运行时进程为活跃会话续签）。所以真实暴露窗口不是 5 分钟，而是**会话的整个生命周期**：插件可以持续窃取每个新签发的令牌。

「暴露窗口 ≤5 分钟」只在「单次窃取」语义下成立。对持续驻留的插件，窗口 = min(会话存活期, 插件驻留期)。这远大于 5 分钟。

这是一个真实的过度声称！「暴露窗口 ≤ 5 分钟 ✅ 成立」不准确。准确说法：单个被窃令牌的有效期 ≤5 分钟；但插件可持续窃取续发令牌，实际冒用窗口延续至会话结束或插件移除。

等等，撤销机制呢？§9.4.2 撤销查询「账号停用与会话结束时必选」。发现插件作恶后，所有者卸载插件+结束会话。但这需要「发现」。在发现之前，窗口持续。

所以这项保证应改为：「单令牌有效期 ≤5 分钟（限制单次窃取的窗口）；但插件可随会话续发持续窃取，持续冒用窗口 = 会话存活期」。PRD 现在写 ✅ 成立，是部分错误的——它让人以为 5 分钟后风险消失。

这是**重要**级（或阻断？）。它是 §9.4.1 新增的「真实保证边界」表中的一行，而这版的核心就是「如实写出边界」。写错一行边界 = 核心目标未达成。但也不是设计错误，是表述不准确。我定为**重要**。

嗯，让我再想想是否够阻断。任务说判定标准是零阻断+零重要。无论我定为阻断还是重要，结论都是「不可冻结」。区别在于措辞。我认为这条算**重要**（应修），因为机制本身（短时令牌+撤销）是对的，只是「暴露窗口≤5分钟」的表述掩盖了持续窃取。但也有一种观点认为这就是过度声称=与 v2.10 被否的「过度声称」同类，而该轮同类问题被列为重要（kimi-k3 重要 2）。所以定为重要与先例一致。

### 「不防冒用活跃会话」已声明——那么 §9.2 说「§9.4 签发面与判定面不在插件可影响之列」，这与「不防冒用」是否自洽？

§9.2 范围声明（v2.11 限定）：
> **§9.4 的「签发面与判定面」不在「插件可影响」之列**——§4.6.5 的两进程划分把身份判定与签名移出了插件的可达范围。
> **但该例外不覆盖「冒用活跃会话」**：运行时进程必须持有令牌才能调用业务系统，插件可窃取该令牌直接使用。详见 §9.4.1 的残留声明。

这两段并置，读起来是自洽的：签发面与判定面免疫 + 使用面（持有面）不免疫。§9.2 已经加了「但该例外不覆盖冒用活跃会话」。我认为 §9.2 这边是自洽的。

§10.1 的指针：
> **令牌体系例外（v2.11 补指针）**：§9.2 的范围声明中，「§9.4 签发面与判定面」不在插件可影响之列——依据是 §4.6.5 的两进程划分与部署基线。但冒用活跃会话令牌不在该例外内（§9.4.1 残留声明）。

也是自洽的。

但还有一个问题：「使用面」不免疫意味着什么？意味着插件可以用窃取的令牌直接调用业务系统——此时业务系统的执行点（§9.2 唯一执行点）会执行这些调用（因为令牌合法、验签通过）。所以 §9.2 的「唯一执行点」对插件窃令牌路径其实是**忠实的执行者**——插件没有绕过执行点，而是带着合法令牌通过执行点。这与「插件可绕过执行点」是不同的路径。§9.2 的连带含义段说「任何依赖本执行点唯一的条款，对所有者所批准的插件均不成立」——这个结论对窃令牌路径仍然成立吗？

有意思：窃令牌路径下，执行点仍然唯一且正常工作——插件只是冒用了合法身份。所以：
- 红线 1（同一套校验）：窃令牌路径下，插件的调用经过了同一套校验——只是身份是别人的。红线 1 形式上成立？不，红线 1 防的是 Agent 绕过权限。插件冒用高权限用户的令牌，数据范围校验按该用户执行——底层校验正常，是身份被冒用。这更像「账号被盗」的情形。§9.8.2 已声明「账号被盗时操作者是否为本人」不可证明。插件窃令牌 ≈ 账号被盗的技术等价物。

这些语义纠缠在 PRD 里没有完全理清，但大致框架是自洽的：不防冒用 + 追溯已排除（红线 3 第二段）。

好，还有一个点：**「声明不可伪造」+「判定面免疫」的成立依赖「会话状态写入面关闭」**。§4.6.5 新增「平台服务进程不接受来自运行时进程对会话状态与授权判定的任何写请求」。这就是任务 3 的重点。

## 任务 3：平台服务进程的信任输入面是否足够？

> 平台服务进程**不接受**来自 Agent 运行时进程对**会话状态与授权判定**的任何写请求。会话生命周期事件由平台服务进程**基于认证事件自行维护**，不依赖运行时进程通知。

问题：会话的创建与结束由谁触发？
- 创建：用户登录→认证事件→平台服务进程创建会话。认证事件来自哪里？如果登录请求直达平台服务进程的认证端点，OK。但 PRD 没写登录端点归属（上面已指出）。
- 结束：用户登出？会话超时？账号停用？
  - 用户登出：用户在工作台点登出→请求到哪个进程？工作台 API 在哪个进程？如果工作台 API 在运行时进程，登出请求要先经运行时进程→平台服务进程。但「不接受运行时进程对会话状态的写请求」——登出请求算不算「对会话状态的写请求」？如果算，那用户登出无法传导！
  
这就是任务提示的矛盾点：**「会话结束立即失效」（§9.4.2、§3.3.4）要求登出/停用时关闭会话与 Agent 通道，而「不接受运行时进程写会话状态」可能阻断这个传导**。

PRD 的解法是「会话生命周期事件由平台服务进程基于认证事件自行维护，不依赖运行时进程通知」。那么登出是「认证事件」吗？认证事件通常指登录（认证成功）。登出算「去认证事件」？如果登出请求直达平台服务进程（不经过运行时进程），那 OK。但用户在运行时进程的 Agent 会话里点登出，这个请求架构上怎么直达平台服务进程？

可能的架构：所有认证相关端点（登录/登出）都在平台服务进程，前端直接调用。这是合理架构，但 PRD 没写。而不写的话，「不接受写请求」与「登出如何传导」之间的矛盾就悬而未决。

再深一层：**「会话结束」的判定**。§9.9.4 令牌随会话结束失效。会话何时结束？用户登出、超时、账号停用、管理员强制结束。超时和账号停用可以由平台服务进程自行判定（不依赖运行时进程）✓。用户登出需要入口——未定义在哪。管理员强制结束——所有者操作，经什么端点？身份层端点（在平台服务进程）✓。

还有：**会话的「活跃」状态**。签名接口「只为当前已认证会话签发」——需要知道会话是否活跃。平台服务进程自己维护 ✓。但「活跃」的一个要素是「用户在运行时进程里还有活动」——如果会话活跃性依赖运行时进程的活动心跳，那心跳算不算「会话状态写请求」？如果算，被禁；如果不算（心跳不是写请求而是查询附带的），那插件可以伪造心跳维持会话活跃？这是个边角问题。

核心问题还是：**登出路径未定义**。这是「信任输入面」表述的直接后果：写完「不接受写请求」后，必须同时说明「会话生命周期如何被合法触发」，否则实现者要么违反约束（让运行时进程转发登出）要么无法实现登出。PRD 用「基于认证事件自行维护」试图回答，但「认证事件」未定义是否包含登出，以及登出请求的入口进程未指定。

我认为这是**重要**级（也可能是阻断）。它是 v2.11 新增约束的直接逻辑后果，且与已有条款（§9.4.2 会话结束立即失效、§3.3.4 停用即关闭 Agent 通道）存在张力。修法：明确「认证事件」枚举（登录、登出、超时、停用、管理员吊销），并指明这些事件的入口直接在平台服务进程（不经过运行时进程）。

等等，还有「账号停用→Agent 通道立即关闭」（§3.3.4）。停用操作由所有者/搭建者经身份层端点执行（平台服务进程）→平台服务进程自己会话状态更新→令牌撤销。这条链不经过运行时进程 ✓。所以停用 OK。

登出是唯一有问题的。还有超时：平台服务进程自行判定 ✓。

所以最小修复：声明登录/登出端点归属平台服务进程（或等价机制）。**重要**级。

另外任务问「这条约束是否与『会话结束立即失效』要求冲突？」——如果登出无法传导，就冲突。但按善意解读（登出端点在平台服务进程），不冲突。PRD 没写明，所以是「模糊」而非「冲突」。重要级，修法是写明。

## 任务 4：v2.11 是否又引入新的过度承诺？

§4.6.5 的部署基线限定：
> **部署基线限定（v2.11 新增）** | 上述边界**在以下基线下成立**：两进程**分属不同容器或不同系统用户**；**禁止跨进程调试**；**无共享可写文件系统**；两进程间接口**有调用方鉴别**。**基线之外的部署不属于本节的保证范围**

这些是产品能保证的，还是部署方要遵守的？

- 「两进程分属不同容器或不同系统用户」：这可以由交付包（Docker 骨架）保证——阶段一验收锚点 ⑥ 已要求「Docker 骨架中平台服务进程与 Agent 运行时进程分离」。所以产品交付的默认部署满足这条 ✓（产品能保证默认形态）。
- 「禁止跨进程调试」：部署方可以在自己的主机上对任何进程 ptrace——产品无法强制。这是部署方纪律。产品能做的是默认配置不开启调试，但无法阻止部署方开启。
- 「无共享可写文件系统」：Docker 骨架可以保证默认不挂载共享卷 ✓（产品默认），但部署方可以改挂载。
- 「接口有调用方鉴别」：产品设计可以保证 ✓。

所以四条基线里，部分是产品交付形态可保证的（默认配置），部分是部署方必须维持的（不绕过默认）。PRD 写「基线之外的部署不属于本节的保证范围」——这个写法本身是诚实的：它把保证限定在基线内。

但问题是：**部署方是否有途径知道这些基线？** 这些基线写在 PRD 里，而 PRD 是内部文档。部署方拿到的是交付包+操作手册（§7.1 阶段七交付物：操作手册）。如果操作手册不写这些基线，部署方可能会破坏基线（比如为了方便调试挂载共享卷、开启远程调试），从而使安全保证失效而不自知。

这算不算 PRD 的问题？PRD 的阶段七验收锚点 ② 要求「操作手册覆盖所有者/搭建者/员工三种角色的完整流程」——没提部署基线的告知。嗯，这是一个可指出的点：**部署基线（§4.6.5）是安全保证的成立条件，但没有任何条款要求把这些基线写入交付物（操作手册/部署文档）告知部署方**。建议级或重要级。

考虑到 §7.4.4 已有先例（首版无灾备「必须书面告知客户」），这里缺一个同类要求。我认为算**建议**级偏重要。嗯……安全保证的成立条件未传递给部署方，这个比较实在。定为**重要**吧？还是建议？

让我用「如果不修会怎样」来测试：部署方违反基线→两进程隔离失效→插件可触及私钥→回到 v2.9 威胁。但部署方在信任边界内（§4.1.1 二：实例所有者与基础设施管理员不防御）！等等——部署方/基础设施管理员本来就在信任边界内，他们做什么都防不住。那「部署基线」防的是谁？防的是「无意破坏」而非「恶意部署方」。恶意部署方本来就防不住（自托管固有性质）。所以基线的意义是「善意的部署方不要无意破坏隔离」——那就必须告知。不告知→善意部署方可能无意破坏→保证失效且无人知情。

这与「所有者批准插件时须如实告知放弃项」（§9.6.2，kimi-k3 重要 5 修复的）是同一原则：**后果的知情**。所以我认为这是一条**重要**：部署基线的告知义务未纳入交付物要求（§7.1 阶段七锚点/操作手册）。修法：阶段七锚点或操作手册要求中补「部署基线与安全成立条件」。

其实等等，我再确认一下阶段七锚点原文：「② 操作手册覆盖**所有者 / 搭建者 / 员工**三种角色的完整流程」——没有部署方角色。§4.5 的交付形态有「部署包交付：对方自己部署运维」。所以部署方确实是真实角色且操作手册不覆盖。好，这条成立：**重要**。

还有其他新增断言要检查：

§4.6.5「插件可达范围（v2.11 改写）」：
> **可核验的事实**：身份判定与私钥**位于不加载插件的进程内**，只能经**受控接口**访问。
> **机制条件**：插件能否实际触及它们，由（a）两进程间接口的授权规则、（b）进程运行边界**共同决定**，**以负向测试为准**。

这个表述是诚实的（可核验事实 vs 机制条件分开）。OK。

§9.4.1 负向测试新增：
- 「插件无法为『无活跃认证会话的主体』取得令牌」——可判定？要判定这个，需要枚举「无活跃认证会话的主体」并尝试。测试方法：构造一个没有会话的主体，插件尝试取得其令牌，应失败。可判定 ✓。
- 「签名请求含主体指定字段时被拒并告警」✓ 可判定。
- 「插件通过跨进程接口尝试影响会话状态被拒」✓ 可判定（假设接口有定义）。
- 「平台服务进程不加载任何插件（可核验的启动配置）」✓ 可核验。

让我细读：§9.6.3 第 8 项说「⚠️ 加载与卸载不暴露独立产品端点（加载发生在进程启动时、卸载须免审批，见 §4.1.1 四）」。§9.11.2 说「插件的生命周期动作（动作全集）经产品接口发生，仍受本节约束」。§4.1.1 四要求「动作全集逐项必须留痕」。

如果加载/卸载没有产品端点，它们如何留痕？进程启动时加载→运行时进程自己写审计？运行时进程写审计的通道是什么？审计写入经过哪个进程？如果审计库由平台服务进程写（审计数据属 KVVI，独立于平台库），运行时进程要上报审计事件→这是运行时→平台的接口。而 §4.6.5 禁的是「会话状态与授权判定」的写请求，审计事件上报不在禁止之列（合理）。但机制未定义。

更重要的是「经产品接口发生」与「不暴露独立产品端点」的措辞张力：§9.11.2 说生命周期动作经产品接口发生，§9.6.3 说加载/卸载不暴露独立产品端点。这两个表述放在一起，字面上冲突：加载/卸载要么经产品接口（有端点），要么不经（无端点）。

善意解读：§9.11.2 的「经产品接口发生」指安装/注册/激活（有端点的三个）；加载/卸载是进程行为，由运行时记录留痕（不经业务端点但仍有审计上报通道）。但字面读就是「改一半」：§9.11.2 说全集经产品接口，§9.6.3 说其中两项无端点。

这是一个真实的表述不一致。**建议或重要？** 它影响的是审计条款的适用范围表述。修法：§9.11.2 改为「安装/注册/激活经产品接口发生；加载/卸载由运行时进程在进程行为中记录并上报」。定为**建议**级偏重要。嗯……这个其实挺实的，因为「审计留痕」的成立机制对加载/卸载是空的：谁在何时把「加载」「卸载」写进审计库？进程启动时运行时进程自检上报？如果插件已被加载，插件能否拦截这次上报？（能！插件与运行时同进程，可拦截审计写入——§5.7.3 已承认插件可拦截审计写入！）

哦这个就有意思了：**加载动作的留痕发生在加载之后**（插件加载完成后运行时进程才上报「已加载 X」），而一旦被加载，插件就可以拦截审计写入（§5.7.3 明确承认）。所以「加载」动作的审计留痕**不可信**——恶意插件可以加载后拦截/伪造自己加载的留痕！

等等，时序：进程启动→加载插件→插件代码运行→运行时上报「插件 X 已加载」到审计。如果插件在加载时即获得执行能力，它可以 hook 审计上报函数，让「加载 X」这条记录消失或篡改。所以 §4.1.1 四的「动作全集逐项必须留痕」对「加载」一项不成立——除非加载留痕由**加载前的引导代码**完成（先留痕再加载），或由平台服务进程观察（但平台服务进程无法观察运行时进程的内部加载）。

同理「卸载」：卸载的留痕在卸载前还是卸载后写？卸载前写→可信（插件还在但要被卸了，它会拦截「我要被卸载」的留痕吗？如果留痕在卸载执行前写入，插件此刻还能拦截）。卸载后写→由谁写？运行时进程还活着（其他插件或宿主代码），可以写。

所以：加载/卸载的留痕都依赖运行时进程的诚实上报，而运行时进程内含恶意插件时上报不可信。这与 §9.10.2 已承认的循环依赖（「留痕保证的是『生命周期动作经接口发生』，不是『插件运行期行为受审计约束』」）部分重叠——v2.9 的知情说明只承认「经接口发生」的留痕可信。而加载/卸载不经接口（无端点），它们的留痕恰好落入「不可信」区！

v2.11 把加载/卸载留在审计全集里（✅ 须留痕），但没有说明它们的留痕机制与可信度边界。按 v2.9 的诚实原则，这里应该有一句：「加载/卸载的留痕由运行时进程上报，以运行时进程未被同进程插件拦截为前提——该前提对已作恶插件不成立」。
