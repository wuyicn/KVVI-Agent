v2.3 仍有安全机制与术语冲突，暂不够格冻结开工。

## 阻断（必须修，否则不能开工）

### 1. Agent 专属确认可被绕过，缺少服务端可验证的确认凭证

- **位置**：§9.2、§9.6.1、§9.7.2
- **原文**：  
  §9.2：“UI 与 Agent 必须调用同一个业务命令端点。”  
  §9.6.1：“额外防护……仅对 Agent 发起的操作。”  
  §9.7.2：“执行前向用户展示完整的结构化参数，要求显式确认。”
- **问题**：文档没有定义统一端点如何可信地区分 UI 与 Agent 请求，也没有规定确认结果如何绑定到具体命令。若仅靠请求字段声明“这是 UI 操作”或“已经确认”，Agent 路径可以绕过其唯一的提示注入防护。A1 删除第一层后，显式确认已成为核心安全边界，不能只停留在交互描述。
- **建议**：规定由服务端签发一次性确认凭证，绑定用户、会话、业务系统、目标对象、完整参数摘要、到期时间及执行通道；统一命令端点对 Agent 请求强制验签、核对参数摘要并防重放。执行通道不得由模型或普通请求参数指定。

### 2. 员工“最高风险动作”没有可执行清单，L3 未真正闭环

- **位置**：§9.6.2、§9.6.4、§9.7.2
- **原文**：  
  §9.6.2 的清单只列“权限策略、工具归属、聚合口径、系统创建”。  
  §9.6.4：“员工……其中最高风险类别须所有者审批。”  
  §9.7.2：“按 §9.6.4 的清单，须所有者审批的动作执行前送审。”
- **问题**：§9.6.4 并没有“最高风险类别清单”，只有按发起人划分的规则；§9.6.2 又是搭建变更清单，不是员工业务动作清单。因此实现者无法判断哪些员工动作只需本人确认、哪些必须送所有者审批。所谓“统一到 §9.6.4”只是统一了引用位置，没有统一判定规则。
- **建议**：在 §9.6.4 明确定义员工动作风险分级及封闭清单，或明确引用承载风险等级的契约字段；同步修正 §9.7.2 的“按清单”引用。

### 3. “工具归属不可变”与“工具归属可审批变更”仍直接冲突

- **位置**：§9.1、§9.6.2、§9.6.3、§9.6.5
- **原文**：  
  §9.1：“双网关工具归属……地基。”  
  §9.6.2：“工具归属——改变工具所属网关。”  
  §9.6.3：“所有……工具归属……必须经过唯一发布通道。”  
  §9.6.5：“产品级分类……地基，不可改；启用范围……可经审批变更。”
- **问题**：L1 虽在 §9.6.5 正确拆成两层，但 §9.6.2、§9.6.3 仍沿用“改变工具归属”的旧表述，继续允许经审批修改地基。实现者仍会得到两套相反规则。
- **建议**：将 §9.6.2、§9.6.3 中的“工具归属”全部改为“同一产品级网关分类内的工具启用范围”；明确产品级分类不进入实例发布差异、也不存在审批修改路径。

### 4. 租户引用规则仍有两套互斥定义，S10 未解决

- **位置**：§9.3.1、§9.9.2
- **原文**：  
  §9.3.1：“模型生成的引用中不含租户字段”“租户来自令牌，不来自模型”。  
  §9.9.2：“所有 `target_ref` / `AssetRef` 携带……租户标识”“租户明确为引用自身携带……的字段”。
- **问题**：一处规定引用不含租户，另一处规定所有引用必须自带租户；同时 §9.3.1 说租户不作为定位依据，§9.9.2 又把引用绑租户称为定位阶段的根本保障。无法据此确定引用结构、生成方及服务端定位算法。
- **建议**：固定一种表达。较小改法是区分“模型可见的逻辑引用”和“服务端签发的不可篡改资源句柄”：前者不含租户，后者可在服务端封装租户并与令牌租户比对；明确定位始终以令牌租户为准。

### 5. 会话结束与账号停用不能按现有机制立即使令牌失效

- **位置**：§3.3.4、§9.4.2、§9.9.4
- **原文**：  
  §3.3.4：“停用……Agent 通道立即关闭。”  
  §9.4.2：“短时令牌 + 版本比对，二选一或并用”“撤销查询（可选）”。  
  §9.9.4：“随会话结束而失效。”
- **问题**：仅采用短时令牌时，已签发令牌会一直有效到期；仅比较授权版本也不能感知“会话结束”。撤销查询又被定义为可选。因此“立即关闭”和“随会话结束失效”没有必选执行路径。L9 只解决了权限版本变化的一部分。
- **建议**：对账号停用和会话结束规定强制机制，例如必须查询会话/账号撤销状态，或使用强制递增的会话版本并校验；短时有效期只能作为故障时残留窗口，不能替代立即撤销。

### 6. 发布唯一通道仍是声明，尚未达到“旁路技术不可达”

- **位置**：§9.6.3
- **原文**：“任何绕过通道的写入或部署在技术上不可达”“不得存在直接修改存储、调用内部部署接口等旁路。”
- **问题**：没有定义谁拥有已发布存储的写权限、发布服务与运行时的读写边界、内部部署接口如何鉴权，也没有相应负向测试。原 S3 要解决的正是“发布路径唯一性缺少强制机制”，当前仍主要是规范性陈述。
- **建议**：补最小强制模型：只有发布服务身份可写已发布版本；运行时和搭建服务只读；审批结果与待发布版本摘要绑定；部署端只接受发布服务签发的版本；加入直写存储、直调部署接口及篡改审批后版本的负向测试。

## 重要（应修）

### 1. 草稿归属接管缺少未指定时的结果，L6 仍只闭环一半

- **位置**：§3.3.2、§3.3.6
- **原文**：  
  §3.3.2：“草稿……所有权转移给继任者。”  
  §3.3.6：“要求为两者都指定接手人——草稿……不触发告警。”
- **问题**：虽然已区分“流程继任者”和“归属接管人”，但只规定了在途单据未指定时进入兜底挂起；没有说明草稿未指定接管人时是阻止停用、转给所有者，还是允许无主归档。孤儿草稿路径仍存在。
- **建议**：明确草稿接管失败的唯一结果，并与“不得成为孤儿数据”一致；同时将停用检查中的“全部在途单据”改为“全部未完成内容”，避免前后步骤范围不同。

### 2. L7 声称“统一为所有者手动指定”，正文仍以自动解析为第一顺位

- **位置**：§3.3.5、§10.3 Q14
- **原文**：“① 按组织关系自动解析 → ② 所有者手动指定 → ③ 兜底。”
- **问题**：若本轮修订目标确为“继任者统一由所有者手动指定”，该修改没有落实；正文及决策表仍明确坚持自动优先。若 L7 只是要统一“谁有权进行手动指定”，则修订清单表述过度，容易导致下一轮误改。
- **建议**：二选一统一：要么改正文为所有者手动指定；要么把修订说明改成“手动指定路径统一为仅所有者可操作”，保留自动解析。

### 3. A1 的保护范围只覆盖不可逆写入，未覆盖读取与信息泄露

- **位置**：§9.7.1、§9.7.2、§9.7.3
- **原文**：“即使注入成功进入上下文，也无法产生不可逆后果”“未通过只生成草稿。”
- **问题**：提示注入也可能诱导 Agent 调用读取工具、扩大查询目标或在回复中暴露高权限用户本可访问但当前没有请求的数据。读取没有“草稿”，也不属于不可逆动作，现有测试只断言“目标数据不得发生变化”，无法覆盖保密性后果。
- **建议**：明确 A1 本轮只防错误写入，不能声称完整处置提示注入；若要覆盖读取，补充敏感读取的参数展示/二次确认或结果最小化规则及泄露负向测试。

### 4. “一致性校验”与“不承诺语义等价”存在方法冲突

- **位置**：§9.7.2、§9.8.2
- **原文**：  
  §9.7.2：“校验‘当前用户消息 → 目标对象 → 动作 → 参数’是否一致；不一致则拒绝。”  
  §9.8.2：“不能证明二者语义等价”“模型如何理解用户的话是不可审计的黑箱。”
- **问题**：若“一致性”指语义一致，正文已经承认其不可可靠判定；若只指消息、会话和参数的结构绑定，则当前没有这样限定。容易重新引入已删除的“可证意图”假设。
- **建议**：把一致性校验限定为可机器判断的结构条件，例如当前消息 ID、对象引用有效性、确认凭证中的参数摘要；不得将自然语言与操作的语义等价作为放行条件。

### 5. 红线 3 的名称仍超过实际承诺边界

- **位置**：§2.5.2 红线 3、§9.8.2、§10.1
- **原文**：  
  红线 3：“操作可归责”“业务责任人（员工本人）”。  
  §9.8.2：“不能证明用户意图”“账号被盗时操作者是否为本人”不能证明。
- **问题**：A7 修订后，系统能证明的是账号、执行通道、展示参数和确认记录，不能证明自然人本人或其业务意图。“可归责到员工本人”仍可能被理解为强于实际能力的责任承诺。
- **建议**：将红线名称和正文收敛为“操作可追溯至账号与执行通道”；把业务责任归属明确为制度规则，不宣称系统能够证明自然人意图。

### 6. A6 不变量同时规定“拒绝发布”和“最高风险审批”，结果不唯一

- **位置**：§9.8.1
- **原文**：  
  “不满足则拒绝发布。”  
  “若确有此类配置需求，差异报告须标记为最高风险级别并显式警告审批人。”
- **问题**：若违反不变量必须拒绝，审批人没有可批准的对象；若最高风险审批可以放行，则它并非不变量。S5 的强制机制因此存在例外歧义。
- **建议**：首版应明确违反即拒绝，删除可审批放行表述；若后者仅描述未来版本，应明确“必须先实现防差分机制，不能由审批豁免”。

### 7. 地基不变量检查仍缺少可判定规则

- **位置**：§9.1
- **原文**：“检查产出物是否试图覆盖或修改 §9.1 表中的任一项”“格式合法的契约同样可以定义一条绕过权限校验的状态迁移。”
- **问题**：列出了检查目标，却没有定义哪些契约字段、状态迁移或组合构成“修改地基”。尤其“终态不可逆”“绕过权限校验”需要明确机器判定条件，否则双引擎只能各自实现不同解释。
- **建议**：为每项可由产出物触达的地基列出封闭不变量及错误码，并要求双引擎使用同一组正反例验证。

### 8. 密钥轮换的信任更新路径仍未闭合

- **位置**：§9.4.1
- **原文**：“业务系统配置身份层公钥（或其指纹）”“轮换须支持双密钥并行期。”
- **问题**：没有说明业务系统如何可信获得新公钥、谁有权更新信任锚点，以及旧密钥泄露时为何还能等待“无在途令牌”。普通轮换和应急吊销被混在一起。
- **建议**：区分计划轮换与密钥泄露应急吊销；明确新公钥的认证分发路径和授权主体。泄露场景不得等待旧令牌自然结束。

### 9. “关联账号”没有定义，S7 的间接自授权无法验收

- **位置**：§9.6.7
- **原文**：“不得将自己或关联账号纳入配置范围。”
- **问题**：“关联账号”没有身份映射或判定标准，测试无法确定哪些账号应被拦截。搭建者也可能通过角色、用户组或组织范围间接获得权限，而不直接把自己的账号加入。
- **建议**：改为基于最终权限展开结果检查：任何由搭建者发起的变更，只要会扩大其本人有效业务权限，就拒绝或转交所有者审批；不要依赖未定义的“关联账号”概念。

## 建议（可选）

### 1. 修正两处失效的交叉引用

- **位置**：§9.8.1、§10.4
- **原文**：  
  §9.8.1：“纳入发布通道……见 §9.6.4。”  
  §10.4：“A1–A8……总览见 §9.10。”
- **问题**：发布唯一通道实际在 §9.6.3；A1–A8 的状态总览实际在 §9.11，§9.10 是运行与运维安全。
- **建议**：分别改为 §9.6.3、§9.11。

### 2. 统一“确认”“审批”“发布”三个术语的对象

- **位置**：§9.6、§9.7
- **原文**：搭建变更、员工业务动作均混用“确认”“审批”，但承担者和生效点不同。
- **问题**：容易把员工本人确认、所有者批准、发布通道生效实现成同一种状态。
- **建议**：固定为“用户确认业务命令—所有者批准高风险事项—发布服务使系统定义生效”三种独立事件，并分别定义审计字段。

我逐项检查了 L1–L9、L11、S1–S8、S10–S12，并检查了 §9.1–§9.11 的连续编号及正文交叉引用。

以下修订在所给文本中未发现实质问题：

- **L2**：Q9 已明确把个人粒度、扩大数据范围、放宽字段可见性排除在免审批之外，与 §9.6 基本一致。
- **L4**：§6.2 已收敛为取源、构建、启动和初步品牌替换，不再声称路线 A 产品化完成。
- **L5**：§2.6 已将工作模式会话绑定业务系统，并规定新建会话才能变更。
- **L8/L11**：§9.9.1、§9.9.3 已删除“切换即废止/引用不可能出现”的过度表述，承认复制、缓存和跨会话引用风险。
- **S1**：§9.7 已删除无法强制的“阻止注入进入上下文”第一层。
- **S6**：基础校验与 Agent 额外防护的概念分层本身与红线 1 可以并存；问题在于额外防护缺少可信执行凭证，而不是分层原则错误。
- **S8/S11**：§9.10 已覆盖模型数据流出、配额、配置和审计防篡改；审计存储至少给出了追加写、哈希链或 WORM 的明确要求。

- **A7 与红线 3**：两者不必天然矛盾；只要把红线 3 收敛为账号级可追溯，而非自然人意图证明，即可自洽。
- **依赖外部资料，无法核实**：DSH 实测情况、KVVI-Builder 契约是否已锁定、13 份 Meta-Schema 与双引擎测试结果、MIT/品牌规范原文。

结论：阶段一的取源和工程骨架可以先做，但涉及身份、发布、令牌及 Agent 执行的安全契约尚不能冻结；若“不再改动”，这份 PRD 不宜直接作为完整产品的开工基线。
