总体判断：v2.3 对 S1–S12 的修订大部分真实落地，但“发布唯一通道”与“扩展通道插件安全”仍未闭环，且 UI 路径确认缺口等新问题需修复。

## 阻断（必须修，否则不能开工）

### 1. 独立部署下“发布唯一通道”无法强制，缺少配置发布签名/审批绑定
- **位置**：§9.6.3、§4.1
- **原文**：§9.6.3“唯一通道：上述变更只能通过发布通道生效；任何绕过通道的写入或部署在技术上不可达”；§4.1 业务系统独立部署，Agent 通过接口契约操作，不碰数据库。
- **问题**：业务系统是独立部署的，其权限策略配置存储或部署接口位于客户环境。§9.6.3 只声明“技术不可达”，但未定义业务系统如何验证配置来自已审批的发布通道。§9.4.1 只解决身份令牌签名，没有解决“配置发布”的签名或审批状态绑定。任何能直接接触业务系统配置存储、部署 API 或运维入口的人（客户管理员、入侵者）都可以绕过发布通道直接修改策略。独立部署下“绕过通道技术上不可达”不成立。
- **建议**：为配置发布增加签名或审批状态绑定；业务系统运行时只接受带有效发布签名/审批标识的配置更新；明确发布通道与业务系统的部署边界及密钥管理，否则审批形同虚设。

### 2. 扩展通道插件/动态插件无安全控制，可绕过权限与地基
- **位置**：§5.7.1、§5.7.3、§9.5.2
- **原文**：§5.7.1“运行时动态插件：临时实验（注册路由、Service、UI），仅进程内存”；§5.7.3“可扩展不等于可改地基”；§9.5.2“凭搭建权限获得生产业务数据访问权”明确不可以。
- **问题**：动态插件可在 KVVI 运行时进程内注册 Service、HTTP 路由或 UI，与工作模式共享运行时。若搭建者可以使用该通道，则可在进程内执行代码、直接访问业务数据或注册额外接口，绕过 §9.2 的唯一策略执行点、§9.6 的发布通道和红线 4。§9.1 的地基不变量检查只针对 MetaSchema 产出物，不检查插件代码，因此该攻击面未被覆盖。
- **建议**：将插件安装/注册纳入权限控制，仅所有者可批准；运行时动态插件默认禁用或在安全环境部署；插件注册行为审计留痕；禁止搭建者通过扩展通道访问业务数据面。

## 重要（应修）

### 1. UI 路径缺少不可逆操作确认，可能导致 Agent 防护被绕过
- **位置**：§9.6.1
- **原文**：§9.6.1“额外防护：仅对 Agent 发起的操作：否（UI 用户正常操作不受此层影响）”。
- **问题**：UI 用户直接执行不可逆操作（如批量删除）不经过 Agent 路径的执行前确认与审批，攻击者可通过 UI 路径（如社会工程、CSRF、被盗会话）绕过 §9.7 的注入防护。这与红线 1 精神相悖：UI 已成为更低的防护门槛。
- **建议**：明确 UI 路径对不可逆操作也必须具备等价的确认或审批机制；至少规定不可逆操作在 UI 上须二次确认并留痕，避免“额外防护仅对 Agent”造成安全不对称。

### 2. 未禁止搭建者配置同伙，预授权可放大绕过风险
- **位置**：§9.6.7、§9.6.4
- **原文**：§9.6.7“不得将自己或关联账号纳入配置范围”；§9.6.4“可以预先授权……给搭建者预先授予某类变更的权限”。
- **问题**：§9.6.7 只禁止配置“自己或关联账号”，未定义“关联账号”，也未禁止配置同伙把其数据范围扩大为“公司全部”。若所有者给搭建者预授权“配置员工业务权限”且范围过大，搭建者可绕过逐笔审批配置同伙，造成数据越权。
- **建议**：明确所有扩大数据范围档位或放宽字段可见性的变更必须逐笔审批，不得通过预授权自动放行；定义“关联账号”判定规则。

### 3. 执行前确认界面缺乏防呆设计，用户疲劳可削弱 A1 防护
- **位置**：§9.7.2
- **原文**：“显式确认：执行前向用户展示完整的结构化参数（目标对象、动作、字段、原值 → 新值），要求显式确认”。
- **问题**：未规定确认界面的防呆要求。用户可能习惯性点“确认”，尤其当操作数量多、参数复杂时，确认疲劳会使防线失效。这直接影响 A1 的实际防护效果。
- **建议**：对高风险动作强制二次确认、默认拒绝、禁止“全部同意”按钮；批量操作逐条展示；确认界面设计需通过可用性测试。

### 4. 租户标识在引用中的表述不一致，可能导致实现混淆
- **位置**：§9.3.1、§9.9.2
- **原文**：§9.3.1“租户标识不进入工具参数……模型生成的引用中不含租户字段”；§9.9.2“所有 target_ref / AssetRef 携带不可由模型修改的租户标识”。
- **问题**：两处表述有潜在冲突：§9.3.1 说引用不含租户字段，§9.9.2 说引用携带不可由模型修改的租户标识。实现者会困惑租户标识究竟存储在引用中还是仅由服务端注入。这影响跨租户防御的实现正确性。
- **建议**：统一措辞为“模型生成的引用不承载可被模型控制的租户字段；任何租户标识仅由服务端在生成/验证时注入，定位时以令牌导出租户为准，引用中出现的租户信息只用于比对”。

### 5. 模型数据流出脱敏机制未落地，自带 Key 模式下更难强制
- **位置**：§9.10.1
- **原文**：“发送前最小化与脱敏：只发送完成任务所需字段；敏感字段按策略脱敏。”
- **问题**：未说明脱敏由哪个组件、在哪个环节执行。若由 Agent 运行时组装上下文，则必须依据 FieldPolicy 或脱敏策略执行，但 PRD 没有规定该执行点。结合 §3.2“每人自带 Key”模式，员工可自由选择模型服务，组织策略更难强制。
- **建议**：明确脱敏执行点在组装 LLM 上下文前，必须以 FieldPolicy/脱敏策略为准；自带 Key 模式下该策略仍强制，模型路由须经组织批准。

## 建议（可选）

1. **审计日志读权限归属**：§9.10.2 只说读权限独立于搭建权限，未说明授予谁，建议明确审计读权限授予所有者或独立审计角色，否则审计功能无法使用。
2. **私钥轮换责任方**：§9.4.1 规定轮换流程但未明确私有化交付下由谁执行，建议在部署说明中标注责任方。
3. **模型路由与自带 Key 的关系**：§3.2 与 §9.10.1 存在张力，建议细化组织策略如何覆盖自带 Key 场景，避免数据经个人凭据流出到未经批准的模型服务。
