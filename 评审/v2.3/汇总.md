## 三、两份评审独立发现的同一问题

### ★ 租户标识表述自相矛盾（两份评审均列出）

| 位置 | 原文 |
|---|---|
| §9.3.1 | 「模型生成的引用中**不含租户字段**」「租户来自令牌，不来自模型」 |
| §9.9.2 | 「所有 `target_ref` / `AssetRef` **携带**……租户标识」 |

**这是 v2.3 新增 §9.3.1 时引入的新矛盾**——为解决 S10 而写的规则，与 §9.9.2 冲突。

**修法（两份评审一致）**：区分两层——
- **模型可见的逻辑引用**：不含租户字段
- **服务端签发的资源句柄**：由服务端封装租户，定位时以**令牌租户**为准
- 引用中出现的租户信息**只用于比对**，不作定位依据

## 四、逻辑复评的其他发现

### 阻断级

| # | 问题 | 核心 |
|---|---|---|
| **L3-1** | **Agent 专属确认缺服务端可验证凭证** | A1 删掉第一层后，显式确认成为**核心安全边界**，但未定义「统一端点如何可信区分 UI 与 Agent 请求」「确认结果如何绑定到具体命令」。若只靠请求字段声明，**Agent 可绕过其唯一的注入防护** |
| **L3-2** | **员工「最高风险动作」无可执行清单** | §9.6.4 只有按发起人划分的规则，**没有清单**；§9.6.2 是搭建变更清单。L3 只统一了引用位置，没统一判定规则 |
| **L3-3** | **工具归属仍冲突（改了一半）** | §9.6.5 已正确拆两层，但 §9.6.2/§9.6.3 **仍用旧表述「改变工具所属网关」** |
| **L3-4** | 租户引用两套互斥定义 | 见上 |
| **L3-5** | **令牌不能按现有机制立即失效** | §3.3.4 说「停用立即关闭 Agent 通道」，但 §9.4.2 的撤销查询是**可选**，短时令牌也不能感知「会话结束」 |
| **L3-6** | **发布唯一通道仍是声明** | 未定义谁拥有存储写权限、发布服务与运行时的读写边界、内部部署接口如何鉴权 |

### 重要级

- **草稿未指定接管人时的结果未定义**——L6 只闭环一半，孤儿草稿路径仍在
- **L7 我改错了方向**——我统一成「所有者手动指定」，但原问题只是「统一**谁有权**手动指定」；正文仍坚持自动优先
- **A1 只覆盖不可逆写入，未覆盖读取与信息泄露**——注入可诱导读取工具或扩大查询目标
- **「一致性校验」与「不承诺语义等价」方法冲突**——若指语义一致则已承认不可判定
- **红线 3 名称超过承诺边界**——A7 修订后应改为「可追溯至账号与执行通道」
- **A6 不变量同时说「拒绝发布」与「最高风险审批」**，结果不唯一
- **地基不变量检查缺可判定规则**——「终态不可逆」等需要机器判定条件
- **密钥轮换的信任更新路径未闭合**——如何可信获得新公钥、泄露场景不能等待
- **「关联账号」未定义**——S7 的间接自授权无法验收

## 五、安全审查的其他发现

### 阻断级

| # | 问题 | 核心 |
|---|---|---|
| **S3-1** | 独立部署下「发布唯一通道」**无法强制** | 业务系统在客户环境，配置存储与部署接口在其侧。**任何能接触该环境的人可绕过通道**。「绕过技术上不可达」在独立部署下不成立，需**为配置发布增加签名/审批状态绑定** |
| **S3-2** | ★ **扩展通道（插件）本身是攻击面** | §5.7 把四条扩展通道作为**能力**写入，但**从未作为威胁考虑**。动态插件可在运行时进程内注册 Service / HTTP 路由 / UI，与工作模式共享运行时——**可绕过 §9.2 唯一执行点、§9.6 发布通道与红线 4**。§9.1 的地基检查只针对 MetaSchema 产出物，**不检查插件代码** |

> **S3-2 是三轮评审中第一次出现的「我自己列出的特性变成了攻击面」。**
> 我在 §5.7 写「一切皆插件」时，只看到扩展能力，没看到它同时是一条**代码执行通道**。

### 重要级

- **UI 路径缺不可逆操作确认**——§9.6.1 说「额外防护仅对 Agent」，导致 **UI 反而比 Agent 门槛更低**，攻击者可走 UI 路径绕过
- **未禁止搭建者配置同伙** + 预授权可放大绕过风险
- **执行前确认缺防呆设计**——用户疲劳（习惯性点确认）会削弱 A1 防护
- **模型数据流出脱敏未落执行点**——未说明由哪个组件在哪个环节执行；自带 Key 模式下更难强制

### 安全审查的收敛信号

> 「未发现新的可执行攻击路径方面：**无证据表明本 PRD 存在未覆盖的提示注入注入器问题**，
> 除已列出的扩展通道与发布通道缺口外。」

**三轮下来，安全评审开始收敛。**

## 六、三轮评审的趋势（重要判断）

| 轮次 | 发现的性质 | 典型问题 |
|---|---|---|
| 第 1 轮 | **设计空洞** | 无人力假设、规则变更未定义、注入、越权 |
| 第 2 轮 | **声明 vs 机制** | 「写了但要实现时无路可走」 |
| **第 3 轮** | **实现级细节** | 签名、凭证、防呆设计、脱敏执行点、判定规则 |

**第 3 轮的诉求已经大量超出 PRD 的合理精度。**

本轮发现中，相当一部分是**实现规范**而非**产品需求**：

| 第 3 轮的要求 | 它实际属于 |
|---|---|
| 确认凭证如何签发与验签 | 技术设计 |
| 发布服务与运行时的读写边界 | 技术设计 |
| 确认界面的防呆设计 | 交互设计 |
| 地基不变量的机器判定条件与错误码 | 技术设计 |
| 脱敏的执行点与组件 | 技术设计 |
| 密钥轮换的信任更新路径 | 技术设计 |

**继续在 PRD 里写这些，会把它变成一份低质量的技术设计文档**——
PRD 的价值是**定义做什么与不做什么**，不是定义签名算法的字段集。

## 七、处理建议

### 建议：PRD 到此冻结，实现级要求另立文档

| 项 | 处置 |
|---|---|
| **租户标识矛盾**（两份评审共同发现） | ✅ **必须修**——这是真矛盾，改动小 |
| **L3-3 工具归属残留旧表述** | ✅ **必须修**——改动小 |
| **L3-2 员工风险清单缺失** | ✅ **必须修**——补一份封闭清单 |
| **S3-2 扩展通道安全** | ✅ **必须修**——这是**设计级**遗漏，不是实现细节 |
| **L3-5 令牌立即失效** | ✅ 修——把撤销查询从「可选」改为**账号停用/会话结束时必选** |
| **红线 3 名称收敛** | ✅ 修——一句话 |
| **A6 结果唯一化** | ✅ 修——删掉「最高风险审批可放行」 |
| **L7 改错方向** | ✅ 修——改回「自动优先，手动指定仅所有者可操作」 |
| 确认凭证、发布签名、防呆设计、判定规则、脱敏执行点、密钥轮换路径 | ⏭ **转入《技术设计文档》** |

### 理由

1. **前 3 项 + S3-2 + 红线 3** 是**真问题**，且改动小，应修。
2. **技术设计类要求**若继续塞进 PRD：
   - 会稀释产品文档的可读性；
   - 会让「冻结」变得不可能——每轮复评都会提出新的实现细节；
   - 而这些细节**本来就应该由实现者在技术设计中决定**，PRD 只需提出**约束与目标**。

3. **三轮评审已证明方法有效**：第 1 轮找出设计空洞，第 2 轮找出「声明 vs 机制」，
   第 3 轮开始收敛到实现细节。**这是收敛的信号，不是失败的信号。**
