让我仔细审读这份 PRD v2.10，作为第十轮独立评审人。任务是尽力证伪 v2.10，判定标准加严为「零阻断 + 零重要」。

任务要点：
1. 两进程划分是否真的关掉了两条路径（签名预言机 + 会话状态篡改）？
2. 有没有新的「改一半」？
3. 是否引入新的过度承诺？
4. 负向测试是否可判定？
5. 产品级判断：信任形状是否在 §10.1、§0.11、§9.4.1 三处如实且一致表达。

让我逐条分析。

### 1. 两进程划分是否关掉了两条路径？

v2.10 的修法：
- 平台服务进程（身份层：会话状态、授权判定、签名模块、发布通道）不加载插件
- Agent 运行时进程（Agent Loop、Skill、插件宿主）加载插件
- 签名接口只为当前已认证会话签发；令牌声明全部由平台服务进程从服务端会话状态导出，调用方不得指定；请求含主体指定字段即拒绝并告警。

问题 (a)：插件在 Agent 运行时进程内，能否影响平台服务进程的会话状态？

关键问题：**会话状态在哪里维护？** §4.6.1 说平台数据包含「账号、会话（含会话绑定的公司与业务系统）、授权版本、撤销状态、发布记录与契约包版本」，存放在平台库。平台服务进程负责平台库访问。

但是——**会话操作本身来自哪里？** Agent 运行时进程处理用户消息。会话的创建、消息的追加、会话状态的更新（比如会话结束、公司选定）这些操作，是 Agent 运行时进程在做，还是平台服务进程在做？

§4.1 架构图：
- 平台服务进程：身份层：会话状态、授权判定、签名模块、发布通道
- Agent 运行时进程：Agent Loop、**会话持久化**、模型路由、工具与 Skill 注册、模式开关、系统分区、插件宿主

注意！架构图里 Agent 运行时进程包含「**会话持久化**」！这与平台服务进程的「会话状态」是什么关系？如果「会话持久化」（会话消息记录、上下文）在 Agent 运行时进程，而「会话状态」（认证状态、绑定公司、授权版本）在平台服务进程，那么两者之间有接口。

这里有一个潜在的攻击路径：插件在 Agent 运行时进程内，它是进程内任意代码。它可以：
1. 直接调用两进程之间的受控接口（如果接口只按进程身份鉴权，插件与运行时同进程，插件可以借用运行时的身份/凭据调用平台服务进程的任何接口）。
2. 篡改 Agent 运行时进程内的会话持久化数据，或者篡改运行时发送给平台服务进程的请求内容。

关键问题：**两进程之间的「受控接口」如何鉴权？** PRD 在 §4.6.5 只写了「接口受控：两进程之间为受控接口；签名接口的授权规则见 §9.4.1 ②」。§9.4.1 ② 定义了签名接口的授权规则（只为当前已认证会话签发、声明不得由调用方指定、越界即拒绝）。

但是：
- 「当前会话」由谁判定？§9.4.1 ② 说「签名进程只为平台服务进程中已认证的会话签发」。那么会话的认证状态在平台服务进程内。Agent 运行时进程请求签名时，必须传递某种会话标识（session id 或者已有的会话凭证）。插件能否伪造或窃取另一个会话的标识？
  - 如果会话标识是可预测的或者可被插件从运行时进程内读取（插件是进程内任意代码，可以读取运行时进程内存中的所有会话标识），那么插件可以**为当前主机上另一个活跃会话请求签名**——即「借他人会话」。
  - 但这个攻击的含义是什么？插件借会话 B（属于员工乙）的标识请求签名，得到的是绑定会话 B 的令牌——即插件可以以员工乙的身份操作业务系统。这是否违反「插件无法取得非当前会话主体的令牌」？严格说，「当前会话」是哪个会话？插件自己没有会话。测试如何模拟「插件请求他人令牌」？如果插件窃取同进程内另一个活跃会话的标识并请求签名，签名进程会认为「这是会话 B 的请求」，签发绑定会话 B 的令牌。插件于是取得了「非自己会话主体」（插件根本没有会话）的令牌。
  
  这个攻击是否成立取决于「受控接口」如何鉴别「请求来自哪个会话」。PRD 没有定义。PRD 只说「不接受请求方声称的身份」——但请求必须携带某种会话标识，否则签名进程不知道为哪个会话签发。如果会话标识本身可以被插件获取（同进程内存），那么「当前会话」判定对插件不成立。

  不过，等等——需要评估这在威胁模型中的严重性。插件已经是 TCB，它本来就可以：在 Agent 运行时进程内拦截用户乙的请求、篡改参数、直接调用业务系统（带着运行时持有的令牌）。插件想以乙的身份操作，本来就可以在乙的会话消息流里注入工具调用（它控制工具执行路径）。所以「插件窃取会话标识请求签名」相比「插件直接劫持运行时对业务系统的调用」并没有新增能力——插件作为运行时进程的 TCB，本来就能以任何活跃用户的名义行动（通过劫持该用户的会话处理流程）。

  但是！v2.10 声称的负向测试是「插件无法取得非当前会话主体的令牌」。如果「当前会话」判定依赖会话标识传递，而插件能窃取任意活跃会话标识，则这个负向测试的断言**不成立**——插件可以取得任意活跃会话主体的令牌。不过细想：插件能借会话 B 的标识取得令牌，这个令牌绑定会话 B（用户乙、公司、业务系统、授权版本）。插件拿着这个令牌可以直接调用业务系统，绕过了……嗯，本来插件就可以这么做（通过运行时）。

  真正的威胁是什么？v2.10 想消除的威胁是「插件取得任意主体的令牌」（包括不在线的用户、其他公司的用户）。如果签名进程只为「平台服务进程中已认证的会话」签发，那么插件最多只能取得**当前活跃会话**主体的令牌。非活跃会话的用户（比如已下班的员工丙），插件无法为其取得令牌——除非插件能伪造会话。插件能伪造会话吗？会话创建是平台服务进程的职责（认证在平台服务进程）。插件要创建会话，需要调用认证接口——需要用户凭据。插件没有用户凭据（密码不经过插件）。所以插件不能凭空创建会话。

  所以两进程划分后的真实保证是：**插件能冒用的主体范围 = 当前有活跃会话的用户集合**，而不是「任意主体」。这比 v2.9 好（v2.9 是任意主体），但比 v2.10 声称的弱吗？v2.10 声称的是「插件无法取得非当前会话主体的令牌」。问题：哪个是「当前会话」？对一个插件来说，没有「当前会话」。这个负向测试的语义其实是：「插件无法取得非**活跃**会话主体的令牌」或者「插件无法为不在线的主体取得令牌」。

  嗯，这里要小心。让我重读 §9.4.1 ②：
  - 「请求主体：签名进程只为平台服务进程中已认证的会话签发；不接受请求方声称的身份」
  - 「令牌声明来源：actor/role/tenant/授权版本/业务系统全部由平台服务进程从服务端会话状态导出；调用方不得指定」
  - 「请求内容：调用方只能请求『为当前会话签发令牌』，不能请求『为某主体签发某声明』」
  - 「越界即拒绝：请求含任何主体指定字段即拒绝，并告警」
  - 「可测性：因此负向测试是可判定的：『插件无法取得非当前会话主体的令牌』」

  关键模糊点：「当前会话」的判定机制未定义。调用方（Agent 运行时进程）请求签名时，必须标识「哪个会话」。这个标识如何传递、如何防伪，PRD 没有定义。如果实现是「运行时进程传递 session_id，签名进程查会话状态」，那么：
  - 插件（同进程任意代码）可以读取运行时进程内存中的所有 session_id，然后以运行时的身份（同一连接、同一进程凭据）为任意活跃 session_id 请求签名。
  - 结果：插件取得任意活跃用户（包括其他公司、高权限的所有者，只要其会话活跃）的令牌。
  
  这是否违反「插件无法取得非当前会话主体的令牌」？字面上：插件请求的不是「当前会话」（插件无会话），而是「会话 B」。所以插件**能**取得非其会话主体的令牌。负向测试的断言为假。

  但是，测试如何实施？「测试环境如何模拟插件请求他人令牌」——这正是任务问题 4。如果 PRD 没有定义会话标识的防伪机制，那么这个测试无法判定通过/失败，取决于实现。

  这是一个真实的漏洞还是实现细节？PRD 的边界是「怎么做属技术设计文档」。但这里的问题是：**产品级安全属性未定义**——「当前会话」的判定依据（会话标识的保密性/不可伪造性要求）是产品安全属性，就像 v2.6 判定「链接签名属性属产品级」一样。PRD 在 §3.5.1 为先例写明了链接签名的最小安全属性（签发主体、非对称、防重放等）。同样，签名接口的「会话标识防伪」属产品级安全属性，没有它，「插件无法取得非当前会话主体的令牌」不可测。

  不过，我得再想想这个攻击的实际增量。插件是 TCB，同进程内它已经可以：
  - 拦截、篡改任何用户会话的消息流和工具调用
  - 在用户的会话里注入操作（以该用户身份，经执行点）
  - 直接读取运行时持有的令牌（运行时调用业务系统时必然持有令牌！）
  
  等等，最后一点很重要：**Agent 运行时进程调用业务系统时必须持有委派令牌**。令牌由平台服务进程签发后交给运行时进程使用。插件在运行时进程内，可以读取这些令牌。所以插件本来就能拿到任何活跃用户（其会话正被运行时处理）的令牌！两进程划分根本没有阻止这一点——它阻止的只是插件**直接读私钥**和**篡改会话状态**。

  那么 v2.10 的两进程划分带来的真实安全增量是什么？
  1. 插件不能读私钥 → 不能**自己签发**任意主体令牌（离线、批量、长期有效、任意声明）。
  2. 插件不能篡改服务端会话状态 → 不能提升自己的会话权限（比如把会话绑定的公司改掉、把授权版本改掉）。
  3. 插件不能为非活跃用户取得令牌。
  
  但插件仍然能：
  - 窃取运行时进程内存中任何活跃会话的已签发令牌（短期有效，≤5分钟）。
  - 以任何活跃用户的身份发起操作（劫持会话处理流程）。
  
  这是「进程隔离」的固有边界：你把插件和运行时放一起，插件就继承了运行时的一切能力。v2.10 把身份判定和签名移出去了，这是实质改进。但 v2.10 是否如实声明了「插件仍可窃取活跃会话的短时令牌、仍可劫持活跃会话」？

  让我检查 PRD 是否如实表达了这一点。§4.6.5：「插件可达范围：插件仅能触及本进程内的资源；不能触及身份判定与私钥」。这句话字面上成立——活跃会话的令牌就在本进程内，插件能触及；身份判定与私钥不在本进程，插件不能触及。但这句话没有告诉读者「插件能触及本进程内的所有活跃会话令牌」这个重要的剩余风险。

  §10.1 红线 3 第二段：「插件运行期的业务操作 ❌ 不覆盖。插件不经执行点、无调用埋点，且 §5.7.3 已承认它可拦截审计写入。这些操作不在追溯保证内」——这已经承认了插件可以做任意业务操作且不被审计。所以「插件以活跃用户身份操作」其实已经被红线 3 的放弃段覆盖了吗？部分是：红线 3 第二段承认插件运行期业务操作不在追溯保证内。但两进程划分声称保护的「令牌信任体系」呢？§9.4.1 说「令牌体系例外：§9.4 令牌体系不在『插件可影响』之列——两进程划分把身份判定与签名移出了插件的可达范围（构造性，非自律）」。

  注意 §9.2 范围声明末尾的这段（v2.10 新增）：「⚠️ 令牌体系例外（v2.10）：§9.4 令牌体系不在「插件可影响」之列——§9.4.1 的两进程划分把身份判定与签名移出了插件的可达范围（构造性，非自律）。但该例外的成立以隔离被实现为前提；若隔离未落地，§9.4 立即回到本节的连带范围内。」

  这句话说「身份判定与签名移出了插件的可达范围」。字面成立（身份判定与签名确实移出去了）。但「令牌体系不在插件可影响之列」作为整体断言是否过强？插件仍然可以：
  - 窃取活跃会话令牌（令牌本身在运行时进程内流通）。
  - 用窃取的令牌以该用户身份调用业务系统（不经过执行点，直接 HTTP 调用业务系统）。业务系统验签通过、令牌有效、审计记录的是该用户的操作——**这就是 v2.8/v2.9 所说的「验签通过、审计完美、不可检测」的残留形式**！只是范围从「任意主体」缩小到「活跃会话主体 + 5分钟窗口」。

  这是一个关键的如实性问题：v2.10 是否承认了这个残留路径？让我搜索……§9.4.1 的修法部分说「插件在进程内可做的一切，都不能触及身份判定与私钥——这是构造性的」。没有提及「插件可窃取运行时进程内流通的活跃会话令牌」。

  评估其严重性：
  - 威胁从「任意主体、任意声明、不可检测」缩小到「活跃会话主体、短时窗口、声明受限于会话状态」。这是实质改进。
  - 但「不可检测」部分仍然成立：插件用窃取的令牌直接调用业务系统，业务系统侧审计记录「用户乙在公司X执行了操作」——验签通过、审计完美。唯一的区别是这个操作的源 IP/通道可能不是正常的 Agent 通道？不，插件可以直接从运行时进程发起，看起来和正常调用一样。
  - 等等，令牌绑定「唯一请求标识」和会话。插件用窃取令牌调用，审计会记录会话 B 的通道。所以审计看起来完全正常。

  所以残留威胁：**插件可冒用任何活跃会话主体的身份，在令牌有效期内（≤5分钟）以该主体操作业务系统，验签通过、审计完美、不可检测**。

  两进程划分没有消除这个，而且**原则上无法消除**——因为运行时进程必须持有令牌才能调用业务系统，而插件与运行时同进程。这是「插件在运行时进程内」的固有后果。除非：令牌绑定到运行时进程的某个插件不可提取的密钥（如 mTLS 客户端证书存于插件不可读的内存区——但插件是进程内任意代码，没有这种东西）。或者运行时本身不持令牌、由平台服务进程代理调用业务系统（但那样业务系统调用也要过平台服务进程，架构大改）。

  所以诚实的表述应该是：「两进程划分把插件可冒用的主体从『任意主体（含离线主体、跨公司）』收窄为『当前活跃会话的主体』，时间窗收窄为令牌有效期。插件窃取活跃会话短时令牌的路径**仍然存在，且属插件在运行时进程内的固有性质**——与插件可拦截审计、可绕过执行点同级，属 TCB 既有语义。」

  v2.10 没有写这句。§9.4.1 的表述「§9.4 令牌体系不在插件可影响之列」（§9.2 范围声明）**过强**——插件可以影响令牌体系的使用面（窃取并使用活跃令牌），只是不能影响签发面与判定面。

  这是否构成「重要」级问题？按加严标准（零阻断+零重要），需要判定这是阻断还是重要。

  让我再想想。这个残留路径是否使 v2.10 的负向测试「插件无法取得非当前会话主体的令牌」为假？
  - 如果「取得」包括「窃取运行时内存中已签发的令牌」，那么插件**能**取得非……等等，「当前会话」是谁的会话？对插件而言没有当前会话。如果负向测试的语义是「插件进程外的测试插件尝试取得任意指定主体（如管理员、其他公司员工）的令牌」，那么：
    - 若该主体无活跃会话：插件无法取得（两进程划分挡住了）。✓
    - 若该主体有活跃会话：插件可以窃取（从运行时内存）或借其 session_id 请求新签名（若接口允许按 session_id 签发）。✗
  - 所以这个测试的判定取决于「当前会话」的定义与测试时该主体是否有活跃会话。PRD 没有定义清楚。

  另外，测试还依赖「会话标识防伪」机制（session_id 是否足以请求签名）。如果签名接口的实现是「运行时进程与签名进程之间有进程级认证（如 mTLS），请求携带 session_id」，那么插件借运行时进程身份（同进程，可用其证书）为任意活跃 session_id 请求签名——完全可行。这意味着「签名接口只为当前已认证会话签发」对插件的约束力=「插件可为任何活跃会话取得令牌」。

  嗯，但是等一下，我需要公平一点：插件为活跃会话取得令牌 vs 插件直接在运行时会话流程里注入操作，前者不比后者强。插件已经可以以任何活跃用户身份做任何事情（它是运行时 TCB）。所以「插件窃取活跃令牌」没有给插件**新的主体范围**——它本来就能以活跃用户身份行动。真正的收窄是：**非活跃主体完全免疫了**。这在 v2.9 是不成立的（v2.9 插件可以签任意主体令牌，包括离线的、其他公司的）。

  所以 v2.10 的真实保证是：
  1. 插件不能冒用**无活跃会话**的主体。✓（构造性）
  2. 插件不能**伪造声明**（不能给自己签「公司全部」权限的令牌，因为声明从会话状态导出）。✓
  3. 插件不能**长期持有**信任（令牌 ≤5 分钟，且可撤销）。✓
  4. 插件仍可冒用活跃会话主体（与 TCB 语义一致，且被红线 3 放弃段部分覆盖）。

  问题只在于 PRD 是否**如实说出第 4 点**以及负向测试的精确语义。我认为这是一个「重要」级问题：§9.2 的「令牌体系例外」表述过强（「不在插件可影响之列」），且 §9.4.1 未声明「活跃会话令牌在运行时进程内流通、插件可窃取使用」这一残留路径。按加严标准，重要项也必须修。

  但它是阻断吗？阻断应该是「不修就不能开工」的级别。第九轮的阻断是「隔离方案不成立」。v2.10 的隔离方案**成立**（它确实把签发面与判定面移出去了，这是构造性的），只是**表述过强 + 残留路径未声明**。我倾向于判定为「重要」——需要补一段如实声明，并收紧负向测试的语义（「非活跃会话主体」而非「非当前会话主体」）。不过，负向测试语义不精确是否会让测试不可判定？「插件无法取得非当前会话主体的令牌」——测试实施时可以构造：插件尝试取得「当前无任何活跃会话的管理员」的令牌→应失败（可判定 ✓）；插件尝试取得「另一活跃会话主体」的令牌→按当前 PRD，可能成功（窃取/session_id 借用），测试预期是什么？PRD 没说。所以这个测试的**完整语义未定义**。

  嗯，让我再读一遍负向测试的原文（§9.4.1 负向测试列表）：「伪造签名、用已吊销密钥签名、用其他身份层签发的令牌、篡改声明字段后重签、**插件无法取得非当前会话主体的令牌**、**签名请求含主体指定字段时被拒并告警**、**签名进程不加载任何插件**（可核验的启动配置，v2.10）」。

  「签名请求含主体指定字段时被拒并告警」——这条测试很好，可直接判定。
  「插件无法取得非当前会话主体的令牌」——如分析，语义模糊。「当前会话」是谁的？测试时插件没有会话。如果解释为「插件请求一个不属于任何活跃会话的主体的令牌，应被拒」，则可判定且成立。如果解释为「插件无法取得任何其他主体的令牌」，则不成立（活跃会话可被冒用）。语义需要收紧。

  好，这是发现一：**「令牌体系例外」表述过强 + 残留路径（活跃会话令牌窃取/会话标识借用）未声明 + 负向测试语义需收紧为「无活跃会话的主体」**。我判定为重要（不修会导致误读安全保证的边界，且测试语义依赖实现自由发挥）。是否升级为阻断？考虑：它不影响开工（机制方向正确、可构造），但按「加严标准零重要」它也必须修。我先定为重要。

  等等，再考虑一下「会话状态篡改」路径是否真的关了。任务问题 1(a)：插件能否影响平台服务进程的会话状态？

  会话状态的操作面：哪些接口会写会话状态？
  - 会话创建（认证）：需要用户凭据，插件无凭据。但如果认证接口被运行时进程代理调用呢？用户登录请求经过运行时进程？通常登录是 Web 端直接到身份层。PRD 没细说。如果登录流量经过运行时进程，插件可以窃取用户密码！嗯——架构上，Web 端（搭建舱/工作台）与身份层的关系：§4.1 架构图顶部是 KVVI 自有 Web 端，下面能力层，然后平台服务进程、运行时进程。Web 端与谁通信？运行时进程（Agent 对话）和平台服务进程（登录、权限）？登录大概率直接到平台服务进程（身份层）。但 PRD 未定义。如果登录经过运行时进程，插件窃取凭据→创建任意主体会话→整个两进程划分失效。这是实现级，但 PRD 可以要求「认证流量不经过加载插件的进程」作为产品级约束。PRD 没有写这条。嗯，这值得提吗？让我看看有没有依据……§4.6.5 只列了两个进程的内容，没说 Web 端流量路径。「认证流量不经过插件进程」是两进程划分成立的**必要前提**，PRD 未声明。不过，这是否属于「实现细节」？按先例，v2.10 把「签名与身份判定不得与插件同进程」作为产品级决策；同理「认证入口不得在插件进程内」应该是同级约束。我认为这可以并入发现一（两进程划分的接口面未完整定义：签名接口有授权规则，但**会话操作接口、认证接口**没有任何规则）。

  这正是任务问题 1(a) 的核心：「两进程的接口本身是否可能被插件滥用（例如以运行时身份发起会话操作）」。PRD 只定义了**签名接口**的授权规则（§9.4.1 ②），但两进程之间的接口不止签名一个：
  - 会话状态读写（会话持久化在运行时进程！会话状态在平台服务进程——两者之间必有同步/查询接口）
  - 授权判定查询（运行时是否需要查授权？不，授权判定在业务系统侧和执行点……等等，执行点在哪？）
  
  嗯，让我想想「唯一执行点」（§9.2）在哪个进程。§9.2 说「UI 与 Agent 必须调用同一个业务命令端点，由服务端统一执行全部校验」。这个业务命令端点是**业务系统**的端点（独立部署）。所以执行点在业务系统侧，不在两个进程内。授权判定在业务系统侧执行（基于令牌声明）。那平台服务进程的「授权判定」是什么？可能是指「身份层的权限管理判定」（谁能授予权限、授权版本管理）。OK。

  还有「发布通道」在平台服务进程。发布通道的调用方是搭建舱（Web 端）→平台服务进程？不经过运行时进程？应该不经过。OK。

  那两进程之间的接口主要是：
  1. 签名请求（运行时→平台服务）——有规则 ✓
  2. 会话状态查询/同步？架构图说运行时进程有「会话持久化」，平台服务进程有「会话状态」。会话的认证状态、绑定公司在平台服务进程；会话的消息历史在运行时进程？当运行时处理消息时，需要知道「这个会话的当前公司、当前用户、授权版本」来构造业务调用——它怎么知道？要么平台服务进程推送，要么运行时查询。如果有「会话状态查询接口」，插件可以调用它读取任意会话状态（信息泄露，次要）。如果有「会话状态更新接口」（比如会话结束通知、公司绑定），插件若能调用**写**接口，就能篡改会话状态——会话状态篡改路径复活！
  
  PRD 没有定义两进程间除签名外的接口规则。§4.6.5 说「接口受控」——和 v2.9 的「受控接口」是同一个词！第九轮批评 v2.9「『受控接口』零授权语义」，v2.10 只给签名接口加了授权规则，**其余接口仍是「受控接口」四个字，零授权语义**。

  这是发现二：**两进程间接口只定义了签名一个的授权规则；会话状态、撤销状态、发布等其余跨进程接口仍是「受控接口」笼统表述——若其中任何写接口（如会话状态更新、撤销登记）可被插件借运行时身份调用，会话状态篡改路径即复活**。这正是任务问题 1(c) 问的：「受控接口若只是同主机上的另一个端口，插件是否可以直接调用？」

  按 PRD 精度边界，接口细节属技术设计。但**「平台服务进程的写接口必须鉴别调用方主体，不得仅按进程/网络位置信任」**是产品级安全属性——否则 §9.4.1 声称「会话状态篡改路径已关闭」就没有依据。类比：v2.9 的「受控接口」被批为零授权语义；v2.10 修了签名接口但留下其余接口。这构成「改一半」吗？部分是。我判定为重要（可能是阻断，需要斟酌）。

  让我斟酌阻断 vs 重要。阻断标准：「必须修，否则不能开工」。如果两进程划分的安全故事依赖于「其余接口不被滥用」而 PRD 完全没说，那么实现者可能实现成「同主机端口 + 无鉴权」，于是会话状态篡改路径复活，整个 v2.10 的核心修复落空。这类似第九轮的阻断性质。但另一方面，PRD 可以主张「接口设计属技术设计文档，PRD 只要求『受控』+ 签名规则」。反驳：第九轮已经判定「受控接口」四字不构成安全属性；v2.10 对签名接口补了规则，等于承认了「受控」二字不足——那么对其余接口仍只写「受控」，就是同类缺陷。而且 v2.10 自己在 §0.11 说「两条路径下验签通过、审计完美、不可检测完整保留。因此 v2.9 的修复并未消除它自己定义的威胁」——若会话状态写接口无规则，路径 (b) 仍未消除。

  嗯，但要严谨：会话状态篡改 (b) 的具体机制是「插件篡改同进程的会话状态」。v2.10 把会话状态移到平台服务进程后，插件要篡改它必须**通过跨进程接口**。如果两进程间**根本不存在**「写会话状态」的接口（会话状态只由平台服务进程自己按认证事件写），那么路径 (b) 关闭——不需要接口授权规则，因为接口不存在。但 PRD 没说「不存在写会话状态的跨进程接口」。架构图显示运行时进程有「会话持久化」——会话的生命周期事件（创建、结束）由谁触发？用户登出→谁告诉平台服务进程结束会话？如果运行时进程可以通知「会话 X 结束」，插件就能伪造该通知→强制任意用户下线（DoS，次要）或更糟。如果运行时进程可以上报「会话 X 绑定了公司 Y」……那更糟。

  所以：PRD 未枚举两进程间的接口清单，也未声明「平台服务进程不接受来自运行时进程的会话状态写请求」。这是一个真实的缺口。级别：我倾向于**重要**偏高，但考虑到它是 v2.10 核心修复（路径 b 关闭）的直接依据缺失，且第九轮同类问题（受控接口零语义）就是阻断——我认为可以判**阻断**。嗯，让我再想想。

  第九轮阻断的原文：「(b) 会话状态篡改——身份层（会话状态、授权判定）仍在插件同进程，架构图未改」。v2.10 的修复：身份层移出插件进程。这个修复**在架构层面成立**：会话状态现在在不加载插件的进程里。剩下的问题是「跨进程接口是否允许插件间接篡改」。这是一个**新的、更窄的**问题，而不是「修复不成立」。架构上插件不再能「直接改内存」，只能「通过接口影响」——这已经是实质改进。接口滥用风险是否必须在 PRD 层关闭？PRD 层可以加一句「平台服务进程不接受运行时进程对会话状态与授权判定的写请求；会话生命周期事件由平台服务进程基于认证事件自行维护」——这是产品级约束（属于「系统是什么」而非「怎么做」，按 v2.5 先例：部署拓扑属 PRD）。缺了它，「会话状态篡改路径已关闭」的声称依赖实现者的善意。

  我判定：**重要**（应该修，补一条接口面约束），不判阻断的理由是：架构改进是真实的，残留风险是「接口设计必须遵守的约束未写明」，属于「声明不全」而非「方案不成立」。但按加严标准，重要也必须修。嗯，实际上让我再考虑下——如果我在第十轮判它「重要」，按加严标准 v2.10 仍不可冻结（零阻断+零重要）。所以判重要和判阻断对结论的影响一样：不可冻结。区别在于改的紧迫性定性。我会把「接口面约束缺失 + 负向测试语义 + 令牌窃取残留未声明」打包成一个重要项（或两个），结论是不可冻结（按加严标准）。

  等等，我要小心不要过度判。让我重新评估「令牌窃取」是否真的未声明。红线 3 第二段（§10.1）：「插件运行期的业务操作 ❌ 不覆盖。插件不经执行点、无调用埋点……这些操作不在追溯保证内」。插件用窃取令牌调用业务系统=「插件运行期的业务操作」→已被红线 3 放弃段覆盖（追溯不保证）。而安全维度（越权能力）：插件用窃取令牌只能做「该用户本来就能做的操作」——没有权限放大！因为令牌声明=该用户的真实权限。插件窃取管理员活跃令牌能做管理员能做的事——但插件本来就能在管理员的会话里注入操作做同样的事。所以**没有权限放大，只有通道变化**（从「注入会话」变成「直接调用」），且审计维度已被红线 3 放弃段覆盖。

  所以「令牌窃取残留」的真实增量≈零（相对 TCB 基线）。PRD 没声明它，固然不理想，但是否构成「过度承诺」？§9.2 范围声明说「§9.4 令牌体系不在插件可影响之列」——严格读，「令牌体系」指签发、验签、声明、失效这套机制。插件不能影响这套机制本身（不能伪造、不能篡改声明、不能阻止失效）——成立。插件能「使用」这套机制的产出（窃取令牌）——这算「影响令牌体系」吗？语义边界案例。我认为 PRD 的表述**勉强成立但有误导风险**，最佳实践是补一句「插件可窃取并使用运行时进程内流通的活跃会话令牌（无权限放大，且其操作追溯已由 §10.1 红线 3 第二段排除）——两进程划分消除的是伪造与提权，不是冒用活跃会话」。这可以是建议级或重要级。

  嗯。让我把它定为**重要**：因为它直接关系到 §0.11 声称的「两条路径已关闭」是否如实——路径关闭的是「伪造面」，「冒用面」以残留形式存在，PRD 应如实声明，否则 §9.2 的「令牌体系例外」会被读成「插件完全无法影响令牌使用」，与 §10.1 红线 3 第二段（插件可做不可追溯的业务操作）之间存在张力。三处一致性（任务问题 5）在这里有裂缝。

### 2. 有没有新的「改一半」？

v2.10 改了：架构图、§4.6.5、§9.4.1、§4.1.1 四、§9.6.2、§9.11.2、§10.1、§3.1、§10.3、§2.5.2、§9.2、§7.1。

检查未改的条款是否仍隐含「身份层与插件同进程」假设：

a) §9.4 三条硬性要求第 3 条：「令牌由**身份层**签发，不由 Agent 运行时代发。」——与两进程划分一致 ✓（身份层现在在平台服务进程）。

b) §9.4.2「撤销查询（账号停用与会话结束时必选）：身份层提供撤销状态查询」——一致 ✓。

c) §3.5.1 链接签名：「签发主体：链接签名必须由身份层或其同等信任锚点签发」+ v2.10 §9.4.1 ④「同一隔离适用于链接签名……其私钥同样不得驻留在加载插件的进程内」——一致 ✓。

d) §4.6.4 平台库安全边界：「业务系统运行时不得直连平台库……对平台库的依赖只能经身份层的服务接口」。身份层现在在平台服务进程，平台库访问也在平台服务进程——一致 ✓。§4.6.4 还说「若身份层与平台库同进程宿主，『直连』与『经服务』的边界会被弱化」——现在身份层与平台库访问同在平台服务进程，这个担忧仍然有效但已被接受 ✓。

e) §9.1 地基清单「身份与鉴权：账号、登录、会话、身份源适配器」——地基项，不受进程划分影响 ✓。

f) §2.6 会话绑定「模式与公司都在会话创建时确定」——会话状态在平台服务进程，一致 ✓。

i) §9.10.2 插件控制要求：「仅所有者可批准安装/注册」「搭建者不得安装或注册」——批准动作发生在哪个进程？插件批准记录存哪？批准记录含指纹，加载/激活时比对——「加载/激活」发生在运行时进程（插件宿主），比对逻辑若在运行时进程执行，插件可跳过比对！等等，这个之前轮次提过吗？§9.6.2「加载/激活时与批准记录比对，不一致则拒绝并告警」——比对由谁执行？插件宿主在运行时进程，而插件是进程内任意代码：一个已加载的恶意插件可以**拦截后续插件的指纹比对**（篡改比对逻辑或批准记录缓存）。不过，首个插件的加载比对谁来拦截？加载时的比对逻辑属平台运行时代码，首个恶意插件加载前比对已完成；加载后它可以篡改后续比对。链式注册已声明（§9.6.2「插件在进程内注册另一个插件不受本节接口约束」）。所以「插件篡改指纹比对」部分被链式注册声明覆盖——PRD 已承认 TCB 语义。嗯，但指纹比对本身：批准记录存平台库（平台服务进程），比对在加载时（运行时进程）——插件可篡改运行时内存中的批准记录缓存或比对代码。这是 TCB 固有问题，PRD 已通过链式注册声明部分承认。是否值得提？可以提一句：指纹比对的执行点在插件同进程，比对保证以「首个插件加载前」为限——但链式注册声明已经覆盖了「一个插件引入另一个插件」的情形，指纹比对被篡改本质上是同一类。我认为不必单独提，避免凑数。

k) §4.6.5「插件可达范围：插件仅能触及本进程内的资源；不能触及身份判定与私钥」——任务问题 3 直接问这句。进程边界在什么条件下不成立：同主机、共享文件系统、共享 socket、共享平台库凭据。
   - 同主机：插件进程与平台服务进程同主机，插件能否通过 ptrace/调试接口读平台服务进程内存？以同用户运行的进程，ptrace 可以！除非以不同用户运行+加固。PRD 说「两进程分离部署，Docker 骨架体现」——Docker 容器隔离可以防 ptrace（不同容器+no ptrace）。但 PRD 只说「进程分离」，未说「以不同容器/不同用户运行，禁用跨进程调试」。「插件仅能触及本进程内的资源」——这句话在「同主机同用户 + 允许 ptrace」下**不成立**（插件进程可以 ptrace 平台服务进程读私钥）。等等，插件是运行时进程内的代码，它要做的是 ptrace **另一个**进程——插件代码在运行时进程内执行，运行时进程是否有权限 ptrace 平台服务进程？如果同用户，Linux 下默认 yama ptrace_scope=0 允许同用户 ptrace；scope=1 则只允许子进程。Docker 容器默认有 ptrace 隔离吗？容器内进程只能 ptrace 同容器进程（PID namespace 隔离）——如果两进程分属不同容器，插件根本看不到平台服务进程。所以「分离部署」若=「分容器」，则成立；若=「同容器两进程」或「同主机两进程同用户」，则不成立。PRD 说「阶段一 Docker 骨架即须体现」——暗示 Docker 层面分离，但没写明「不同容器/不同用户、禁跨进程调试」。
   
   「插件仅能触及本进程内的资源」是绝对表述，其成立依赖部署形态细节（容器隔离、用户隔离、ptrace 策略、共享卷、共享 socket 目录）。按 v2.6 的教训（不得使用无依据的绝对表述），这句话应该加限定：「在声明的部署基线下（两进程分属不同容器/不同系统用户、无共享可写文件系统、平台服务进程不暴露未鉴权端口）」。否则这就是任务问题 3 要找的「新的过度承诺」。
   
   另外共享文件系统：私钥「不得随部署包明文分发，不得进入镜像、仓库或日志」（§9.4.1）——若两容器共享卷且私钥在卷上，插件可读。§9.4.1 已禁止私钥进镜像/明文分发，但未禁止「共享卷」。这个算部署细节。
   
   还有共享 socket：两进程间接口若用 unix socket 在共享目录，插件可连上该 socket 直接调用平台服务进程接口——回到接口鉴权问题（发现二）。如果接口调用只靠「能连上 socket」即信任（同机信任），插件直接调用签名接口/会话接口。§9.4.1 ② 说签名接口「不接受请求方声称的身份」——但插件用 socket 发起「为会话 X（窃取来的活跃 session）签令牌」的请求，不含主体指定字段，只有 session 标识——会被接受！所以「受控接口」若没有调用方鉴别（mTLS 或等效），插件可任意调用。这强化发现二：**两进程间接口的调用方鉴别机制缺失，是产品级缺口**。

   我把「插件仅能触及本进程内的资源」判为**重要**：过度承诺，需要加部署基线限定词。或者……它是否重要到阻断？这句话是 §4.6.5 的核心声称之一。它的成立条件（容器/用户隔离、无共享凭据、接口鉴别）全部未写。按 v2.5/v2.6 先例（「技术上不可达」被判过度承诺而收窄），这句同性质。判重要，修法是补「部署基线」限定。

### 3. 负向测试可判定性（任务问题 4）

「插件无法取得非当前会话主体的令牌」需要的前置条件：
1. 「当前会话」的判定机制（会话标识如何传递、防伪）——未定义。
2. 测试环境需要一个「已批准的插件」+「一个非活跃主体」（可判定 ✓）或「另一活跃会话主体」（判定取决于接口语义）。
3. 「取得」的定义：包括「从运行时内存窃取已签发令牌」吗？若包括，测试必然失败（插件必能窃取）；若只指「通过签名接口取得新令牌」，则需定义接口的会话鉴别。

所以该测试按当前文本**不完全可判定**——它的通过/失败取决于实现者如何设计会话标识机制。§0.11 声称「因此负向测试变成可判定的」是**过度声称**。这印证发现一/二。修法：把断言收紧为「插件无法通过签名接口为**无活跃认证会话的主体**取得令牌」+ 要求「会话标识不可被插件用于冒领」（产品级属性：签名接口须验证请求所涉会话与调用方会话绑定关系……嗯，或者更简单：签名请求只能由运行时进程代表其正在处理的会话发起，且令牌回投绑定到该会话的上下文）。

其实有个干净的产品级修法：**签名接口的会话绑定**——「签名请求必须携带平台服务进程颁发的会话凭证（如会话创建时下发的会话密钥/session token），插件不可得」。但会话凭证得交给运行时进程使用（运行时代表会话请求签名）——插件同进程又能读到。除非每次签名请求都由 Web 端（用户侧）携带会话凭证直接到平台服务进程换取令牌再交给运行时？那样运行时不接触会话凭证……但运行时调用业务系统需要令牌，插件照样能读令牌。根本无解（TCB）。所以诚实的收敛就是：断言收窄为「无活跃会话的主体不可冒用」+ 声明「活跃会话主体的冒用属 TCB 既有语义，与红线 3 第二段一致」。
