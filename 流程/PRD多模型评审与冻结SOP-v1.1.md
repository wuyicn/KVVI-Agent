## 1. 目标与原则

本 SOP 用于把一份 PRD 从初稿推进到可追溯的冻结版本。完成标志是：评审问题有明确处置、重大分歧由产品负责人裁决、终审通过、产品负责人批准冻结。

1. **独立评审**：各评审席位先分别阅读同一份锁定的初稿，不看其他模型的意见；原始报告一经提交即保存，不回改。
2. **单一主笔**：只有主笔修改 PRD 正文。其他模型提交问题、依据和建议，不各自产出竞争版本。
3. **证据与版本留痕**：每个问题对应文档位置、触发场景或依据；保留初稿、每轮评审、问题表、修订差异和决策记录。
4. **产品负责人裁决**：模型可以提出方案，但不得自行决定业务目标、范围、优先级、产品规则及互相冲突的要求。
5. **终审独立**：终审模型审查修订后的完整版本，不承担该轮主笔工作。
6. **按结果推进**：以问题关闭和冻结门槛为准，不按评审轮数或日程自动放行。
7. **【v1.1 新增】评审不等于收敛**：评审只能发现问题，不能保证问题有限。当轮次增加而问题层次不下降时，必须走 §8 的处置，**不得以继续润色代替处置**。

PRD 冻结只表示需求基线获得批准；它本身不等于原型、技术方案、测试环境或开发就绪评审已经完成。

### 2.2 【v1.1 新增】对抗性评审席位

| 角色 | 默认模型／责任人 | 职责 |
| --- | --- | --- |
| **对抗性评审** | 与初稿作者、主笔均**不同家族**的前沿模型 | **目标是推翻，不是确认。** 见下方职责定义。 |

**为什么单独设席**：本 SOP 原有的「反方评审」职责是「质疑前提、检查复杂规则、隐含约束、边界」——
这属于**逻辑与边界检查**。而对抗性评审做的是另一件事：
**假设文档是错的，努力构造反例去证明它错。**

**职责定义（必须写进提示词）**：

1. **目标是证伪**。若通篇未找到问题即为本次评审失败。
2. **优先级**：不是「哪句话写得不好」，而是「**哪条主张站不住**」。
   具体地，优先攻击：
   - **未言明的前提**——某个结论依赖一个从未声明的假设；
   - **结论当前提**——用自己要证的结论作为论据；
   - **约束对象错位**——某条约束管的是 A，但被用来支撑关于 B 的结论；
   - **自我否证**——文档某处已写出与某主张矛盾的事实，但该主张未被修改；
   - **不可测的断言**——写成了保证，但没有可判定的验收方式。
3. **必须给出「可否冻结」的明确结论**，以及**最小阻塞项**（只列真正拦住冻结的，不罗列）。
4. **不得为了凑数把建议升格**。若只找到建议级问题，必须明确说「按标准可以冻结」。

**实证依据**：本次执行十轮中最重的 5 条发现全部出自对抗性视角——

| 版本 | 发现 | 性质 |
|---|---|---|
| v2.5 | 「技术上不可达」推理链不成立 | 结论当前提 + 约束对象错位 |
| v2.8 | 插件批准只绑定「名字」，未绑定内容 | 精度标准不统一 |
| v2.9 | 签名隔离只移私钥，未关签名请求路径 | 自我否证 |
| v2.9 | 负向测试「无法取得签名能力」不可判定 | 不可测的断言 |
| v2.10 | 动作集规则本身错误（批准集 ≠ 审计集） | 规则本身不成立 |

模型版本可能变化。每次评审都在封面记录**实际模型 ID、推理强度、调用平台、调用地域、日期和材料版本**。更换型号时维持席位职责，并在本 SOP 的执行记录中写明替换原因；不要把动态别名当作已固定的模型快照。

## 3. 启动条件与材料

开始评审前，流程负责人准备一个只读的"评审包"：

- PRD v0：文档编号、版本、日期、责任人和变更摘要齐全。
- 业务背景：目标用户、问题、目标、成功指标、已有约束和已知非目标。
- 有则附上原型、流程图、术语表、现有系统说明、数据/API 契约和相关依据；没有的标记为"缺失"，不要让模型虚构。
- 标注哪些内容属于事实、假设、待决策事项；给附件统一编号。
- 明确材料的共享边界。调用渠道和部署地域要分别核实；国内厂商模型通过第三方平台调用，不自动等于材料在中国境内处理。无法提供给终审模型的信息，应在终审包中说明删减范围；若删减影响核心判断，不得声称已完成完整终审。

### 3.1 【v1.1 强化】共享边界必须落成记录

> **实证**：本条 v1.0 已写，但本次执行**全程未落实**——
> 文档被发送至多个厂商端点，**未记录任何调用地域与共享边界**；
> 且因网络阻断导致的席位缺席**直到第五轮才被发现**。
> **一条没有被记录的要求，等于没有要求。**

评审包封面必须包含下表，**每次评审填一行**：

| 条目 | 填写内容 |
|---|---|
| 材料版本与校验值 | 文件名 + SHA-256（见 §3.2） |
| 席位 | 业务／技术／用户流程／反方／**对抗性** |
| 实际模型 ID（非别名） | |
| 推理强度 | |
| 调用平台 | |
| **调用地域** | |
| 材料共享边界 | 该席位可见的材料范围；如有删减，写明删减项 |
| 日期 | |

### 3.2 锁定与变更

锁定 v0 后记录文件名与校验值，评审期间不得静默改写。发现事实错误时发布 v0.1，并让受影响的评审席位基于同一新版本重评。

> **【v1.1 补充】指纹口径必须写清**：
> 指纹应覆盖**评审对象全文**；若同时冻结评审记录，须说明清单覆盖范围。
> 本次执行曾出现「把修正前的旧指纹写进冻结记录」的错误——**指纹必须由工具生成，不得手写**。

## 4. 标准流程

### 4.0 【v1.1 新增】第 0 关：机械核查门禁

**在任何人／模型评审之前，先跑机械核查。全绿才进入第 1 关。**

**为什么单列**：有一类问题**不需要理解语义就能发现**，但模型反复漏掉。
让前沿模型把注意力花在「§9.12 标题写四轮、正文五轮」上，是**双向浪费**：
既浪费模型能力，又因为模型不可靠而漏掉。

**实证（本次执行）**：

| 错误 | 谁发现 |
|---|---|
| 「七项地基」实为八项 | 本地 27B 模型 —— **三份前沿模型全部漏掉** |
| §9.12 标题「四轮」正文五轮 | 本地 27B 模型 |
| §10.4 残留「四轮」 | 两个模型（但**核实者本人用 grep 也没搜到**，见 §4.1.5） |
| §4.6 小节顺序 4.6.4 排在 4.6.3 之前 | 本地 27B 模型 |
| §4.6.5「三类数据」实为四类 | 本地 27B 模型 |

**结论**：**计数、编号、引用、表格结构类错误，脚本比模型可靠。**
自建的约 400 行核查脚本对上述全部错误**零漏报、零误报**。

**最低检查项**（可按文档调整，但不得减少）：

| # | 检查 |
|---|---|
| 1 | 小节编号顺序（不得出现 4.6.4 在 4.6.3 之前） |
| 2 | 交叉引用有效性（「见 §x.y」必须存在） |
| 3 | 表格列数一致（编辑时吞换行会把两行并成一行） |
| 4 | 转义管道符 `\|` 不得被算作列分隔 |
| 5 | **轮次／版本计数一致性**（含「改为『N轮』」这类**修订记录里的描述**） |
| 6 | 版本状态残留（如「v2.6 仍需验证」而当前已是 v2.11） |
| 7 | 已废弃表述残留（旧结论不得当作当前主张使用，历史记录除外） |
| 8 | 自称条数与实际行数（「四条规则」表里必须真有四行） |
| 9 | **跨节引用计数**（「§4.6.1 的三类数据」必须与该节标题一致） |
| 10 | **锚点编号顺序**（①②③⑥④⑤ 属未重排） |
| 11 | 结构完整性（代码围栏配对、标题层级不跳级） |

**辅助功能：传播检查报告**
把「关键概念」在全文的**全部出现位置**一次性列出，供主笔扫查——
**它替代的是「靠记忆回想哪里还提到过」，不是替代审阅。**

**⚠️ 机械核查的能力边界（必须写明）**：

| 能做 | **不能做** |
|---|---|
| 编号、引用、计数、结构 | **判断「这句话是否否证了别处的结论」** |
| 把同一概念的出现位置摊开 | **判断「两处列举是否指同一个东西」** |
| 检查「自称 N 条」与表行数 | **判断某条主张是否成立** |

> **工具全绿 ≠ 文档正确。** 本次执行的实证：
> 核查工具的**全部盲区都由外部评审发现，从未由自查发现**；
> 且被独立评审者本人当面指出：「工具无法代为核实」语义矛盾。
> **机械核查是入场门槛，不是评审替代品。**

### 4.1 第 1 关：独立评审

分别向各席位发送同一评审包和各自职责。**不得向后一个模型展示前一个模型的报告。**

各报告至少包含：

1. 结论：可修订／需产品裁决／材料不足；**不得直接宣布 PRD 冻结**。
2. 问题：精确位置、触发场景、影响、建议和严重度。
3. 依据：PRD 原文、附件编号、已验证事实；推测明确标记为推测。
4. 待确认问题：说明缺失什么信息、谁能决定。

**对抗性席位额外要求**：明确的「可否冻结」结论 + 最小阻塞项（见 §2.2）。

所有原始报告锁定后，才进入汇总。主笔的评审报告也必须在其主笔工作开始前锁定。

### 4.1.5 【v1.1 新增】第 1.5 关：发现核实

**在汇总之前，逐条把评审发现回原文核对。**

**为什么需要**：评审者**会编造**。把举证责任写在提示词里（§4.1 第 3 点）**不足以防止**。

**实证（本次执行）**：
- 某模型编造 2 条：声称「§5.5 未包含 `money` 类型」（实际在十类枚举内）、
  「§3.3 未处理未提交单据」（实际有整行处理）。
- **但核实方也会错**：一次用 `grep "轮评审的发现已全部处理"` 未命中，
  核实方据此**几乎判定某评审编造**——实际是原文写作 `**四轮**评审`，
  **markdown 粗体标记打断了模式匹配**。

**因此核实必须是双向的**：

| 方向 | 要求 |
|---|---|
| **对评审** | 每条发现必须能在原文定位；无法定位的标记为「待复核」，**不得直接采纳、也不得直接判为编造** |
| **对核实工具** | 核实用的搜索模式必须**对格式化标记鲁棒**；先说「我的核实方法可能错」，再说「评审可能错」 |

**核实的输出**：问题合并表中增加「核实结论」列——
`已定位` / `部分定位` / `未定位（待复核）`。

> **未定位的问题不得关闭，也不得直接丢弃。**它要么是评审的错，要么是核实方法的错。

### 4.2 第 2 关：主笔汇总与产品裁决

主笔以 v0 和各份原始报告生成《问题合并表》。同一问题可合并，但**保留全部来源**；相反意见并列展示，不用多数票决定。主笔先给出处理建议，不立即修改有争议的正文。

**【v1.1 新增】合并表必须包含「传播范围」列**（见 §9.A）：
主笔须为每个待修问题**预先列出**受影响的其它章节。理由见 §4.3。

产品负责人先裁决以下事项：改变目标或非目标、增删功能、角色权限取舍、规则冲突、优先级、成本或时效承诺、对外口径。**没有决定的事项保持"待决策"，不得写成已确定需求。**

### 4.3 第 3 关：单一主笔修订

主笔基于已裁决的问题表生成新版本，交付：

- 完整的新版本；
- 上一版 → 新版的变更记录或差异；
- **问题 ID → 修改位置 → 验收条款 → 传播位置** 的对应表；
- 未解决问题与理由。

修订必须覆盖受影响的相关章节。例如更改角色权限时，同步核对流程、状态、接口、异常处理和验收标准。
**不得只改一处文字便宣称问题关闭。**

#### 【v1.1 强化】「改一处、不传播」是最高频的失效模式

**实证**：本次执行十轮中，**有 5 轮出现同一模式**：

| 版本 | 表现 |
|---|---|
| v2.6 | 承认插件可绕过执行点，只改了 2 处，**漏了另外 2 处依赖「它不存在」的条款** |
| v2.7 | 修好了引用，但接口清单的**测试语义**没跟上 |
| v2.8 | 新写「插件可拦截审计」，**未传播到任何审计相关条款** |
| v2.9 | **为修「改一半」而做的统一，本身又是「改一半」**（留下重复行 + 旧列举） |
| v2.10 | 跨节计数写「三类」而该节已改为「四类」 |

**根因**：**新写的一句话会否证别处已有的结论，而回扫全文没有工具化。**
机械核查查不出这类问题（§4.0 边界表）。

**强制动作**：

1. 主笔在修订前，对每个待修问题**填写「传播范围」**（§9.A 的列）。
2. 修订完成后，**用传播检查报告**（§4.0）逐一核对所列位置是否都已同步。
3. 对应表中必须写明**每个传播位置的处置**——`已同步` / `不适用（理由）`。
4. **未列传播范围的问题，不得标记为已关闭。**

### 4.4 第 4 关：定向复核

把新版、差异和对应问题发回**提出问题的评审席位**，要求其判断
「已关闭／部分关闭／未关闭／引入新问题」。
跨领域改动同时发给受影响席位；若核心目标、主流程、权限模型或数据契约整体重写，各席重新独立评审新版本。

主笔只对有证据的问题继续修订，形成后续候选版。每一轮都保留差异和问题状态。

#### 【v1.1 强化】定向复核必须多问一句：「这个修法本身成立吗」

**只说「你把我说的问题改了吗」不够。**
评审者倾向于回答「我要的表述出现了 → 已关闭」——
**但评审者自己提的修法也可能是错的。**

**实证（本次执行）**：v2.9 按评审要求「统一动作集合并引用同一集合」执行，
作者标为已关闭；**下一轮判定该规则本身不成立**：

> **批准的对象天然是子集，审计的对象才是全集。**
> 强制「引用同一集合」必然产生扭曲。
> 且现实中不可执行——「加载」是进程启动行为（每次重启都要重新批准？），
> 「卸载」是清除恶意插件的紧急动作（要求审批反而设障）。

**因此定向复核的问题清单必须包含 4 问**：

| # | 问题 |
|---|---|
| 1 | **我提的问题关闭了吗？**（已关闭／部分关闭／未关闭） |
| 2 | **修订引入了新问题吗？** |
| 3 | **【新增】我提的处置方式本身成立吗？** 若不成立，说明断在哪里 |
| 4 | **【新增】这个改动需要传播到的地方，都传播了吗？** |

**并且必须说明**：定向复核**不能替代完整重评**——
它只检查「我关心的那条」，不检查全文。

> **本次执行的重要教训**：从第 4 轮起，本方**放弃了定向复核，全部改用全新视角**。
> 而「改一处、不传播」模式**恰好从那时起变得慢性**（见 §4.3 的 5 轮记录）。
> **机制上说得通**：全新视角只会从头再找一遍，**不会回头验旧账**。
> **建议：定向复核与全新视角并行，不可互相替代。**

### 4.5 第 5 关：独立终审

向终审模型提供最终候选版、v0、版本差异、各份原始报告、问题合并表、产品负责人决策记录和定向复核结论。要求它独立检查：

- 原有 P0/P1 问题是否真正关闭；
- 修订是否引入跨章节冲突或新需求；
- 角色、权限、状态、数据/API 和异常路径是否相互一致；
- 每项可开发需求是否有可检验的验收条件；
- 是否仍有未声明的假设或未裁决的业务问题。

终审只能输出「通过／未通过／因材料不足无法判断」及带证据的问题清单。「通过」仍须由产品负责人批准后才可冻结。

#### 【v1.1 新增】终审席位不可用时的 fallback

**实证**：本次执行中，终审席位因**网络层阻断连续缺席 5 轮**
（目标端点 TCP 可连但 TLS 握手被重置；对照端点均正常）。
v1.0 **对此没有任何备案**，导致执行方临时自定规则。

**必须事先约定**：

| 情形 | 处置 |
|---|---|
| **终审席位缺席** | 由**至少两个不同家族**的席位共同承担终审，且**冻结门槛加严一级**（见下） |
| **加严方式** | 正常门槛为「P0/P1 为零」；终审缺席时加严为「**P0/P1/P2 均为零，或 P2 已由产品负责人逐条签认**」 |
| **缺席必须披露** | 冻结记录中须写明：缺席的席位、缺席原因、是否存在替代、替代的局限 |
| **恢复后** | 终审席位恢复可用后，加严自动解除 |

> **为什么加严而不是照常**：缺席的席位在历史上**已被验证有效**
> （本次执行中，推理链不成立、精度标准不统一等最重发现均出自该家族）。
> 它缺席时，**跨家族交叉验证的强度下降**，应以更严门槛补偿。

## 5. 终审未通过的退回规则

| 问题性质 | 退回对象 | 重新进入终审前的动作 |
| --- | --- | --- |
| 措辞、编号、引用或验收条件不清，改法明确 | 主笔 | 修订并给出问题 ID 与差异；终审定向复核。 |
| 状态、权限、数据/API、异常处理或实现判断有争议 | 技术席位 → 主笔 | 技术席位核查依据，主笔修订，受影响席位复核后再终审。 |
| 用户流程、中文术语或一线操作场景有争议 | 用户流程席位 → 主笔 | 用户流程席位逐步核查，主笔修订；复杂规则可加反方复核。 |
| 假设、复杂规则或跨章节约束被推翻 | 反方与受影响席位 → 主笔 | 重新定义问题及影响范围；必要时各席重评。 |
| **主张站不住、前提未声明、断言不可测** | **对抗性席位 + 主笔** | **对抗性席位给出反例；主笔修订后由该席位确认反例是否消除** |
| 涉及业务范围、优先级或相互冲突的产品决定 | 产品负责人 → 主笔 | 产品负责人作出书面决定；相关席位重评修改结果。 |
| **相同问题反复出现，或材料不足** | **产品负责人指定事实来源或验证任务** | **补业务事实、原型或技术验证；完成前不得以反复润色代替关闭。** |
| **【v1.1 新增】每轮都出现新的 P0/P1，层次不下降** | **产品负责人** | **进入 §8 的处置，不得继续常规修订。** |

**退回原则**：小范围问题只做定向复核；核心需求、主流程、权限模型或数据契约有实质变化时，重新启动受影响领域的独立评审。终审问题按同一套问题 ID 管理，不另建一份无法对应的清单。

## 6. 问题分级与关闭口径

| 等级 | 判定口径 | 冻结要求 |
| --- | --- | --- |
| P0 阻断 | 目标或核心规则矛盾；会导致主要流程无法完成，或关键权限、数据处理不可接受 | 必须关闭。 |
| P1 重要 | 核心流程、状态、接口、异常或验收条件缺失，足以让实现或测试产生重大歧义 | 必须关闭。 |
| P2 一般 | 局部边界或次要流程不清，但不阻断已定义的核心需求 | 关闭，或由产品负责人明确记录保留理由、影响和后续负责人。 |
| P3 编辑 | 表述、格式、引用等不改变需求含义的问题 | 可进入编辑待办；终稿应完成必要校对。 |

**【v1.1 新增】P3 应由机械核查承担，不占用模型评审注意力。**
计数、编号、引用、格式类问题属 P3；它们**不需要语义理解**，
且模型在此类问题上**已被证实不可靠**（§4.0 实证）。
**建议：P3 不由评审席位提出，而由第 0 关直接拦下。**

“已关闭”须有修订位置与复核结果；“不采纳”须有理由与产品负责人确认；“待决策”不算关闭。
**模型声称 PASS、问题数量减少或主笔自评完成，都不构成关闭证据。**

**【v1.1 补充】主笔的自评不算证据，主笔所在家族的同族评审也不算独立复核。**

## 7. 冻结门槛与冻结动作

同时满足以下条件，产品负责人才能批准冻结：

- 各席独立评审、合并表、各轮差异和终审报告均可追溯。
- **【v1.1】第 0 关机械核查全绿，并在冻结记录中留存核查输出。**
- P0、P1 为零；P2 已关闭或有负责人签认的保留记录。
- 所有改变业务范围或规则的冲突已经由产品负责人裁决。
- 目标、范围和非目标明确；角色、主流程、状态、权限、数据/API、异常和验收条款互相一致。
- 终审对**同一个最终候选版本**出具“通过”；终审后没有未经复核的正文修改。
- **【v1.1】每个已关闭问题都有「传播范围」记录与传播处置。**
- **【v1.1】若终审席位缺席，已按 §4.5 加严并披露。**
- 产品负责人确认版本号、日期、文档文件和冻结范围。

冻结时生成《冻结记录》，包含文档编号、版本号、校验值、终审结论、剩余 P2/P3、产品负责人决定、冻结日期和后续变更入口。冻结件设为只读；之后的实质修改通过变更申请形成新版本，并按影响范围重评。

**【v1.1】解锁冻结时，必须保留旧版校验清单。**旧校验值是历史版本可追溯的唯一依据。

## 8. 【v1.1 新增】收敛判据与不收敛处置

### 8.1 为什么需要这一节

v1.0 假设「评审能把 PRD 收敛到可冻结」，但没有说明**假如不收敛怎么办**。

**本次执行的实证**：十轮评审，**每一轮都仍产出 P0 级发现**，
而且**问题层次是逐轮上升的，不是逐轮变浅**：

```
第 1–2 轮   设计空洞          （没写）
第 3–4 轮   声明 vs 机制      （写了但没有实现路径）
第 5–6 轮   推理链不成立      （写了但推不出来）
第 7–8 轮   精度标准不统一    （标准建立了但没贯彻到关键处）
第 9 轮     修法本身不成立    （按评审改的，但改法错）
第 10 轮    规则本身错了      （立的规则就错）
```

**这说明该文档有一条很长的「未言明的设计决策」长尾。**
每一轮对抗性评审撬出一条。**在这种情况下，继续润色式修订可能永不收敛。**

### 8.2 收敛判据

| 判据 | 含义 |
|---|---|
| **已收敛** | 连续两轮 P0 = 0，且 P1 数量**递减** |
| **未收敛** | 连续三轮 **P0 + P1 总数不下降** |
| **发散** | 某一轮出现**比上一轮更深**的 P0（规则级 / 架构级） |

### 8.3 判定「未收敛」或「发散」后的处置

**不得继续常规修订。**必须二选一，由产品负责人决定：

**处置 A：补事实，停止润色**

> **问题可能不在措辞，而在缺失的事实。**

按 §5 最后一行执行——指派具体的事实补全任务：

| 缺什么 | 补什么 |
|---|---|
| 外部系统的实际能力 | 实测 / 源码阅读 / 对方确认 |
| 产品决策未定 | 产品负责人书面决定 |
| 「这机制能不能强制」 | 技术原型验证 |
| 场景未验证 | 真实用户流程走查 |

**在事实补齐之前，不接受「再改一版看看」式的修订。**

**处置 B：按保留项冻结**

> **承认这份文档无法在冻结前消除全部问题，如实冻结并记录保留项。**

| 要求 | 说明 |
|---|---|
| 保留项必须逐条签认 | 产品负责人确认「知道它存在、接受它、指定后续负责人」 |
| 不得写成「已解决」 | 保留就是保留 |
| 冻结记录必须写明 | 保留项清单、影响、后续责任人 |
| 后续入口 | 每个保留项对应一个变更申请的入口 |

> **为什么处置 B 是正当的**：**「零遗留」不是一个可达到的标准，而是一个可声明的目标。**
> 一份**如实记录了自己局限**的 PRD，比一份声称没有问题但实际有的 PRD 更安全。
> 本次执行中，文档的安全性主张在逐轮变得更诚实：
> 从「技术上不可达」→ 收窄主体 → 承认「批准只绑名字」不够 → 承认隔离只消除部分威胁。
> **这个过程本身就是价值，不应因为它没有终点而否定它。**

| 核实方 grep 未命中断言某评审编造 | **核实方错**（原文含 markdown 粗体标记） |

### A.6 席位缺席

| 席位 | 缺席轮次 | 原因 |
|---|---|---|
| 某前沿家族 | 6–10（连续 5 轮） | **网络层阻断**：目标端点 TCP 可连、TLS 握手被重置；对照端点正常 |

**v1.0 对此无备案，执行方临时自定加严规则。** → §4.5

## 附录 B：机械核查的最小可用实现

任何脚本语言均可。核心要求是**可重复、可留档、可版本化**。

| # | 检查 | 实现要点 |
|---|---|---|
| 1 | 小节编号顺序 | 记录每个父节下已出现的子节号，出现更小的号即报错 |
| 2 | 交叉引用 | 先收集全部标题号，再扫描 `§x.y` 引用 |
| 3 | 表格列数 | **转义管道符 `\|` 不计入** |
| 4 | 轮次一致性 | **匹配前先剥离 markdown 标记**（`**四轮**评审` 要能被 `四轮评审` 匹配） |
| 5 | 版本残留 | 当前版本号由文件头解析，不硬编码 |
| 6 | 废弃表述 | 维护废弃词表 + **历史语境白名单**（按连续非空块判断，不按单行） |
| 7 | 自称条数 | 标题里的中文数字 ↔ 下方表格数据行数 |
| 8 | 跨节引用计数 | 标题 `#### x.y N类` 与引用处 `§x.y 的 N类` 比对 |
| 9 | 锚点编号 | 同一行内 ①②③… 的下标必须单调递增；**排除引用型描述** |
| 10 | 结构 | 代码围栏配对、标题层级不跳级 |

**两条来自踩坑的实现建议**：

1. **匹配前剥离 markdown 标记**——否则 `**四轮**` 会漏，而**人工 grep 同样会漏**（本次实际发生）。
2. **历史语境要按「连续非空块」判断，不能按单行**——同一段里往往前半句在讲「v2.5 曾写」，后半句才引用该表述。
