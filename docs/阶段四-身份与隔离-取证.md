## 一、为什么隔离必须落在数据库上

`工具/check_stage4.py` 起的不是内存里的假库，而是一个**真实 PostgreSQL 17**。
理由是阶段四要证的东西有一条共同性质：**应用层的检查无法独立地证伪自己**。

「A 公司的账号读不到 B 公司的数据」如果由应用代码判定，那么写错的判定
和正确的判定用的是同一份代码 —— 测试只能证明「代码和自己一致」。
所以这里做了两层，而且**第二层是数据库执行的**：

| 层 | 执行者 | 可独立观测吗 |
|---|---|---|
| 会话绑公司 + 引用绑租户（§9.9.2/§9.9.3） | 应用 | 否 —— 同一份代码 |
| **RLS 策略**（`20-business.sql`） | **PostgreSQL** | **是** —— 测试可绕过应用层，自己设 GUC 后直接发 SQL |

`isolation.test.mjs` 里那条「绕过应用层直接查（只设 GUC）仍然读不到别家」
用的就是第二条路：它不调用 `refs.mjs`、不调用 `authorization.mjs`，
只 `set_config` 然后 `SELECT`。

## 二、五档数据范围：按**实际可访问集合**，不按编号

PRD §2.5.1 明确：店铺与部门的包含关系**未规定**，二者**可能交叉**，
因此 `['SELF','STORE']` 与 `['DEPARTMENT']` 之间**不存在编号大小关系**。

固定装置就是按「交叉」造的：

```
A 公司
  销售部 (sales)
    └ 销售一组 (sales-a)      ← alice 在这里，门店一
  财务部 (fin)                ← bob 在这里，门店二

记录                                                   档位能读到的
  alice 自己的单        sales-a / 门店一 / alice        SELF ✓  DEPT_AND_CHILDREN ✓  STORE ✓
  bob 自己的单          fin     / 门店二 / bob          COMPANY ✓
  同组别人的单          sales-a / 门店一 / bob          DEPT_AND_CHILDREN ✓  STORE ✓
  门店一别人的单        fin     / 门店一 / bob          STORE ✓（部门对不上）
```

`DEPARTMENT_AND_CHILDREN` 那条用例**同时**断言「子树内读得到」与
「子树外读不到」——只断言后者的话，一个恒空的读取也能通过。

## 三、这一层查出来的东西

### 3.1 `fieldVisibility` 恒返回 `HIDDEN`（真 bug，已修）

字段可见性的合并规则写成「从 HIDDEN 起步、只允许变严」，
而 HIDDEN 已经是最严的一档 —— 于是**任何显式授权都升不上来**，
函数恒返回 HIDDEN。

这个 bug 的危险在于它**看起来更安全**（永远不泄漏），
所以很容易一路蒙混过关；它实际的效果是把字段权限整个废掉 ——
该看的也看不到，而且没人会报错。

**修法**：把「没有策略命中」与「命中多条取最严」分成两件事 ——
无命中 → HIDDEN；有命中 → 在命中项里取最严。

### 3.2 审计时间戳的毫秒截断（真 bug，已修）

`audit_append` 用 `now()`（PostgreSQL 微秒精度）算入链哈希，
而校验方（Node 的 `Date`）只有毫秒精度 —— 往返一次就丢精度，
**每一条都被判成篡改**。这是一个恒假的校验。

**修法**：写入时 `date_trunc('milliseconds', now())`，两边对齐。

### 3.3 「UPDATE 会报权限错」是错的（测试期望错，已改）

原以为审计写者角色 `UPDATE` 审计表会抛 `42501`。
实测不会：`DO INSTEAD NOTHING` 规则在**权限检查之前**重写语句，
所以即使是没有任何表权限的角色，`DELETE` 也返回 `DELETE 0`。

断言「会报错」会把一个**正确的实现**判成失败。改为断言真正要验的性质：
**影响行数为 0、内容没变、链仍然自洽**。

## 五、这个门禁是**有载荷的**（不是恒绿）

把 RLS 策略里的租户条件拿掉，再跑一次：

```
锚点①  ✗ §9.9.1 同一账号在两家公司的会话各自只看得到自己那家（并发会话）
锚点②  ✗ 绕过应用层直接查（只设 GUC）仍然读不到别家
锚点②  ✗ COMPANY 仍受租户约束：它是「本公司的全部」，不是「全部」
锚点③  ✓ 14 条用例全部通过      ← 未被影响
锚点④  ✓ 5 条用例全部通过       ← 未被影响
锚点⑥  ✓ 5 条用例全部通过       ← 未被影响
退出码=1
```

**该红的两条红了，不该红的没红。** 一个「什么都报红」的检查器和
一个「什么都报绿」的检查器同样没有用，这一条同时排除了两者。

## 七、与阶段一证据的一处改动（必须说清）

平台服务进程原来有一条 Dockerfile 断言：**依赖数为 0**。
阶段四起它需要一个数据库驱动（`pg`），所以那条断言**被收窄为「零 DSH 依赖」**：

- 原来的断言用「依赖数为 0」当「不加载插件」的**代理**；
- 代理比被代理的性质更严 —— 严到会把一个纯数据库驱动也挡在外面；
- 现在直接断言真正的那条：**依赖声明里没有 `@deepseek-ai/*`，
  且装机树里也没有**。镜像里依然没有可加载的插件材料。

这是**放宽一条断言**，所以写在这里而不是悄悄改掉。
