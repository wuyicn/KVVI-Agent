## 一、锚点① §9.2 差分测试：为什么必须是「同一个执行点」

§9.2 的缺陷原述值得逐字读一遍：

> 「UI 与 Agent 依据同一份契约，**不等于**运行时走同一段授权代码。」

所以差分测试**不能**通过「对比两份实现是否一致」来做 —— 那本身就已经承认有两份实现。
本项目的做法是让第二条路径**不存在**：`services/platform/src/commands.mjs` 的
`execute()` 是唯一执行点，UI 路径与 Agent 路径都调用它。

于是差分测试的构造是：

1. 用**同一个**会话、**同一个**执行点，构造「UI 会拒绝的请求」；
2. 当作 Agent 发来的请求重放（调用方自称是 Agent，**服务端不看这个声明**）；
3. 断言得到**同码拒绝**。

覆盖 §9.2 点名的五类，加两条 §9.3.1 的：

| 用例 | 结果 |
|---|---|
| 基线：UI 允许的请求通过 | 200（先证明「拒绝」不是别的原因造成的） |
| ① 隐藏字段直接构造请求 | 403 `KVVI_FIELD_NOT_WRITABLE` |
| ② 只读字段 | 403 |
| ③ 脱敏字段 | 403（见 §三.2 的说明） |
| ④ 非法迁移 | 403 `KVVI_TRANSITION_NOT_DEFINED`，并给出当前状态 |
| ⑤ 数据范围之外 | **404**（与「不存在」同码，§9.3「响应不可区分」） |
| ⑥ 跨公司 | **404**，不透露对方存在 |
| ⑦ 请求体含 `tenant`/`actor`/`role` | 400 `KVVI_CALLER_SUPPLIED_IDENTITY` |
| ⑧ **嵌套**里塞身份字段 | 400，且指出路径 `patch.meta.tenant` |

**UI 的「隐藏」不是安全控制**（§9.2 硬性要求 1）：同一字段，读路径由投影过滤、
写路径由执行点拒绝 —— 两条路径分开验，不靠一句「UI 会拦」。

## 二、锚点② §9.4.x 负向测试

### 2.1 §9.4.1 信任锚点与密钥

令牌从「不透明随机串」换成了 **Ed25519 非对称签名**。理由不是性能，
而是 §9.4.1 那条：**共享密钥会在每个业务系统侧扩大泄漏面**。
非对称之后业务系统**能验不能签**。

| 负向用例 | 结果 |
|---|---|
| 伪造签名 | 拒（`BAD_SIGNATURE`） |
| 篡改声明后用**自己的密钥**重签 | 拒（沿用原 kid → 签名对不上；换自己的 kid → 不在信任集） |
| 用**其他身份层**签发的令牌 | 拒（`iss` 比对） |
| 用已吊销密钥签名 | 拒（公钥不在集合里，与伪造同路径） |
| **无活跃会话 → 签不出令牌** | 403 `KVVI_NO_ACTIVE_SESSION` |
| **签名请求含主体指定字段** | 400，**并写一条审计告警**（"告警"是可查的记录，不是日志级别） |
| 令牌声明加未知字段 | 拒签（声明字段集是**封闭**的） |
| 令牌有效期 | ≤ 5 分钟，且**三处引用同一个配置项** |

**密钥轮换有并行期**：旧公钥仍可验，在途令牌不会因一次轮换全体失效。

### 2.2 §9.4.2 失效规则 / §9.4.3 版本协商 / §9.4.4 离线降级 / §9.4.5 可区分

这一组的核心是**把六件事分开**，而不是合成一个「校验通过/不通过」：

| 检查 | 需要平台在线 | 平台不可用时 |
|---|---|---|
| 验签 | ❌ | 继续可用 |
| 到期 | ❌ | 继续可用 |
| 契约版本比对 | ❌ | 继续可用 |
| 撤销 / 授权版本查询 | ✅ | 缓存窗口内降级，超窗失败关闭 |
| 签发 | ✅ | 拒绝 |

用例逐条覆盖：在线且缓存未过期时**撤销立即生效**（缓存放行被专门证伪）、
离线无缓存 → 503、离线窗口内 → 放行且**标注「离线期放行」**、超窗 → 拒、
「在线」以**能否取到权威状态**为准而不是进程存活。

§9.4.5 要求**同时失配时两个原因都要给**：契约版本 + 授权版本同时失配 → 响应里
两个原因都在，且**拒绝严格性不变**（仍是 403）。

## 三、这一层查出来的东西

### 3.1 `scopeContext` 静默丢掉了 `DEPARTMENT` / `STORE` 三档（真 bug，已修）

`scopeContext` 读的是 `ctx.deptId` / `ctx.shopId`，而业务端点按**令牌声明**现拼 ctx ——
那里面**没有这两个字段**。后果不是报错，是**静默降级**：
`deptSubtree` 变成空数组，`DEPARTMENT` / `DEPARTMENT_AND_CHILDREN` / `STORE`
三档全部匹配不到任何行 ——**「五档数据范围」实际只剩 `SELF` 和 `COMPANY`**。

方向是 fail-closed（少给权限），所以它不会泄漏；但它会让合法用户被莫名其妙地拒绝，
而且**从测试上看就是一次「正常拒绝」**。

修法：让 `scopeContext` **自己查成员关系**得到部门与店铺，调用方不必记得传。

> 这个 bug 是「五档」这个说法最容易被架空的形态：**代码里写着五个档位，
> 运行时只有两个生效**。它由阶段五的用例逮到 —— 阶段四的用例之所以没逮到，
> 是因为它们**直接把 scope 对象喂给 SQL**，绕过了「谁来构造 scope」这一步。

### 3.2 「脱敏」到底是读策略还是写策略

最初只把 `HIDDEN` 与 `READONLY` 判为不可写，`MASKED` 可以写。
推敲后改为：**可写 ⟺ `VISIBLE`**。

理由：写命令是**部分合并**（`data || patch`），写入一个刚刚被脱敏、
用户看不到原值的字段，等于**盲写覆盖**。fail-closed 的读法在这里是对的。

### 3.3 本地能判的拒绝，不能被远端不可达掩盖

原实现里，平台不可达且无缓存时**先**返回 503，于是
「契约版本失配」这个**纯本地**结论被一个远端依赖盖住了。
§9.4.5 的整个动机就是「拒绝风暴要可诊断」—— 报 503 会让运维去查平台，
而问题在契约版本。

改为：本地已判出的拒绝**优先返回**，并如实标注
`authorizationStatusChecked: false`（**没查到**，不是「查了没问题」）。

## 四、锚点③ §9.6.4.1 风险分级

**封闭清单**（不是可扩展注册表 —— §9.6.4.1 明写「开放清单会让『哪些动作要审批』
变成实现者的自由裁量，既无法测试，也无法审计」）：

| 级别 | 触发 | 处置 | 用例 |
|---|---|---|---|
| R1 | 单笔创建/修改/提交 | 直接执行 | ✓ |
| R2 | 单笔终态变更、单笔删除 | 执行前确认 + 留痕 | ✓（未确认 → `DRAFT_ONLY`，数据不变） |
| R3 | **批量** / **跨业务分组** / **超金额阈值** | 须所有者审批 | ✓（无审批 → 拒；摘要匹配 → 放行；摘要不匹配 → 拒） |

### ★ 本阶段最重要的一条

> **「员工访问其范围外记录 + 所有者已批准」的唯一预期是拒绝。**

§9.6.4.1（v2.15 终审重要 3）写得很明确：**审批是基础校验之上的额外防护，
不能替代基础授权**。所以校验顺序是**基础授权在前、风险分级在后**，
并且有一条专门反证顺序的用例：

- 「范围外记录 + 完全匹配的审批」→ **404**（基础授权拒掉，与审批无关）
- 「既是 R3 又越权、且不给审批」→ 得到的是 **404 而不是 `OWNER_APPROVAL_REQUIRED`**
  （若顺序反了，会先问审批）

**这条门禁是有载荷的。** 把实现改成「有审批就跳过基础授权」，再跑一次：

```
✖ ★ 范围外记录 + 所有者已批准 → 仍然 404
ℹ tests 15  pass 14  fail 1
```

**只有那一条变红，其余 14 条照常通过** —— 该红的红了，不该红的没红。

## 五、锚点④ / G5 交付包完整性

`工具/交付包.py` 维护 `交付/交付包清单.json`：11 个组件，每个带
**路径、类别、版本、文件数、内容指纹**，外加一个覆盖清单本身的**交付摘要**。

它查四件事：

1. 清单里的每一项都在，且指纹一致；
2. **清单之外不存在未覆盖的组件** —— 只查「列了的还在」不够，多出来的文件同样进包；
3. 交付摘要与清单内容一致；
4. **交付内容里没有私钥**（§9.4.1：不得随包明文分发）。

> 第 4 条单列：它一旦出问题，前三条全过也没用。

**反向测试 8/8**：改组件内容不刷新清单 → 红；改版本号 → 红；改交付摘要 → 红；
清单漏列组件 → 红；塞一个私钥文件 → 红；清单不存在 → 退出码 **2**（不是「通过」）。

## 六、与阶段一证据的一处关系

阶段一取证的是「平台服务进程**不加载任何插件**」，判据是
`dshPackagesPresent = false` 且容器内无 `@deepseek-ai/` 目录。
阶段五的 `§9.4.1` 把**签名私钥**同样放在这个进程里 ——
于是「私钥与插件不同进程」这条，用的是阶段一那份**已经复核过的**启动配置取证。
`工具/check_topology.py` 在本阶段后复跑仍为通过。
