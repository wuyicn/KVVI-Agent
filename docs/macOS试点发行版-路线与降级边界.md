# macOS 试点发行版：三条路线与降级边界

> 2026-09-26 业主决定：第一版改为 **macOS 私有化本机发行版**，不做 Linux 企业服务器部署，后续再做。 > 本文记录这三条路线各自的形态、成本与代价，以及第一版对外必须写明的降级。 > 需求正文见 `KVVI-Agent 私有化发行版与产品闭环补充需求-v1.0.md` §9.5 与 §15；本文不复述它。

## 三条路线

| 阶段 | 方案 | 定位 | 客户需要先装什么 | 数据库 |
|---|---|---|---|---|
| 当前第一版 | **C** | 试点／早期客户 | Homebrew `postgresql@17` | KVVI 自建集群，一个实例三个库 |
| 产品闭环稳定后 | **A** | 商业发行版 | 什么都不用 | 数据库打进发行包，一键安装 |
| 企业多人正式部署 | Linux 版 | 企业服务器 | Docker | **三个独立实例** |

**D 不采用**（改为 SQLite／嵌入式库）：会失去 PostgreSQL RLS，也就是 §9.9 那个**独立于应用代码的第二执行点**。`services/platform/sql/20-business.sql` 的文件头写得很直白 —— 应用层的检查是「同一份代码既决定又检查」，它无法独立地证伪自己。删掉它换来的便利，不值得。

**B 暂不采用**（依赖 Docker Desktop）：那更适合开发部署，不适合作为 Mac 产品体验 —— 客户为了用 KVVI 先去装 Docker Desktop，比先装一个 PostgreSQL 更重。

## 「预装 PostgreSQL」与「用自己的数据目录」不矛盾

这是第一版设计里最容易读错的一处，单独说清：

Homebrew 的 formula 提供的是**二进制**（`initdb`、`postgres`、`pg_dump`、`pg_restore`、`psql`），不是「一个正在跑的服务」。KVVI 用这些二进制在 `$KVVI_HOME/pgdata` **自己 `initdb` 一个集群**，监听 `127.0.0.1:$KVVI_PG_PORT`，socket 放在 `$KVVI_HOME/run`。

于是：

- 客户自己的集群保留它的端口、它的 `postgresql.conf`、它的库，**KVVI 从不连它**；
- 「KVVI 使用自己的数据目录与端口」与「PostgreSQL 是预装的」两条同时成立；
- 前置条件因此是**一套二进制**，而不是「必须先有一个在跑的实例」—— 手册可以这么写。

## 第一版必须对外写明的两处降级

### 一、三个独立实例 → 一个实例三个库

| 保留 | 降级 |
|---|---|
| 平台库 / 业务库 / 审计库的**逻辑分离** | ~~三个独立 PostgreSQL 实例~~ → 一个实例内的三个数据库 |
| 每个数据库**独立角色** | ~~实例级进程与配置隔离~~ → 同一个 `postgresql.conf`、同一个端口、同一个 superuser |
| 业务数据继续使用 **RLS** | — |
| 审计库只能通过 `audit_append` 写入 | — |
| 普通写入角色没有直接修改审计记录的权限 | — |

**为什么这不推翻既有设计**：上面「保留」的四条都不依赖实例数量 —— 它们靠的是独立数据库、独立角色与 GRANT/REVOKE，这些在一个实例里同样成立，`services/platform/tests/isolation.test.mjs` 就是验它们的。

**真正失去的是什么**：一个实例被攻破时，三个库一起失去；三个实例形态下，攻破平台的库不带出审计库。这是**故障与攻陷范围**上的差别，不是「权限判据」上的差别。说清这一点，比含糊地说「隔离变弱了」有用。

### 二、两个容器 → 一个用户下的两个进程

`PRD §4.6.5` 的措辞是「两进程分属不同容器**或**不同系统用户」。第一版两条都不满足：平台与运行时都作为安装它的那个用户运行。

内网令牌仍然鉴每一个平台→运行时的调用，运行时仍然只监听回环地址，所以**跨进程越权**没有直接打开；但一个能读该用户文件的本地攻击者能同时碰到两者。补法有两条 —— 回到 Docker，或者给运行时代码单独建一个系统用户；**后者更便宜，应当在试点结束前补上**。

## 第一版的七条硬性验收

| # | 要求 | 不成立会怎样 |
|---|---|---|
| 1 | 固定支持的 PostgreSQL 大版本（17），不跟随 Homebrew 最新版 | 客户 `brew upgrade` 后版本漂移，行为与取证时不一致 |
| 2 | 安装器自动检测 Apple Silicon 与 Intel 两套 Homebrew 路径 | Intel 机器上检测不到，报成「未安装」 |
| 3 | KVVI 使用自己的数据目录与端口，不污染客户已有数据库 | 客户既有的库被迁移脚本碰到 —— 与「私有化」背道而驰 |
| 4 | 自动创建三个数据库与对应角色，不让客户手工执行 SQL | 手工步骤既是出错来源，也无法被安装器验证 |
| 5 | 支持备份、恢复与数据库版本升级 | 客户的数据没有退路；试点版尤其不能没有 |
| 6 | 卸载应用时默认保留客户数据 | 一次误卸载等于删库 |
| 7 | PostgreSQL 未安装或版本错误时给出**明确引导**，不能只显示启动失败 | 「启动失败」会把版本问题伪装成程序缺陷 |

第 7 条值得展开：**当前这台开发机就没有装 PostgreSQL**（`/opt/homebrew/bin/psql` 与 `/usr/local/bin/psql` 都不存在），所以「未安装」这条分支随时可以在本机真实地验一遍，不需要造场景。

## 验收机器的问题

G9 要求「一台从未安装过 KVVI 的 macOS 机器」。这件事**在本机按字面做不到** —— 本机已经装过。

三条可选，**业主 2026-09-26 选定第一条**：

| 做法 | 是不是「另一台机器」 | 采用 |
|---|---|---|
| 开发机上的**全新 macOS 用户账号**（独立 `$HOME`，无任何 KVVI 痕迹） | ❌ 同一台机器 | ✅ **本次选定** |
| **UTM / Tart 里的虚拟机**（干净 macOS） | ✅ | 后续按需 |
| 另一台**真实 Mac** | ✅ | 后续按需 |

**代价必须写进证据**：全新用户能证到「安装、初始化、备份恢复、卸载保留数据在一个从未跑过
KVVI 的环境里成立」，**证不到**「不同 macOS 版本、不同硬件、真无外网、真另一台机器」。
取证文档按 §13 的证据纪律如实标注，不得因为「是同一台机器」而略过。

**后续触发条件**：对外正式交付前，或客户环境出现与开发机明显不同的 macOS 版本时，
补一次虚拟机或真机验收。
