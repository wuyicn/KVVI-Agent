## 事项 1 · 看板在当前契约下没有载体（卡 4）

### 1.1 现状事实

**我核实过的**：

| 事实 | 核实方式 |
|---|---|
| `view_type` 只有 `FORM` / `LIST` / `DETAIL` | 读 `view-schema.lce-safe-v1.schema.json` 的 `Spec.properties.view_type.enum` |
| 唯一的实体组件注册表含 **23 个组件，无任何图表** | 全仓库扫描 **1293 个 json**，找到 2 个 `COMPONENT_REGISTRY` 引用；只有 `vue_element_approved` 有实体内容，另一个 `synthetic-component_registry` **只有引用、无 content** |
| 组件类型分布 | 页面级 3（Form/List/DetailPage）、容器 2（Section/Grid）、字段类 10、展示类 5、按钮类 3 —— **无 line / bar / pie / gauge / scatter / funnel / radar 之类** |
| PRD §5.1 给 `dashboard-builder` 定的目标契约 | 「`view-schema` + **聚合口径配置**」 |

**我还没核实的**：

- 生产环境的注册表是否与此不同（我拿到的是**测试 fixture**，`asset_id: vue_element_approved`）
- 是否存在**另一个**契约专门承载看板
- 「聚合口径配置」是否指某个我尚未识别的 schema

### 1.2 问题的确切形状（核实后细化）

卡 4 的产出是**两半**：**聚合口径** + **图表**。核实后两半的情况不同：

| 半边 | 载体 | 状态 |
|---|---|---|
| **聚合口径** | **有** —— 它是 `CAPABILITY` 资产（由 `CAPABILITY_REGISTRY` 承载），`view-schema.queries[].query` 通过 `DataQueryRef` → `CapabilityRef` **引用**它 | ✅ **有载体** |
| **图表** | **无** —— 没有对应的 `view_type`，注册表里也没有图表组件 | ❌ **无载体** |

**所以问题收窄为**：卡 4 的**口径那一半可以装配**（引用已登记的口径 capability），
**图表那一半无处安放**。

> **更正**：本节早先写「不是聚合口径落在哪个 schema」，措辞不准确 ——
> 口径的载体是找到的（`CAPABILITY`）。真正缺的只有图表。

### 1.3 三种可能

| | 可能 | 若是，则 | 需要做的事 | 结论 |
|---|---|---|---|---|
| **A** | 生产注册表**另有图表组件**，`vue_element_approved` 只是测试 fixture | §1.1 的结论不适用 | 拿到生产注册表即可继续 | ✅ **已采纳** |
| **B** | 看板需要**新的 `view_type`** | `view-schema` 契约要**扩展**（`enum` 加值） | 走契约变更流程 + G2 改造点登记 | ✗ 不需要（见 1.5） |
| **C** | 图表作为**组件加进注册表**，看板用 `DETAIL` 承载 | 契约不动，只扩注册表 | 需要图表组件的登记定义 | △ 承载改用 `LIST`；组件形态保留为 A 的后续手段 |

**三者对工程量的影响差别很大**：A 是零成本，B 要动契约（走 SOP），C 要产组件定义。

### 1.4 决策：采用 A（2026 年阶段三）

> **产品侧决定：先用 A。后期遇到什么问题再解决** ——
> 图表功能做成**组件 / 插件**加进注册表（即 C 的形态），届时再处理。

### 1.5 ⚠️ 更正：问题比原先写的**小得多**

核实后必须修正两处：

**（一）看板本来就有载体 —— `LIST`。** `ListPage` 的 `viewTypes` 是 `["LIST"]`，
「看板」与「列表」的差别**在放了什么组件**，不在视图类型。
所以**不需要**新增 `view_type`（B 被排除）。

**（二）口径的接入通路是完整的，且已端到端跑通。**
`Spec.queries[]` → `DataQueryRef` → `CapabilityRef`，节点侧 `props.data`
写 `DataBindingRef {queryCode, itemKey, maxItems}`。已产出并验证：

| 产出 | 验证 |
|---|---|
| `样例/view-schema/月度销售看板.spec.json` + `context-看板.json` | 结构 + 语义 + 引用**三层通过**；6 项改坏全部被拒 |
| `样例/view-schema/看板-口径登记.json` | §9.8.1 不变量**判定通过**；3 项改坏全部被拒 |
| `工具/check_invariant.py --input` | 新增通路，自测 5/5 → **9/9** |

**所以真正缺的只有「图表组件的名字」** —— 而名字来自注册表，正是决策 A 的范围。

## 事项 2 · ~~`app-model-command` 没有校验入口~~ → **已自行解决**

> **这条曾被我列为阻塞，核实后不成立。记下来因为它是个教训。**

**当时的判断**：全量结构校验器报 `no_spec_definition`，所以该契约无法验证。

**核实后**：它的 `$ref` 指向 **`#/$defs/Command`**，**根定义不叫 `Spec`**。
把「根定义不叫 Spec」当成「没有校验入口」，凭空造出了一个不存在的阻塞。

**修正后实测**：**78 条用例判定一致 78/78** ✓

### 由此修掉的一个方法论错误

契约的用例带一个 `entry` 字段，**它决定该用例该用哪个根定义校验**：

| `entry` | 根定义 |
|---|---|
| `spec` | `#/$defs/Spec` |
| `compiled-draft` | `#/$defs/CompiledDraft` |
| `registered` | `#/$defs/RegisteredContract` |
| `command` | `#/$defs/Command` |

**我曾只按 `valid` 筛用例、不按 `entry` 选根定义** —— 结果拿 `registered` 态的值
去校验 `Spec` 定义，得到「缺 20 个必填字段」，看起来像产出物坏了。

**修正后按 entry 映射，四个契约全部 100% 一致**：

| 契约 | 用例数 | 判定一致 | 不符 |
|---|---|---|---|
| `tool-spec` | 34 | **34** | 0 |
| `app-model-command` | 78 | **78** | 0 |
| `workflow-spec` | 69 | **69** | 0 |
| `permission-spec` | 58 | **58** | 0 |

该映射已烤进 `工具/lib/full_bundle_check.mjs`（`ENTRY_TO_DEF`），
调用方传 entry 名或 `$defs` 名都能选对 —— **不再依赖人记得**。

## 事项 4 · `CAPABILITY` 资产的**登记内容没有契约**（卡 4 新发现）

**现状**：13 份 MetaSchema 里，`capability_code` 只出现在 `common.schema.json` 的
`CapabilityRef` 里 —— 那是**引用形式**（`asset_type` + `capability_code` + `digest`）。
**没有任何一份契约定义了 capability 资产本身**的合法形态：
`category` / `inputSchema` / `outputSchema` / `itemKeys` / `runtimeDigest` /
`rateLimit` / `sideEffects` … 这些字段没有 Schema 管。

旁证：`tool-spec` 的 `$defs` 里**有一个 `CapabilityRef` 定义，但全文件没有任何地方引用它**
（只有定义、没有使用）—— 看起来是一个未接上的占位。

**影响**：
- `view-schema` 引用 capability 时，验证器能查出「引用错了」（未登记 / 摘要不符 /
  `category` 不对 / `params` 不合 `inputSchema`）；
- 但**查不出「这条登记内容本身是否合法」** —— 例如 `itemKeys` 为空数组、
  `outputSchema` 与 `inputSchema` 不自洽、`state` 不是 `PUBLISHED` 之外的值。
- 所以卡 4 的验收里，**「口径登记内容合法」这一项不在覆盖范围内**，
  SKILL.md 已把它写进「已知边界」。

**需要谁决定**：产品侧 —— 是否要为 capability 资产补一份契约（或明确它归
平台侧资产、不由搭建产出）。

**不阻断卡 4**（引用层已验证），但会让「口径」这一半的**形态合法性**留在契约外。

## 事项 5 · 五份产出「逐份通过」但没有构成一个系统（**已解决**，值得记下）

> 这条是 `0D-1` 的闭环检查查出来的，**不是**任何一份逐份校验能查出的。
> 记下来是因为它是一类**结构性盲区**，不是一次手误。

**当时的事实**：

| 来源 | `general_item` 的字段 | 摘要 |
|---|---|---|
| `样例/business-schema/通用事项.spec.json`（`data-model` 的产出） | `item_no` / `title` / `detail` / `amount` / `due_date` / `item_status` | `898c0ae1…` |
| `样例/view-schema/context.json` 内嵌的那份 | `title` / `category` / `quantity` / `amount` / `due_date` / `notes` | `518077ba…` |

**两边各自都过完整校验**，但表单绑定的 `category` / `quantity` / `notes`
在真正的模型里**根本不存在**。同族第二处：字段类型注册表在业务侧叫
`fake-business-types`、视图侧叫 `business-field-types-core`，摘要相同、
`asset_id` 不同，而引用校验按 `asset_id` 找。

**根因**：`工具/check_skill_output.py` 逐份校验，每份都在**自己的上下文里**
自洽；没有任何环节要求「五份产出引用同一个模型」。

**已修**：`工具/视图样例上下文.py` 由数据模型样例重建两份视图上下文；
表单改绑真实字段；两份 `SKILL.md` 的内嵌示例同步重嵌并复验。

**遗留**：这一类缺陷目前**只有蓝图检查器能发现** —— 不经过蓝图的产出不受此保护。
已记入 `进度.md` N13。
