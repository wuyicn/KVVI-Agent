## 一、判据

**什么算「上游默认品牌元素」**：会被渲染成用户可见文本的上游产品名、Logo、文案。

**什么不算**（不得计入残留）：

| 类别 | 例子 | 为什么不算 |
|---|---|---|
| npm 包名 | `@deepseek-ai/dsh-*` | 代码标识符，用户不可见；改名会破坏上游升级 |
| provider / API 名 | `deepseek` 作为模型供应商 | 是**外部服务名**，不是产品品牌 |
| 变量 / 类型名 | `DeepSeekClient` | 代码内部标识 |
| 文件路径 | `packages/client/...` | 非用户可见 |

> **这条区分是清单的核心**：把「包名里含 deepseek」当成品牌残留，会导致
> 要么误报泛滥、要么被迫改包名而破坏上游升级。**残留只算用户看得见的那部分。**

### 为什么 R3/R4 用中性表述，而不是写死「KVVI 搭建引擎」

写死产品名会让**产品名有两个来源**：一处是构建期注入的 `DSH_CLIENT_TITLE`
（它已经决定了浏览器标题与产品抬头），另一处是这两个 locale 字面量。
两处一旦不同步，界面就会出现两个产品名。

中性表述（「本系统」「本服务」）同时满足三点：消除品牌残留、
语义对用户更清楚、**产品改名时无需跟着改**。

> 这与 `kvvi-brand` 采用「读 `DSH_CLIENT_TITLE` 而非写死」是同一条原则：
> **产品名保持单一来源。**

### ⚠️ 清理源码后必须重建产物

检查器**同时查源码与产物**，这不是冗余：

| 谁查得出什么 | 场景 |
|---|---|
| 源码 | 「还没构建就已存在」的残留 |
| 产物 | 「源码已改但**没有重新构建**」的残留 |

本次修复时**两者都命中了** —— 源码清干净后产物仍报 9 项，因为产物还是旧的。
只查其一都会漏，而这两类是**不同的失败**。

重建命令（只重建受影响的包，秒级）：

```bash
pnpm --filter @deepseek-ai/dsh-client-ui-plugin-manager bundle
pnpm --filter @deepseek-ai/dsh-client-ui-settings-models bundle
pnpm --filter @deepseek-ai/dsh-client-ui-sidebar-documentpreview bundle
```

## 三、检查方式（锚点③「机器可检」）

```bash
python3 工具/check_brand.py         # 逐项核销
bash 工具/check_brand_自测.sh       # 反向测试：证明它在该红时会红
```

检查器**只检查会被渲染成文本的载体**，不做全仓库字符串搜索：

| 载体 | 检查什么 |
|---|---|
| `manifest.webmanifest` | `name` / `short_name` 字段 |
| `apps/web/dist/index.html` | `<title>` |
| locale 字典 | 字符串**值**（键名不计） |
| 构建产物 `lib/client.js` | 同上（产物才是用户真正加载的东西） |

**明确不检查**：包名、import 路径、变量名、`deepseek` 作为 provider 名的出现。
