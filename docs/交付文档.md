## 一、交付包构成

组件清单、版本与内容指纹见 `交付/交付包清单.json`（11 个组件）：

| 组件 | 内容 |
|---|---|
| `contracts` / `protocol` / `meta-schema-validator(-full)` | 契约层与验证器 |
| `platform-service` | 平台服务进程（身份层 / 授权 / 签名 / 认证端点 / 访客后端） |
| `runtime-service` | Agent 运行时进程（容器入口） |
| `agent-preset-builder` / `agent-preset-worker` | 两个模式的预设（含五个搭建 Skill） |
| `client-plugin-brand` / `bundle-kvvi-app` | 品牌客户端插件与 Profile Bundle |
| `schema-samples` | 产出样例、蓝图、行业扩展包、黄金样例 |

### 1.1 交付形态：**自包含 tar**（业主选定）

```bash
python3 工具/fork.py --rebuild --into /tmp/kvvi-fork   # 上游干净副本 + 我们的 35 个文件
python3 工具/fork.py --bundle                          # → 交付/包/kvvi-delivery.tar.gz
```

| | |
|---|---|
| 产物 | `交付/包/kvvi-delivery.tar.gz` —— **12364 条目 / 25.1 MB** |
| 内容 | KVVI 全部交付组件 **+ 重建出来的 `vendor/dsh`** |
| 特点 | **解压即可运行，不需要联网**、不需要访问 GitHub |
| 可核验 | tar 里的 `vendor/dsh` 是**重建产物**（不是工作副本），重建结果与 `forks/dsh/改造点指纹.json` **逐字节一致**（35/35） |

> **为什么源码仓库里没有整个 fork**：上游是 12100 个文件，我们只动 **35 个**。
> 入库整个上游，代价是**每次上游更新都要在 200 MB 的 diff 里找出我们的 35 个文件**。
> 所以仓库只存**改动**（`forks/dsh/变更/`，1157 KB），交付时现打一份自包含的包。

核验：`python3 工具/交付包.py --check` —— 逐项复合**内容指纹**，
并检查**清单之外没有未覆盖的组件**、**交付内容里没有私钥**。

## 二、部署基线与安全成立条件（PRD §4.6.5）

### 2.1 基线

> **本节列出的条件成立时，§4.6.5 的边界才成立。**

| # | 条件 | 本方案中的对应 |
|---|---|---|
| 1 | 两进程**分属不同容器或不同系统用户** | `docker-compose.kvvi.yml` 的 `platform` / `runtime` 两个 service |
| 2 | **禁止跨进程调试** | 不共享 pid/ipc namespace |
| 3 | **无共享可写文件系统** | 各自独立的 named volume，无共享挂载 |
| 4 | 两进程间接口**有调用方鉴别** | 受控端点要求 `KVVI_INTERNAL_TOKEN` |
| 5 | **平台服务进程不加载任何插件** | 镜像内没有 `@deepseek-ai/*`；可核验的启动配置 |
| 6 | **签名私钥仅存于签名进程** | 私钥由运行期挂载，不进镜像、不进仓库、不进日志 |
| 7 | **审计库不共享主机管理域 / 备份通道 / DBA**（§4.6.1） | 三个库分属三个容器、三个卷、三个 superuser 口令，且只在 `internal: true` 的网络里（`工具/check_db_isolation.py`） |

前四条在 compose 里成立；第五条由 `工具/check_topology.py` 与 `/topology` 端点复核；
第六条由「镜像内无私钥」的构建期约束保证。

### 2.2 ⚠️ 基线之外**不属于保证范围**

**明确不保证的情形**（读者不要把下面的部署当作满足基线）：

| 情形 | 为什么不保证 |
|---|---|
| 两进程部署在**同一容器**或同用户下 | 插件与身份判定同进程，「不加载插件」不再成立 |
| 挂载了**共享可写卷** | 重新开出一条进程间越权路径 |
| 开放了**跨进程调试** | 调试通道即任意读写 |
| 受控接口**未配置调用方鉴别** | 任何能到达该端口的进程都能调 |
| **私钥被放进镜像或仓库** | 签名私钥应仅存于签名进程；分发即泄漏 |
| 把三个库**合并成一个** | 「审计不可篡改」与「读权限独立」都只剩纪律 |
| 把三个库放在**同一台主机**上 | ⚠️ **本方案目前就是这样。** §4.6.1 的「不共享主机管理域」在容器/卷/口令三层已成立，**「独立主机」未成立** —— 那是托管面的决定 |

### 2.3 已确认的**固有边界**（不是待修缺陷）

> **已批准插件可冒用活跃会话的既有令牌。**
>
> 业务系统调用必须持有已签发的令牌，而运行时进程就是持有者；插件与该进程同进程，
> 可窃取任何活跃会话的短期令牌并直接调用业务系统。该令牌是真实权限、验签通过。
>
> **两进程划分消除的是「伪造与提权」，不是「冒用活跃会话」。**
> 其操作追溯已由红线 3 第二段排除。**交付时不得把这条写成「已解决」。**

## 三、验收证据包（PRD §7.1 阶段七）

```bash
python3 工具/验收证据包.py            # 跑各阶段判据并生成证据包
python3 工具/验收证据包.py --verify   # 复核证据文件与指纹
```

证据包位于 `交付/证据/`：`验收证据包.json` + 每个判据一份 `.txt`（输出**原样**保存）。

**设计上只做三件事：跑、原样存、记指纹。** 本工具**不做第二判定者** ——
如果它把各检查器的输出解析成自己的结论，两个判定者迟早不一致，
而不一致时无法判断该信谁。

> ⚠️ 各检查器输出末尾都有「本阶段未覆盖」一节，它**一并被收进证据文件**。
> 把「测过什么」与「没测什么」分开存放，会让后者在交付时消失。

## 五、交付时的诚实清单：**不主张**什么

| 不主张 | 依据 |
|---|---|
| 不主张**安全评审已完成** | 冻结记录 §「不主张什么」；§9.12 要求发布后由专门人员做正式威胁建模 |
| 不主张**契约层已验证完整** | 验证器自述 `semantic_validation_complete=false`、`runtime_verified=false`。13 份契约里只有 **3 份**（`business-schema` / `view-schema` / `app-spec`）走**完整校验**；`workflow-spec` 是「结构 + N9 补的 complete check」，`tool-spec` / `permission-spec` / `app-model-command` / `migration-plan` 等**仍只有结构校验** |
| 不主张**模型输出稳定** | 黄金样例兑现的是「装配确定性」，不是「同一需求十次同一蓝图」 |
| 不主张**运行期行为符合配置** | 各检查器判定的是**配置**；运行期是否真按配置执行不在判定内 |
| 不主张**审计对插件运行期有效** | 完整性以「写入者不拦截审计」为前提；已作恶插件可拦截 |
| 不主张**访客可区分个体** | 追溯单位是签发人 + 链接 + 通道 |
| 不主张**部署面已满足 §4.6.1** | 三个库在同一实例上；逻辑隔离做到了，部署隔离没有 |

### `workflow-spec` 的 complete check 覆盖到哪一层

契约的 `$defs.Spec.$comment` 把五件事声明为 complete-check 职责。
实现落在 `工具/check_workflow_semantics.py`，**覆盖边界必须一并交付**：

| # | 项 | 覆盖情况 |
|---|---|---|
| 2 | per-step coverage | ✅ 做（出边 + 可达性 + 能否走到终态） |
| 3 | graph order | ✅ 做（状态/动作引用、`initial` 唯一、终态无出边） |
| 5 | 100-leaf total | ✅ 做（**保守读法**：状态+迁移+分支+谓词 ≤ 100） |
| 1 | role directory resolution | ✅ 做（解析目标 = `工具/lib/role_directory.py`） |
| 4 | selector field matrix | ⚠️ **只做最弱读法**：字段是否存在 |

**#4 为什么没做全**：契约只给了检查的**名称**，没给判据。
「matrix」至少三种读法都说得通 ——(a) 字段类型×操作符×值类型、(b) 字段是否存在、
(c) 分支覆盖不留缝 —— **三种读法会拒绝不同的配置**：选 (c) 会把
「只处理 5 万以上、其余走 default」这种完全合法的流程拒掉。
按猜测实现一个会挡人的校验器，比没有更糟：它会断言一件契约从没说过的事，
而下一个翻契约的人找不到，只能回来读实现，**把一个人的猜测变成产品行为**。
故 (a) 与 (c) **明确不实现**，并在检查器输出里逐次写明。

> 另：`Transition` 在契约里 `additionalProperties: false`，**没有 `when`**。
> 因此「迁移带条件」这种形态在本契约里无处安放 —— 检查器会把它当缺陷报出，
> 而不是假设某处存在更复杂的条件分支语义。
