# KVVI-Agent 搭建预览与会话体验改进设计

日期：2026-10-12。状态：用户已确认书面设计，进入实施计划；产品代码尚未修改。

## 目标与用户流程

让搭建者用业务语言描述需求，直接看到能检查和试填的表单，提出修改后看到预览更新，最后点击按钮提交审批。所有者与员工的日常 AI 回复同样不展示内部技术过程。保留已有审批、权限和数据隔离边界，不把“已生成”说成“已发布”。

用户已同意的方向：描述需求 → 左侧生成表单预览 → 右侧对话修改 → 搭建者确认提交 → 所有者审批发布。

2026-10-12 布局原则补充（用户确认）：全局导航保持最外侧，内容区辅助内容统一放左侧。会话区为左侧业务预览、右侧主会话；业务区为左侧 AI 辅助、右侧表单与记录。业务 AI 默认收起，点击「AI 协助」展开；支持收起及调宽，已有对话和表单不因收起而重置。先在 7506 验证，正式接入不变更审批边界。

本次从普通登记表开始，覆盖店铺登记的文字、单选、日期、多行文字、必填及不重复规则。复杂跨表、附件、图表和插件生态不在本轮扩展。遇到不支持的需求明确说明，不生成看似可用的假控件。

## 已核对的问题

- 7500 的店铺管理会话存在 102 个内容为空的 assistant-step 外层，每个仍有 16px 间隔。内层不显示不等于外层不占布局。
- 搭建者预设已有业务语言要求，但实际回复仍出现模型、接口、工具、校验器、文件路径。现有模型指令不足以保证日常界面体验。
- 同次会话有 134 个模型步骤、153 次工具调用，其中命令操作 111 次，涉及查找规范、探查环境和调试验证方法。最后两次提问应答失败分别等待约 178 秒与 268 秒。总时长还包含正常等待用户回答，不能全部算作生成时间。
- 当前业务页面读取已发布结果；发布服务已有提交、审批和发布分离，但未发现与搭建对话联动的草稿表单预览入口。

上述现象来自 2026-10-12 对当前页面、会话记录及代码的只读检查，不代表改进已经完成。

## 方案选择

采用“业务会话展示层 + 固定草稿准备能力 + 草稿预览工作台”。复用已有会话、表单呈现和发布通道，不另造审批系统。

只加强提示词无法消除空消息占位，也不能替代预览与提交按钮；仅加静态预览则可能出现预览内容和实际提交不同。因此本轮同时约束展示、草稿版本和提交内容。分阶段实现，每阶段独立验证，不把原型当成服务已接通。

## 会话展示与后台执行

后台工具执行、推理及内部检查仍记录在受控诊断中，但不进入业务消息列表。隐藏节点及只含后台内容的空步骤不产生消息外层、间距、滚动锚点或复制内容。流式步骤从无可见内容变成有内容时再呈现；完成后不得留下空位。不得删除历史原始记录。

运行时只显示一个更新中的简短状态，例如“正在整理表单”“正在检查填写规则”“预览已更新”。没有真实完成证据时不显示完成，不估造百分比。错误、权限拒绝和需要用户回答的业务问题不能随后台过程一起消失；同一故障合并提示，提供能执行的恢复动作。

面向所有角色的正常回复只包含业务进展、结果、待决定事项。结构化错误和检查结果由平台转成业务文案；AI 的交流约束覆盖进度、问题、目标摘要与最终答复。原始自由文本历史不批量重写；新工作台的状态与交付摘要以结构化结果为准，不再直接把内部执行说明作为交付页。不得用删技术关键词的方式破坏字段值、业务编号或用户自己的文字。

需要用户输入时，当前问题必须始终可见。提交不再调用临时提问工具等待一句“可以提交”。已知无人接收的交互失败必须结束等待并显示恢复入口，不能重复隐形等待数分钟。

## 固定草稿准备能力

平台提供受控的草稿准备入口，接收已确认的表单字段、类型和业务规则。普通登记表的公共结构、组件映射及验证入口由产品内置，AI 不再为每张表搜索源码、搭建验证环境、安装依赖或直连数据库探查权限。

该入口生成与现有发布协议兼容的完整草稿内容，调用既有权威验证能力并返回结构化错误、可呈现表单和草稿版本。只处理已支持的表达；不允许任意代码、任意路径或任意数据库访问。修改提交当前版本和改动要求，保留未修改项，版本冲突时要求重新读取，不能静默覆盖。

当前生产组件注册与部分检查能力有限，不能拿测试 fixture 当生产通过证明。首版显式列出能实际呈现和验证的组件；缺少权威验证入口或语义不支持时阻止“可提交”状态。安全与发布检查不因追求速度而跳过。

权限尚未确定时允许预览，但不默认赋予销售或其他角色全量访问。工作台显示“使用权限待确认”，用户明确配置后才能提交。搭建者在预览中试填不代表其获得正式业务记录使用权。

## 预览工作台

保留全局导航。主内容左侧为较宽的表单预览，右侧为搭建对话；窄屏用“预览 / 对话”切换，保持同一草稿状态。初始无草稿时显示具体引导，不显示大块无说明的空白。

左侧包含表单名称、生成进度或草稿状态、可试填的控件、业务规则摘要以及“确认提交”。右侧只承担需求补充、修改指令和必要问题。用户说“手机号改为必填”等要求后，左侧更新并标出变更，保留版本标识供系统核对，但不向用户展示内部编号。

试填使用独立的临时数据，不能调用正式记录写入、审批执行或外部连接。必填和格式可在预览检查；不重复规则以明确标记的示例记录试验，不读取正式数据来制造“验证通过”。发布后的实际权限和并发约束仍需运行时验收。

状态至少区分：等待需求、正在生成、有内容但检查未完成、可提交、正在提交、待审批、需要修改、已发布。只在完整验证通过、权限配置已确认且版本未变化时允许提交。检查中和失败时保留上一个可见草稿，并明确标注不是最新完成版本。

## 草稿版本与确认提交

草稿快照归属当前公司、搭建意图和授权工作区；会话切换后清理前一工作区的预览与试填状态。服务端校验归属及当前搭建资格，不能相信前端传来的公司、用户或任意文件路径。员工不能读取搭建草稿。

预览绑定不可变的草稿版本与完整内容摘要。点击“确认提交”提交该快照，不触发 AI 重新生成。服务端在提交时复验登录、搭建资格、草稿归属、完整性与版本，并复用发布通道及搭建意图绑定。内容自预览后变化时拒绝提交旧确认，展示最新内容让搭建者重新核对。

提交有幂等标识：双击、请求超时后重试和页面刷新不重复创建审批单。恢复时读取实际提交状态，不把未知结果当失败或成功。成功后显示“已提交，等待所有者审批”，不得显示“已发布”。

固定按钮必须由用户真实点击，不能由 AI 输出内容触发。既有 AI 发布提交工具继续保留其人工确认保护；新的界面提交走专用的已认证、人为点击流程，不全局移除工具审批。所有者提交自己的修改仍遵守既有禁止自审批规则，不能借预览入口绕过。

旧工作区只读导入其有效草稿，不依赖扫描任意目录。现有店铺草稿不自动提交、发布或覆盖。无法确定工作区和表单归属时显示选择或修复提示，失败关闭。

## 组件职责与现有代码接点

| 层 | 职责与接点 |
| --- | --- |
| 会话呈现 | `ui-chat` 的 `ChatNodeSeat`、业务呈现判断与消息间距；确保后台及空步骤在布局外，不改原始事件 |
| AI 搭建约束 | `agent-presets/kvvi-builder` 与业务启动上下文；调用固定能力，减少查找和重复播报；员工预设保持业务文案一致 |
| 草稿准备服务 | 受控生成、完整校验、版本与归属检查；不把逻辑塞入 React 组件 |
| 预览及对话工作台 | `kvvi-panel` 复用会话与表单呈现，注入预览读取、修改与提交动作；预览数据和正式记录分开 |
| 发布服务 | `publish-api.mjs`、`publish.mjs`、搭建意图；保留权限、审批和发布事务，接入快照核验与幂等 |

## 验收标准

1. 包含 102 个空步骤的真实会话不再留下对应间隔；流式、刷新、历史加载、切换会话和回到底部正常。原始诊断事件仍可由授权诊断读取。
2. 搭建者、所有者、员工的状态、错误和确认控件不出现内部术语；新建、修改、失败重试的模型回放及实机会话检查同样通过。业务字段值和用户文字不被误删。
3. 八字段店铺登记在需求确认后生成可试填预览；字段类型、必填及规则与草稿一致。标准场景不发生环境探查、依赖安装或直连库命令。记录模型生成、检查、网络及用户等待的独立耗时，不承诺未经实测的秒数。
4. 修改一项后预览更新；旧版本确认不能提交；双击与超时重试只产生一个审批单。未完成、无权限及跨公司读取或提交均被拒绝。
5. 预览试填不写正式库；正式系统不因草稿编辑而改变。待审批不会被呈现为已发布，审批自我授权仍被阻断。
6. 先在 7506 确认工作台布局，再在隔离测试数据中跑真实预览和提交流程，最后接入 7500。源代码测试通过不能替代浏览器与真实身份验收。

## 交付顺序与本次边界

实现顺序为：消除空白占位与业务状态 → 固定准备及检查能力 → 预览和修改 → 快照提交 → 各角色联测。布局继续沿用 7506 确认、7500 接入的既有约定。

本设计不修改冻结需求、不扩大账号权限、不删除会话，也不提交现有店铺草稿。书面设计审阅通过后再形成实施计划，并在计划确认后开始产品代码修改。
