# KVVI 统一业务与分组管理正式接入设计

状态：2026-10-09 用户已确认书面设计，进入实施计划阶段。目标是把已确认的 7506 分组界面接入 7500 的真实账号、业务数据和发布流程。本文件补充实施设计，不修改冻结 PRD，不代表功能已经交付。

## 已确认的产品规则

- 取消业务系统列表和页头业务切换器。点击「业务」直接进入统一的表单与记录工作台，左侧按分组组织。
- 分组属于公司，由搭建者统一管理。员工只按既有权限查看、提交或修改表单记录，不能管理分组和表单结构。
- 搭建者可以新增、重命名、删除分组，并调整表单归组。删除分组保留表单及记录，移入「未分组」。
- 删除表单采用归档，可恢复，不清空历史数据。
- 新增和编辑表单接入真实搭建与发布流程，不用原型中的即时假发布替代。
- 分组管理在正式接入范围内。实施可以分步，但不能把仅迁移外观标为整版接入完成。

## 界面与使用流程

顶部显示「业务」，保留新增分组、新增表单、编辑表单、归档表单和按需展开的 AI 协助。归档按钮与确认窗口明确说明数据保留，不能写成永久删除。搭建者另有「已归档」入口及恢复操作。

左侧使用单层分组。表单只归属一个分组，也可以不归组。分组可折叠，搜索覆盖全部有权显示的表单。空分组仅在搭建模式可见。员工不显示其无权访问的表单、草稿或归档表单；不通过分组名、计数或搜索结果泄露隐藏表单。

工作区保持以会话为主，业务页保持以表单和记录为主。业务页切换表单时，记录、草稿及 AI 上下文仍绑定对应的真实表单标识；不能合并到一个假业务标识而串用记录。刷新、重登、换浏览器后，公司分组和归组关系仍一致。

## 正式数据保留方式

界面取消系统层级，不等于改写底层发布标识。保留现有 assetId、systemId、schemaCode、契约版本、记录主键与审计引用；沿用真实数据读写和发布接口。原型中的 GAD、访客等示例不得导入正式数据库。

新增公司范围的目录元数据：分组表保存公司、分组标识、名称、顺序和版本；表单目录表以公司与真实 assetId 为唯一键，保存分组引用、归档状态、操作人、操作时间和版本。关联约束必须包含公司，防止跨公司归组。

升级后现有真实表单默认进入「未分组」，由搭建者整理。不根据原型示例名创建正式分组，也不迁移或复制业务记录。分组是目录组织方式，不承担数据授权功能。

## 服务端能力与权限

在现有平台产品 API 中新增目录读取、分组新增改名删除、表单归组、表单归档和恢复能力。客户端仅展示服务端确认结果，失败时保留原状态并提示原因。接口的最终路径和错误码在实施计划中列出。

写操作必须同时满足：有效会话、所属公司、当前 BUILDER 模式及仍有效的搭建资格。公司与用户取自可信会话，不接受请求体自报。现有所有者只有按平台规则进入搭建模式后，才能执行这些目录操作；本功能不额外授予任何账号搭建资格。

具有搭建资格但当前处于员工模式的用户，可看到切换搭建模式的入口，不能直接写分组。管理员标签本身也不代替搭建资格。员工的记录权限继续由既有授权执行点、字段规则和 RLS 判定，不另建一套前端权限。

目录读取按真实表单权限过滤；对归档状态的检查放在共用的业务执行路径，覆盖界面 API 与 Agent 工具。不能只在左侧隐藏后，仍允许通过旧链接或工具正常操作归档表单。

新增、改名、归组、删除分组、归档与恢复均留审计记录。采用事务与版本检查防止并发覆盖；创建和状态切换支持安全重试。归组时检查目标分组存在且属于本公司；删除分组和移出成员在同一事务完成。

## 表单归档与恢复

归档保留契约、记录和历史引用，但停止普通目录展示及普通表单操作。归档后的新请求和尚未提交的写入必须被共用执行点拒绝；已提交的历史写入不回撤。客户端收到归档状态后退出编辑并提示，不把提交失败显示为成功。

恢复使用原标识和原有权限，不创建新记录副本，不重置授权。原分组仍存在则恢复其关联，否则进入「未分组」。恢复不会自动批准未发布的契约修改。归档列表只提供必要的管理元数据；查看历史记录仍需原有业务读取权限。

本轮不提供永久删除记录或清空表单数据。归档不改变备份、审计留存与既有发布审核规则。

## 新增和编辑表单

复用正式搭建入口、工作区绑定和契约产物。新增表单在搭建与审核完成后进入可用目录；归组意图由服务端绑定到真实资产，失败不得出现无实际表单的成功条目。

编辑已有表单进入对应搭建工作区，修改生成草稿并继续经过既有校验和发布流程。在新版本通过前，员工继续使用有效的已发布版本。仅调整目录分组不修改契约，也不触发重新发布。

## 实施边界与发布顺序

先补目录元数据、服务端权限与生命周期检查，再接入分组界面和搭建入口，最后验证并更新 7500。7506 保留为已确认的视觉参考，不作为真实功能验收环境。

平台迁移采用增量建表，不破坏既有数据。部署前记录版本并备份相关数据库；客户端包需要重新构建，DSH 改造同步登记到 fork 镜像，使用现有试点部署流程更新。归档启用后不能直接回退到忽略归档状态的旧服务；回退必须保留归档守卫，或在维护状态中完成经确认的兼容处理。

不顺带修改登录策略、角色授权、冻结契约或其他项目。是否提供 Agent 直接管理分组的工具作为单独能力评审；本轮必须保证 Agent 访问业务时遵守相同权限和归档规则。

## 验收条件

1. 登录 7500 点击业务即看到统一分组目录，无系统列表中间页或系统切换器，展示真实表单而非示例数据。
2. 搭建者新增和重命名分组、移动表单后，刷新及另一浏览器会话仍得到同一结果。
3. 删除含表单的分组，表单移到未分组，记录数量、记录标识和内容不变；事务失败不能发生部分移出。
4. 员工及未进入搭建模式的账号直接调用写接口也被拒绝；跨公司标识、伪造身份、资格撤销均不得绕过。
5. 只读员工不能提交或编辑记录，无权限员工不能通过目录、搜索、旧链接或 Agent 取得隐藏数据。
6. 表单归档前确认影响，归档后旧链接和 Agent 工具受限；恢复后原数据和原权限仍有效。验证并发写入与归档的结果一致性。
7. 新增及编辑表单可从搭建到审核发布走通，失败有真实原因，原型身份切换、假审核和示例发布不会出现在 7500。
8. 工作区会话、业务记录视图、表单草稿及右侧 AI 对同一表单使用一致标识，切换表单不串数据。
9. 平台针对测试、客户端行为测试、构建、真实组合浏览器测试与 fork 重建检查通过，并保存登录角色与数据核对证据；健康检查或截图不能替代这些验收。
