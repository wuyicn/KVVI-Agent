# 客户端原key恢复实施设计

对应任务4；服务端查询与SQL38耐久intent已实现，BusinessBody与SystemShell已接线，Agent及真实浏览器尚未验收，不能据此宣称完整刷新恢复。

- 耐久记录优先放在业务库，保存公司、账号、gateway、规范化端点、原key、请求摘要与操作状态；浏览器不耐久保存业务字段值、Cookie或会话令牌。账号/公司/gateway必须由当前认证入口取得；session用于当次界面响应归属，重新登录同一人可查询自己的旧操作。
- 在实际写请求之前先向服务端申请/找回耐久intent及原key；同一公司/账号/端点只保留一个未处理intent，准备与确认/取消按统一锁串行，避免多个页签分别铸造key。准备时保存含gateway的规范请求摘要，防止未完成操作被不同输入夺用。准备存储失败时不发送业务写请求；未知结果不能丢记录、换key或自动重新执行。业务内容在本次界面内冻结用于同key重试，但关闭/刷新后不从本地存储还原业务内容。
- 服务端增加按原key查询回执的受权接口。查询与写入使用同一串行锁；回执保存原字段编码和gateway，用于重验当前动作/字段/行范围。只返回该身份、端点及key的已知提交结果，不返回原字段值。旧回执缺所需元数据时明确进入人工核对，不猜测授权。
- 查不到回执只能返回UNKNOWN，不能据此宣称失败或允许换key：原请求可能尚未到达或等待执行。此状态保留原key，允许继续检查；不凭客户端超时自动清除。安全取消/封存通过服务端耐久tombstone与同一锁完成后，才可准备新操作。
- 已知提交后显示原结果并重新读记录/列表；不把旧PATCH响应合并到新版本中。原session已切换的迟到响应只更新原操作的耐久状态，不导航、不改新身份的草稿或视图。
- 分批验证服务端查询、耐久journal、UI接线与真实浏览器旅程。每批保留撤权、跨身份、响应丢失及重启反例；不能把其中一批冒称整页刷新恢复已完成。


## 服务端协议与后续接线

1. SQL37交付受权回执查询及必要字段编码元数据；不调用业务run，不因缺回执铸造新key。
2. SQL38交付服务端active intent。GET找回同身份active；prepare绑定请求摘要；业务效果/原回执/intent COMMITTED在同business事务改变。原用户重新登录可找回，切换gateway需先处理旧gateway的操作。prepare与写入先取同actor/endpoint锁再取原key锁；已有active时其他key或省略header都不能另起写入。
3. cancel先取同一原key锁；已有回执时只返回已提交状态，不能撤销业务效果；无回执时持久写CANCELED tombstone，未来迟到的原请求必须拒绝。ACK只允许已知提交的操作，给同端点后续的新动作腾出位置，原key回执不删。
4. 服务端签发键使用保留命名空间kvvi-intent.v1，绑定company/user/gateway随机nonce；无已知回执的新效果还必须找到当前endpoint真实intent行，不能伪造前缀、跨账号或跨接口退回legacy写入。get/prepare在读到/分配耐久key前发生超时不回显调用方header为原key。
5. 原字段/记录权限撤销后，GET本人真实intent只返回resultRestricted状态/key，不能读取原result/字段编码；本人仍可cancel未提交操作或ACK已知提交操作的元数据，避免active永久阻挡后续允许的动作。账号、公司、gateway隔离、认证与系统入口门禁保留；取消已提交操作不撤销效果。
6. UI提交前prepare；发生未知结果保留active，恢复只检查原key。刷新/换登录后重新读当前身份及active，不读取另一账号的恢复记录。取消、确认结果与新动作均显式呈现。Agent入口随后接同一机制，各入口分开取证。

服务端协议已用真实隔离PG及故障注入验证；BusinessBody与SystemShell经RecordWriteGuard接线，已有显式恢复组件反例；Agent与真实浏览器旅程仍未完成，不得写成全部UI恢复通过。
