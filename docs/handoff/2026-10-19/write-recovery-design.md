# 写入结果与独立审计恢复

对应12项任务3/4；本文件是实施设计，不是验收通过记录。现有产品API先提交业务库，再追加审计、保存平台库幂等结果；任一后续步骤失败，调用方会收到错误但业务已改变。现有SELECT→run→save也不能阻止同key并发。

采用以下顺序逐批实现，每批先复现失败再修复、提交：

1. 独立审计库增加操作回执及 `audit_append_once`。操作ID与全部实际审计参数绑定；回执和哈希链条目在一个审计库事务提交。同ID不同参数拒绝，重复投递只返回原hash。写者仅有函数执行权。
2. 业务库增加写操作回执，将实际业务效果、原请求摘要、原响应、待投递审计放在同一事务。按公司/账号/端点/key串行；原key不可因超时或过期自动变成新动作。请求内容变化拒绝。事务提交结果未知时保持原key，不把未知当拒绝后重新执行。
3. 创建/PATCH入口接线：现有会话/系统/字段/行范围检查继续执行，回放也先过当前授权；只把业务事务传给底层写入函数。已知提交但审计待投递明确返回pending，后台与原key重试共用幂等投递。缓冲写入失败必须回滚业务效果。恢复响应不跨账号/公司。
4. commands、流程与访客分别接线，不能因为API通过就宣布这些执行入口通过；UI持久保存身份绑定原key另验。测试包含独立审计不可用、回执存储失败、提交/响应丢失、并发、进程重启、授权撤销和不同payload。

业务库回执仅是在线平台下的耐久投递缓冲，不构成PRD §9.4.4所要求的离线签名批次、防篡改缓冲或受信硬件密钥。离线放行与完整审计连续性须另行实现；不得据此扩大离线写入权限。三个库仍独立，不声称存在跨库事务。
