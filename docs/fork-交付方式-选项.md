# `vendor/dsh` 的交付方式：三个选项

> 这份文档解释 N1/N2 到底在问什么，以及三种做法各自的真实代价。
> **结论在第 5 节**；前 4 节是判断依据。

---

## 1. 先把事实摆出来

| 事实 | 数值 |
|---|---|
| KVVI-Agent 仓库的 `.git` | **18 MB** |
| `vendor/dsh`（DSH 上游源码副本） | **约 190 MB**（`packages/` 161 M + `.git` 29 M） |
| **KVVI 实际改动**（对照上游） | **35 个文件**（14 个改上游 + 21 个新增） |
| 上游许可证 | **MIT**（可自由再分发） |
| `vendor/dsh` 是否在版本管理里 | ❌ **不在**（`.gitignore` 明确排除） |

---

## 2. 为什么这是个问题

**产品运行离不开 `vendor/dsh`。** KVVI 不是独立写的软件 —— 它建在 DSH 之上：
两个进程、五个搭建 Skill、品牌插件、Profile Bundle 全都在 `vendor/dsh` 里面。

所以现在的情况是：

```
别人 git clone KVVI-Agent
        ↓
拿到：契约、工具、服务、文档、进度          ✅
拿不到：vendor/dsh                          ❌
        ↓
结果：pnpm install 能跑，docker compose up 起不来
```

**「交付包在干净环境部署成功」这句话，对现在的工作目录成立，对「克隆下来的仓库」不成立。**
这就是 N1。而 N2 是它的影子：`forks/dsh/改造点清单.md` 描述了「怎么重建 fork」，
但**从来没有演练过** —— 一份没被跑过的重建说明，是一份**未被证明可用**的说明。

---

## 3. 三个选项

### 选项 A：整个 fork 入库

把 `vendor/dsh` 从 `.gitignore` 里拿出来，提交进版本管理。

| | |
|---|---|
| ✅ 好处 | `git clone` 直接得到完整可运行的产品。**不依赖任何「重建脚本是对的」这个假设** |
| ❌ 代价 | 仓库从 **18 MB 涨到 200 MB 以上**；每次上游更新都要吞一次巨大的 diff；review 时满屏是上游代码 |
| ⚠️ 注意 | MIT 允许这么做，**没有法律问题** |

### 选项 B：只入库「我们的改动」+ 一条**演练过的**重建命令

保持现状（仓库里只有那 35 个文件与清单），另加一条命令：

```bash
git clone --depth 1 https://github.com/deepseek-ai/deepseek-harness.git  # 拉到指定 commit
python3 工具/fork.py  # 把 35 个文件放回去
python3 工具/fork.py --verify   # 逐文件比对 sha256
```

| | |
|---|---|
| ✅ 好处 | 仓库保持 **18 MB**；上游更新用 `git rebase`（我们的改动只有 35 个文件，冲突面极小）；**重建结果可逐字节验证**（指纹清单已经存在） |
| ❌ 代价 | **必须先跑通一次**，否则它只是文档描述（这就是 N2）；使用者需要能访问上游仓库（网络） |
| ⚠️ 附带好处 | 上游如果改动了我们动过的文件，重建会**大声失败** —— 这正是我们想要的行为 |

### 选项 C：交付时打成一个自包含的 tar 包

源码仓库不动，交付时用一条命令生成完整包：

```bash
python3 工具/交付包.py --bundle   # → kvvi-delivery-<版本>.tar.gz（含 vendor/dsh）
```

| | |
|---|---|
| ✅ 好处 | 源码仓库小；**交付物自包含**，客户不需要联网拉上游；包内容与交付清单指纹一致 |
| ❌ 代价 | 包体 ~200 MB；打包流程本身要有人维护；**它依赖于「有 fork 源码可打」** —— 而那仍来自 A 或 B |

---

## 4. 关键：**A 与 B 不是二选一的对立面**

把三个选项摊开看，要决定的其实**只有一句话**：

> **我们要交付的那个东西，是不是自包含的？**

| 你希望交付物… | 那就 |
|---|---|
| **自包含**（客户不需要联网、不需要跑脚本） | **A**，或者 **B + C**（源码仓库用 B，交付物用 C） |
| 可以**由脚本从上游重建**（客户能联网） | **B** |

**C 单独不成立**：打包总得有个源。C 是「把 A 或 B 的结果打成包」，不是第三个来源。

---

## 5. 我的建议：**B + C**

**源码仓库用 B，交付物用 C。** 理由：

1. **仓库保持 18 MB** —— 上游是 12100 个文件，我们只动 35 个。
   把整个上游入库，代价是**每一次上游更新都要在 200 MB 的 diff 里找出我们的 35 个文件**。
2. **重建是可验证的** —— `forks/dsh/改造点指纹.json` 已经记了 35 个文件的 sha256
   与被改文件的上游基线 sha256。重建不是「希望它对」，而是**逐字节比对**。
3. **交付物仍然自包含** —— 客户拿到的是一个 tar 包，不需要访问 GitHub、不需要跑脚本。
4. **上游漂移会大声失败** —— 这正是我们想要的：上游若改了 `webserver` 或 `web-app`
   （我们改过的地方），重建时报错，而不是悄悄产出一个不一样的 fork。

### 但 B 有一个**必须先做**的前提

**这条重建命令必须真的跑过一次，并且产出与指纹逐字节一致。**
在那之前，B 只是「一份没被证明可用的说明」—— 也就是 N2。
所以 N1 和 N2 的处置是同一件事：**把重建写出来，跑通，把结果记进证据包。**

---

## 6. 决定：**打好 tar**（B + C）—— 已落地

业主选定「交付出去的包是我们打好的 tar」。据此做完的事：

| # | 做了什么 | 结果 |
|---|---|---|
| 1 | `工具/fork.py --export`：把那 35 个文件**存进仓库**（`forks/dsh/变更/`，1157 KB） | ✅ 此前它们只存在于本机 |
| 2 | `工具/fork.py --rebuild`：上游干净副本 + 覆盖改动 → 逐字节比对 | ✅ **35/35 一致** |
| 3 | `工具/fork.py --bundle`：生成自包含 tar | ✅ `交付/包/kvvi-delivery.tar.gz`，**12364 条目 / 25.1 MB** |
| 4 | 进证据包 | ✅ 每次生成证据包都会重跑这条例重建 |

**为什么存文件而不是存补丁**：判据不是「补丁应用成功」，而是「结果与指纹逐字节一致」。
存文件让这个判据**直接就是重建过程本身**，也不受上游文件变动影响。

**为什么 tar 只有 25 MB（原先估 200 MB）**：压缩 + 排除 `node_modules`/`.git`。
交付物自包含 —— 解压即可运行，**不需要联网**。

### ⚠️ 一处未演练：从 GitHub 克隆那条路

`--upstream local` 走的是 `vendor/dsh` 自己的 git 对象，**不需要网络** —— 本次演练走的就是它。
`--upstream git` 从 GitHub 克隆，而**本机当前访问 GitHub 超时**，那条路**未演练**（记为 N23）。

它不影响交付：交付包是打好的 tar，客户不需要拉上游。
它影响的是**我们自己将来做上游 rebase 时**能不能拉到新版本。

---

## 7. 需要你决定什么（已于本次决定：打好 tar）

只需回答一个问题：

> **交付出去的包，是我们打好的 tar（客户直接解压就能起），
> 还是客户自己从上游 + 我们的改动重建？**

- 选「打好 tar」→ 我按 **B + C** 做：写重建命令 → 演练 → 生成 tar → 进证据包
- 选「客户自己重建」→ 我按 **B** 做：写重建命令 → 演练 → 写进交付文档
- 选「都要，且仓库也自包含」→ 我按 **A** 做（并接受仓库涨到 200 MB）

三种我都能做，**区别只在仓库大小与交付包形态**，不在工程量。
