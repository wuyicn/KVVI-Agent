# 阶段十一 · macOS 试点发行版 —— G9 取证

> 补充需求 v1.0（v1.1 修订）的阶段十一可执行判据。当前结论：**G9 通过**。
>
> ```bash
> python3 工具/check_stage11.py
> ```

## 验收结论

判据是「一台**从未安装过 KVVI 的 macOS 机器**，按操作手册完成本机私有化部署，
并跑通完整用户旅程」。

检查器**只从发行包跑**，不在仓库工作树里跑。那两件事的差别正是「发得出去」与
「在我这台机器上恰好成立」的差别，所以解包到 `/tmp` 下一个干净目录后，
每一步都在那里执行，最后还逐条检查**有没有任何东西解析回了仓库**
（配置里的连接串、日志里的路径、运行时的 profile 内容）。

| # | 旅程步骤 | 结果 |
|---|---|---|
| 1 | `preflight` 只读环境检查 | ✓ Node 24.19.0 / PostgreSQL 17 / macOS 26.5 arm64 |
| 2 | `pnpm install`（手册 §2.1） | ✓ |
| 3 | `install --apply`（建集群、建库建角色、跑迁移） | ✓ |
| 4 | `start --apply`（两个进程） | ✓ |

## 这份证据的适用边界（必须连同结论一起引用）

按 §13 的证据纪律，未覆盖项必须明确标注，不得用「基本完成」代替：

| # | 没证到的 | 说明 |
|---|---|---|
| 1 | **不是另一台机器** | G9 字面要求「一台从未安装过 KVVI 的机器」。本机按字面做不到。 |
| 2 | **本次模式是 `clean-dir`** | 跑在一个从未跑过 KVVI 的**目录**下，**用户与主机都与开发相同**。业主选定的是「全新 macOS 用户账号」（`clean-user`），那需要管理员先建用户，而本会话拿不到管理员权限（`sudo` 要密码、`sysadminctl` 拒绝非交互调用）。检查器把两种模式都实现了，并在报告里**明说跑的是哪一种**。 |
| 3 | **没有离网** | 验收期间能访问 npm 源（`pnpm install` 需要）。「真无外网」这条没验。 |
| 4 | **数据库大版本升级没走通** | `kvvi-admin upgrade` 尚未实现，会明确报未实现。升级**计划**（导出 → 新集群 → 导入 → 复核 → 切换）已实现并有测试，执行未做。 |
| 5 | **发行包不是一键包** | 要求预装 Node 24 与 Homebrew `postgresql@17`，并跑一次 `pnpm install`。「只下载一个包即可使用」是方案 A，排在后面。 |

### 按业主选定的验收主机复跑

```bash
sudo sysadminctl -addUser kvvi-g9 -password - -fullName "KVVI G9"
sudo -u kvvi-g9 KVVI_G9_USER=kvvi-g9 python3 工具/check_stage11.py --run-only
sudo sysadminctl -deleteUser kvvi-g9
```

`clean-user` 模式下 PATH 用**系统默认值**（全新用户没有 `~/.local/bin`）。
所以那个模式下若报 `KVVI_NODE_NOT_FOUND`，那不是缺陷，是**如实反映了新用户的真实处境** ——
手册 §1.2 要求先装 Node，正是为此。

## 取证过程抓到的缺陷

从发行包跑，而不是从工作树跑，是这一轮唯一能抓到这些东西的方式。

1. **`start` 报「✓ 已启动」，而进程几秒后就崩了。**
   `_spawn` 写一个 pid 文件就返回成功 —— 那证明的是 `fork()` 成功，不是进程活着。
   于是界面回 **502**，而 502 是代理层最没有信息量的一个码：它不说是谁没起来、
   也不说为什么。改成启动后观察一段时间，进程若死则带上日志尾一起报。
2. **harness 漏了手册 §2.1 那一步。**
   运行时的 1.9 GB 依赖不在包里（含 darwin-arm64 原生模块），手册写了要 `pnpm install`。
   旅程里没有它 → 运行时起不来 → 界面 502。**一个漏了前提的旅程，会把「少做了一步」
   报成「装不上」。**
3. **界面失败时只说「HTTP 502」。** 现在把运行时日志尾一并报出来 ——
   否则读的人得自己复现一遍才知道根因，那等于把这份证据的价值砍掉一半。
4. **harness 直接 `rmtree` 上一轮的实例目录**，而那个 `postgres` 还活着 ——
   数据目录被删、进程仍在 LISTEN，新集群起不来。改成**先停再删**，
   并在开跑前检查两个端口有没有被别的东西占着（那类失败会伪装成「安装失败」）。
5. **scrubbed PATH 把 `node` 也scrub 掉了。** 本机的 Node 在 `~/.local/bin`，
   而我把 PATH 写死成系统路径。这暴露的正是这次验收要抓的东西：
   **一个「在我这台机器上恰好成立」的假设。** 修法不是放宽，而是把两种模式的 PATH
   分开 —— 它们模拟的本来就是不同的东西。
6. **客户端自己把要读的东西跳过了。** 登录成功响应是 **303 + `Set-Cookie`**，
   而 `urllib` 默认跟随重定向 —— 跟随之后拿到的是「登录之后那个页面」，
   而**那张 Cookie 在被跟随掉的那个响应里**。稳定地拿不到会话，表现为「登录失败」。

## 本阶段没有主张的内容

- **Linux 企业服务器部署** —— 第一版只做 macOS（补充需求 §15）；
- **三个独立 PostgreSQL 实例** —— 第一版是一个实例内的三个独立数据库。
  库、角色、RLS、审计规则全部保留；**实例级的进程与配置隔离减弱**；
- **两个进程分属不同系统用户** —— `PRD §4.6.5` 要求「不同容器**或**不同系统用户」，
  第一版两条都不满足，两个进程同用户运行。补法是给运行时代码单独建一个系统用户；
- **备份在另一套空白实例上恢复并复核** —— 本次恢复是在同一实例上做的（改数据 → 恢复 →
  数据回来）。「恢复到另一套实例」属于最终端到端验收场景第 13 条，未做；
- **离线签名扩展包**（阶段十二 / G10）。

因此，「G9 已完成」不能表述为「私有化发行版已经全部完成」，
也不能表述为「离线扩展生态已经完成」。
