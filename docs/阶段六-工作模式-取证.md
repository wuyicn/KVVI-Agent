## 一、锚点① 家具「报货申请」样例（`0C-6`）

### 1.1 它和 `0A-14` 去行业化自查不矛盾

一个要求「地基里没有家具词」，一个要求「一个家具样例」。两者说的是**不同层**
（PRD §5.7.3）：

| 层 | 允许行业词 | 判据 |
|---|---|---|
| **地基**（契约、工具、五个 Skill、预设） | ❌ | `工具/check_industry_neutral.py` |
| **行业扩展包**（追加 `skills/` 目录 + 组件包） | ✅ | **地基未被改动** |

所以包放在 `样例/行业包/` 下，并被**显式豁免**（豁免理由写在检查器里）。
「豁免」在这里不是「这一类检查失效」—— 它的代价是**地基必须一动不动**：

`地基未改动.json` 记录加包**之前** 10 个交付组件的内容指纹（复用
`工具/交付包.py` 的算法），`工具/行业包.py` 逐项复核。**这是「不进地基」的执行点**，
不是一句承诺。

## 二、锚点② 黄金样例（`0D-2`）：先说清「稳定」是什么意思

`0D-2` 的验收原文是「10 组标准需求反复跑，结果稳定」。「稳定」有两种读法，
本工具**只兑现其中一种**，并且在每次运行时都打印出来：

| 读法 | 是否兑现 |
|---|---|
| **装配的确定性**：同一份输入装两次，产出逐字节相同 | ✅ **兑现**（可机器判定） |
| **模型的稳定性**：同一个需求问模型十次，十次给出同一份蓝图 | ❌ **未测，也不该这样测** |

第二条**不应**被含糊地算作已兑现。它既没测，也不该承诺逐字相同 ——
需求本身的歧义会合法地产生不同的蓝图。

这一层真正防的是**装配环节里的非确定性**：遍历顺序、时间戳、随机 id、字典序不定。
它们会让「同一份蓝图装两次得到两个包」，而**在单次运行时看不出来**。

10 组需求全部**刻意中立**（无行业词）—— 它们是地基能力的检验，
行业样例是另一条路径（锚点①）。

### 2.1 顺带验出来的两条约束

- **保留字**：`status` 是契约的 12 个保留字之一，用它报 `FIELD_CODE_INVALID` ——
  报错看起来像「字段名写错了」，实际是「这个名字被平台占用了」。
- **`single_select` 必须带 `type_config.options`**：少了它报
  `CONTRACT_SHAPE_INVALID | fields[n].type_config`，指向一个「看起来跟这个字段没关系」的位置。

## 三、锚点③ 双网关隔离（`0D-7` 隔离部分）

四类越界，**每一类都能分别答出「是哪一条失守」**：

| 类别 | 拒绝码 | 关键用例 |
|---|---|---|
| **工具串用** | `KVVI_WRONG_GATEWAY` | 员工会话调搭建工具；**判定看分类表，不看调用方声明** |
| **数据旁路** | `KVVI_BUILD_PERMISSION_IS_NOT_DATA_PERMISSION` | 只有搭建权限、无任何数据档位 → 读取被拒 |
| **自授权** | `KVVI_SELF_GRANT_FORBIDDEN` | 搭建者把自己纳入配置范围（**与有没有权限无关**） |
| **自审批** | `KVVI_SELF_APPROVAL_FORBIDDEN` | 安全敏感变更由提出者本人批准 |

**数据旁路那一条最容易被做错**：§3.1 的表格里搭建者「工作模式业务操作 ✅」——
产品禁的是**凭搭建权限**取数，不是禁止搭建者做业务。所以判据是
「有没有业务侧授权」，不是「是不是搭建者」。用例里配了正向对照。

每类都验证**拒绝留痕**（`DENY` 记录 + 链仍然自洽）。

## 四、锚点④ 访客路径（§3.5）

### 4.1 整个设计的支点是「把主体从访客换成签发人」

访客没有账号，所以「他是谁」没有答案。处理方式是把**所有以主体为参照的判断**
换到签发人身上：

| 问题 | 答案 |
|---|---|
| 行范围按谁解释 | **签发人**（§3.5.1 v2.16 终审阻断 T1） |
| 新记录的归属算谁 | 服务端按绑定确定，**访客不得覆盖** |
| 出问题追溯谁 | 签发人 + 链接 ID + 提交通道（**不承诺区分访客个体**） |

审计里 `actor_kind='VISITOR'` 与 `actor_id=签发人` **分开表达**——
同时做到「不冒充签发人」和「入口有主」。这是 §3.5.4 那条
「受限落地形式而非等价形式」在数据结构上的样子。

### 4.2 覆盖的负向组

| 组 | 用例要点 |
|---|---|
| **签发资格** | 只有读权限 → 拒；无权限 → 拒；绑定项越界 → **拒而不是截断**；有效期有产品级上限 |
| **链接签名** | 篡改内容 → 验签失败；改 nonce → 验签失败；公钥可独立验证 |
| **行范围与归属** | 绑定与签发人归属不符 → 拒；访客覆盖归属字段 → 拒（5 个字段逐一）；关联对象越权 → 拒且**不返回任何候选** |
| **权限回收后旧链接** | 签发人停用 → 链接全失效；授权版本变化 → 拒 |
| **在线优先** | 平台可达时**实时查**，缓存不构成放行依据；离线超窗 → 失败关闭 |
| **限流四维度** | 链接 / 来源 / 签发人 / 公司，超限**拒绝并记录**，不排队不降级 |

> 「不返回任何候选」那条是专门断言的：§3.5.1 明写
> **不得因此给访客增加列表或查询能力**。所以 `checkRelatedRef` 的成功返回值
> 只有 `{ok:true}`，用例直接断言**键的集合**。

## 五、这一层查出来的东西

### 5.1 审计表不允许 `VISITOR` 通道（真缺陷，已修）

第一次提交时数据库报了 `audit_entries_gateway_check` 约束冲突 ——
`gateway` 只允许 `USER` / `BUILDER`。这不是「加个值」而已：
§3.5.4 要求记录**访客通道**，而通道枚举里没有它，就等于
**访客操作只能被记成别的东西**。

修法是把约束 `DROP` + `ADD`（而不是改 `CREATE TABLE`，因为已存在的表不会重跑列定义），
同时给 `actor_kind` 加 `VISITOR`。

### 5.2 签发链接记的是**会话冻结的**授权版本（真缺陷，已修）

`issueLink` 原先把 `session.authzVersion`（签发令牌时的快照）写进链接，
于是「权限回收过、又新发一张链接」时，**新链接一签发就是废的**，
失败理由是 `KVVI_ISSUER_AUTHZ_CHANGED` —— 看起来像「签发人权限有问题」。
改为记**当前**版本。

### 5.3 测试自身的三个坑（记下来因为它们会重复出现）

| 现象 | 原因 |
|---|---|
| `permission denied for table policies`，报错位置在**清理语句**上 | 平台库角色只有 `SELECT, INSERT, UPDATE`（审计优先的库刻意不给 DELETE）。清理要用 UPDATE |
| 用例之间互相污染，后面的用例报 `KVVI_RATE_LIMITED_ISSUER` | 前面十几个用例各自发过链接，累计撞上**签发人维度限流** —— 那条限流本来就在工作 |
| 清理语句命中 0 行却不报错 | `UPDATE` 打在一个不存在的主键上。用例前提没建立，现象却是「功能坏了」 |
