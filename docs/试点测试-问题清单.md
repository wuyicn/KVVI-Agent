## 问题 1 · 安装停在第 4 步（启动数据库集群）

| 项 | 内容 |
|---|---|
| 测试账号 | 无（安装期，还没有账号） |
| 操作 | `python3 distribution/bin/kvvi-admin install --apply --yes`（用默认数据目录 `~/Library/Application Support/KVVI-Agent-Pilot`） |
| 预期结果 | 安装完成，输出初始化令牌路径 |
| 实际结果 | `✗ {'kind': 'start-server', 'stderr': 'pg_ctl: could not start server'}`，退出码 3 |
| 严重程度 | **阻断**（安装无法完成，界面永远起不来） |
| 截图或错误 | `log/postgres.log`：`postgres: invalid argument: "Support/KVVI-Agent-Pilot/run"` |
| 是否稳定复现 | **是**（100%） |

**根因**：端口、`listen_addresses` 与 socket 目录全塞在一个 `pg_ctl -o '-p … -c …'`
字符串里。`pg_ctl` 按空白切分 `-o` 的实参，而 macOS 默认数据目录
`~/Library/Application Support/…` **含一个空格**，`postgres` 收到的是空格后那半截。

> ⚠️ **为什么 G9 没抓到**：G9 的验收目录是 `/tmp/kvvi-stage11-*`，**没有空格**。
> 默认数据目录从来没被任何一次自动化走到过。

**顺带看到的更重的一条**：只写在 `-o` 里，这三样就只是**那一条命令**的属性。
人工 `pg_ctl start -D pgdata`、将来的 launchd 拉起，都会静默退回
`/tmp` socket + 端口 5432 + `listen_addresses='localhost'`，
而 `initdb` 设的是 `--auth-local=trust` —— 本机任一进程都能免密以超级用户连上 KVVI 的库。

**修法**：写进 `pgdata/postgresql.conf` 的一段（带首尾标记、可幂等重写），
启动命令不再带 `-o`。回归测试用**含空格的路径**做用例。

## 问题 2 · 发行包少了整整一类运行时文件

| 项 | 内容 |
|---|---|
| 测试账号 | owner（登录能成） |
| 操作 | 登录后打开界面 |
| 预期结果 | 出现对话区 |
| 实际结果 | 界面显示 `HARNESS Failed to load plugins`，`web boot: 24 entries did not activate`，每一条都在等 `sessions` 服务 |
| 严重程度 | **阻断**（界面完全不可用） |
| 截图或错误 | `log/runtime.log`：`12 entries did not activate` + 7 条 `failed to import` |
| 是否稳定复现 | **是** |

**根因**：`工具/发行包.py` 的 `should_skip` 里有一条 —

```python
if '/lib/types/' in probe:
    # `.d.ts` 是编译中间产物，运行时用不到；`lib/*.js` 要留。
    return True
```

那句注释的**前提是错的**。DSH 的 tsconfig 用 `outDir: lib/types`，所以 `.d.ts`
**和编译后的 `.js` 都落在那里**，而包与包之间正是按 `.js` 相对路径互相 import：

```
…/session-format-catalog/lib/index.js
  → …/dsh-compaction-image-offload/lib/types/projection.js
```

整目录一甩，`vendor/dsh` 下 **2052 个** `lib/types/**/*.js` 全没了（包内 0 个）。

> ⚠️ **为什么 G9 没抓到**：G9 只看 `GET /` 是不是 HTTP 200。页面确实是 200 ——
> 它只是什么都做不了。**「HTTP 200」与「界面可用」是两件事**，
> 而这一条在验收脚本里被当成了同一件事。

**修法**：`lib/types` 只甩类型与 sourcemap，`.js` 留下；
`REQUIRED` 加一条代表性文件；`--check` 增加**数量对齐**判据
（源树 `lib/types/**/*.js` 个数必须等于包内个数）；
`--self-test` 增加一条反向用例：摘掉一个**不在 `REQUIRED` 里**的 `.js` 必须变红。

## 问题 3 · 每一条 `POST /api/*` 挂死

| 项 | 内容 |
|---|---|
| 测试账号 | owner |
| 操作 | 经平台端口 7500 登录后打开界面 |
| 预期结果 | 界面连上，出现对话区 |
| 实际结果 | 界面「重新连接中…」，输入框不可用；控制台反复 `connection generation was not ready within 15000ms` |
| 严重程度 | **阻断** |
| 截图或错误 | `curl -X POST http://127.0.0.1:7500/api/session/list` **永不返回**（10 秒上限打满，0 字节响应） |
| 是否稳定复现 | **是**（GET 全正常，POST 全挂） |

**根因**：登录门那一段无条件 `await readBody(req)`，把请求流**读干**，
然后对绝大多数路径 `return null` 落回转发；而 `forwardHeaders` 的注释写着
「删掉 `content-length` 让 node 重新计算」，**代码里并没有删**。
上游于是收到一个声明了 75 字节、实际一个字节都不发的请求，一直在等。

**判据**：绕过平台、直接打开运行时进程（7401）—— 界面完全正常。
「一半可用」比整条不通难查，因为它同时给出了「服务是好的」这个答案。

**修法**：只有 `isGatePath` 认的路径（登录/登出）才读体；`forwardHeaders` 真正删掉
`content-length`（大小写不敏感）。回归测试断言**发出去的字节数必须等于声明的字节数**。

## 问题 4 · 每一条 `POST /api/*` 被回 403

| 项 | 内容 |
|---|---|
| 测试账号 | owner |
| 操作 | 同上，问题 3 修掉之后再打开界面 |
| 预期结果 | 界面连上 |
| 实际结果 | 界面仍然「重新连接中…」；网络面板里每一条 `POST /api/*` 都是 **403** |
| 严重程度 | **阻断** |
| 截图或错误 | `POST /api/settings/describe → 403`、`POST /api/session/modelCatalog → 403`…（GET 全 200） |
| 是否稳定复现 | **是**（GET 200 / POST 403，完全按方法分） |

**根因**：运行时的 browser-trust 栅栏同时查两件事：Host 属于本机，
**且浏览器带上的 `Origin` 与 Host 是同一个 authority**。
平台代理只改写了 Host（`127.0.0.1:7500` → `127.0.0.1:7401`），
却把 Origin 原样透传成 `http://127.0.0.1:7500` —— 这对值不自洽，于是 403。

浏览器不给同源 `GET` 附 `Origin`，只给 `POST` 附，所以症状**完全按请求方法分开**。

**修法**：`Origin` 跟着 Host 一起改写为目标 origin，并删掉 `Referer`
（它是平台的地址，留着与 Origin 不一致）。

## 问题 5 · 首次初始化没有界面

| 项 | 内容 |
|---|---|
| 测试账号 | 无（还没有账号） |
| 操作 | 按 `安装手册.md` §4：「打开界面 → 界面会要一次性初始化令牌 → 填公司名、所有者账号与口令 → 提交」 |
| 预期结果 | 界面上有一个要令牌与公司名的表单 |
| 实际结果 | 界面只有「账号 / 口令 / 登录」三项，**没有任何令牌输入口**；`/bootstrap/state` 与 `/bootstrap/owner` 只有 API，没有任何页面消费它 |
| 严重程度 | **阻断**（客户按手册走不到第二步；建不出企业就永远进不去系统） |
| 截图或错误 | 登录页完整 HTML 里没有 `token` 字段；`services/platform/src/` 全树搜 `bootstrap` 只命中 `server.mjs / bootstrap.mjs / migrate.mjs`，没有界面 |
| 是否稳定复现 | **是** |

**本次怎么绕过的**（**不是**客户能走的路径）：

```bash
TOKEN=$(cat "$KVVI_HOME/secrets/bootstrap.token")
curl -X POST http://127.0.0.1:7500/bootstrap/owner -H 'content-type: application/json' \
  -d "{\"token\":\"$TOKEN\",\"companyName\":\"…\",\"login\":\"owner\",\"password\":\"…\"}"
# → 201；再调一次 → 410（一次性，符合设计）
```

> ⚠️ **G9 为什么没抓到**：G9 的验收旅程是**直接调 API** 的，
> 它走的是「客户走不到的那条路」，所以「界面没有这一步」看不见。

---

**修法**（与登录页同一个模块、同一种做法）：

- 新增 `GET /kvvi/bootstrap`：一个**自包含**的页面（样式与脚本内联、无外部资源），
  四个框 —— 初始化令牌、企业名称、所有者账号、所有者口令；
  提交走 `fetch` + JSON 打**已有的那个** `/bootstrap/owner`，判据一行都不重复；
- 未初始化时，`/kvvi/login` 与未登录的根路径**都跳到这里**。
  原来的行为是把客户丢到登录页 —— 而那个实例上他一个账号都没有，是条死胡同；
- 已初始化后，这个页面 303 回登录页；调用方没接 `bootstrapPending` 时也按
  「已初始化」处理，忘接线不会把入口放出去；
- `/kvvi/bootstrap` 加进 `isGatePath`：业务面板对 `/kvvi/*` 里非 `/kvvi/panel`
  的路径一律回 404 JSON，不排出去的话，客户打开初始化页看到的是一句
  `KVVI_PANEL_NOT_FOUND`。

回归测试 9 条，其中三条是「不成立就会静默坏掉」的：
未初始化必须送到初始化页、已初始化后不能再进、文案表必须覆盖
`bootstrap.mjs` 的全部对外错误码（服务端只给码，页面给话）。

## 新增问题

### 问题 10 · 重启机器之后，实例起不来

| 项 | 内容 |
|---|---|
| 测试账号 | 无（运维） |
| 操作 | 停掉两个进程 + 停掉数据库集群，然后按手册 §3 跑 `kvvi-admin start --apply --yes` |
| 预期结果 | 实例起来（手册 §3 就是这么写的；§3 的 launchd 步骤跑的也是这条命令） |
| 实际结果 | `✗ KVVI_CLUSTER_NOT_RUNNING：数据库集群没在运行。先跑 kvvi-admin install --apply，或手动起：pg_ctl -D …/pgdata start`，退出码 2 |
| 严重程度 | **阻断**（「重启电脑」这个场景下，实例起不来 —— 登录、面板、Agent 全都用不了） |
| 截图或错误 | 见下 |
| 是否稳定复现 | **是** |

两件事叠在一起：

1. **`start` 不负责起集群，`stop` 也不停集群。** 两个子命令对集群是不对称的，
   而 `kvvi-admin` 下**没有任何一条子命令能起集群**。手册 §3 只说「起服务」，
   没有一个字提到 PostgreSQL 得先在跑。
2. **它给的恢复指引本身跑不起来。** 照提示执行 `pg_ctl -D …/pgdata start`：

   ```
   致命错误:  在启动期间postmaster变成多线程的
   提示:  设定LC_ALL环境变量为一个合法的区域。
   ```

   这正是本仓库自己的注释里记过的那个 macOS 坑（`pg.py` 模块说明第 4 行），
   而 `start` 偏偏把它**从提示里漏掉了** —— 用户按提示做，撞上第二句完全不同的报错。

**连带的**：手册 §3 的 launchd 自启（`ProgramArguments = kvvi-admin start --apply --yes`）
在**每次开机后必然失败**，而 `KeepAlive` 会让它反复重试、反复失败。
本次没有实际 `launchctl load`（不想在本机装一个会持续失败的自启项），
但这条由上面两条直接推出。

**手工按 `start` 的提示补齐 `LC_ALL` 之后**，集群起来了，两个进程起来了，
数据完好：公司 `星河科技（试点）`、5 个账号、角色、审计 11 条、`builder` 的搭建授权都还在，
登录回 303。**所以这一条不是数据问题，是「起不来」的问题。**

**修法**：

- `start` 从「要求集群已经在跑」改成「**集群没在跑就把它拉起来**」
  （新增 `ensure-cluster` 步骤，幂等：在跑就跳过）。它排在两个只读检查之后、
  两个进程之前；
- 起集群的命令**只留一处定义**（`pg.cluster_start_step()`），
  `cluster_plan` 与 `start_plan` 都用它 —— 写两处就是「其中一处会漏 `LC_ALL`」，
  而这正好就是本条缺陷的形态；
- 前置检查的判据换成「集群**装出来了没有**」（缺 `PG_VERSION` 才算问题），
  集群只是没在跑不算 —— 那正是「重启电脑」最常见的状态；
- 手册 §7 的排错表补一行：「机器重启后想再起来 —— 直接跑 `kvvi-admin start`」。

**实测**：停掉集群 + 停掉两个进程（监听端口归零），只跑一条
`kvvi-admin start --apply --yes`：

```
✓ check-config: 只读
✓ check-ports: 只读
✓ ensure-cluster: 已拉起
✓ prepare-dfs-profile: 已存在，未覆盖
✓ start-platform
✓ start-runtime
✓ start 完成
```

公司、5 个账号、搭建授权、登录（303）全部照旧。

### 问题 11 · 令牌 5 分钟一过期，界面就变成一堆看不懂的报错（**本轮最高频**）

| 项 | 内容 |
|---|---|
| 测试账号 | owner、builder、staff-view 都出现 |
| 操作 | 登录之后正常操作，5 分钟后再点任何东西 |
| 预期结果 | 提示「会话已过期，请重新登录」并把人送到登录页 |
| 实际结果 | 各处报出**互不相同、且都看不懂**的东西：<br>· 业务面板：`KVVI_INVALID_TOKEN`（一个原始错误码，没有任何解释）<br>· 添加工作区：`无法打开文件夹 directory picker failed … Unexpected token '<', "<!DOCTYPE "... is not valid JSON` |
| 严重程度 | 功能（**重要**）+ 体验（**这是每 5 分钟必现的一条**） |
| 截图或错误 | 面板把错误码直接 `<code data-kvvi-error>` 渲染出来；`Unexpected token '<'` 是因为拿到了登录页的 HTML |
| 是否稳定复现 | **是**（`TOKEN_TTL_MS` 写死 5 分钟，§9.4.2 的上限） |

两个独立的原因叠成一个症状：

1. **`/api/*` 未登录时被 303 重定向到登录页，而不是回 401 JSON。**
   `gate.mjs` 的 `gated()` 把 `/api/*` 判成要过门；没会话就 303 到 `/kvvi/login`。
   `fetch` 默默跟随重定向，拿到的是登录页的 HTML，客户端 `JSON.parse` 当场炸。
   仓库里其实已经写下了正确的判据（`ALLOW_BEFORE_LOGIN` 那条注释：
   「`/kvvi/panel` 面板数据端点自己会判令牌，**返回 401 而不是重定向**」），
   以及 `server.mjs` 那句「API 调用方要的是 **401**（它不会去跟一个重定向）」——
   只是 `/api/*` 这条最主要的 RPC 通道漏在外面。
2. **面板拿到 401 之后什么都不做。** 它把错误码当文案显示出来，
   既不说「会话过期了」，也不跳登录页。**手动刷新一下就恢复** ——
   也就是说，界面明明知道该去哪，却没说。

## 问题 13 的修法与验收

**改法**（宿主平面，一行）：`dsh-kvvi-app` 的 `cordis.patch.yml` 加


## 问题 11 的修法（已完成，`d0ec48b`）

**分离**：浏览器会话凭据（`typ: browser`，30 分钟，可续）与业务令牌
（`typ: delegated`，≤5 分钟，§9.4.2 不变）成了两个值、两条验证路径、一个共享的会话权威。
**互换必须失败** —— 这是「分离」在代码里的判据，有直接用例。

**受控续发**：`POST /auth/renew` 的判据不是「凭据没过期」，而是「**会话还有效**」，
每次都重查 `sessions.state`、`users.status` 与两个 `authz_version`。
过期的凭据在宽限期内仍可换一张新的（睡一觉回来无感恢复），
而**只有这一个端点**接受过期凭据；`/api/*` 上带过期凭据则顺手换一张挂在响应上，界面不闪断。

| 情形 | 结果 |
|---|---|
| 管理员撤权（`authz_version` +1） | `KVVI_AUTHORIZATION_CHANGED` + `relogin: true` |
| 会话被吊销 | `KVVI_SESSION_ENDED` |
| 账号停用 | `KVVI_ACCOUNT_NOT_ACTIVE` |
| 问得太勤 | **429 + `relogin: false`**（「别问这么勤」≠「你得重新登录」） |

**连带修掉的三处**：

- `/api/*` 未通过时回 **401 JSON**，不再 303 到登录页 HTML —— 那正是
  `Unexpected token '<', "<!DOCTYPE "…` 的来处。仓库里早就写着正确判据，只是这条主 RPC 通道漏了。
- Cookie 存活期跟着凭据走，不再另设一个 1 小时（两个数字各自都对，合起来是最坏的状态）。
- 多一张非 HttpOnly 的到期时刻 Cookie：`kvvi-session` 是 HttpOnly，前端读不到它，
  于是**无从知道**会话该续了 —— 这是「连接异常提示」的前提。

`session-continuity.test.mjs`（11 项）覆盖：分离、寿命、签发上限、宽限期内续发、
撤权/吊销/停用后拒、限速不改判据、其它路径不加宽。platform 362 全绿。

## 本轮新发现

### 问题 17 · 请求体超过 64 KB 被**静默**当成空请求体

| 项 | 内容 |
|---|---|
| 操作 | 发布：一次提交六份契约 |
| 实际结果 | `KVVI_ASSET_ID_REQUIRED` —— 报的是「缺少字段」 |
| 真正原因 | `readBody(req, limit = 64*1024)` 超过上限时 **`return null`**，而 `null` 与「没有请求体」是同一个值；实测契约 65 KB |
| 严重程度 | 功能（**重要**：发布这个动作**只要交真实契约就必然撞上**） |
| 是否稳定复现 | **是** |

修法：超限返回一个可辨认的记号（不是 `null`），`/api/v1` 上限提到 4 MB，
超限回 `413 KVVI_BODY_TOO_LARGE`。另外把剩余字节读掉再返回 ——
直接 return 会让连接停在半路，客户端看到的是「连接被重置」。

### 问题 18 · 把 PostgreSQL 的错误当成了领域错误

| 项 | 内容 |
|---|---|
| 操作 | 重跑一次发布提交 |
| 实际结果 | 响应体是 `{"0":"键","1":"值","2":"\"",…}` —— 一份**逐字符**的 JSON |
| 真正原因 | 判据写的是 `error?.code !== undefined`，而 **pg 错误也有 `code`**；它的 `error.detail` 是**中文字符串**，`{ error, ...detail }` 把字符串展开成索引→字符 |
| 严重程度 | 功能（**重要**：基础设施故障被报成调用方的参数问题，而响应体本身是垃圾） |
| 是否稳定复现 | **是** |

修法：判据改成 `error instanceof PublishError`。另：唯一冲突（`publish_drafts_one_open`
索引说「同一份变更已经有一张开着的草案」）**不是故障** ——
现在把已有的那张交回去（`reused: true`），重跑脚手架不失败。

### 还没解决的一条：契约存储的形状与真实系统的形状**对不上**

平台的 `published_contracts` 是 **「(类型, 系统代号) 一份」**。
而搭出来的真实系统是：**两张视图**（登记表单 + 列表）、**七个工具**。
发布能成功，员工看到的却是其中一张视图；其余六份工具契约发上去了，
而没有任何读取路径会看到它们。

脚手架**不假装它解决了**，而是把两件事都做：按一套**明说的约定**装订
（`{tools: [...]}`，依据是平台自己的测试用的形状，不是契约 schema 规定的），
并把「装订丢掉了什么」逐条打印出来。

**这条要你定**：要么让平台按契约自己的 `asset_id` 存（那 `view-schema` 就能存多份，
而投影要改成按视图代号取），要么给每类定义一个容器形状（`{views: [...], tools: [...]}`）。
两条都要动投影与面板，得先定再做。

另外：搭建者这份 `permission-spec` 里**没有只读角色**（`sales` 有 create/update，
`sales_manager` 有 read/update/assign）。所以第 3 步「三个员工：只读 / 增改 / 无权限」
这一组，用这份契约只能测出「增改」与「无权限」两档 ——
**只读那一档要搭建者补一个角色**，不是平台的问题。

### 问题 19 · 同一个请求被门判了两次（**跑 ① 时撞出来的**）

### 问题 20 · 写操作没有幂等键

第 ⑤ 条量出来的：同一条建记录请求打三次，建出**三条不同的记录**。
「重连不重放」当时靠的是**客户端不自动重试** —— 一个**约定**，
任何一个新调用方都可能不遵守。而重连恰恰是最容易重复发一次的时刻
（响应没回来、连接断了、客户端不知道那一次到底成没成）。

修法：`Idempotency-Key` 请求头（**只认头，不认体** —— 放进请求体它就成了
一条模型可见的参数）。窗口内重发回**当初那个响应**，不是错误 ——
回「重复」会让重连的客户端以为失败，而它其实成功了。
只记成功的动作：记失败会把「第一次权限不足被拒、第二次权限给了再试」
变成「窗口内永远回那个 403」。

顺带守住一条不变量：第一版把写策略的 SQL 写在路由里，
`工具/check_publish_channel.py` **当场变红**。那条判据是对的 ——
它是 §9.6.3 在代码层面唯一的保证。挪回 `publish.mjs` 的 `writePolicies`。

## 问题 24 · `stop` 报成功，而进程还活着（**阻断，已修**）

| 项 | 内容 |
|---|---|
| 操作 | 试点实例反复 `--fast` 重启之后，看现场 |
| 实际结果 | **两个活了两个半小时的孤儿平台进程**，各自还被一个浏览器连着；`kvvi-admin stop` 当时报的是 `✓ stop 完成` |
| 严重程度 | **阻断** |
| 是否稳定复现 | **是**（三次） |

### 怎么发现的

不是读代码读出来的，是**数现场**数出来的：

```
$ ps -eo pid,etime,command | grep platform/src/server.mjs
15421  02:34:34  启动于 10:11:44   ← 不在监听，也没有 pid 文件指向它
16774  02:31:10  启动于 10:15:08   ← 同上
26949  01:41:51  启动于 11:04:27   ← 只有这一个在监听 7500
```

### 三件事单独看都对

| 环节 | 它做的事 |
|---|---|
| `kvvi-admin stop` | 发 SIGTERM、删 pid 文件、报成功 |
| 平台的 SIGTERM handler | `server.close(() => process.exit(0))` |
| Node 的 `server.close()` | 停止接受新连接、**放掉监听套接字**，回调挂在「所有既有连接都关闭」之后 |

浏览器长期持有 keep-alive 与流式连接 —— **那个回调永远不触发**。于是：

1. 监听套接字已释放 → **新进程能绑上同一个端口** → 重启「看起来成功了」；
2. 旧进程一直活着 → 它服务的是**撤权前就开着的那一页**，而它内存里的授权版本是
   撤权之前的那一份 → 与 §9.4.4「平台在线时撤销立即生效」直接冲突；
3. `status` 读 pid 文件，而 pid 文件已被新进程覆盖 → **旧进程查不到**。

### 实测复现

对两个孤儿各发一次 SIGTERM，6 秒后都还在：

```
pid 15421 发 SIGTERM 前：TCP 127.0.0.1:7500->127.0.0.1:55768 (ESTABLISHED)
         ⚠️ 6 秒后仍然活着
pid 16774 发 SIGTERM 前：TCP 127.0.0.1:7500->127.0.0.1:54922 (ESTABLISHED)
         ⚠️ 6 秒后仍然活着
```

而且——**只有监听套接字没了**。`lsof -iTCP:7500` 里它们只剩 ESTABLISHED，
LISTEN 是新的那个进程。这正是「重启看起来成功了」的原因。

### 修法（三层）

| 层 | 改动 |
|---|---|
| 平台 | 关停时 `closeIdleConnections()` 放掉空闲连接；再有 `SHUTDOWN_GRACE_MS`（默认 5 秒）**硬期限**，到点 `closeAllConnections()` 并 `process.exit(0)`。定时器 `unref()` —— 它自己不能成为「进程活着」的理由 |
| `stop` | 发 SIGTERM 之后**等**（10 秒），到期还在就升级 SIGKILL，再等 5 秒；**把这次升级报出来**（`SIGTERM 未生效，已用 SIGKILL 结束`）——静默升级会让平台的关停路径有 bug 而永远没人知道 |
| 「已退出」的判定 | 先 `waitpid(pid, WNOHANG)` 认领自己的子进程 —— 僵尸也能让 `os.kill(pid, 0)` 成功，于是**已经死掉的进程会被判成「还在」**，白等一轮再报一条假的「杀不掉」。这一条是负向测试当场抓到的 |

### 证据

**行为**（真实试点、真实连接）——按住一个**空闲 keep-alive** 和一个**在飞的请求**，然后 `stop`：

```
✓ stop-runtime
✓ stop-platform
✓ stop 完成
耗时 6 秒                              ← 空闲连接立刻放掉；在飞的那条等硬期限
✓ pid 67228 已经没了（修复前它会一直活着）
残余平台进程 0 个
关停日志：{"event":"platform-service-down","signal":"SIGTERM","forced":true}
```

## 问题 28 · 流程在当前试点上永远不可执行

| 项 | 内容 |
|---|---|
| 操作 | 三档员工分别查 `GET /systems/customer/records/:id/actions` |
| 实际结果 | **三档全是 `actions: []`**，包括有 FLOW 权限的 `staff-edit` |
| 严重程度 | 重要 |

两个独立原因叠在一起：

**① 记录的初始状态不在工作流的状态集里。**
`20-business.sql` 把 `state` 的默认值写死成 `'draft'`：

```sql
state text NOT NULL DEFAULT 'draft',
```

而搭建者契约里的工作流初始状态是 `not_followed`：

```
states: not_followed(initial) → following → won / lost
```

`nextActions(spec, 'draft')` 在 `states.get('draft')` 上取不到，直接返回 `[]`。
**一条新记录出生在一个没有工作流认识的状态里，于是流程永远起不来。**

**② 动作名是两套词表。**
契约的 FLOW 策略写的是 `actions: [SUBMIT, CLOSE]`，而工作流的
`action_code` 是 `start_follow` / `close_won` / `close_lost`。
运行时的判据是 `canAct('FLOW', workflow_code, candidate.action)` ——
拿 `start_follow` 去比一条只批了 `SUBMIT` 的策略，**永远匹配不上**。
而 `policy-compile.mjs` 里已经写过一次这类坑（契约 `READ_ONLY` / 运行时 `READONLY`）：
**编译不报错，只产生一条永远匹配不上的策略，表现是「员工被拒绝」。**

阶段九把这件事记成「流程动作按钮未做（无迁移端点）」—— **那个说法不准**：
迁移端点 `POST /records/:id/transitions` 是有的，`GET .../actions` 也有，
**是状态与动作名对不上，于是端点永远没有可执行的动作可选。**

## 问题 28 的修法（**已修**）：流程链路四处独立取错

### 症状与根因

三档员工拿到的可执行动作**全是空的** —— 界面上一个流程按钮都没有。
四个人分别读四个不同的名字，**没有任何两个是相同的**：

| # | 读什么 | 契约/搭建者写的 | 运行时读的 | 后果 |
|---|---|---|---|---|
| 1 | 新记录的**出身状态** | `states[].state_code` 里 `initial: true` 的那个（`not_followed`） | SQL 里写死 `state text NOT NULL DEFAULT 'draft'` | 记录出生在工作流不认识的态里，`nextActions` 找不到出边 |
| 2 | 这个**流程的身份** | `resource_ref.asset_id = 'customer_follow'` | `workflow.workflow_code ?? '*'` → **`'*'`**（契约根本没有这个字段） | 与任何策略都不匹配 |
| 3 | 一个**动作** | `actions: ['SUBMIT','CLOSE']`（**类别**） | `nextActions` 给的 `action_code`（`start_follow`） | 拿业务名比类别，永远不匹配 |
| 4 | 权限在**哪个状态**有效 | `subresource: {type:'STATE', code:'following'}` | `canAct` 没有状态参数 | 编译时记进「声明了但执行不了」 |

任何一条单独错，结果都是同一句话：**「没有可执行的流程动作」**。

### 决定依据：氚云 + 我们自己的 schema

- **`INITIATE` 与 `TIMEOUT_REMINDER` 各自只出现在一处的枚举里** ——
  `permission-spec` 的 FLOW `actions` 有 `INITIATE` 而没有 `TIMEOUT_REMINDER`；
  `workflow-spec` 的 `kind` 反过来。而 `Transition` **必填 `from_state`** ——
  这意味着「进入流程」这一跳在契约里**没法表达成一个迁移**（草稿不是契约状态）。
  设计时是知道的：所以它只作为**权限**存在。
- 氚云（泛微）的[流程介绍](https://help.h3yun.com/236525549/)里，
  流程**不是独立实体**（表单开一个开关就有了它，没有自己的编码），
  而「草稿」是**关掉流程后回落的态** —— 即「还没进流程」。

### 四处怎么修的

| # | 改法 | 在哪 |
|---|---|---|
| 1 | 新记录的出生状态取契约里 `initial: true` 的那个；没有流程的系统仍是 `'draft'`（那才是它的常态）。**想让记录先当草稿，就在契约里声明一个 initial 的草稿态** —— 平台不替搭建者发明一个 | `system-api.mjs` 的 `initialStateOf()` |
| 2 | 资源改用**业务对象**（就是平台注册契约时用的那个 id） | `system-api.recordActions` / `workflow.step` |
| 3 | `nextActions` 同时给出 `action`（业务名，回传用）与 `kind`（类别，判权限用）；两处调用点传 `kind` | `workflow.mjs` |
| 4 | 迁移 `25-policy-flow-state.sql` 给 `policies` 加 `state_code`；编译器把它落进行里；`canAct` 加状态判据 | `sql/` + `policy-compile` + `authorization` |

**第 4 条连带的两个坑**：

- 唯一约束 `(company, role, dimension, resource_code)` 必须**含状态**，
  否则同一角色在同一张流程的不同状态上各写一条就插不进去。
  新约束用 `NULLS NOT DISTINCT`（PostgreSQL 15+；本部署固定 17）——
  默认的 NULL 互不相等会让「不限状态」那一档重复插。
- 编译的 dedupe key 也**必须含状态**，否则「跟进中可成交」会把
  「已流失可复活」合并掉，只剩最后那条的状态。

## 阶段二 · 发布只对**新**记录生效（**已完成**）

> 氚云的流程介绍里有一条明确的不变量：
> 「流程修改**仅对新提交数据生效**，已有数据维持原流转规则。」
> 我们此前没有它 —— **发布即改全部**。试点上已经看得到这个形状：
> 11 条老记录停在 `draft`，新记录从 `not_followed` 起，一次发布就把在途的
> 那几条带到了新版流程上，而它们当前那个状态在新版里还存不存在都没人问过。

### 做了什么

| 改动 | 在哪 | 为什么 |
|---|---|---|
| 记录多一列 `workflow_version` | 迁移 `26-record-workflow-version.sql`（**业务库**） | 记录在**出生时**钉住那一刻的流程版本 |
| 按版本读契约 | `contracts.contractAt()` | 历史版本一直留着（契约只追加、不覆盖），所以读得回来 —— 这是这一列能成立的前提 |
| 投影接受钉住的版本 | `runtimeProjection(companyId, assetId, {workflowVersion})` | **只钉流程这一份**：模型、视图、权限照旧用最新版。「发布只对新数据生效」说的是**流程的走法**，不是「整份应用冻在某一天」 |
| 读不到就报错，**不退回最新版** | 同上（`KVVI_WORKFLOW_VERSION_MISSING`） | 静默退回等于把这条不变量又丢掉一次，而症状是「在途记录悄悄改走了新流程」，比直接报错难查得多 |
| 动作清单与执行**用同一版** | `system-api` 的 `/actions` 与 `/transitions` 两处 | 两边各读各的会出现「列表说能做、做的时候说不能」 |

`workflow_version IS NULL` 的含义写清楚了：**这条记录出生在钉住机制之前**
（或它所属的系统没有流程）→ 按当前版走。那是尽量接近原意的重建，不是一条规则。

### 证据

**判据（可执行，且证过它会红）**：`publish-runtime-e2e` 新增 ⑩ ——
先建一条记录，再把流程**改成一版状态名与动作名全不重叠的**（可分辨，不用猜它读了哪版），
然后断言：新记录走新版、**老记录仍走老版且真的推得动**。
把钉住那一步临时去掉 → ⑩ 当场变红。

**真试点**：

```
新记录：状态 not_followed；DB 里 workflow_version = 3（= 当前发布的流程版本）
老记录：19 条 workflow_version 为 NULL（钉住机制之前建的）
        ↑ 用超级用户查的 —— 业务库开了 RLS，普通角色不设作用域会读到 0 行，
          那个 0 看起来像「一条都没钉住」
新记录 /actions → HTTP 200 状态=not_followed 可执行=['start_follow']
        ↑ 能读出来，就证明「按钉住的版本取契约」这条路是通的
```

**全量**：平台 419 条通过 / 0 失败（新增第 419 条就是 ⑩）。

## 阶段三 · 字段约束真的执行（**已完成**）：`required` 与 `write_policy`

> 起因是氚云的[字段权限](https://help.h3yun.com/236514731/)：它有
> **可见 / 可写 / 必填 / 打印** 四档，而且「新增数据权限」与「查看编辑数据权限」
> 是**分开配**的。原以为我们要动冻结的元 schema 才能追上 ——
> 一查发现**根本不用**：

| 要表达的东西 | 氚云放在哪 | **我们已经有** |
|---|---|---|
| 必填 | 字段权限的一档 | `business-schema` 的 `Field.required` |
| 只在新增时可写 | 新增权限 vs 查看编辑权限 | `Field.write_policy = CREATE_ONLY` |
| 人不可写 | （没有这一档） | `Field.write_policy = SYSTEM` |

而**运行时一条都没执行**：`createRecord` 把 `data` 原样写进 jsonb，
`updateRecord` 把补丁原样合并。搭建者按契约写了 `required: true`，
效果只体现在表单的星号上 —— **又一次「声明了，没生效」**，与问题 28 同一形状。

### 做了什么

| 改动 | 在哪 | 为什么这样 |
|---|---|---|
| `checkFieldValues()` / `assertFieldValues()` | 新文件 `services/platform/src/field-rules.mjs` | 三条契约约束的**唯一判据**（必填、`CREATE_ONLY`、`SYSTEM`） |
| 在**唯一写入点**执行 | `refs.mjs` 的 `createRecord` / `updateRecord` | 记录有**四个**写入点（产品 API、命令执行器 `commands.mjs`、访客链路 `visitor.mjs`、流程迁移）。只在一个适配器里检查，另外三个就是绕过口 —— **「换个调用方就能跳过」的东西不叫约束** |
| 校验失败 → **400** | `api-router.mjs` 只映射 `FieldRuleError` | 不映射会一路穿到兜底变 500，调用方会去重试一个永远不会成功的请求。方向与 `admin-api` 那处（服务端出错报成 400）正好相反 |
| 逐字段返回违规清单 | 响应体 `problems` | 只说「参数错误」的话，调用方补一个被打回一次 |

**两个刻意的取舍，都写进了代码注释**：

1. **`required` 只在新增时查。** 更新是**补丁**语义（`data || patch`），
   「这次没带」不等于「把它清空」。在更新时要求必填字段出现，
   会把每一次「只改一个字段」变成必须回传整条记录 —— 那不是必填，那是替换。
2. **没有已发布模型时不拒。** 「没有模型」不等于「这次写入不合法」，
   它是**另一件事**，而那一件事已经有判据且在更早的地方
   （`runtimeProjection` 对缺契约的系统直接拒绝出投影）。
   在这里再拒一次是同一个判据的第二份实现，代价是 14 个与被测性质无关的用例
   全染红 —— 那是**用噪声换「看起来严格」**。有判据而不执行才是漏。

```
② 写契约里没有的字段 → HTTP 400  {"error":"KVVI_FIELD_NOT_DECLARED", …}
```

## 阶段四 · 按角色的字段必填（含**契约层的一次有意扩展**）

> 业主裁定：「氚云的必填是按角色/节点可配的……这个必要做；
> 打印权限首版可不做。」于是这一阶段只做必填。

### 为什么必须动契约层

模型层的 `Field.required` 是**全局**的：改了影响所有人。
而「这个角色在这一步必须填」是**按角色**的 —— 它得有地方放，否则搭建者表达不了，
也就等于没做（唯一生效通道是发布）。

| 放哪 | 行不行 |
|---|---|
| `business-schema.Field.required` | ✗ 全局的，改不了单角色 |
| 平台库加一列 | ✗ 只让**运行时**支持；契约写不出来 → 发布通道带不出去 |
| **`permission-spec` 的 FIELD 策略加一个可选属性** | ✓ 本来就是四维权限里 FIELD 那一维 |

**改动**（`contracts/meta-schemas/0a-full-r1/permission-spec.v1alpha1.schema.json`）：

```json
"required_field": { "type": "boolean", "default": false,
                    "description": "这一档是否要求该字段有值（按角色）" }
```

- **可选属性**，不进 `required` 数组 → 既有契约一律保持有效（**向后兼容**）
- 名字不叫 `required`：JSON Schema 自己有一个 `required` 关键字，
  同一个对象里两者并排像笔误，而这份文件的读者包括下一个照着改 schema 的人
- **不并进 `field_mode`**：可见性与必填是**两个正交的轴**。
  挤在一起会丢掉「**只读**且必填」——而它合法且常见：
  值由别人或流程填，但在你这一步它必须已经存在

这一次扩展是**对并入基线的修改**，`contracts/来源与指纹.md` §五·补 逐条记了：
改了什么、为什么、连带改了哪些文件、以及**没做什么**。
并入时那句「与源仓库逐字节一致」从这一刻起不再成立 ——
必须成立的是「每一处偏离都有记录」。

### 运行时侧

| 改动 | 在哪 |
|---|---|
| `policies.field_required boolean` | 迁移 `27-policy-field-required.sql`（**平台库**） |

### 三处入口，只存在一处

| 「提交」的可能入口 | 实际 |

| 搭建者的工作台（面板） | **没有** —— 面板的 API 客户端只有 `listDrafts / getDraft / decideDraft / publishDraft`，**没有 `submitDraft`** |

## 问题 12（界面半边）的修法：模式面按会话收窄（**已部署，真机验过**）

### 为什么上一轮「修了」却没修好

问题 13 修的是 `kvvi-mode-router` 的 `agentPresets.select` —— 它**只在点下去之后拦**。
界面照样把六个模式摆出来，员工能点开、能选中，只是建会话时才失败。
§2.6 写的是「员工不应看到『模式』」，不是「员工看到之后会被拒」——**看得见就已经不成立了**。

### 改在哪

`packages/host/kvvi-mode-router` 里再包一层 `agentPresets.remoteExportList`。
这一层是**唯一**的出口：菜单里的模式清单、设置页里六个预置的完整列表、
「新任务默认」那个标记，全都来自这一次调用。

收窄成两件事：

| 字段 | 收窄成 | 为什么 |
|---|---|---|
| `presets` | 只剩本会话被绑定的那一个 | 工位上的会话只有一个可能的取值 |
| `modeSelectionEnabled` | `false` | 模式是登录门绑定的，选择器与那个开关都不该出现 |

**收窄的是「看见什么」，不是「能做什么」。** 能做什么仍由上面那些包装在真正的操作上判 ——
两件事都要有，缺一个就成了「藏起来当权限」。

### ★ 关掉选择器不会改变任何会话的预置（先把这条排掉的）

`selectionPolicy()` 在 `enabled=false` 时会把 `defaultId` 退回 `config.default`（`standard`），
所以动手前必须先确认预置不是从 `defaultId` 来的。查证：

- `session-controller/agent.ts` 的 `composeAgent(presetId)` 用的是**请求里的** `presetId`；
- 而 `kvvi-mode-router` 包了 `sessionController.create`，`enforceCreateRequest()` 把
  `agentPreset: mode.preset` **钉进建会话请求**（`kvvi-mode-router/src/index.ts:139`）。

所以 `defaultId` 只在不经过路由的路径上才有意义，KVVI 的会话一律由网关定。**这条不成立就会
把搭建者的工具集打掉**，属于必须先证再改的那一类。

## 问题 29 的修法：给搭建者一个**提交发布**的工具（已部署、已跑起来）

业主裁定：「**可以在生成的表单有确认发布的按钮，也可以和 Agent 说确认提交发布**」。
两件事用一个机制同时满足：**工具 + 一次确认**。

### 做了什么

| 件 | 在哪 | 为什么 |
|---|---|---|
| 新包 `@deepseek-ai/dsh-tool-kvvi-publish` | `packages/tool/kvvi-publish/` | 工具跑在运行时里，**工作区在它手上**（`session.header.cwd`）—— 这是「读得到契约」的那一侧 |
| 一个工具 `publish_submit` | 同上 | 读工作区的六份契约 → `POST /api/v1/publish/drafts` → 回草案 id 与差异摘要 |
| 一条 `tools/pre-execute` 闸 | 同上 | 只对 `publish_submit` 回 `{kind:'ask'}` → **界面上弹一次确认面板**，就是业主要的那颗按钮 |
| 挂在搭建者预置 | `kvvi-builder/agent.cordis.yml` | 与 `kvvi-worker` 挂业务工具同一形状 |

**为什么闸只对这一个工具**：闸门放宽到所有工具，用户很快就会学会无脑点确认。
**为什么 `ask` 在这里是对的**：它在没有应答者时**拒绝**（fail closed），
所以「没人在场就静默提交」不会发生 —— 而提交是不可逆的（草案进了通道，所有者会看到）。

**为什么提交只用本会话的 `BUILDER` 身份**：审批与发布仍在所有者那边（§9.6.1，
服务端各自判）。工具只提交，**批不了自己那一份**。

### ★ 部署时撞到的两个坑（都记下来）

**① 加了 workspace 包，发行树必须重新 `pnpm install`，而且必须重启运行时。**

症状极具误导性：**界面完全正常**（登录、翻会话、打字都行），**只有发消息没反应** ——
点发送什么都不发生，会话日志一个字不写。浏览器控制台**没有报错**。

真因：`apps/cli/node_modules` 里没有新包的软链（发行树的 `node_modules` 是
从我早先备份复制的，pnpm 认为「已经是最新的」而不重建链接）。链补上之后
**还不行** —— 因为运行时进程是在链接存在**之前**起的。重启之后一切正常。

> 这是「改一处、不传播」的又一张面孔：**新包 + 老进程 = 静默不回话**。
> 而且它的报错面**是空的** —— 没有 500、没有页面错误、没有日志。

**② 重部署之后，已经打开的页面会卡在重连循环。**

浏览器控制台刷 `[connection] connection lost, retry #79` / `generation is still not ready
after 3000ms`。干净重启两个进程 + 刷新页面即恢复。

### 真跑起来之后，Agent 的表现（这一轮最有价值的部分）

我让搭建者说「**确认提交发布**」，它做了这些（都不是我教的）：

```
读取 契约/ 下的文件（6+7=13 份 JSON）
Bash 重算契约文件摘要
Bash 定位 publish_submit 的实现        ← 工具**确实挂上去了**，模型看得见
读取 契约/_校验/结果/00-命令与摘要.md、00-需求.md
查询平台：published contracts v1..v5
Bash 复现装订规则与 change_digest
```

然后它**拒绝盲目提交**，并弹出一张带三个选项的确认：

> 当前六份契约与已发布的 v5 逐字节相同，装订还会丢下 03-客户列表。要照原样提交吗？
> 1. 先别提交，先解决列表页（推荐）
> 2. 照原样提交
> 3. 我要改内容再提交

它还自己算出来：「我把当前工作区按装订规则算出的变更摘要是 `sha256:44c7ef50…`，
与那张已发布草案的 `change_digest` **逐字节相同**。所以照原样提交只会得到一张
差异为空的 v6 草案」。

**这比我预期的好**：它没有为了完成任务而制造一张空草案，而是先说明「提交也带不上列表页」。

### ★ 它还发现了我的工具的一个漏报

> 「`06-工具/schemas/` 下 8 份请求/响应 Schema —— **装订器整目录跳过，连注记都不报**。」

属实。我的 `contractFiles` 会跳过 `schemas/`（那些是被工具契约引用的片段，不是契约，
混进 `{tools:[…]}` 会得到 8 份没有 `tool_code` 的东西），但**跳过这件事没写进 `notes`** ——
而 `03-客户列表-view-schema.json` 被丢下是**报了**的。同一类事情两种处理，就是不一致。

CLI 脚手架的注释讲了为什么要排除它们，但也没把「排除了什么」交出去。
**这一条要修**（下一轮）：把「按目录整块跳过」也进 `notes`。

## 本轮的两条流程教训

1. **同步产物不能按「源码变没变」挑，要按「产物与源码一不一致」挑。** 部署品牌时第一轮标题还是旧的 —— 因为 `ui-layout`/`ui-sidebar` 把产品名**内联**进了自己的 `lib/client.js`，而它们不在「最近改动」名单里。改成遍历全部 52 个客户端包逐个比哈希，才发现只有那两个内联了产品名。
2. **旧进程会伪装成「系统没通」。** #30 那一条里，工具连到 7400 上的旧实例，对面回了个重定向 —— 整条链路看起来是「通道没应答」，真相是「连错了地方」。**换端口或重装之后，必须先确认旧实例已经不在了。**
