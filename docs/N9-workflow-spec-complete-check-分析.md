# N9 · `workflow-spec` 的 complete check —— 分析

> 契约自己在 `$defs.Spec.$comment` 里写了这句话：
>
> > **Structure only: role directory resolution, per-step coverage/graph order,
> > selector field matrix and 100-leaf total are complete-check responsibilities.**
>
> 也就是说：**这五件事，契约明确声明不归结构校验管**，而本仓库**没有 complete check 实现**。

---

## 一、这五件事分别是什么，各自漏掉会怎样

| # | 项 | 具体是什么 | 漏掉的后果 |
|---|---|---|---|
| 1 | **role directory resolution** | 每个 `role_ref` 是否指向**真实存在的角色** | 审批指派给一个不存在的角色 → **没人能批** → 流程静默卡死 |
| 2 | **per-step coverage** | 每个非终态是否**至少有一条出路**；每个状态是否**从 initial 可达** | 状态进得去出不来 → **流程静默卡死**；或状态根本走不到 → 死代码 |
| 3 | **graph order** | 迁移引用的状态是否存在；`initial` 是否唯一；终态是否无出边 | 迁移指向不存在的状态 → 运行时抛错或静默忽略 |
| 4 | **selector field matrix** | 选择器里用的字段，类型是否与**模型**对得上 | 选择器永远匹配不上 → 静默走 default 链 |
| 5 | **100-leaf total** | 状态 + 迁移 + 选择器分支的总量上限 | 规模失控（性能与可读性） |

> **#1 与 #2 的后果是同一句话**，而且 §3.3.3 已经把它写成了产品的立场：
> **「卡住的流程无人知道要处理，是审批系统最隐蔽的故障」**。
> 这两项不是「合规洁癖」，它们直接对应产品自己承认的最坏失效模式。

---

## 二、五项的实现代价差得很远

| # | 需要什么外部输入 | 算法 | 代价 |
|---|---|---|---|
| **2** | **不需要** | 图可达性 + 出边检查 | **小**（~60 行） |
| **3** | **不需要** | 集合比对 | **很小**（~30 行） |
| **5** | **不需要** | 计数 + 比较 | **极小**（~10 行） |
| **1** | 需要 **role directory** | 引用解析 | 中（要像 view-schema 那样把角色目录放进 context） |
| **4** | 需要 **business schema 的字段类型** | 类型矩阵比对 | 中（要读模型字段类型） |

**前三项是纯图与算术** —— 不需要任何跨契约输入，加起来约 100 行。
**后两项需要外部输入**，走的是 view-schema 已经用过的那套模式
（fake_assets + 引用解析），但要把两份契约连起来。

## 三、三种处置

### 方案 A · 全补（五项都做）

- **收益**：锚点① 的「通过 MetaSchema 校验」在这个契约上**名实相符**
- **代价**：约 2–3 天（#1 与 #4 要接线）
- **风险**：#4 的「正确」定义要靠猜 —— 契约只说「field matrix」，
  **没有给出矩阵的确切形状**。猜错的校验器比没有校验器更糟：
  它会把人挡住，而理由是错的

### 方案 B · 补前三项（我倾向这个）

- **收益**：**把两个「静默卡死」的失效模式关掉** —— 那正是产品自己承认的最坏情形
- **代价**：**约半天**
- **保留**：#1 与 #4 仍在结构校验之外，但**写明**——不是「不知道」，是「已知未做」

### 方案 C · 什么都不补，只把口径写死

- 交付文档写明：这个契约**只有结构校验**，「通过 MetaSchema 校验」对它指的是**结构层**
- **代价**：0
- **问题**：§3.3.3 引用的那句「卡住的流程无人知道要处理」是**产品自己写的立场**，
  而我们**有能力用 100 行把它变成机器可检的** —— 不做，是一种选择，但要说清楚是这个选择

## 四、我的建议：**B**，并把 #4 单独挂出来

| 做什么 | 为什么 |
|---|---|
| **补 #2 #3 #5** | 纯图与算术，无外部依赖；**关掉的两个失效模式正是产品自认最坏的那种** |
| **#1 挂起** | 它需要把 permission-spec 的角色目录接进来。**技术上不难**，但它把「流程」与「权限」两份契约绑在一起 —— 那是产品结构决定，不该由我在补校验器时顺手定了 |
| **#4 挂起，并写清原因** | 契约只说了「field matrix」而**没给形状**。按猜测实现一个会挡人的校验器，比没有更糟 |

**#4 挂起这一点值得单独说**：这是本仓库第一次遇到「契约声明了一项职责、但没给判据」。
其余四项都能从契约的定义推出来，只有 #4 推不出来。

## 四·补 · 「#4 要靠猜」到底是什么意思

我把契约里与选择器有关的定义全读了一遍，结论是：**契约给了检查的名称，没给判据。**

### 契约给了什么

| 定义 | 内容 |
|---|---|
| `Selector1..5` | 一个**嵌套深度阶梯**：Selector1 = Predicate；Selector2 = Predicate 或 all/any/not(Selector1)；……直到 Selector5。`Selector` = Selector5 |
| `PredicateField` | `{type: "FIELD", code}` —— **只有字段名，没有字段类型** |
| `Predicate` | 按操作符分档：`eq`/`ne` 的值可以是 boolean / 整数 / 字符串 / null；`gt`/`gte`/`lt`/`lte` 的值只能是整数或字符串 |

### 「field matrix」至少有三种都说得通的读法

| 读法 | 检查什么 | 它会拒掉什么 |
|---|---|---|
| **(a) 字段类型 × 操作符 × 值类型** | 模型里 `money` 字段不能用 `gt` 比字符串 | 类型用错的配置 |
| **(b) 字段是否存在** | `code` 能不能在 `businessSchemaRef` 指向的模型里找到 | 悬空字段 |
| **(c) 分支覆盖矩阵** | 多个 `choices` 之间**不重叠、不留缝** | 有缝或重叠的分支 |

**三种读法会拒绝不同的配置。** 选 (a)，一个用字符串比金额的流程被拒 —— 合理；
选 (c)，一个「只处理 5 万以上、其余走 default」的流程可能被拒 —— 而那**完全合法**。

### 为什么这是「猜」而不是「推断」

**其余四项的判据能从字段语义推出来**：

| # | 为什么可推 |
|---|---|
| 1 | 契约说 "role directory resolution"，而 `permission-spec` 里**定义了 role directory** —— 目标物是明确的 |
| 2 3 | `State` 带 `initial` / `terminal`，`Transition` 带 `from_state` / `to_state`。**可达性与出边只从这些字段就能定义** |
| 5 | 契约说 "100-leaf total"。唯一的模糊是「什么算一个叶」，我可以取一个保守定义并**写明** |
| **4** | 契约**只给了名称** —— 既没说是哪两个维度的矩阵，也没说违不违规的判据 |

### 为什么「猜错的校验器比没有更糟」

一个过严的校验器会：
- **挡住正确的配置**（builder 明明做对了却被拒）；
- 而拒绝理由会**断言一件契约从没说过的事** —— 于是下一个人去翻契约，找不到，只能回来读我的代码，把我的猜测当成规则。

**那就是把一个人的猜测变成了产品行为。**

### 所以 #4 其实有三个处置，不是一个

| | 内容 | 代价 |
|---|---|---|
| **挂起** | 不实现，写明「契约声明了但未给判据」 | 0 |
| **取最弱读法 (b)** | 只查「字段在模型里存在」—— 这是唯一一个**不需要猜维度**的读法（它其实就是 #1 的同构：解析引用） | 小 |
| **问出判据** | 由产品侧给出「矩阵」的确切含义，再实现 | 等一个答复 |

**我倾向「取最弱读法 (b)」** —— 因为它其实是 #1 的同一件事（**解析引用**），
只是解析的对象从「角色目录」换成「模型字段」。它不会误拒任何东西，
而且它挡掉的那个失效模式是真的：**选择器引用了不存在的字段 → 永远匹配不上 → 静默走 default 链**。

真正要「猜」的 (a) 和 (c)，我不做。

### 三个新结论（分析阶段没预料到的）

#### 1. 契约为 `workflow-spec` 的 `states/transitions/actions` 留了一条**空集合法**的路

`Spec` 的 `oneOf` 第二个分支要求这三个数组 **`maxItems: 0`** ——
它是给 `REGISTERED_CHAIN_SELECTION`（把审批链走已登记流程）准备的。
代价是：**一份 `states: []` + `transitions: []` 的流程，结构校验完全通过。**
它不是一个空流程，它是一个**死流程** —— 而结构层没有任何一句话说它不对。
这正是 complete check 必须存在的原因，也是「结构通过 ≠ 能跑」最具体的一例。

#### 2. `rejected` 在本仓库的样例里**全都堵死了** —— 十个样例加一个行业包

`PRD §7.4` 的状态机写法是：

> 草稿 → 待审批 → 已通过（终态）/ **已驳回 → 重新提交**

`workflow-builder` 的 SKILL 也把这件事写成红线：

> **驳回目标态必须显式** …… **最常见的设计缺陷是驳回后无处可去。**

而 10 组黄金样例与家具行业包的流程，`rejected` 都是
**`terminal: false` 且没有任何出边** —— 一个进得去出不来的非终态。
（唯一做对的是 `样例/workflow-spec/通用事项审批流.spec.json`，它有 `resubmit` 回边。）

**这不是校验器的假阳性，是三个生成器共同的缺陷**：它们各写一份流程字面量，
三处都漏了那条回边。已给 `工具/黄金样例.py`、`工具/行业包样例.py` 补上
`resubmit`：`rejected → draft`。这也验证了「补校验器」的价值 ——
**判据存在的第一件事，就是发现已有的产出不合判据。**

#### 3. 「已驳回」的两种合法写法只差一个布尔量

一个「驳回即终止」的流程让它成立，唯一要改的是 `terminal: true` 并删掉回边。
所以本检查器报的不是「你必须允许重提」，而是
**「你写下了 `terminal: false`，却没有给出路 —— 这两句自相矛盾」**。
判据落在**契约字段的自洽性**上，不落在产品的业务口径上。

### 顺带修掉的三个既有问题

| 问题 | 症状 | 处置 |
|---|---|---|
| `工具/交付环境.py` 依赖外部注入三个数据库口令 | `.kvvi-docker.env` 被清掉后干净环境部署直接失败，报 `required variable ... is missing a value` | 改为**干净环境自己生成一次性口令**，并在多次 compose 调用间保持一致 |
| `工具/进度.py` 的 `open_items()` 边界找错 | 每次 `--write` 静默删掉「未关闭事项」表下的引用块（优先级文档指引） | 边界改为「下一个二级标题」，并把那段指引交给生成器产出 |
| 行业包地基基线没跟上 N4 | `platform-service` 从 48 个文件变 51 个（N4 新增 retention 三件套），基线仍记 48 | 走 `--rebaseline --reason` **留记录**重设，不覆盖 |

### 这一层仍未覆盖的（不是「不知道」，是「已知未做」）

| 未做 | 为什么 |
