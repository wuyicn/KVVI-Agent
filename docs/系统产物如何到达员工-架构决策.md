# 系统产物怎么到员工那里 —— 一条一直没定的缝

> 这条缝是用户提问时暴露出来的：
>
> > 新员工下载这个 KVVI 平台，**肯定是空白的没有产物**。登录账号，
> > 搭建出来的系统产物**如何更新**？使用系统安装，或者搭建出来的产物
> > 是有 MCP 功能，员工安装后登录账号密码就**同步了系统数据**——
> > 这个我们要确认清楚。
>
> 问题本身是对的。下面先把**已经定过的**和**从来没定的**分开。

---

## 一、已经定过的（PRD 冻结文本，不要重新讨论）

| # | 决策 | 出处 |
|---|---|---|
| 1 | 搭建产出的业务系统**独立部署** | `Q1`、§4.2 |
| 2 | 工作模式 Agent **不碰数据库**，只通过**接口契约**读写 | §2.5 工程结论 |
| 3 | 契约包**版本化**，版本号单调递增 | §4.1.1 五 |
| 4 | 契约**只激活经发布通道送达的包**；本地存在其他包**不构成激活依据** | §4.1.1 五、§9.6.3 第 9 项 |
| 5 | 契约版本不符即**拒绝**，不降级、不做兼容猜测 | §4.1.1 五 |
| 6 | 界面隔离：员工**看不到搭建引擎的任何入口** | §2.3 |
| 7 | 平台服务进程是**唯一对外入口**，运行时进程不在宿主网络暴露 | §4.6.5 |

**第 3、4、6 条合起来已经蕴含一件事**：员工的界面**不是**「他本机搭出来的」，
而是「服务器告诉他该长什么样」。所以「空白 → 同步」这个方向**与冻结设计一致**。

## 二、从来没定的（这条缝）

**没有一句话说：发布之后，那份契约怎么到达员工那一端。**

分成两个独立的问题，历史上被混在一起：

| 问题 | 现在的答案 |
|---|---|
| **业务数据（单据、审批记录）在哪？** | ✅ 已定：服务器上的业务库（独立实例） |
| **系统定义（界面长什么样、流程怎么走）在哪？** | ❌ **没定** |

第二个问题才是「新员工下载下来是不是空白」的真正含义。

---

## 三、三种走法

### A · 服务端渲染（SPA 从服务器取）

员工用浏览器打开服务器上的工作台。系统定义**不下发到客户端**，
客户端只是个壳：登录 → 服务器说有哪几个系统 → 渲染。

- **优点**：版本只有一份（服务器）；与第 6 条界面隔离最省事；没有「离线用旧版本」的问题
- **缺点**：员工断网就用不了；「下载安装客户端」这件事没有意义
- **与你的描述冲突**：你说的是「下载 / 安装后登录」——A 里没有「安装」这一步

### B · 客户端渲染 + 契约从服务器同步

员工装 KVVI 客户端（就是现在的 DSH 运行时）。**登录后**，
客户端从服务器拉本公司**已发布的契约包**（含系统定义、表单、流程），
在本地渲染；业务数据仍在服务器，经接口契约读写。

- **优点**：与你的描述一致（空客户端 → 登录 → 同步出系统）；
  界面隔离在客户端就成立（拉下来的包里没有搭建能力）
- **代价**：
  - 契约包**必须签名**，否则员工能改本机契约绕过授权——§9.4.1 的签名体系正好是这个用途，但现在没有「客户端验签」这条路径
  - 需要一套**同步协议**：拉什么、什么版本、什么时候重拉、版本不符怎么办（第 5 条已定：拒绝）
  - 契约包在客户端落盘 → 「本地其他契约包不构成激活依据」这条要**真的实现**，不是文档里写一句
- **这条最接近你描述的形态**

### C · 产物带 MCP，员工装上就同步

把系统产物做成一个 **MCP 服务**，员工本地装它，登录后它负责与服务器同步。

- **优点**：复用 MCP 生态，安装/更新有现成形状
- **代价**：MCP 是**工具调用协议**，不是**界面协议**。它能让 Agent 调系统，
  但**给不了员工界面**——「已发布的系统或单个表单进行权限设置」
  这件事落在 MCP 上无处安放
- **判断**：**C 解决不了你的问题**。它是一条「让 Agent 调系统」的路，
  而你的场景要的是「让员工看到并操作系统」。两者不是一件事。

## 四、我建议 B，理由是它同时满足你的描述与冻结设计

| 你的原话 | B 里怎么成立 |
|---|---|
| 「搭建者先在本地构建，只有他一个人看得到」 | 未发布的契约只在本机 → 别人拉不到 |
| 「点发布，就部署到服务器」 | 发布通道写入服务器，产生新契约版本 |
| 「所有人都看得到」 | 员工登录后拉到那个版本 |
| 「新员工下载下来是空白的」 | 对——空客户端，登录前没有任何系统 |
| 「登录账号密码就同步了」 | 拉契约包 + 建会话，两件事一起发生 |
| 「搭建者给已发布系统或单个表单设权限」 | 权限在服务器判定；客户端只渲染服务器说能看的 |

**但 B 有两个必须现在定的事**，它们决定要不要写一堆代码：

| # | 要定的事 | 不定会怎样 |
|---|---|---|
| **B1** | **契约包要不要签名？谁验？** | 不签 = 员工改本机契约就能绕过权限，而 §9.4.1 的签名体系本来是为此建的 |
| **B2** | **同步粒度：整个系统还是单个契约？** | 粒度错了会让「改一个表单要重下整个系统」变成常态 |

## 五、与现有实现的关系（诚实交代）

现在的 7400 是**单机形态**：平台服务 + 运行时 + 三个库都在一台机器上，
员工与搭建者共用同一个运行时。

那个形态**只实现了 A 的一部分**，而且：

- `systems` 表已经能列「本公司已发布的系统」（上一轮做的）
- 但**契约内容对平台不可读** —— 所以面板列得出系统名，打不开系统界面
- 也就是说：**B 需要的那条路，现在是断的**，断点就是「契约内容在哪」

> 这与上一轮我报告的「待办与聚合口径卡在契约不可读」**是同一个缺口**。
> 那不是两个问题，是同一个：**契约内容没有被任何服务持有**。
> 它对 A 够用（A 里客户端不碰契约），对 B **必须解决**。

## 六、要你定的一句话

**员工的界面是「打开浏览器连服务器」，还是「装个客户端、登录后同步出系统」？**

- 选「浏览器连服务器」→ 走 A，契约不用下发，工作量小，但「安装客户端」这件事不存在
- 选「装客户端、登录同步」→ 走 B，要补：契约存储（可被平台读）、下发协议、客户端验签，以及 §4.1.1 五那条「本地包不构成激活依据」的真正实现

**C（MCP）我不建议**：它是工具调用协议，给不了员工界面，解决的是另一个问题。
