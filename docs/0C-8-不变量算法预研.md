## 一、要不变量化的到底是什么

§9.8.1 的原缺陷：

> 店长有「店铺总销售额」但无权看员工甲的个人业绩；
> 他查询「本店总额」与「除甲外总额」，**相减即得甲的个人销售额**。

PRD 的决策是**首版不做聚合防差分**，理由是该产品的数据对具备相应权限者开放，
不产生「可见汇总但不可见个体」的权限切分。**但这个理由有前提，且前提必须被机器检查**：

| 前置约束 | 说明 |
|---|---|
| **不得产生「汇总可见、个体不可见」的权限切分** | 只要能看某个汇总口径，就必须能看构成该口径的个体数据 |

**违反即拒绝发布，不存在审批放行路径。**（§9.8.1）

## 二、形式化

### 2.1 组织模型与档位语义

**档位取自契约层**，不另立定义 —— `permission-spec.v1alpha1.schema.json` 的
`DataPolicy.data_scopes`：

```json
"enum": ["SELF", "STORE", "DEPARTMENT", "DEPARTMENT_AND_CHILDREN", "COMPANY"],
"minItems": 1, "maxItems": 5, "uniqueItems": true
```

**⚠️ 它是数组**（1–5 个，可多选）。这一条直接决定判定形态，见 §3.1。

**组织模型** `M` 是判定的**显式输入**（而非从档位编号推导）：

| 分量 | 内容 |
|---|---|
| `tenants` | 公司集合 |
| `depts` | 部门树（`dept → parent`） |
| `shops` | 店铺集合 |
| `users` | 用户 → `(tenant, dept, shop, id)` |

**档位谓词** `holds(u, r, s)` —— 用户属性 `u=(tenant,dept,shop)` 在档位 `s` 下能否访问归属为 `r=(tenant,dept,shop,owner)` 的记录：

| 档位 | 谓词 |
|---|---|
| `SELF` | `r.tenant=u.tenant ∧ r.owner=u.id` |
| `STORE` | `r.tenant=u.tenant ∧ r.shop=u.shop` |
| `DEPARTMENT` | `r.tenant=u.tenant ∧ r.dept=u.dept` |
| `DEPARTMENT_AND_CHILDREN` | `r.tenant=u.tenant ∧ r.dept ∈ subtree(u.dept)` |
| `COMPANY` | `r.tenant=u.tenant` |

> **多公司隔离是任何档位的隐含前提**（§9.9.2）：`u.tenant ≠ r.tenant` 时一律不可访问。

### 2.2 不变量

对一个聚合口径 `A`（资源范围 `resource`，可见性档位集合 `scopes`，注入档位 `inject`）：

```
不变量：   ∀u ∈ Viewers(A).  Constituents(A, u) ⊆ Access(u)
```

其中
- `Access(u)` = u 通过**常规查询**能访问的记录集合；
- `Constituents(A, u)` = **注入后** A 实际聚合的记录集合。

## 三、可机器判定的条件

### 3.1 为什么不能按档位编号比较

PRD §2.5.1 的硬规定：

> **不得假定「档位编号越大 = 数据集合越大」**——本文档**未规定店铺与部门的组织包含关系**，
> 二者可能**交叉**。

这在契约层得到印证：`data_scopes` 是**数组**。`["SELF","STORE"]` 与 `["DEPARTMENT"]`
之间**不存在编号大小关系** —— 集合关系取决于组织模型本身。

**判定器的用例里有直接的交叉反例**：
`店铺口径 / DEPARTMENT 可见` 与 `DEPARTMENT 口径 / STORE 可见` **都被判为不可用**，
而按编号它们「看起来」是 2 < 3 或 3 > 2 —— 编号比较在这里给不出正确答案。

### 3.2 三个判定层（这是本预研的核心结论）

判定器把不变量拆成三层，**每层的可判定性与作用不同**：

| 层 | 判什么 | 可判定性 | 作用 |
|---|---|---|---|
| **L1** | **口径可用性**：是否存在任何用户的档位能覆盖该口径的聚合范围 | ✅ 有限枚举 | 抓住「口径与可见性不匹配」这类**配置错误**（如全公司口径配 SELF 可见 → 无人能看） |
| **L3** | **注入一致性**：查询实际返回的范围是否**超出**用户的可访问范围 | ✅ 有限枚举 | **唯一能真正失败的一层**，也是 §9.8.1 攻击成立的条件 |
| **L2** | **不变量本体**：能看 A 的是否都能看构成它的每一条 | ⚠️ **恒真**（见下） | **防御性检查**，不是主要检查点 |

### 3.3 ⚠️ 关键发现：L2 恒真，不变量由 L1+L3 保证

**这是本预研最重要的结论，必须明说，否则实现者会以为「跑一个 L2 就安全了」。**

**为什么 L2 恒真**：`Viewers(A)` 的判定（档位能否覆盖整个 `resource`）与
`Constituents(A)` 中每条记录的判定（档位能否覆盖这条记录）**用的是同一个谓词**。

> 能覆盖整个范围 ⟹ 必然能覆盖范围内的每一条。

**所以只要「能看 A」与「能看每条记录」共用同一套档位判定，L2 就不会失败。**

**这不变量是恒真的吗？** 不是 —— 它是**「数据范围强制注入」在正确实现下成立的同义改写**。
真正会失败的场景是**两者不是同一个范围**：

| 场景 | 结果 |
|---|---|
| 声明可见性 `COMPANY`（能看全公司汇总），但查询**只注入 `SELF`** | 用户看到全公司汇总，却看不到构成它的任何他人记录 → **违反** |
| 声明可见性 `COMPANY`，但查询**完全不注入**，而聚合范围跨店 | 持有 `STORE` 档位的用户会看到超出自身范围的汇总 → **违反** |
| 可见性与注入一致 | 成立 |

**这就是 L3 存在的原因**，也是判定器两条 L3 用例（`★` 标记）验证的性质。

### 3.4 判定的输出形式：反例

判定器不返回「是/否」了事，而返回**可直接用于报错的反例**：

```json
{
  "ok": false, "layer": "L3",
  "counterexample": {
    "user":   { "tenant": "t1", "dept": "sales", "shop": "store-2" },
    "why": "该用户持有此口径的可见性档位，但档位覆盖不到聚合范围；查询又未注入数据范围……"
  }
}
```

**这是「拒绝发布」时该展示给搭建者的东西** —— 一个能定位到具体用户属性的反例，
比「不变量不成立」这句话有用得多。

## 四、判定算法与复杂度

### 4.1 算法

```
check(org, A):
  users        ← org 的全部属性元组 (tenant, dept, shop)        # 不是用户实例
  constituents ← records_matching(org, A.resource)               # 属性等价类

  L1: viewers ← [u ∈ users | covers(u, A.scopes, A.resource)]
      若 constituents 为空        → 拒绝（聚合范围在本部署不存在）
      若 viewers 为空             → 拒绝（口径与可见性不匹配）

  L3: 若 A.inject 为空            → ∃u ∈ users. ¬covers(u, scopes, resource) → 拒绝
      否则                       → ∃u. covers(u,scopes,res) ∧ ¬covers(u,inject,res) → 拒绝

  L2: 防御性逐条检查（正确实现下不会触发）
```

### 4.2 复杂度

| 量 | 规模 | 说明 |
|---|---|---|
| 用户属性元组 | `\|tenants\| × \|depts\| × \|shops\|` | **不是用户数** —— 这是关键 |
| 记录属性等价类 | 同上 × 2 | `owner` 唯一无法有限枚举的维度，见下 |

**`owner` 的处理**：`SELF` 档位下 owner 可以是任意人，无法有限枚举。判定器对每条
属性组合**同时**给出 `owner=self` 与 `owner=other` 两种取值。

> **这是保守的，且保守方向是「更容易报违反」**：`owner=other` 构造出
> 「用户看得到汇总、却看不到别人贡献的记录」这一最不利情形。
> 若连它都不违反，则任何真实数据状态都不违反 —— **因此不会漏报**。

**规模结论**：判定是 `O(|tenants| · |depts| · |shops|)` 量级的**有限枚举**，
与实际用户数和记录数**无关**。对一个 `10 公司 × 100 部门 × 50 店铺` 的部署，
属性组合约 `5 万` —— **可判定，不需近似**。

## 六、本预研的局限（必读）

| # | 局限 | 影响 |
|---|---|---|
| 1 | **`owner` 维度靠保守枚举**，不是精确判定 | 可能对某些极端配置**过度拒绝**（假阳性）。方向是安全的（不漏报），但会牺牲一点可用性 |
| 2 | **角色分配不在输入里**，故 L3 保守遍历**全部用户属性元组** | 同上：可能拒绝「实际上没人持有该口径」的配置。保守方向安全 |
| 3 | **未覆盖运行时动态组织变更** | 判定基于**发布时刻**的组织模型。若发布后部门树变更使约束不再成立，当前判定器**检不出** —— 这属 §9.6.3 发布通道之外的问题，须另行设计（见待办 1） |
| 4 | **不解析 `WHERE` 子句，只判范围一致性** | 这是**有意**的，因为不需要 —— 理由见 §6.1。但**跨表/多源聚合**的情形未验证（见待办 2） |
| 5 | **仅实现为原型，未接入发布通道** | 本交付物满足 G3「预研完成并给出可机器判定的条件」；**接入是阶段五的工作** |
| 6 | **未做性能实测** | 复杂度是推导的，未在真实规模的契约包上跑过 |

### 6.1 为什么不需要解析 `WHERE` 子句（一次自我更正）

本预研初稿曾把「PRD 原始攻击用的是『除甲外总额』，即**过滤排除**而非**范围差异**，
故当前形式化可能没覆盖攻击的确切形态」列为待办。**重新推演后，该担忧不成立**：

PRD 原始攻击要成立，需要**两个条件同时满足**：

1. 店长能看「本店总额」与「除甲外总额」；
2. 店长**看不到甲的个人业绩**。

而第 2 条在「数据范围强制注入」下**不成立** —— 甲是店内员工，其记录属于本店，
店长的 `STORE` 档位**覆盖**它。

**关键在于**：本判定器检查的正是「**能看汇总 ⟹ 能看构成汇总的每一条**」
（L3）。一旦这条成立，**任何过滤条件都无法构造出「看不到的个体」** ——
因为能被过滤掉的个体，本就在用户的可见范围内，排除后相减得不到新信息。

**所以不解析 `WHERE` 子句不是缺口，而是**：过滤排除的威胁**已被 L3 蕴含**。
真正需要保留的待办是**跨表/多源聚合**——那里 `Constituents` 的构成方式与单表不同。

> **记录这次更正本身**：初稿的措辞会让实现者以为存在一个未覆盖的攻击面而重复劳动，
> 或反过来**因为担忧而误以为判定器不可用**。两种代价都不小。

### 待办（阶段五开工前须解决）

1. **动态组织变更**：发布后部门树/店铺归属变更，是否需要重新判定？若需要，触发点在哪？
2. **跨表 / 多源聚合**：当前形式化把聚合的输入视为**单一记录集合**。若一个聚合口径
   从多个来源（连接、子查询、多个业务实体）取数，`Constituents` 的构成方式需要扩展。
   这是本预研**未验证**的部分，须在阶段五开工前明确。
3. **性能实测**：在真实规模的契约包上验证复杂度推导。

## 七、结论

**G3 的判据「给出可机器判定的条件」已满足**：

| 要求 | 交付 |
|---|---|
| 判定条件明确 | §3.2 的三层定义 + §3.4 的反例输出格式 |
| 可机器判定 | `工具/check_invariant.py` —— 12 个用例覆盖成立/拒绝两侧 |
| 判定器可信 | `工具/check_invariant_自测.sh` —— 5/5，含「非恒真」「非恒假」「分层生效」与关键性质验证 |
| 不依赖近似 | §4.2 —— 枚举的是**属性元组**，与用户数、记录数无关 |

**§6.1 记录了一次自我更正**：初稿担心「未解析 `WHERE` 子句 = 漏掉 PRD 原始攻击」，
重新推演后确认**该担忧不成立** —— 过滤排除的威胁已被 L3 蕴含（能看汇总 ⟹ 能看每一条，
则能被过滤的个体本就在可见范围内）。

**真正未验证的是跨表/多源聚合**（待办 2），须在阶段五开工前明确，不得默认它已被覆盖。
