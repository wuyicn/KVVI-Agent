# 数据模型推导（data-model）

把一段业务描述变成领域无关的数据模型。这是所有其他搭建 Skill 的地基：
表单是模型的可写视图，审批流是模型的状态迁移，看板是模型的聚合读视图。
**模型错了，后面三样全错。**

## 何时用

- 用户描述了业务但没说数据结构：*「我们公司报销要走审批」*
- 用户直接问模型设计：*「这个系统的数据表怎么设计」*
- **在写任何表单、流程、看板之前**——先推导模型，不要边写界面边补字段

## 不预设行业词汇

本引擎不带行业组件库。不要因为听到「报销」就套一张既有费用表模板，
也不要引入「工单」「报货单」「病历」这类行业家具当作原语。
**从用户实际说出的名词和动词里推导实体**，用户没说的不要编。

## 推导流程

### 1. 抽名词 → 候选实体

把业务描述里的名词圈出来，逐个判断：

| 判据 | 结论 |
|---|---|
| 有生命周期（会经历状态变化） | **实体** |
| 需要被多次创建、每条有独立身份 | **实体** |
| 只是描述另一个东西的属性 | **字段** |
| 是固定的少数几个选项 | **枚举值**，不是实体 |

复数的、可数的、需要「查某一条」的 → 实体。单数且从属于某实体的 → 字段。

### 2. 抽动词 → 关系与状态迁移

动词决定两件事：

- **关系**：*「员工提交申请」* → 员工与申请之间有一条 `提交者` 关系
- **状态迁移**：*「提交后进入待审批」* → 申请实体有 `状态` 字段，迁移由 workflow-builder 接管

动词里凡出现「审批 / 通过 / 驳回 / 撤销 / 关闭」的，都要收敛成状态枚举，
**不要**做成布尔字段。布尔字段无法表达「驳回后重新提交」。

### 3. 定字段

每个字段必须能回答四个问题：

| 问题 | 说明 |
|---|---|
| 类型 | string / number / integer / boolean / date / datetime / enum / ref / text / file |
| 必填 | 业务上真的必须有，还是只是常见？**别把常见当必须** |
| 约束 | 长度、范围、格式、精度。金额用整数分或定点小数，**绝不用 float** |
| 来源 | 用户填的 / 系统生成的（时间戳、单号）/ 从别处引用来的 |

### 4. 定关系

| 关系 | 何时用 | 建模方式 |
|---|---|---|
| 一对多 | 一条主记录挂多条明细 | 子表持 `父id` |
| 多对多 | 两边都能挂多条 | 中间表，或数组字段 |
| 引用（ref） | 只是指向另一实体 | 存对方 id，不复制字段 |

关系**必须显式声明**，不要靠字段名暗示——`部门名称` 是复制了字段，
`部门id` 才是引用。复制字段会在源头改名时静默漂移。

### 5. 定状态机

凡是实体有生命周期的，写出状态枚举和允许的迁移：

```
状态: 草稿 → 待审批 → 已通过
              ↓
            已驳回 → 草稿（可重新提交）
```

每个迁移标注：谁能触发、触发后哪些字段变、是否需要审批记录。

### 6. 定不变量

业务规则里「必须/不能/至少」这类句子是不变量，要落成**约束**而不是注释：

- 跨字段：*「结束时间必须晚于开始时间」*
- 跨记录：*「同一员工不能有两条进行中的申请」*
- 计算字段：*「总额 = 明细行金额之和」* ——标明是存还是算

## 输出格式

推导完输出一份模型草案，结构如下：

```yaml
实体: 申请
  说明: 一次业务请求的完整生命周期记录
  字段:
    - { 名: id,       类型: string,  必填: 是, 来源: 系统 }
    - { 名: 申请人id, 类型: ref(员工), 必填: 是, 来源: 用户 }
    - { 名: 金额,     类型: integer, 必填: 是, 来源: 用户, 约束: "分为单位, >0" }
    - { 名: 状态,     类型: enum[草稿,待审批,已通过,已驳回], 必填: 是, 来源: 系统 }
    - { 名: 提交时间, 类型: datetime, 必填: 否, 来源: 系统 }
  关系:
    - { 名: 明细, 类型: 一对多, 目标: 申请明细 }
  状态机:
    - { 从: 草稿, 到: 待审批, 触发: 申请人提交 }
    - { 从: 待审批, 到: 已通过, 触发: 审批人通过 }
    - { 从: 待审批, 到: 已驳回, 触发: 审批人驳回 }
  不变量:
    - "同一员工不能有两条状态为待审批的申请"
```

## 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 把属性当实体 | 表爆炸，或该拆的没拆 | 有独立身份和生命周期的才是实体 |
| 把实体压成字段 | 无法记录多条 | 「多条明细」必须建子表 |
| 用布尔代替状态 | 驳回后无法回退 | 用状态枚举 |
| 金额用 float | 累加误差，对不平账 | 整数分或定点小数 |
| 复制字段代替引用 | 源改名后静默不一致 | 存 id 做 ref |
| 业务规则写进注释 | 无人执行，形同不存在 | 落成约束或不变量 |
| 编造用户没说的规则 | 原型与业务不符 | 标为待确认，不要猜 |

## 交接

模型定完后交给下游 Skill：

- 每个可写实体 → `form-builder`
- 每条状态机 → `workflow-builder`
- 每个聚合读视图 → `dashboard-builder`
- 每个跨系统边界 → `api-spec`
