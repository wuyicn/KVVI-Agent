# 审批流编排（workflow-builder）

把业务里的「谁来批、按什么条件批、批完怎样」变成可执行的流程定义。

审批流的本质是**状态机 + 人**：状态机定「能去哪」，人定「谁能推」。
两者分开建模，不要混成一张节点图。

## 何时用

- 用户描述了审批规则：*「金额超过 5 万需要总监审批」*
- 用户描述了多级流转：*「提交后先主管、再财务、再总经理」*
- `data-model` 定出的状态机需要落到具体人

## 前置

状态机必须已由 `data-model` 定好。若没有，**先定状态机再编排审批人**——
跳过状态机直接画审批节点，会做出无法表达「驳回后重新提交」的流程。

## 生成规范

### 1. 节点类型

| 节点 | 语义 | 产出 |
|---|---|---|
| 开始 | 流程入口，由提交动作触发 | — |
| 审批 | 需要人做决定，可多人 | 通过 / 驳回（可要求填意见） |
| 条件 | 按表达式分流，不消耗时间 | 命中分支 |
| 抄送 | 通知但不阻塞 | 无（流程继续） |
| 自动动作 | 改字段、发通知、调接口 | 字段变更 |
| 结束 | 收敛到某个终态 | — |

**条件节点不产生等待**，不要把它当成「等某人确认」——那要用审批节点。

### 2. 审批人解析

审批人**不要写死人名**。按优先级从这些策略里选：

| 策略 | 适用 | 说明 |
|---|---|---|
| 发起人直属主管 | 日常审批 | 跟着组织关系走 |
| 指定角色 | 职能审批 | 如「财务角色」 |
| 指定人 | 特例 | 硬编码，要标注为什么 |
| 字段指定 | 表单里选了审批人 | 表单必须有该 ref 字段 |
| 逐级上报 | 多级审批 | 指定起始层级与级数 |

**审批人解析失败必须有兜底**（转交管理员或挂起并告警），
不能静默卡住——卡住的流程无人知道要处理。

### 3. 条件分支

条件表达式只允许**引用表单字段与系统字段**，禁止任意代码：

```yaml
- 条件: 金额 > 50000
  分支: 总监审批
- 默认: 主管审批
```

规则：

- **必须有一条默认分支**。条件都不命中时流程要有去处。
- 条件要**互斥且有序**，从上往下第一个命中的生效。
- 金额比较用整数分，不要用浮点。
- 每个条件分支都要有测试示例（见下方）。

### 4. 多人审批的收敛方式

| 方式 | 语义 | 何时用 |
|---|---|---|
| 或签 | 任一人通过即通过 | 值班、候补审批人 |
| 会签 | 全部通过才通过 | 需要多方确认 |

**默认用或签**，会签必须显式声明——会签会让流程卡在最后一个人那里。

### 5. 驳回、撤回、超时

| 场景 | 处理 |
|---|---|
| 驳回 | 回到**哪个**状态必须写明（回草稿可改重提，还是直接终止） |
| 撤回 | 发起人可否撤回、能撤到哪一步——默认只能在首个审批节点前撤 |
| 超时 | 时长 + 动作（提醒 / 自动通过 / 升级上级）。**不设超时要有理由** |
| 转交 | 审批人可否转交他人，转交后原审批人的待办如何处理 |

驳回目标态**必须显式**。最常见的设计缺陷是驳回后无处可去。

### 6. 权限与可见性

- 谁能发起这个流程
- 每个审批节点谁能操作（解析后的人，还是角色所有人）
- 非参与者能否看到流程进度（通常可看，但不能操作）
- 审批意见谁可见

## 输出格式

```yaml
流程: 费用报销审批
绑定实体: 申请
触发: 提交动作
节点:
  - { id: n1, 类型: 开始, 触发: 申请人提交 }
  - { id: n2, 类型: 条件, 表达式: "金额 > 50000" }
  - { id: n3, 类型: 审批, 名称: 总监审批, 审批人: { 策略: 指定角色, 角色: 总监 }, 收敛: 或签 }
  - { id: n4, 类型: 审批, 名称: 主管审批, 审批人: { 策略: 发起人直属主管 }, 收敛: 或签 }
  - { id: n5, 类型: 自动动作, 动作: "置状态=已通过, 记录通过时间" }
  - { id: n6, 类型: 结束, 终态: 已通过 }
边:
  - { 从: n1, 到: n2 }
  - { 从: n2, 条件: "金额 > 50000", 到: n3 }
  - { 从: n2, 默认: 是, 到: n4 }
  - { 从: n3, 结果: 通过, 到: n5 }
  - { 从: n3, 结果: 驳回, 到: n1-驳回, 目标态: 草稿, 需填意见: 是 }
  - { 从: n4, 结果: 通过, 到: n5 }
  - { 从: n5, 到: n6 }
兜底: { 审批人解析失败: 转交管理员并告警 }
超时: { 时长: 48h, 动作: 提醒; 72h: 升级至上级 }
```

### 测试示例（必填）

每个条件分支给至少一条走通的样例输入，证明分支可达：

| 场景 | 输入 | 期望路径 |
|---|---|---|
| 小额 | 金额 = 10000 | n1 → n2 → n4 → n5 → n6 |
| 大额 | 金额 = 80000 | n1 → n2 → n3 → n5 → n6 |
| 大额被驳 | 金额 = 80000，总监驳回 | …→ n3 → 回草稿 |
| 边界 | 金额 = 50000 | 走默认分支（含等号规则要写清） |

**边界值必须有一条用例**——`>` 还是 `>=` 是审批纠纷的常见来源。

## 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 审批人写死人名 | 人员变动后流程失效 | 用角色/关系策略 |
| 没有默认分支 | 条件不命中时流程悬空 | 必须有默认分支 |
| 驳回目标态未定 | 驳回后无处可去 | 显式写驳回目标态 |
| 条件与状态机脱节 | 批完状态不对 | 先定状态机 |
| 默认会签 | 卡在最后一人 | 默认或签，会签显式声明 |
| 审批人解析无兜底 | 流程静默卡死 | 转交或告警 |
| 无超时 | 待办永久堆积 | 设超时或写明理由 |
| 边界值无用例 | `>` / `>=` 争议 | 边界值单列用例 |
