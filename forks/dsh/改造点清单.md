### B 类改造点（能力扩展，非品牌）

与 A 类不同：A 类是「改了上游已有的东西」，下面这两条是**给上游加了一个它没有的能力**。

| ID | 路径 | 改动 | 为什么改（N3） | 冲突可能性 | 升级处置 |
|---|---|---|---|---|---|
| **DSH-B5** | `packages/host/webserver/`（3 个文件：`src/index.ts`、`README.md`、`tests/webserver.spec.ts`） | **放宽** `Config.host`：从 `'127.0.0.1' \| '0.0.0.0'` 改为接受显式 IPv4 字面量（新增 `IPV4_LITERAL` 校验，禁前导零） | 上游两条约束夹击后**只剩 loopback 一个可用值**：startup 拒绝 `0.0.0.0`，而 schema 只接受 `127.0.0.1 \| 0.0.0.0`。而 loopback 在各容器内是隔离的，**平台服务进程因此够不到运行时进程**，PRD §4.6.5 的请求分流无从落地。按 §4.1.1「若 DSH 与规则不同，修改 DSH，而不是改规则」处理 | 🟡 **中**（上游若动 host 枚举会冲突） | 重新应用放宽；若上游自己也加了显式地址支持，**改用上游的**并销项 |
| **DSH-B6** | `packages/bundle/web-app/`（2 个文件：`src/index.ts`、`tests/trusted-hosts.spec.ts`） | **`resolveLanTrust` 计入显式绑定地址**：非 loopback、非 all-interfaces 时，把该地址加入 `trustedHosts` | 少了这一条会得到一个**更难读的失败**：绑定成功，但经该地址发来的每个请求都被 browser-trust fence 拒绝，表现为「服务不可达」而不是「绑定配置错」 | 🟡 **中** | 同 B5 |

> **⚠️ 这两条保留了原有语义，不是解除限制**（务必在复评时核对）：
>
> | 原有语义 | 是否保留 |
> |---|---|
> | `0.0.0.0` 被 startup 拒绝（最危险的形态） | ✅ **保留**，未动 startup |
> | 未显式指定时默认 `127.0.0.1` | ✅ **保留**，未改默认值 |
> | schema 仍拒绝非 IPv4 字面量（域名等） | ✅ **保留**，新增校验反而更严（禁前导零） |
>
> **净效果是「增加一个受控出口」，不是「打开通配符」。**

### ⚠️ 本节登记的路径用了**目录前缀**，这是一次有意的取舍

DSH-B5/B6 各覆盖一个包内的多个文件。用目录前缀意味着**该包内任何**文件的改动
都会被判为「已登记」，比逐文件登记宽。

**为什么接受**：这两个包的改动都源于**同一个决策**（N3），拆成逐文件条目会把
一个改造点摊成 5 条，反而看不出它们是同一件事。

**代价与边界**：本清单对**其它**包与文件的拦截力度不变 —— 校验器仍会报出
任何未登记的新路径。若将来这两个包出现**与 N3 无关**的改动，须拆回逐文件登记。

### ⚠️ DSH-A1 的一次补丁面削减（已执行，值得记录）

初版改动里，`pnpm add` **顺带把 61 个依赖重新字母排序** —— 上游 baseline 本身是无序的
（4 个条目堆在末尾），`pnpm add` 把它们归了位。

**后果**：git 看到 **4 个 hunk、61 条变动**，而语义上**只加了 1 行**。
这会把上游升级时的冲突面放大 60 倍。

**已修正**：按上游原序重建 dependencies，把新依赖**追加在末尾**（沿用上游自己的习惯）。

| | 修正前 | 修正后 |
|---|---|---|
| git hunk 数 | 4 | **1** |
| 变动条目 | 61 | **1** |
| 语义变动 | +1 依赖 | +1 依赖 |

**已验证** `pnpm install --frozen-lockfile` 仍通过（顺序不影响 lockfile）。

> **这是本清单的第一条实际价值**：它让一处**本来会持续放大冲突面**的改动被压到最小。
> `pnpm add` 会重新排序 —— **下次用它加依赖时须重新执行本削减。**

#### ⚠️ 关于这次削减的一次诚实记录

削减当天**只改了工作区，没有提交**。已提交的 `7c2ab77` 里仍是 61 移位的版本。

后果不是显现在代码上，而是显现在**判断上**：次日查 `git status` 时，
看到的 6 个 hunk 其实是「正在撤销重排」的修正 diff，却被误读成「一处问题改动」——
**连 diff 的方向都读反了**，还据此下了「上次声称的削减根本不存在」的结论。

真实情况是：削减做对了，只是**留在工作区没落库**。

**由此给校验器加了一条检查**（见第五节）：工作区有未提交改动时 `--check` 直接判红。
理由是它会让「已提交的 fork」和「眼前的 fork」不是同一个东西 ——
本次这个错误，如果有那条检查，当场就会红。

> **教训**：「我改好了」和「它已经进仓库了」是两件事。
> 凡是声称「已修正」，必须附一条**能重跑的验证命令及其输出**，而不是一句结论。

## 四、升级上游时的操作顺序

1. **不要试图合并 `pnpm-lock.yaml`** —— 直接删掉重新生成
2. 合 A3/A4（tsconfig 加行）—— 通常自动合并
3. 合 A1（package.json 加行）—— 通常自动合并；**合完检查顺序是否被工具重排**
4. **A2 手工重做**（删内测声明注册）—— 这是唯一需要理解意图的一处
5. **A6-A9 品牌清理**（4 个文件）：A6 直接保留我们的值；
   A7/A9 若上游改动了同一文案，按语义重新应用**中性表述**（不要恢复上游原文）；
   A8 若上游重新启用 `welcomeBody`，同样改中性表述
5. B 类全部保留，无需处置
6. **升级后跑** `python3 工具/g2_改造点.py --check` —— 确认没有未登记的改动

## 五、自检

```bash
python3 工具/g2_改造点.py            # 打印改造点清单（从 git 现算）
python3 工具/g2_改造点.py --check    # 校验：是否有未登记的改动
```

**`--check` 会用 git 现算 fork 相对基线的全部改动，与本文登记比对。**
它判红的情况有四类：

| 判红条件 | 含义 |
|---|---|
| 工作区有未提交改动 | 「已提交的 fork」与「眼前的 fork」不是同一个东西 |
| 有改动但没登记 | 违反 §7.5.3「未登记不得合并」 |
| 登记了但代码里没有 | 登记失效（上游可能已合并该能力，或改动被回退） |
| 本文表格写的文件数与代码不符 | 手写数字没跟着代码走，会让人低估冲突面 |

\`\`\`bash
bash 工具/g2_自测.sh   # 反向测试：证明校验器在该红的时候真的会红

python3 工具/g2_改造点.py --manifest         # 生成内容指纹
python3 工具/g2_改造点.py --verify-manifest  # 校验内容未偏离登记
\`\`\`

**自测当前 9/9 通过**（干净→绿；未提交/untracked/已提交未登记/数字错/登记失效/内容被篡改→红；恢复→绿）。

> 本项目已连续四次出现「工具报绿、实际不对」，所以每个校验器都必须先证明它会红。

## 六、本清单已知的不足

| # | 不足 | 说明 |
|---|---|---|
| 1 | **基线是分支点，不是 tag** | 上游若改写历史，基线可能失效 |
| 2 | **未评估「上游若也做同样改动」的收敛可能** | 例如上游某天自己加了品牌 slot 扩展点，B2 可能可简化 |
| 3 | **未量化上游漂移速度** | 本清单只说「上游仍活跃」，没有实际的提交频率数据 |
| 4 | **`vendor/dsh` 不入库**（已部分缓解） | 清单在库内，**fork 本身在库外** —— 克隆 KVVI-Agent 得不到 fork。已加 `改造点指纹.json`（**每个登记文件的 sha256 + 被改文件的上游基线 sha256**；由 `python3 工具/g2_改造点.py --manifest` 生成，故不写死数量）：**丢失可检测、上游漂移可检测，但仍不可恢复** —— 内容仍须另行备份 |
| 5 | **未验证「重建可行」** | 清单描述了怎么改，但**没有实际演练过从零重建 fork** —— 声称的可重建性未经验证 |
