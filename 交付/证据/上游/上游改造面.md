## 2. 风险判定规则（说明理由）

规则只用了两个可复核的输入：**上游改动次数** + **我们对这个文件做了什么**（M / D）。

- **高** = 我们在上游文件上做了修改（M），且上游自基线起改过该文件 **≥ 10 次**。理由：以 2,677 个提交的密度，同一文件被改 10 次以上说明它是上游的高频演进区域，我们的插入点大概率落在上游反复改写的行区间里。
- **中** = M 或 D，且上游改过 **2–9 次**。理由：有真实的上游演进，但密度不足以断言必然相撞；其中「D」（我们删了上游文件）单列说明——这是**语义冲突**，上游改进的东西被我们整块拿掉了。
- **低** = 上游只改过 **1 次**。单次改动通常是一次性清理，撞车概率低。
- **无** = 上游 0 次。

**补充观察（不改变上面的分层，但影响修复成本）**：我们落在上游文件上的改动**绝大多数是 1–5 行的插入式补丁**（`tsconfig.host.json` +4/-0、`tsconfig.client.json` +2/-0、`tsconfig.base.json` +4/-0、`apply.ts` +2/-0、`packages/README.md` +1/-0），冲突面本身很小；但其中相当一部分文件是**生成物**（`pnpm-lock.yaml`、`docs/module-graph.*`、`slot-catalog.ts`），这些文件必然文本冲突，代价却是可机械重算的。

## 6. 我没验 / 跳过 / 判不了的部分（如实列）

1. **`path=` 是精确路径匹配，不追重命名。** 如果上游把某文件改名，改名前的提交不会挂在旧路径上。我**没有做重命名追踪**，所以所有 0 计数对「上游曾改名过该文件」这一情形是潜在假阴性。已抽查的两个 0 计数文件（`trusted-hosts.spec.ts`、`webserver.spec.ts`）在上游 master 仍以原路径存在，但只查了 2 个，未做全量存在性校验（84 个）。
2. **`since` 窗口边界有渗漏。** GitHub 的 `since` 与 `author.date` 不完全对齐，落在窗口内的提交有少量作者日期早于 2026-09-17（实测 `tsconfig.host.json` 7/188、`docs/module-graph.md` 2/120、`pnpm-lock.yaml` 9/371），其中一部分可能已经包含在我们的基线 `ddefc45f` 里。因此**计数在边界上略偏高（约 2–4%）**，但不足以改变任何一条的分层结论。
3. **只看文件路径与提交标题，没比 diff。** 「上游改了什么」一栏是 commit subject 归纳，不是逐 hunk 比对。**具体某个改动是否真的会与我们相撞，我没有验证**——特别是 `packages/api/gateway/src/index.ts`（+61 行）和 `packages/client/ui-conversation/tests/skeleton.client.spec.tsx`（+73 行），判不了。
4. **未做真实的 merge/rebase 试算。** 本报告给的是「碰撞面」，不是「实际冲突数」。要得到实际冲突数需要真的试合一次，那超出只读范围。
5. **`packages/` 以外的目录没有降级跳过**（因为总数 126 < 300），但目录归组统计我并未做：全部 126 条都是逐文件查的。
6. **80 条新增文件只按「上游是否存在该路径」抽查了 4 条**（全部 Not Found），未逐条做存在性确认——它们的计数全为 0 是 API 结果，不是我的推断。
